# 第六十三章. 上下文预算与长任务耐力

## 63.1 本章目标

第六十二章定了规划的粒度：heavy 任务切成 10 步以上。但粒度解决的是"每步起点该多大"，解决不了"每步跑起来累积多少"：每一次工具输出、每一条报错、每一段观察都在往上下文里堆，长任务的上下文体积是单调递增的。本章引入上下文预算体系：步骤历史的三段分层压缩，外加"模型输入"与"审计记录"两条线的分离。

完成本章后，你将能够：

- 解释注意力稀释如何导致长任务"越跑越偏"，而不是"跑着跑着忘了目标"；
- 实现步骤历史的三段分层压缩：最近全文、中间摘要、最老标题；
- 在确定性压缩与 LLM 压缩之间做取舍，并从审计、复现、延迟三个角度说清理由；
- 保证压缩只作用于模型输入，审计记录永远保持全量。

本章新增代码集中在（将如下所示）：

```text

```

预算对象的生命周期与记账方式，复用第六十章 `tool_budget.py` 的既有模式：查用前、记账后用、超限给结构化结果、快照落审计——只是把"单步骤"换成"整个任务"。

## 63.2 为什么需要这一章

长任务失败很少是显式崩溃，更多是一种缓慢的"跑偏"：第 3 步还在按任务要求做，第 7 步基本正常，第 12 步开始忽然去改第 2 步的文件、重跑早已通过的测试、重写已经有结论的摘要。人们习惯说"模型忘了目标"，但机理不是遗忘——窗口就在那，目标还在那，只是被**稀释**了。

注意力稀释的机理可以用一句话讲清：窗口里的内容越多，"这是目标、这是约束"的信噪比就越低，而模型的注意力会优先被**最近、最显著**的内容吸引——在长任务里，最近的显著内容通常是最后一条报错。于是形成正反馈：报错越多，模型越盯着报错；越盯着报错，越在修报错；修报错的过程中又引入新的报错。长任务后半程"不干活、光顾着和自己的历史搏斗"，就是这个回路的外在表现。

所以上下文预算不是一个成本优化问题（省 token 只是附带收益），而是一个**稳定性问题**：它保证任务目标、当前步骤指令、与本步骤直接相关的观察，在窗口里始终占稳定份额，不被累积的噪音淹没。

## 63.3 实现步骤

### 63.3.1 三段分层压缩

预算对象挂在任务级（整个长任务生命周期），步骤历史的总预算比如 16k token。超预算时，历史按"年龄"分三段压缩：

```python
def compress_history(steps, *, budget_tokens: int, recent_n: int = 3) -> list[CompressedStep]:
    """三段：最近 N 步全文；中间段结构化摘要；最老段只留标题+状态。"""
    out = []
    for i, step in enumerate(steps):
        age = len(steps) - 1 - i
        if age < recent_n:
            out.append(CompressedStep(step, level=FULL))       # 最近：全文
        elif age < recent_n * 4:
            out.append(CompressedStep(step, level=SUMMARY))    # 中间：摘要
        else:
            out.append(CompressedStep(step, level=TITLE))      # 最老：标题+状态
    # 仍超预算时，从最老段起逐段收紧：SUMMARY→TITLE，再合并同状态步骤
    ...
```

三段的划分对应模型对历史的实际用法：最近几步的全文之所以要保，是因为当前步骤经常是在"接着上一步的报错继续修"，丢一行 stderr 都可能让重试变成原地打转；中间段的价值是"发生了什么、结论是什么"，结构化摘要足够；最老段的价值只剩"这事做过、结果是成败"，标题加状态就够了。

两条不变式：**任务目标与当前步骤指令永不压缩**——它们不进预算池，始终钉在窗口头部；**压缩结果按步骤列表的哈希缓存**，列表没变就不重算。prompt 构建是每轮都跑的热路径，不能每轮重复压缩几十条历史。

### 63.3.2 确定性压缩 vs. LLM 压缩

中间段的摘要有两种实现。LLM 压缩看似更"智能"，但这里的默认选择是**确定性压缩**：

```python
def summarize_step_deterministic(step) -> str:
    """模板化摘要：标题 + 结果状态 + 报错尾部 + 触及文件清单。"""
    status = "completed" if step.status is PlanStepStatus.completed else "failed"
    return (
        f"步骤[{step.title}]: {status}"
        f" | 报错尾部: {step.error_tail or '无'}"
        f" | 触及文件: {', '.join(step.touched_files[:5])}"
    )
```

理由有三条，每一条都足以让确定性版本成为默认：

1. **审计**：确定性压缩是纯函数，同样输入永远同样输出，事后可以从审计记录精确还原"模型当时看到了什么"。LLM 摘要不确定，同一个任务重跑，中间段历史可能完全不同——排查"那次为什么跑偏"时，连"它当时看到什么"都无法复现，审计就失去了锚点。
2. **延迟**：步骤历史每轮构建，中间段可能有几十条。LLM 压缩意味着每轮多出一次批量调用，把 prompt 构建从毫秒级拖到秒级，直接叠加在每一次模型轮次的延迟上；确定性压缩是字符串拼接，零外部依赖。
3. **可用性**：第五十七章已经确立"LLM 路径优先、规则路径兜底"的离线可用性原则。压缩链路在离线部署（无密钥、无 LLM）下必须照样工作，确定性版本天然满足，LLM 版本不满足。

LLM 压缩没有废弃，但定位为**可选增强开关**：LLM 可用且任务标记为高优先级时，可以用它对中间段产出更有语义的摘要。但确定性版本必须始终在场作为降级路径——这和第五十七章"重排失败静默降级为词法重排"是同一条设计线：增强项失败不能阻断主链路。

### 63.3.3 两条线：模型输入与审计记录

本章最容易破坏的纪律是一句话：**压缩只作用于模型输入，绝不触碰审计记录**。两条线永不合并：

- **模型输入线**：prompt 构建时拼出来的东西——三段压缩后的历史 + 钉住的目标 + 当前步骤指令。这是"模型看到的"。
- **审计线**：每一步的完整观察、完整工具输出、完整事件流，原样持久化。这是"系统记录的"。

为什么必须分开：

第一，审计要回答"模型看到了什么、它实际输出了什么"。如果压缩就地发生，原文不可逆地丢失，事后复盘"那次为什么偏"连证据都没有。第二，从检查点重放（第四十五章）依赖全量记录——重放的输入必须和原执行一致，记录被压缩过，重放的就不是原任务了。第三，同一份步骤在两条线上本来就该长得不一样：模型看到的是"该步失败，报错尾部 200 字"，审计里有 2000 字的完整 stderr——**这个差异正是审计的价值：系统知道模型知道得比它少**。

```python
def build_step_prompt(task, plan) -> StepPrompt:
    compressed = compress_history(task.steps_done, budget_tokens=task.history_budget)
    return StepPrompt(
        goal=task.goal,                            # 永不压缩，钉在头部
        current_step=plan.current(),               # 永不压缩
        history=[s.render() for s in compressed],  # 仅存在于模型输入线
    )
# 审计线走另一条管道：step.observation 全量持久化，与 prompt 构建互不引用
```

一个实践中的小坑：两条线的实现里，压缩后的 prompt 和全量记录都要进事件流（一条 `prompt_built` 事件带压缩快照，一条 `step_observed` 事件带全量输出）。两条事件分开存、分开查，不要存一个"已压缩的观察"去省空间——省下的那点空间，换不来事后复盘的能力。

## 63.4 本章小结

- 长任务的"跑偏"不是遗忘，是稀释：窗口填满后注意力被最近的报错吸引，形成"修报错 → 添报错 → 再修报错"的正反馈。上下文预算是稳定性措施，不是成本措施。
- 三段压缩匹配模型对历史的实际用法：最近全文（接着它干活）、中间摘要（知道发生了什么）、最老标题（知道做过就行）。
- 确定性压缩为默认，LLM 压缩为可选增强并保留降级路径：审计可复现、构建零延迟、离线可运行，任何一条都足以让确定性版本兜底。
- 任务目标与当前步骤指令永不进入预算池，始终钉在窗口头部。
- 模型输入线与审计线永不合并：压缩只发生在 prompt 构建侧，全量记录是事后复盘与检查点重放的锚点，也是"系统知道模型知道得比它少"的依据。

至此，长任务治理的三部曲收束：切得够细（第六十二章）、判得够严（第六十一章）、跑得够久（本章）。它们共同回答的是同一个问题：如何让一个跨越几十轮调用的模型，在长任务里既保持能力，又保持可控。
