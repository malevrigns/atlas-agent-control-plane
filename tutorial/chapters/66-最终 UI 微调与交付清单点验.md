#### 66.6.2.1 为什么这些项放在后端服务里

​        设置页和验收页需要从接口读取清单。

​        如果清单只写在 Markdown 里，页面无法展示，也无法让测试检查。

​        所以：

```Plain
product_acceptance_service.py  给页面和接口用
final-delivery-checklist.md    给人最终自查用
```

​        两者职责不同。

### 66.6.3 微调最终回答卡片

​        打开 `ui/app/components/conversation/agent-run-block.tsx`。

​        最终回答卡片增加顶部标签：

```TypeScript
<div className="mb-4 flex items-center gap-2 border-b border-white/10 pb-3 text-xs font-semibold uppercase tracking-[0.18em] text-zinc-500">
  <ClipboardCheck className="text-blue-400" size={15} aria-hidden="true" />
  {failed ? "Task Error" : "Final Answer"}
</div>
```

#### 66.6.3.1 为什么加这个标签

​        中间对话流会出现：

```Plain
用户消息
Agent 说明
计划步骤
工具调用
最终回答
```

​        最终回答是交付物，应该和普通过程消息区分开。加 `Final Answer` 标签后，用户能一眼知道这块是任务收尾结果。

### 66.6.4 收紧 Markdown 正文尺寸

​        打开 `ui/app/components/markdown-content.tsx`。

​        把 Markdown 正文从偏大的 `text-base leading-8` 收紧为：

```TypeScript
<p className="mb-3 text-[15px] leading-7 text-zinc-400 last:mb-0">
  {children}
</p>
```

​        列表也保持相同尺寸：

```TypeScript
<ul className="mb-3 list-disc space-y-1 pl-5 text-[15px] leading-7 text-zinc-400 last:mb-0">
  {children}
</ul>
```

#### 66.6.4.1 为什么要这样调

​        Agent 最终回答经常包含：

```Plain

要点
链接
代码路径
产物说明
```

​        字号过大会导致一屏只能看到很少内容。最终章不追求花哨，而是让长答案更耐读。

## 66.7 关键理解

​        本章最重要的是理解：最终验收不是新功能，而是交付动作。

​        开发阶段关注：

```Plain
某个模块是否能跑
某个接口是否返回
某个页面是否显示
```

​        交付阶段关注：

```Plain
用户能不能完成完整任务
失败时能不能定位
产物是否可追溯
下一位开发者能不能接着维护
```

​        第二个重点是：验收清单要同时给机器和人使用。

​        机器用测试检查清单项是否存在。

​        人用 Markdown 清单执行真实任务验证。

​        第三个重点是：课程项目和生产项目之间仍然有差距。

​        本课程完成的是核心 Agent 产品体验和工程骨架。生产环境还需要继续补齐权限、审计、监控、资源隔离、成本控制等能力。

## 66.8 技术难点与亮点

​        技术难点：

​        展开来看，第一，最终章不能继续无限加功能，要控制范围；第二，验收清单需要覆盖全部核心能力，但不能变成散乱文档；第三，UI 微调要提升可读性，不能引入新的大改动风险；第四，测试需要固定验收项，避免文档和接口逐渐漂移。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        项目亮点：

​        具体来说，第一，产品验收接口覆盖最新错误、文件和最终回答能力；第二，最终回答有明确交付卡片层级；第三，Markdown 正文更适合长答案阅读；第四，独立交付清单把运行命令、页面任务和预期效果集中到一个文件。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

## 66.11 常见问题

- 问题：最终验收清单里有人工确认项，是不是说明功能没完成？

​        解释：不是。页面交互、VNC 画面、真实搜索质量这类体验需要人工观察，不能只靠单元测试判断。

- 问题：为什么不把最终交付清单全部写进 README？

​        解释：README 适合快速启动。最终交付清单更长，单独成文更便于逐项执行。

- 问题：为什么最终章还要改 UI？

​        解释：最终回答是用户最后看到的交付物。轻量微调标题、字号和层级，可以提升完成感和可读性。

- 问题：生产系统是不是已经完整了？

​        解释：课程项目已经完成核心体验和工程骨架，但生产环境还需要权限、审计、监控、计费、资源配额、密钥托管等能力。
