## 51.4 本章技术方案

​        本章采用“入口组件 + 子组件 + 视图模型”的拆法。

```Plain
ConversationTimeline
  |
  +-- 负责加载、错误、空状态判断
  +-- 负责组合消息流、计划块和步骤详情弹层

conversation/view-model.ts
  |
  +-- 把 messages + events + plan 转换成页面要展示的结构
  +-- 解析 plan_created、step_started、step_completed、tool_called 等事件

  |

  +-- 不直接请求 API
  +-- 不直接修改 zustand store
```

​        这个拆法的重点是：

​        展开来看，第一，`store` 管远程数据和动作；第二，`view-model` 管事件到 UI 数据的转换；第三，`component` 管展示和点击回调；第四，`page` 和 `ChatWorkspace` 只做页面组合。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

import type {

  ChatMessage,
  PlanStep,
  SessionEventItem,
} from "../../types";

export type TimelineItem =
  | { kind: "message"; id: string; created_at: string; message: ChatMessage }
  | { kind: "plan"; id: string; created_at: string; event: SessionEventItem };

export type StepView = PlanStep & {
  startedAt: string | null;
  completedAt: string | null;
  toolEvent: SessionEventItem | null;

    id: string;
    assignee: string;

    status: string;
    output: string;

    status: string;
  };

#### 51.6.3.1 字段含义

​        从实现顺序看，第一，`TimelineItem`：页面时间线的统一条目。它把消息和计划事件放进同一个列表，方便按时间排序展示；第二，`StepView`：前端真正展示的步骤结构。它不是后端原始 `PlanStep`，而是在 `PlanStep` 基础上补充了开始时间、完成时间、工具事件和摘要；第三，`MultiAgentInlineResult`：多 Agent 工具输出的前端解析结果。步骤卡片和最终回答都会读取它；第四，`AgentRunViewModel`：`ConversationTimeline` 最终需要的数据结构。入口组件拿到它之后，只需要负责渲染。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        如果放进 `ui/app/types.ts`，会让全局类型文件越来越大。

### 51.6.4 抽出 view-model 转换逻辑

​        创建 `ui/app/components/conversation/view-model.ts`。

​        这个文件负责把后端消息和事件转换成前端展示模型。

​        核心职责有三个：

​        放到工程语境里看，第一，构建时间线条目；第二，根据事件更新步骤状态；第三，解析工具输出中的多 Agent 结果。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

```TypeScript
export function buildAgentRunViewModel(
  messages: ChatMessage[],
  events: SessionEventItem[],
  plan: AgentPlan | null,
): AgentRunViewModel {
  const timelineItems = buildTimelineItems(messages, events);
  const latestPlan = plan ?? getLatestPlanFromEvents(events);
  const finalEvent =
    [...events]
      .reverse()
      .find((event) => event.type === "task_done" || event.type === "task_error") ??
    null;

  return {
    finalEvent,
    latestPlan,
    timelineItems,
  };
}
```

#### 51.6.4.1 这段代码在流程中的位置

​        调用链路是：

```Plain
useSessionStore
  |
  | messages / events / latestPlan
  v
ConversationTimeline
  |
  v
buildAgentRunViewModel()
  |
  v
AgentRunBlock / MessageBubble / StepCard
```

​        也就是说，`view-model.ts` 是 store 和组件之间的转换层。

​        store 不需要知道页面具体怎么画。

​        组件也不需要自己到处解析事件。

#### 51.6.4.2 为什么这样设计

​        后端事件是业务事实：

```Plain
plan_created
step_started
tool_called
step_completed
task_done
```

​        前端展示需要的是 UI 状态：

```Plain
哪个步骤 running
哪个步骤 completed
哪个步骤绑定了工具事件
最终回答是什么
```

​        这两者不是同一个东西。

​        把转换逻辑抽到 `view-model.ts`，后续第 52 章做动画和状态回放时，只需要扩展这一层，不需要在 JSX 里到处加判断。

### 51.6.6 收敛 ConversationTimeline 入口

​        修改 `ui/app/components/conversation-timeline.tsx`。

​        重构后，它只做五件事：

1. 处理 loading。
2. 处理 error。
3. 处理 empty。
4. 调用 `buildAgentRunViewModel()`。
5. 组合消息、计划块和步骤详情弹层。

```TypeScript
export function ConversationTimeline({
  events,
  messages,
  onSelectToolEvent,
  plan,
  planning,
  executing,
  selectedToolEventId,
  task,
}: ConversationTimelineProps) {
  const [detailStep, setDetailStep] = useState<StepView | null>(null);

  if (messages.type === "loading" || events.type === "loading") {
    return <TimelineLoadingState />;
  }

  if (messages.type === "error") {
    return <ErrorBlock message={messages.message} />;
  }

  if (events.type === "error") {
    return <ErrorBlock message={events.message} />;
  }

  const viewModel = buildAgentRunViewModel(messages.data, events.data, plan);

  if (viewModel.timelineItems.length === 0) {
    return <TimelineEmptyState />;
  }

  return (
    <>
      <div className="flex-1 overflow-y-auto px-8 py-8 max-md:px-4">
        <div className="mx-auto grid max-w-3xl gap-7">
          {viewModel.timelineItems.map((item) =>
            item.kind === "message" ? (
              <MessageBubble key={item.id} message={item.message} />
            ) : viewModel.latestPlan ? (
              <AgentRunBlock
                events={events.data}
                finalEvent={viewModel.finalEvent}
                key={item.id}
                onSelectToolEvent={onSelectToolEvent}
                onOpenStep={setDetailStep}
                plan={viewModel.latestPlan}
                planning={planning}
                selectedToolEventId={selectedToolEventId}
              />
            ) : null,
          )}
          <TaskStatusCard task={task} />
          {planning || executing ? (
            <RunningBlock
              text={
                planning
                  ? "正在理解任务并生成计划..."
                  : "正在执行计划并同步工具结果..."
              }
            />
          ) : null}
        </div>
      </div>
      {detailStep ? (
        <StepDetailDialog
          onClose={() => setDetailStep(null)}
          onSelectToolEvent={onSelectToolEvent}
          step={detailStep}
        />
      ) : null}
    </>
  );
}
```

## 51.7 关键理解

​        本章最重要的是理解“组件拆分不是按 UI 长相随便切”。

​        一个好的拆分应该回答三个问题：

```Plain
这个组件负责什么？
它从哪里拿数据？
它通过什么事件通知上层？
```

​        如果一个组件既解析事件、又维护弹层、又展示步骤、又处理工具输出，它就太重了。

​        第二个重点是理解 `view-model`。

​        后端给的是事件事实，前端要的是展示状态。中间需要一层转换逻辑。把这层放进 `view-model.ts`，比散落在 JSX 中更容易测试和维护。

​        第三个重点是设计 token 要克制。

​        本章不追求抽象所有 className，只抽最常重复、最能表达语义的样式。这样既能减少重复，又不会把 Tailwind 写法复杂化。

## 51.8 技术难点与亮点

​        技术难点：

​        从实现顺序看，第一，拆组件时不能改变 props 数据流；第二，拆 view-model 时不能改变事件排序和步骤状态判断；第三，设计 token 不能过度抽象，否则反而更难读；第四，重构后要确保 TypeScript 能发现漏掉的 import 和 props。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        项目亮点：

​        放到工程语境里看，第一，对话时间线入口文件从大组件收敛为页面编排文件；第二，消息、计划、步骤、弹层和状态块拥有独立文件；第三，事件到 UI 的转换进入 `view-model.ts`；第四，建立了第一层前端设计 token；第五，为第 52 章继续优化流式执行体验打好边界。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。
