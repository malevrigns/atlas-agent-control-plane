# 第三十四章. A2A 协议初识

## 34.1 本章目标
​        第 31 章和第 32 章讲的是 MCP。MCP 让一个 AI 应用能够发现和调用外部工具、资源和提示词，它解决的是“Agent 如何使用工具”的问题。可是当系统继续成熟以后，还会出现另一类需求：一个 Agent 不只是调用工具，而是把一部分任务交给另一个 Agent 协作完成。这个方向就是 A2A，也就是 Agent-to-Agent。
​        本章的目标，是先用确定性接口讲清 A2A 的基本角色和协作流程。我们不会在这一章真实调用远程 Agent，也不会处理远程认证、长任务轮询、artifact 下载和复杂状态同步。第 34 章只做入门：定义 A2A 的领域对象，写一个 `A2aIntroService`，暴露 `/api/a2a/concepts`、`/api/a2a/demo/agent-card` 和 `/api/a2a/demo/message` 三个接口，并在前端右侧环境区展示 A2A 入门面板。
​        学完本章后，你应该能区分 Host Agent、Remote Agent、Agent Card 和 Task，理解 A2A 和 MCP 的差异，也能看懂一次模拟 `message/send` 为什么要先读取 Agent Card，再选择 Remote Agent，最后把任务消息发给远程 Agent。下一章会把远程 Agent 注册成工具，本章先把协议心智模型建立起来。

## 34.2 最终效果
​        本章结束后，后端会新增三组 A2A 入门接口：

```Plain
GET  /api/a2a/concepts
GET  /api/a2a/demo/agent-card
POST /api/a2a/demo/message
```

​        概念接口会返回 Host Agent、Remote Agent、Agent Card 和 Task 的职责说明。Agent Card 接口会返回一个课程内置的示例远程 Agent，它叫 `ResearchAssistantAgent`，能力包括 `research_brief` 和 `source_outline`。消息接口会模拟一次 Host Agent 向这个远程 Agent 发送任务，并返回 task id、状态、输入消息、输出消息和执行步骤。
​        命令行调用可以这样验证：

```Bash
curl http://localhost:8088/api/a2a/concepts
curl http://localhost:8088/api/a2a/demo/agent-card
curl -X POST http://localhost:8088/api/a2a/demo/message \
  -H "Content-Type: application/json" \
  -d '{"message":"请远程研究 Agent 帮我整理 A2A 协议要点"}'
```

​        前端方面，工具预览面板的“环境”页签会新增 `A2A Agent` 面板。这个面板会展示 A2A 核心角色、下一步说明和示例 Agent Card。它目前不展示真实远程调用结果，因为本章还没有把 A2A 接进工具事件流；第 35 章以后，远程 Agent 调用才会像 MCP 工具一样进入 AgentTool 和 `tool_called`。

## 34.3 本章要解决的问题
​        MCP 和 A2A 很容易被混在一起理解。MCP 关注的是 Host 如何使用外部工具，例如文件系统、浏览器、搜索、数据库或业务系统。A2A 关注的是一个 Agent 如何和另一个 Agent 协作。例如主 Agent 负责整体规划，研究 Agent 负责查资料，代码 Agent 负责改代码，评审 Agent 负责检查结果。它们都属于外部能力接入，但抽象层级不同。
​        如果没有 A2A，复杂任务会全部压在一个 Agent 身上。这个 Agent 既要规划，又要调研，又要写代码，还要评审。短任务还能接受，长任务就会出现上下文拥挤、角色混乱和执行边界不清的问题。A2A 的价值，是让 Host Agent 可以识别远程 Agent 的能力，把合适的子任务交出去，并接收远程 Agent 返回的 task 状态、消息和产物。
​        本章先不处理真实远程调用，是因为 A2A 一上来就接真实远程 Agent 会混入太多问题：远程 Agent 地址从哪里来，Agent Card 怎么读取，任务怎么发送，状态怎么轮询，失败怎么处理，结果怎么进入会话事件流。第 34 章先用本地确定性数据把基本流程讲清楚，下一章再把远程 Agent 作为工具接入。

## 34.4 本章技术方案
​        本章继续使用第 33 章整理后的分层结构。A2A 的核心概念放在 `domain/a2a/entities.py`，入门演示逻辑放在 `application/a2a_intro_service.py`，HTTP 请求响应模型放在 `schemas/a2a.py`，路由放在 `presentation/http/routes/a2a.py`。前端新增 `a2a-api.ts` 和 `A2aPanel`，再把它接入 `ToolPreviewPanel` 的环境页签。
​        后端实现采用“确定性演示服务”的方式。`A2aIntroService` 不连接外部 Agent，而是返回固定角色说明、固定示例 Agent Card，并在收到 message 后生成一个模拟 task。这个 task 带有 `read_agent_card`、`select_remote_agent`、`message/send` 和 `task_completed` 四个步骤，让读者清楚看到一次 A2A 调用的顺序。
​        前端实现同样只展示入门信息。它不会提供“调用远程 Agent”的按钮，因为真实调用路径还没有进入工具体系。环境页签展示 A2A 概念和示例 Agent Card，是为了让用户知道系统接下来会具备远程 Agent 协作能力。等第 35 章把 A2A 接成工具后，具体调用结果才进入工具页签和事件流。

## 34.6 实施步骤
​        本章实施顺序和第 31 章 MCP 入门很相似：先定义领域对象，再写应用服务，再写 Schema 和路由，最后接前端面板。区别在于，A2A 的概念更偏 Agent 协作，所以领域对象会围绕 Agent Card、Message、Task 和 Step 展开。

### 34.6.1 定义 A2A 角色模型
​        `A2aRole` 用来描述 A2A 中的核心角色。它包含名称、职责，以及在 AtlasAgent 项目里的映射位置。

```Python
@dataclass(slots=True)
class A2aRole:
    name: str
    responsibility: str
    system_mapping: str
```

​        本章会返回四个角色。Host Agent 是发起任务的一方，负责选择远程 Agent、发送消息并接收结果。Remote Agent 是被调用的一方，接收任务并返回消息、状态或 artifact。Agent Card 是远程 Agent 的名片，描述名称、地址、能力和输入输出模式。Task 则代表一次跨 Agent 协作任务，包含输入消息、执行状态和输出结果。
​        这些概念在后续章节都会继续出现。第 35 章会读取远程 Agent Card 并注册成可调用工具；第 36 章的多 Agent 编排会把多个 Agent 协作放进更大的任务流；后面的 Agent Runner 和任务恢复也会关心远程任务状态。

### 34.6.2 定义 Agent Card 和能力模型
​        A2A 中，Host 在调用远程 Agent 之前，需要先知道远程 Agent 是谁、能做什么、在哪里调用、支持什么输入输出。这个信息由 Agent Card 承载。本章用 `A2aAgentCard` 表示最小模型。

```Python
@dataclass(slots=True)
class A2aCapability:
    name: str
    description: str
    example: str


@dataclass(slots=True)
class A2aAgentCard:
    name: str
    description: str
    url: str
    version: str
    capabilities: list[A2aCapability]
    default_input_modes: list[str]
    default_output_modes: list[str]
```

​        `A2aCapability` 描述远程 Agent 的单项能力，例如 `research_brief` 或 `source_outline`。`A2aAgentCard` 则把多个能力组织在一起，并提供远程 Agent 的地址、版本、默认输入模式和输出模式。这个结构类似 MCP 的 tools/list，但它描述的是一个 Agent，而不是一个普通工具集合。
​        本章的示例 URL 使用课程内置示例地址，不会真实访问。它的作用是让 Agent Card 看起来像真实远程 Agent 的描述，同时不引入外部网络依赖。

### 34.6.3 定义 message 和 task 演示模型
​        A2A 的任务交互不是普通函数调用，而是消息和任务状态。为了展示这条链路，本章定义 `A2aMessagePart`、`A2aTaskStep` 和 `A2aMessageDemo`。

```Python
@dataclass(slots=True)
class A2aMessagePart:
    kind: str
    text: str


@dataclass(slots=True)
class A2aTaskStep:
    index: int
    action: str
    detail: str


@dataclass(slots=True)
class A2aMessageDemo:
    remote_agent: str
    task_id: str
    status: str
    input_message: list[A2aMessagePart]
    output_message: list[A2aMessagePart]
    steps: list[A2aTaskStep]
```

​        `A2aMessagePart` 目前只使用 text，但保留 `kind` 是为了后续扩展文件、数据和 artifact。`A2aTaskStep` 用于展示一次调用中发生的关键动作。`A2aMessageDemo` 则汇总远程 Agent、task id、状态、输入消息、输出消息和步骤。这个结构不是完整 A2A 规范实现，而是本章的教学最小模型。

### 34.6.4 编写 A2aIntroService
​        `A2aIntroService` 是本章的应用服务。它的 docstring 明确说明本章边界：只用确定性数据模拟 Agent Card 和 `message/send`，第 35 章再接真实远程 Agent 调用。

```Python
class A2aIntroService:
    """第 34 章的 A2A 入门应用服务。

    A2A 解决的是 Agent 和 Agent 之间如何互相发现、发送任务、返回结果。
    本章先用确定性数据模拟 Agent Card 和 message/send，
    让读者理解协议边界。第 35 章再接入真实远程 Agent 调用。
    """
```

​        这个服务有三个核心方法：`list_roles()` 返回概念说明，`get_demo_agent_card()` 返回示例 Agent Card，`send_demo_message()` 模拟一次消息发送。这样路由层只负责 HTTP 转换，A2A 入门逻辑集中在应用服务里。

### 34.6.5 返回 A2A 核心角色
​        `list_roles()` 返回 Host Agent、Remote Agent、Agent Card 和 Task。每个角色都有职责说明和项目映射。

```Python
def list_roles(self) -> list[A2aRole]:
    return [
        A2aRole(
            name="Host Agent",
            responsibility="发起任务的一方，负责选择远程 Agent、发送消息并接收结果。",
            system_mapping="AtlasAgent 主 API 中的 Agent Runner 或 A2A 工具调用方。",
        ),
        A2aRole(
            name="Remote Agent",
            responsibility="被调用的一方，接收任务并返回消息、状态或 artifact。",
            system_mapping="外部可协作 Agent，例如研究 Agent、代码 Agent、文档 Agent。",
        ),
    ]
```

​        代码里还会返回 Agent Card 和 Task。这里最值得注意的是 `system_mapping` 字段。它把抽象协议角色映射回当前项目，让读者知道这些概念以后会落在哪里。Host Agent 不是虚构角色，它会对应当前 API 中的 Agent Runner 或 A2A 工具调用方；Remote Agent 则是外部可协作 Agent。

### 34.6.6 返回示例 Agent Card
​        `get_demo_agent_card()` 返回一个示例远程 Agent：`ResearchAssistantAgent`。

```Python
return A2aAgentCard(
    name="ResearchAssistantAgent",
    description="一个模拟的远程研究 Agent，擅长把问题拆成检索要点并返回摘要。",
    url="https://agents.example.com/research",
    version="0.1.0",
    capabilities=[
        A2aCapability(
            name="research_brief",
            description="根据用户问题整理研究摘要和后续建议。",
            example="帮我调研某个技术方案的优缺点。",
        ),
        A2aCapability(
            name="source_outline",
            description="把资料来源整理成结构化提纲。",
            example="把搜索结果整理成可写文章的大纲。",
        ),
    ],
    default_input_modes=["text/plain"],
    default_output_modes=["text/plain", "application/json"],
)
```

​        这个 Agent Card 不是为了真实调用，而是为了让读者看到远程 Agent 应该如何描述自己。Host Agent 需要根据这些信息判断远程 Agent 是否适合当前任务。如果一个远程 Agent 只声明了写作能力，却让它做代码审查，选择本身就不合理。

### 34.6.7 模拟 message/send
​        `send_demo_message()` 接收用户消息，先做空字符串校验。空消息会抛出 `AppException`，不会返回一个无意义的 completed task。

```Python
clean_message = message.strip()
if not clean_message:
    raise AppException(
        message="a2a demo message is required",
        code=400,
        status_code=400,
    )
```

​        校验通过后，服务读取示例 Agent Card，生成一个 `a2a-demo-...` 开头的 task id，并构造四个步骤：读取 Agent Card、选择 Remote Agent、发送 `message/send`、远程 Agent 返回 completed。这个流程就是本章最核心的教学内容。

```Python
steps = [
    A2aTaskStep(index=1, action="read_agent_card", detail="Host 先读取远程 Agent Card。"),
    A2aTaskStep(index=2, action="select_remote_agent", detail=f"根据任务内容选择远程 Agent：{card.name}。"),
    A2aTaskStep(index=3, action="message/send", detail="Host 把用户任务包装成 A2A message。"),
    A2aTaskStep(index=4, action="task_completed", detail="远程 Agent 返回任务状态和输出消息。"),
]
```

​        返回结果中的 `output_message` 会明确说明这是第 34 章模拟响应，第 35 章才接入真实远程 Agent 调用。这样用户不会误以为这里已经进行了真实 A2A 网络请求。

### 34.6.8 定义 API Schema
​        `api/app/schemas/a2a.py` 把领域对象转换成 HTTP 响应模型。概念响应包含 roles、protocol 和 next_step；Agent Card 响应包含名称、描述、URL、版本、能力和输入输出模式；message 请求只需要一个 message 字段。

```Python
class A2aMessageSendRequest(BaseModel):
    message: str = Field(min_length=1, max_length=4000)


class A2aMessageDemoResponse(BaseModel):
    remote_agent: str
    task_id: str
    status: str
    input_message: list[A2aMessagePartResponse]
    output_message: list[A2aMessagePartResponse]
    steps: list[A2aTaskStepResponse]
```

​        `message` 使用最小长度和最大长度限制，是为了让接口边界明确。A2A 消息未来可能包含文件、结构化数据和 artifact，但本章先只允许文本，这样概念更聚焦。

## 34.7 关键理解
​        本章最重要的理解，是 A2A 和 MCP 解决的问题不同。MCP 让 Agent 使用外部工具；A2A 让 Agent 与另一个 Agent 协作。工具通常是一个动作或资源入口，远程 Agent 则可能有自己的任务理解、计划、执行和结果整理能力。
​        第二个关键点是 Agent Card。Host Agent 不应该盲目调用一个远程地址，它要先读取 Agent Card，知道对方是谁、能做什么、支持哪些输入输出模式，再决定是否把任务交给它。Agent Card 就像远程 Agent 的能力声明和调用说明。
​        第三个关键点是 Task。A2A 协作不是简单函数返回，远程 Agent 可能需要一段时间执行，也可能返回状态、消息、artifact 或后续动作。本章先用 completed 的模拟 task 展示基本结构，后续真实接入时再处理 running、failed、artifact 等情况。
​        第四个关键点是 Host Agent 仍然要负责整体任务边界。A2A 并不意味着主 Agent 把任务完全甩给远程 Agent。Host 要先判断任务是否适合远程协作，再根据 Agent Card 选择合适对象，然后把输入包装成对方能理解的 message。远程 Agent 返回结果以后，Host 还要决定结果是否足够、是否需要继续追问、是否要把结果写入当前会话或合并到最终回答。也就是说，A2A 是协作协议，不是责任转移协议。
​        第五个关键点是 A2A 的结果需要回到当前产品体验里。用户在 AtlasAgent 工作台里发起任务，就应该能在同一个工作台里看到远程 Agent 的参与痕迹。第 34 章先把概念展示在环境页签，第 35 章再让调用结果进入工具事件流。这个设计能避免远程 Agent 变成后端不可见的黑盒，也方便后续做任务回放、错误排查和引用说明。
​        第六个关键点是 message part 的扩展空间。现在 `A2aMessagePart` 只有 `kind` 和 `text`，看起来很简单，但它已经暗示了 A2A 后续可以承载更多内容形态。远程 Agent 协作不一定只传纯文本，未来可能传文件、数据片段、图像、代码补丁、artifact 引用或结构化 JSON。先把 part 抽出来，而不是把 message 简化成一个字符串，可以让后续扩展更自然。
​        第七个关键点是每一次远程协作都要能被追踪。只要任务跨出了当前进程，就必须留下远程 Agent、task id、输入和输出，否则后续无法回放。

## 34.8 技术难点与亮点
​        本章的难点在于不要把 A2A 提前做成真实调用。真实 A2A 会涉及远程地址、网络错误、任务状态、权限和结果同步，如果一上来全部实现，读者会被工程细节淹没。本章只用确定性服务讲清楚角色和流程，边界更清楚。
​        第二个亮点是分层落点很自然。A2A 领域对象放在 `domain/a2a`，入门服务放在 `application`，HTTP 入口放在 `presentation/http/routes`，前端只做展示。第 33 章刚整理出的结构在这里立即发挥作用，新增协议能力时不需要重新想目录。
​        第三个亮点是前端没有急着做调用按钮。入门面板只展示概念和 Agent Card，避免用户误以为已经可以真实调远程 Agent。真正的调用会在第 35 章进入工具系统，到时候再让调用结果进入 `tool_called` 和工具预览卡片。
​        第四个难点是不要把 Agent Card 理解成普通配置。配置通常由本项目维护，Agent Card 则是远程 Agent 对外声明自己的能力。Host 可以缓存、展示或校验它，但不能把它当成永远可靠的本地事实。真实接入时，Agent Card 可能版本变化、能力变化、地址变化，也可能因为远程 Agent 不可用而读取失败。本章先用固定数据，是为了讲清结构；后续真实调用必须把这些失败暴露出来。
​        第五个亮点是本章的后端接口与前端展示保持了同一套叙事。后端 `/concepts` 解释角色，前端显示核心角色；后端 `/demo/agent-card` 返回示例名片，前端显示 Agent Card；后端 `/demo/message` 演示调用流程，命令行验证展示步骤。每个接口都有清楚的教学目的，而不是为了“多做几个接口”凑功能。
​        第六个难点是避免和现有 Agent Task 混淆。当前项目已经有本地计划任务、Redis Stream 后台执行任务和会话事件。A2A Task 是跨 Agent 协作任务，它将来会进入当前任务体系，但概念上不等于本地 Redis 任务。本章用 `a2a-demo-...` 作为 task id 前缀，就是为了让读者知道它属于 A2A 演示，不是当前会话里的本地任务记录。

## 34.9 面试考点
​        如果面试官问“A2A 和 MCP 有什么区别”，可以回答：MCP 关注 Agent 如何使用外部工具、资源和提示词；A2A 关注 Agent 如何发现并协作调用另一个 Agent。MCP 的对象更像工具服务，A2A 的对象是具备任务处理能力的远程 Agent。
​        如果被问到“Agent Card 的作用是什么”，要说明它是远程 Agent 的能力声明。Host 通过 Agent Card 了解远程 Agent 的名称、地址、版本、能力、输入模式和输出模式，再决定是否发送任务。
​        如果被问到“为什么本章不真实调用远程 Agent”，可以回答：本章是协议入门，先用确定性接口讲清角色和流程。真实调用涉及网络、状态、失败、权限和结果同步，放到第 35 章作为工具接入更合适。
​        如果被问到“Task 和普通函数调用有什么不同”，重点说明 Task 有状态和过程。远程 Agent 可能异步执行，结果不一定立即返回一个字符串，它可能返回消息、artifact、状态变化和后续事件。本章只模拟 completed，是为了先展示最小结构。

## 34.11 常见问题
### 34.11.1 A2A 是不是可以替代 MCP
​        不能。A2A 和 MCP 关注点不同。MCP 让 Agent 使用工具和资源，A2A 让 Agent 与另一个 Agent 协作。一个成熟系统可能同时使用两者：主 Agent 通过 MCP 调工具，也通过 A2A 把子任务交给远程 Agent。

### 34.11.2 为什么 Agent Card 不直接当作工具列表
​        Agent Card 描述的是远程 Agent 的身份和能力，不只是可调用函数列表。它会告诉 Host 这个 Agent 的职责、地址、输入输出模式和能力范围。第 35 章可以把某些远程 Agent 能力适配成工具，但 Agent Card 本身比工具定义更偏 Agent 级别。

### 34.11.3 本章的 URL 会不会真实访问
​        不会。本章的 `https://agents.example.com/research` 只是示例 Agent Card 中的字段，用来说明远程 Agent 会有自己的地址。`send_demo_message()` 不会访问这个 URL，它只返回本地模拟结果。

### 34.11.4 为什么前端只展示概念和 Agent Card
​        因为本章还没有把 A2A 调用接入 AgentTool。前端如果现在提供调用按钮，会让用户误以为已经能真实协作。当前阶段先把概念和示例 Agent 展示出来，下一章再把远程 Agent 调用结果放进工具事件流。

### 34.11.5 为什么 message 限制 4000 字符
​        入门演示只需要文本任务，不应该让用户提交过大的内容。真实 A2A 调用后续会处理更复杂输入，例如文件、artifact 或结构化数据。本章先限制文本长度，让接口边界简单明确。

### 34.11.6 A2A 的 task 会不会进入当前会话事件流
​        本章不会。本章只返回 demo 接口结果，不写会话事件。第 35 章把 A2A 注册成工具后，远程 Agent 调用结果才会进入 `tool_called` 事件，并在工具预览面板中展示。
### 34.11.7 Host Agent 和当前 Planner/ReAct 是什么关系
​        当前项目里的 Planner 和 ReAct 已经承担了一部分 Host Agent 的职责：Planner 负责拆解任务，ReAct 负责执行步骤并选择工具。但 A2A 里的 Host Agent 概念更宽，它不仅可以选择本地工具，还可以选择远程 Agent。第 34 章只是把概念讲清楚，第 35 章以后，A2A 调用会通过工具协议接入 ReAct 执行链路，逐渐让当前系统具备 Host Agent 的外部协作能力。

### 34.11.8 Remote Agent 是不是必须和本项目一样
​        不需要。Remote Agent 可以使用完全不同的技术栈、模型、工具和部署方式。A2A 的价值就在于让不同 Agent 通过共同协议协作，而不是要求它们共享代码库。Host 只需要知道远程 Agent 的 Agent Card、调用入口、输入输出模式和任务状态。至于远程 Agent 内部怎么规划、怎么调用工具、怎么生成结果，是它自己的实现细节。

### 34.11.9 为什么示例 Agent 是研究 Agent
​        研究 Agent 容易帮助读者理解 A2A 的价值。调研、整理资料、生成提纲这类工作天然适合作为主任务中的子任务，主 Agent 可以把它交给远程研究 Agent，再把结果用于后续写作、代码设计或决策。示例选择研究 Agent，不代表 A2A 只能做调研；代码 Agent、测试 Agent、评审 Agent、文档 Agent 都可以用同样模式接入。

### 34.11.10 Agent Card 里的 input modes 和 output modes 有什么用
​        它们告诉 Host 远程 Agent 支持什么输入和输出格式。本章示例使用 `text/plain` 和 `application/json`，是为了表达最基本的文本输入和结构化输出。真实协作中，有的 Agent 可能只接受文本，有的可能接受文件或图片，有的可能返回 artifact。Host 在发送任务前要检查这些模式，避免把远程 Agent 不支持的内容发过去。

### 34.11.11 为什么 message/send 要返回 steps
​        steps 是为了让协议过程可观察。真实 A2A 调用里，这些步骤可能分散在日志、网络请求和状态更新中。入门阶段把它们显式返回，可以帮助读者理解 Host 不是直接调用一个函数，而是先读取 Agent Card，再选择远程 Agent，再发送 message，最后接收 task 结果。这个顺序是后续真实接入的骨架。

### 34.11.12 为什么本章不把 A2A 放进 MCP 面板
​        MCP 和 A2A 都是外部能力，但它们不是同一种能力。MCP 面板展示的是外部工具 Server 和工具列表，A2A 面板展示的是远程 Agent 概念和 Agent Card。如果混在一个面板里，用户会误以为远程 Agent 只是普通工具。分开展示可以让两种协议边界更清楚。

### 34.11.13 A2A 调用失败时应该怎么处理
​        本章还没有真实远程调用，所以只处理空 message 这类本地输入错误。真实接入后，需要处理 Agent Card 读取失败、远程 Agent 不可用、任务超时、状态失败、结果格式不符合预期等情况。这些错误不能静默吞掉，应该进入工具结果、任务状态或会话事件，让用户知道远程协作具体失败在哪一步。

### 34.11.14 A2A 和多 Agent 编排有什么关系
​        A2A 是 Agent 之间通信和协作的协议基础，多 Agent 编排则是更高层的任务组织方式。第 34 章先讲一个 Host 调一个 Remote Agent 的最小流程；第 36 章以后，多 Agent 编排会关心多个远程或本地 Agent 如何分工、并行、汇总和互相校验。没有 A2A 这类协作协议，多 Agent 编排就只能停留在本地模拟。

### 34.11.15 为什么这章仍然放在工具预览的环境页签
​        因为本章展示的是 A2A 能力环境，而不是一次真实调用结果。环境页签适合展示当前系统具备哪些外部能力、有哪些远程 Agent 概念、示例 Agent Card 长什么样。等第 35 章发生真实调用后，结果才应该进入工具页签。这样“能力状态”和“调用结果”不会混在一起。

### 34.11.16 后续真实 A2A 调用会不会复用本章代码
​        会复用概念和一部分结构，但不会直接把 demo 当真实实现。本章的领域对象、Schema 思路和前端展示会继续有用；`A2aIntroService` 的固定数据主要用于教学。真实接入时会新增远程 Agent 配置、Agent Card 读取、message/send Client 和工具注册逻辑，让 A2A 从演示接口进入执行链路。
### 34.11.17 A2A 结果应该由谁合并到最终回答
​        应该由 Host Agent 合并。Remote Agent 负责完成被交付的子任务，返回自己的消息、状态或产物，但最终回答仍然要由当前会话里的主 Agent 组织。这样用户看到的是一个统一回答，而不是多个 Agent 各说各话。真实接入后，Host 需要判断远程结果是否可信、是否完整、是否需要补充调用，再把它纳入最终上下文。

### 34.11.18 远程 Agent 返回的内容能不能直接信任
​        不能默认直接信任。远程 Agent 和工具一样，都是外部能力来源。它返回的结果需要被记录、展示和必要时校验。对于研究类任务，Host 可能还要检查来源；对于代码类任务，Host 可能要跑测试；对于评审类任务，Host 要判断建议是否适合当前代码库。A2A 增强的是协作能力，不代表可以跳过验证。

### 34.11.19 A2A 是否一定是同步调用
​        不一定。本章的 demo 为了简化，直接返回 `completed` 状态。但真实 A2A 任务可能是异步的，远程 Agent 接收任务后先返回 running，之后再通过轮询、回调或事件流更新状态。当前项目已经有任务状态和事件流基础，后面可以把 A2A task 的状态变化映射到会话事件中，让用户看到远程 Agent 的执行过程。

### 34.11.20 A2A 和当前 Redis 任务队列会怎样配合
​        当前 Redis Stream 负责本项目内部 Agent 任务的后台执行。A2A 真实接入后，可以把远程 Agent 调用作为本地任务执行中的一个步骤：本地 Runner 执行到 A2A 工具时，发起远程 task，再把结果写回当前会话。Redis 队列不一定直接承载远程 task，但它可以承载“等待远程结果并写回事件”的本地执行过程。

### 34.11.21 为什么 Agent Card 需要 version
​        远程 Agent 的能力会演进。它可能新增能力、修改输入输出模式、改变返回结构，也可能升级模型和工具链。`version` 能帮助 Host 和运维人员判断当前读取的是哪个版本的能力说明。真实系统里，如果某个远程 Agent 升级后行为变化，版本信息会成为排查的重要线索。

### 34.11.22 A2A 面板以后会不会显示多个 Agent
​        会有这个方向。本章只有一个示例 Agent Card，目的是先讲清结构。真实接入后，前端可以展示多个远程 Agent，每个 Agent 有自己的名称、能力、状态和调用入口。那时 A2A 面板会更像远程 Agent 注册表，而不只是入门说明卡片。

### 34.11.23 A2A 是否需要权限控制
​        真实接入时需要。远程 Agent 可能具备访问外部系统、修改代码、创建工单或读取敏感资料的能力。Host 在调用前要知道当前用户是否有权限，远程 Agent 也可能需要鉴权。本章不处理权限，是因为它还没有真实调用；但架构上要预留这个意识，不能把远程 Agent 当作无条件可信能力。

### 34.11.24 A2A 结果是否应该进入上下文工程
​        如果远程 Agent 的结果会影响后续回答，就应该进入上下文工程。它可以作为工具事件、会话事件或引用资料被后续步骤读取。否则主 Agent 下一步可能看不到远程结果，只能在前端显示一次调用记录。后续章节做最终回答质量和引用体系时，A2A 结果也需要被纳入可追踪上下文。

### 34.11.25 A2A 为什么适合长任务
​        长任务往往包含多个不同性质的子任务，例如调研、编码、测试、评审和文档整理。一个 Agent 全部承担时，上下文和角色都会变重。A2A 允许 Host 把合适的子任务交给专门 Remote Agent，让每个 Agent 在自己的能力边界内工作。这样主 Agent 更像协调者，而不是所有事情都亲自做。

### 34.11.26 本章和第 36 章多 Agent 协作有什么区别
​        本章只讲协议入门，重点是 Host Agent、Remote Agent、Agent Card 和 message/send 的基本流程。第 36 章会更关注编排：多个 Agent 如何分工、任务如何拆分、结果如何汇总、失败如何恢复。可以把第 34 章看作通信和概念基础，把第 36 章看作协作策略和执行组织。

### 34.11.27 为什么要把 A2A 放在 MCP 后面讲
​        MCP 是更低门槛的外部能力接入：先让 Agent 调工具、看工具结果、进入事件流。A2A 的抽象更高，它要求读者已经理解工具调用、事件记录、外部能力展示和执行链路。先讲 MCP，再讲 A2A，学习曲线更自然，也更符合项目从工具增强到多 Agent 协作的演进顺序。

### 34.11.28 A2A demo 里的 task_id 有什么意义
​        `task_id` 让一次远程协作有可追踪身份。即使本章只是模拟，它也体现了真实系统需要追踪远程任务的事实。后续如果远程 Agent 异步执行，Host 就需要用 task id 查询状态、取消任务、关联事件或下载结果。没有 task id，跨 Agent 协作就很难回放和排查。

### 34.11.29 为什么 output_message 里明确说这是模拟响应
​        这是为了避免误导用户。本章没有发起真实远程调用，所以输出必须明确告诉读者它是第 34 章的模拟响应。教程中的演示可以简化，但不能把本地固定数据包装成真实远程结果。这个边界越清楚，后面接真实 A2A 时读者越容易理解两者差异。

### 34.11.30 A2A 是否会改变现有工具预览面板
​        会逐步改变，但不是本章一次完成。本章只把 A2A 概念面板放入环境页签；第 35 章开始，A2A 调用结果会像 MCP 工具结果一样进入工具页签。长期看，工具预览面板会同时承载本地工具、MCP 工具和 A2A 远程 Agent 的调用结果，用户可以在同一个观察区理解 Agent 执行过程。

## 34.12 代码串联阅读
​        这一章的代码虽然分散在后端和前端多个文件里，但阅读顺序很清楚。先看领域对象，再看应用服务，再看 Schema 和路由，最后看前端面板。按这个顺序读，比从页面开始倒着找接口更容易理解 A2A 是怎样进入项目的。

### 34.12.1 从 domain/a2a/entities.py 开始
​        `domain/a2a/entities.py` 是本章最适合先读的文件。它没有 FastAPI、没有 Pydantic、没有 React，也没有网络调用，只定义 A2A 入门需要的几个对象：`A2aRole`、`A2aCapability`、`A2aAgentCard`、`A2aMessagePart`、`A2aTaskStep` 和 `A2aMessageDemo`。这些对象就是本章概念的代码形态。
​        读这个文件时，要特别注意 `A2aAgentCard` 和 `A2aMessageDemo`。前者描述远程 Agent 的能力边界，后者描述一次 message/send 的结果。一个是“调用前如何认识对方”，一个是“调用后如何记录过程”。这两个对象串起来，基本就能理解本章为什么要先讲 Agent Card，再讲 message/send。

### 34.12.2 再看 application/a2a_intro_service.py
​        `A2aIntroService` 把领域对象组织成可调用的应用服务。`list_roles()` 面向概念说明，`get_demo_agent_card()` 面向示例名片，`send_demo_message()` 面向调用流程演示。它没有直接返回 Pydantic 模型，也没有直接处理 HTTP 请求，这一点和第 33 章的分层规则是一致的。
​        这里最关键的是 `send_demo_message()`。它先校验输入，再读取 Agent Card，再生成 task id，最后构造步骤和输出消息。虽然它没有访问远程网络，但流程顺序已经和真实 A2A 的基本心智模型一致。后续真实接入时，固定的 output_text 会被远程 Agent 响应替代，固定的 steps 会被真实调用过程和状态更新替代。

### 34.12.3 然后看 schemas/a2a.py
​        `schemas/a2a.py` 负责把后端概念转换成 HTTP 接口稳定结构。它里面的 `A2aConceptsResponse`、`A2aAgentCardResponse` 和 `A2aMessageDemoResponse` 分别对应三个接口。这样前端不需要理解 dataclass，也不需要依赖应用服务内部对象。
​        Schema 层还有一个很实用的边界：`A2aMessageSendRequest` 对 message 做长度限制。入门章节只允许一段文本任务，能避免接口变成无限制的大输入入口。真实 A2A 支持文件和 artifact 时，也应该通过新的结构显式表达，而不是把所有内容都塞进一个巨大字符串。

### 34.12.4 接着看 presentation/http/routes/a2a.py
​        路由文件展示了第 33 章分层重构后的落点。A2A 的 HTTP 入口不在旧的 `app/api` 下，而是在 `app/presentation/http/routes/a2a.py`。它只做三件事：创建入门服务，把领域对象转换成响应模型，暴露 HTTP 接口。
​        `GET /concepts` 用于展示概念，`GET /demo/agent-card` 用于展示示例 Agent Card，`POST /demo/message` 用于模拟 message/send。路由层没有把 demo 数据写死在函数里，而是调用 `A2aIntroService`。这样后续真实接入时，可以新增真实服务，而不需要把整个 HTTP 文件改成业务逻辑仓库。

### 34.12.5 最后看前端 a2a-api 和 A2aPanel
​        前端的 `a2a-api.ts` 只封装 concepts 和 Agent Card 两个读取接口。它没有封装 message/send 给页面按钮使用，这个选择是有意的：本章 UI 只展示能力环境，不触发真实协作。`A2aPanel` 则把核心角色和示例 Agent Card 展示出来，让用户在环境页签里看到系统正在引入远程 Agent 协作能力。
​        `ToolPreviewPanel` 把 `A2aPanel` 放在环境页签，与 Sandbox、MCP 和 VNC 并列。这个位置说明 A2A 目前还是“能力环境展示”。当第 35 章把 A2A 调用接入工具协议后，调用结果才会进入工具页签。这样前端结构和后端实现阶段保持一致，不会提前展示尚未完成的交互。
​        读前端代码时还要注意 `LoadState` 的一致性。A2A concepts 和 Agent Card 都按 loading、error、ready 三种状态展示，这和 MCP、Sandbox、VNC 的处理方式相同。外部能力越多，前端越需要统一状态表达。否则每个面板都用自己的加载和错误样式，右侧工作区很快会失去一致性。
​        `page.tsx` 中的刷新逻辑也值得看。A2A 有自己的刷新函数，只重新请求 concepts 和 Agent Card，不影响会话消息、文件、MCP 或 VNC。这样用户刷新 A2A 面板时，不会触发无关数据加载。这个小细节体现的是前端状态边界：能力面板可以独立刷新，任务执行流和会话数据不应该被连带扰动。

## 34.13 本章小结
​        本章完成了 A2A 协议入门。后端新增 A2A 领域对象、入门应用服务、API Schema 和 HTTP 路由，提供概念说明、示例 Agent Card 和 message/send 演示接口。前端新增 A2A 面板，把 Host Agent、Remote Agent、Agent Card 和 Task 的概念展示到工具预览环境区。
​        这一章的重点不是远程调用，而是建立正确边界。MCP 是工具协议，A2A 是 Agent 协作协议。Agent Card 是远程 Agent 的能力声明，message/send 是 Host 把任务交给远程 Agent 的入口，Task 是协作过程和结果的承载。理解这些，下一章把 A2A 接成工具时才不会混乱。
​        从工程连续性看，本章也验证了第 33 章分层重构的价值。新的协议能力可以自然落到 `domain`、`application`、`schemas` 和 `presentation/http` 中，前端也能按已有工具预览结构接入新面板。也就是说，A2A 入门不是孤立章节，它同时证明了后端分层和前端工具预览都具备继续扩展的空间。
​        更重要的是，本章把“远程 Agent 参与任务”这件事先放到了可解释的位置。先解释角色、名片、消息和任务，再去实现真实调用，后续代码就不会变成一组看不出意图的 HTTP 请求封装。
​        这种先解释再接入的节奏，也能减少后续调试时的概念混乱。

## 34.14 下一章预告
​        下一章会把 A2A 从入门演示推进到工具接入。远程 Agent 会被注册成可调用工具，Agent 执行任务时可以通过工具协议触发 A2A 调用，并把远程 Agent 的响应写入工具事件流。第 34 章讲清概念，第 35 章开始让它真正参与任务执行。
​        也就是说，第 35 章会回答本章刻意留下的问题：Agent Card 从哪里读取，远程 Agent 如何被包装成工具，message/send 的返回结果如何格式化，前端工具预览怎样展示远程 Agent 的输出。到那时，A2A 不再只是环境页签里的概念面板，而会进入和 FileTool、SearchTool、MCP Tool 同一套执行观察链路。
​        读者可以把本章当作 A2A 的“识别和理解阶段”，把下一章当作 A2A 的“执行和观测阶段”。只有先知道远程 Agent 是什么，才能判断后面把它做成工具时，哪些字段必须保留，哪些错误必须暴露，哪些结果需要写回当前会话。
​        这会让项目从“一个 Agent 使用工具”继续走向“多个 Agent 围绕同一个任务协作”。
