# 第六十二章. 规划粒度与任务拆分

## 62.1 本章目标

第十三章的 PlannerAgent 输出一份 `AgentPlan`，里面是 `PlanStep` 列表，每步带 title、description、expected_output，执行按步推进。但真实跑下来，计划的粒度是两种截然不同的麻烦的源头：有时计划太粗，一步吞下三个子任务，执行器不知道中途该停在哪；有时计划太细，每个文件一个步骤，planner 和 critic 评审十几轮也谈不拢。本章治理规划粒度：按复杂度三级分级、heavy 的硬下限、"宽进严出"的评审原则，外加一个从计划派生的 TodoBoard 视图。

完成本章后，你将能够：

- 解释为什么"一刀切"的规划粒度不成立，以及太严与太宽各自付的代价是什么；
- 用复杂度信号把任务分为 light / standard / heavy 三级，并给出每级的步骤数区间；
- 说明为什么长任务的步骤数有 ≥10 的硬下限，粒度决定的是哪三个物理量；
- 把 TodoBoard 实现为"从计划派生的视图"，并解释为什么不落表、不上图数据库。

## 62.2 为什么需要这一章

太严和太宽的代价不在同一个地方，调参的时候很难同时看见：

**太严的代价是互博。**如果 critic 要求"每步必须对应单一文件、单一函数"，planner 要么硬拆要么注水，critic 每轮都能找出新的问题——双方的标准都"对"，也都"无穷无尽"，评审循环没有终态。规划阶段本应花几秒钟，变成整个任务里最贵的环节；而最后产出的是一份看起来很专业但执行不动的计划：每步小到无法自包含，执行每一步都要重新读一遍任务全文才知道自己要干嘛。

**太宽的代价是边界模糊。**"实现这个功能"这种步骤不是步骤，是任务本身。执行器无法判断何时算做完（只能做到"自认为做完"，这又落回第六十一章的自证陷阱）；验收门禁没有可挂的粒度，只能对整个任务做大验收，一步失败整个任务推倒重来；单步吞下的上下文过大，直接引爆上下文问题。

两种代价的根子相同：**粒度不是计划自身的德性，必须匹配任务的复杂度**。修一个 bug 的正确粒度是 2-3 步，硬要 10 步就是注水表演；做一个跨前后端的新功能，正确粒度是 10 步以上，只给 3 步就是放羊。所以治理的第一步不是改 critic 的规则，而是先给任务定级。

## 62.3 实现步骤

### 62.3.1 复杂度信号与三级分级

分级器只看任务描述里拿得到的低成本信号，不向模型要"感觉"——向模型要感觉是另一个互博源，它自己的判断没法自我验证：

```python
@dataclass(frozen=True, slots=True)
class ComplexityProfile:
    tier: str                    # "light" | "standard" | "heavy"
    step_range: tuple[int, int]
    min_steps: int               # 硬下限，0 表示无

TIER_CONFIG = {
    "light":    (2, 4),
    "standard": (4, 8),
    "heavy":    (10, 15),
}

def classify_task(*, files_estimate: int, new_tables: bool,
                  external_deps: bool) -> ComplexityProfile:
    if new_tables or files_estimate >= 8 or (external_deps and files_estimate >= 4):
        return ComplexityProfile("heavy", (10, 15), min_steps=10)
    if files_estimate >= 3 or external_deps:
        return ComplexityProfile("standard", (4, 8), min_steps=0)
    return ComplexityProfile("light", (2, 4), min_steps=0)
```

三个信号：预估触及文件数、是否涉及新表/迁移、是否有外部依赖（新 API、LLM 链路、浏览器自动化）。信号判定刻意偏向"就高"：把 light 误判成 standard，代价是计划里多两步；把 heavy 误判成 standard，代价是上下文和检查点的双重失守。模糊时一律往高级放。

### 62.3.2 为什么 ≥10 步是硬下限

heavy 的 10 步下限是"硬"的，因为粒度直接决定三个物理量：

1. **单步上下文体积**：10 步以上，每步的上下文天然被压到整体的几分之一；3 步的计划，每步都得背着全部中间状态跑——这正是下一章节上下文爆炸的成因。
2. **检查点密度**：第四十五章的 Checkpoint DAG 能回退多细，取决于计划切多细。5 步的任务失败在第 5 步，可以回退到第 4 步的状态续跑；3 步的任务失败在第 3 步，只能整段重做。
3. **验收粒度**：第六十一章的重试额度是有限资源，步骤越细，单次失败消耗的重试预算越少，门禁链的反馈回路也越短。

"硬下限"的含义是 critic 的检查方向是单向的：**低于 10 步的 heavy 计划必须打回，高于 10 步的计划不强制砍**。下限保物理量，上限管风格——风格问题不应该成为评审的否决项。

### 62.3.3 宽进严出，以及防互博

规划的原则是宽进严出：**生成阶段允许粗糙，评审阶段抓缺口**。让 planner 在生成时反复自我修订，收益很低——模型检查自己的输出，和第六十一章的自证陷阱是同一个结构；缺口应该由一个只对照标准、不看过程的独立 critic 来抓。

但 critic 的 prompt 里必须写进一句话：**"步骤数不是质量标准"**。这句话是防互博的关键。如果 critic 只查"够不够 10 步"，planner 会很快学会注水——"第 7 步：回顾并确认方案"这种不产生任何产出的步骤；反过来，如果 critic 只看步数，一份 10 步的注水计划也能通过评审。critic 真正该查的是三件事：

- **完整性**：计划是否覆盖了任务验收命令要求的全部项；
- **原子性**：每步是否有单一可验证的 `expected_output`（呼应 `PlanStep` 的既有结构）；
- **顺序性**：步骤间有没有隐含依赖没显式声明（第 3 步要用第 1 步建的表）。

步数只作为 heavy 的硬下限单独检查，其余一律按内容评审。这样 planner 没有"凑步数"的动机，critic 没有"挑剔格式"的动机，评审循环有收敛的终态。

### 62.3.4 TodoBoard：从计划派生的视图

前端需要一个实时进度板：哪些步骤做完了、当前在哪一步、总进度多少。最直白的做法是建一张 `todo` 表，把步骤落进去。我没有这么做，因为**计划本身已经持久化了**（第四十五章的 checkpoint 链路就是单一事实源），TodoBoard 只是它在某一时刻的投影：

```python
class TodoBoard:
    """从 AgentPlan 派生的视图，自身不存任何状态。"""

    def __init__(self, plan: AgentPlan):
        self._plan = plan
        self._order = topological_sort(plan.steps)   # 依赖拓扑排序

    def progress(self) -> dict[str, Any]:
        done = [s for s in self._order if s.status is PlanStepStatus.completed]
        current = next((s for s in self._order
                        if s.status is not PlanStepStatus.completed), None)
        return {
            "total": len(self._order),
            "done": len(done),
            "current": current.title if current else None,
            "percent": round(len(done) / max(len(self._order), 1), 2),
        }
```

拓扑排序把"声明顺序"和"依赖顺序"分开：计划里的步骤顺序是叙述顺序，执行和展示走依赖顺序，避免前端把一个"其实还没做但写在前面"的步骤显示成当前步。

为什么不落表、不上图数据库，三个理由：

- **单一事实源**：板子若单独持久化，就多出一个"计划变了板子没跟上"的同步问题——计划被重规划、步骤被合并或删除时，两份状态不一致的排查成本远高于查询成本。派生视图永远和源一致，因为它就是源。
- **规模撑不起图**：单个任务的步骤最多十几条，依赖边几十条，拓扑排序是毫秒级纯计算；图数据库的查询面（路径查询、子图、多跳遍历）在这个规模上完全没有用武之地，引入它只为"架构完整"，不值。
- **进度 API 无状态**：`GET /tasks/{id}/todo` 每次请求现场从计划与步骤状态算出来，不缓存、不回写，不存在并发写坏的可能。

"派生而不存储"是这类视图的通用纪律：**凡是能从既有状态重算出来的数据，都不该再建一份事实源。**

## 62.4 本章小结

- 粒度必须匹配复杂度，而不是匹配"专业感"：light 2-4、standard 4-8、heavy 10-15。一刀切同时是互博和边界模糊的共同根因。
- 复杂度分级方向就高不就低：light 误判成 standard 的代价小，heavy 误判成 standard 的代价是上下文和检查点双重失守。
- heavy 的 ≥10 步是硬下限：它保的是单步上下文、检查点密度、验收粒度三个物理量，不是步数本身。critic 只查下限，不砍上限。
- 宽进严出：生成阶段容忍粗糙，评审阶段抓缺口。critic 必须显式声明"步骤数不是质量标准"，只查完整性、原子性、顺序性——这是防互博的核心。
- TodoBoard 是从计划派生的视图，不是第二事实源：这个规模下内存拓扑排序比任何持久化都便宜，"派生而不存储"直接消灭一整类同步 bug。
