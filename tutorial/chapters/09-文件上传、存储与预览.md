# 第九章. 文件上传、存储与预览

## 9.1 文件上传与本地存储

### 9.1.1 本节目标
​        从这一阶段开始，AtlasAgent 不再只处理文本输入。真实的 Agent 工作台里，用户经常会把需求文档、截图、表格、代码文件或压缩包交给系统，希望后续任务可以围绕这些材料继续展开。因此，文件上传不是一个孤立的按钮，而是 Agent 输入能力的一部分。
​        本节要带读者完成文件上传的第一条基础链路：浏览器通过 `multipart/form-data` 把文件传给 FastAPI，后端使用 `UploadFile` 读取内容，把真实文件写入 API 服务的上传目录，再把文件名、大小、类型、下载地址和创建时间写入 PostgreSQL。前端则在聊天工作台里增加附件上传区，让用户可以看到上传结果并下载原始文件。读到这里，读者需要特别注意两条边界：文件内容保存在哪里，文件元数据又由谁负责维护。

### 9.1.2 最终效果
​        本节结束后，访问：

```Plain
http://localhost:8088
```

​        进入任意会话后，可以在聊天输入框上方看到附件上传区。
​        选择一个本地文件后：
​        浏览器会把文件提交到后端，API 服务把文件内容保存到 `/app/uploads`，同时在 `files` 表里记录这次上传的元数据。页面拿到响应后，会把文件名、文件大小、上传时间和下载入口展示在附件列表里。用户此时看到的不是一个临时文件名，而是一条可以被后续功能继续引用的文件记录。
​        同时后端新增接口：

```Plain
POST /api/files
GET  /api/files/{file_id}
GET  /api/files/{file_id}/download
```

​        本节先完成独立文件能力。文件暂时不绑定到会话消息里。本章后文会继续加入会话文件列表和文件预览。

### 9.1.3 本节要解决的问题
​        第 8 章已经完成会话状态、停止任务、未读清理和 SSE 状态流。
​        但是一个真实的 Agent 工作台不能只接收文本。用户常常需要上传：

```Plain
需求文档
截图
表格
压缩包
代码文件
```

​        这些文件后续可能会被 Agent 读取、分析、预览或作为工具输入。
​        文件上传不能只把文件放到某个目录里。因为页面还需要知道：

```Plain
文件原始名称是什么
文件类型是什么
文件大小是多少
文件如何下载
文件什么时候上传
```

​        所以本节把文件拆成两部分处理：

```Plain
文件内容 -> 保存到本地存储目录
文件元数据 -> 保存到 PostgreSQL
```

### 9.1.4 本节技术方案
​        本节采用“本地磁盘 + 数据库元数据”的方案。
​        可选方案有三种：
​        最简单的做法是只把文件保存到磁盘，不写数据库；这种方式实现快，但页面很难稳定查询文件列表，也无法给后续权限、预览和引用关系留下位置。另一个极端是把文件二进制内容直接写进数据库；它看起来统一，但会让数据库备份、迁移和查询压力变重。课程项目在这里选择中间方案：文件内容落在磁盘，文件元数据进入 PostgreSQL。
​        本节选择第三种。
​        原因是：
​        这样做的好处是边界清楚。文件内容通常比较大，适合交给文件系统或后续对象存储；元数据体积小、结构稳定，适合交给数据库负责查询和关联。本节先使用本地磁盘，是为了让开发环境容易验证；等项目进入部署或生产语境时，`FileService` 这层还可以继续演进，把本地目录替换成 S3、MinIO 或其他对象存储。
​        本节请求链路如下：

```Plain
浏览器选择文件
  |
  v
POST /api/files
  |
  v
FileService
  |
  +-- 清理文件名
  +-- 检查文件大小
  +-- 写入 /app/uploads
  +-- 写入 files 表
  |
  v
前端展示附件和下载链接
```

​        本节会做这些内容：
​        后端部分会从依赖开始，加入 `python-multipart`，让 FastAPI 能够解析浏览器提交的文件表单。随后新增 `files` 表迁移、文件领域实体、Repository、应用服务和 API 路由，让上传、查询和下载都经过清楚的分层。Docker Compose 还会给 API 服务挂载上传目录，避免容器重建后丢失已经保存的文件。
​        前端部分会新增 `file-api.ts`、附件上传组件和附件列表组件，zustand store 负责保存当前页面已经上传成功的附件。这里暂时还不讨论 Agent 如何读取文件内容，重点先放在“文件能可靠上传、保存、查询、下载”这条底层链路上。
​        本节暂时不做这些内容：
​        本节不会把文件绑定到具体消息，也不会做文件分页、文件预览、对象存储、权限控制和 Agent 文件读取。这些能力都需要更完整的上下文关系。课程在这里先把文件模块站稳，本章后文再把文件接入会话维度，并继续处理预览和上下文组织问题。

### 9.1.6 实施步骤
#### 9.1.6.1 安装文件上传依赖
​        进入后端目录：

```Bash
cd backend/api
```

​        安装 `python-multipart`：

```Bash
uv add python-multipart
```

​        FastAPI 接收 `multipart/form-data` 表单上传时需要这个依赖。浏览器上传文件时，请求体不是普通 JSON，而是带边界分隔的表单数据。
​        安装后，`backend/api/pyproject.toml` 会出现：

```TOML
"python-multipart>=0.0.30",
```

​        `backend/api/uv.lock` 也会同步更新。
​        常见误区是手动在 `pyproject.toml` 里加依赖，但没有更新锁文件。后续 Docker 构建或其他机器安装时就可能出现版本不一致。

#### 9.1.6.2 配置上传目录和大小限制
​        打开 `backend/api/app/core/config.py`，在数据库配置后加入：

```Python
upload_dir: str = "uploads"
max_upload_size: int = 10 * 1024 * 1024
```

​        这两个配置分别表示：
​        `upload_dir` 决定文件内容写入哪个目录，`max_upload_size` 决定单个文件允许的最大字节数，默认是 10MB。把这两个值放进配置层，可以让本地开发、Docker Compose 和后续部署环境使用不同取值，而不用修改路由或应用服务代码。
​        本地直接运行 API 时，文件会保存到 `backend/api/uploads`。Docker Compose 运行时，会通过环境变量改成 `/app/uploads`。
​        这里把限制放进配置，而不是写死在路由里，是为了后续部署时可以按机器磁盘和业务需求调整。

#### 9.1.6.5 实现文件 Repository
​        创建 `backend/api/app/infrastructure/repositories/file_repository.py`：

```Python
from uuid import UUID

from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

from app.domain.files.entities import FileObject
from app.domain.files.repositories import FileRepository
from app.infrastructure.database.models.file_object import FileObjectModel

class SqlAlchemyFileRepository(FileRepository):
    def __init__(self, db_session: AsyncSession) -> None:
        self.db_session = db_session

    async def add(
        self,
        original_name: str,
        stored_name: str,
        content_type: str,
        size: int,
        storage_path: str,
    ) -> FileObject:
        model = FileObjectModel(
            original_name=original_name,
            stored_name=stored_name,
            content_type=content_type,
            size=size,
            storage_path=storage_path,
        )
        self.db_session.add(model)
        await self.db_session.flush()
        await self.db_session.refresh(model)
        return model.to_entity()

    async def get(self, file_id: UUID) -> FileObject | None:
        stmt = select(FileObjectModel).where(FileObjectModel.id == file_id)
        result = await self.db_session.execute(stmt)
        model = result.scalar_one_or_none()
        return model.to_entity() if model else None
```

​        Repository 只负责数据库读写，不负责保存文件内容。
​        这样做的原因是：文件内容属于存储层操作，元数据属于数据库操作。把两件事拆开后，后续把本地磁盘替换成对象存储时，数据库 Repository 不需要跟着大改。

#### 9.1.6.6 实现文件应用服务
​        创建 `backend/api/app/application/file_service.py`：

```Python
from pathlib import Path
from uuid import UUID, uuid4

from app.application.unit_of_work import UnitOfWork
from app.core.config import settings
from app.core.exceptions import AppException
from app.domain.files.entities import FileObject

class FileService:
    def __init__(self, uow: UnitOfWork) -> None:
        self.uow = uow
        self.upload_root = Path(settings.upload_dir)

    async def save_upload(
        self,
        original_name: str,
        content_type: str | None,
        content: bytes,
    ) -> FileObject:
        clean_name = self._clean_filename(original_name)
        if not clean_name:
            raise AppException(
                message="file name is required",
                code=400,
                status_code=400,
            )
        if not content:
            raise AppException(
                message="file content is required",
                code=400,
                status_code=400,
            )
        if len(content) > settings.max_upload_size:
            raise AppException(
                message="file is too large",
                code=413,
                status_code=413,
            )

        stored_name = self._build_stored_name(clean_name)
        storage_path = self.upload_root / stored_name
        self.upload_root.mkdir(parents=True, exist_ok=True)
        storage_path.write_bytes(content)

        try:
            file_object = await self.uow.files.add(
                original_name=clean_name,
                stored_name=stored_name,
                content_type=content_type or "application/octet-stream",
                size=len(content),
                storage_path=str(storage_path),
            )
            await self.uow.commit()
        except Exception:
            # 元数据写入失败时清理已落盘文件，避免出现没有数据库记录的孤立文件。
            storage_path.unlink(missing_ok=True)
            await self.uow.rollback()
            raise
        return file_object

    async def get_file(self, file_id: UUID) -> FileObject:
        file_object = await self.uow.files.get(file_id)
        if file_object is None:
            raise AppException(
                message="file not found",
                code=404,
                status_code=404,
            )
        return file_object

    async def get_download_path(self, file_id: UUID) -> tuple[FileObject, Path]:
        file_object = await self.get_file(file_id)
        path = Path(file_object.storage_path)
        if not path.is_file():
            raise AppException(
                message="file content not found",
                code=404,
                status_code=404,
            )
        return file_object, path

    @staticmethod
    def _clean_filename(filename: str) -> str:
        # 只保留文件名本身，避免用户传入 ../ 这类路径片段。
        return Path(filename).name.strip()

    @staticmethod
    def _build_stored_name(filename: str) -> str:
        suffix = Path(filename).suffix
        return f"{uuid4().hex}{suffix}"
```

​        这段代码的业务流程：

```Plain
路由读取上传内容
  |
  v
FileService.save_upload
  |
  +-- 清理原始文件名
  +-- 检查空文件
  +-- 检查文件大小
  +-- 生成磁盘文件名
  +-- 写入上传目录
  +-- 写入 files 表
  +-- commit
```

​        这里有一个有意加入的注释：

```Python
# 只保留文件名本身，避免用户传入 ../ 这类路径片段。
# 元数据写入失败时清理已落盘文件，避免出现没有数据库记录的孤立文件。
```

​        这是安全边界和一致性边界，不是普通代码翻译。文件上传场景里，用户传来的文件名不可信。如果直接拼接路径，可能造成路径穿越风险。文件写入磁盘后，如果数据库提交失败，也需要清理已落盘文件，否则后续很难判断这个文件是否仍然有效。

#### 9.1.6.7 把文件 Repository 接入 Unit of Work

```Python
from sqlalchemy.ext.asyncio import AsyncSession

from app.infrastructure.repositories.file_repository import SqlAlchemyFileRepository
from app.infrastructure.repositories.session_repository import (
    SqlAlchemySessionEventRepository,
    SqlAlchemySessionMessageRepository,
    SqlAlchemySessionRepository,
)

class UnitOfWork:
    def __init__(self, db_session: AsyncSession) -> None:
        self.db_session = db_session
        self.files = SqlAlchemyFileRepository(db_session)
        self.sessions = SqlAlchemySessionRepository(db_session)
        self.session_messages = SqlAlchemySessionMessageRepository(db_session)
        self.session_events = SqlAlchemySessionEventRepository(db_session)

    async def commit(self) -> None:
        await self.db_session.commit()

    async def rollback(self) -> None:
        await self.db_session.rollback()
```

#### 9.1.6.8 实现文件接口
​        创建 `backend/api/app/schemas/file.py`：

```Python
from datetime import datetime
from uuid import UUID

from pydantic import BaseModel

class FileResponse(BaseModel):
    id: UUID
    original_name: str
    content_type: str
    size: int
    download_url: str
    created_at: datetime
```

​        创建 `backend/api/app/api/routes/files.py`：

```Python
from uuid import UUID

from fastapi import APIRouter, Depends, File, UploadFile
from fastapi.responses import FileResponse as DownloadFileResponse
from sqlalchemy.ext.asyncio import AsyncSession

from app.application.file_service import FileService
from app.application.unit_of_work import UnitOfWork
from app.domain.files.entities import FileObject
from app.infrastructure.database.session import get_db_session
from app.schemas.common import ApiResponse
from app.schemas.file import FileResponse

router = APIRouter(prefix="/files", tags=["files"])

def build_file_service(
    db_session: AsyncSession = Depends(get_db_session),
) -> FileService:
    return FileService(UnitOfWork(db_session))

def to_file_response(file_object: FileObject) -> FileResponse:
    return FileResponse(
        id=file_object.id,
        original_name=file_object.original_name,
        content_type=file_object.content_type,
        size=file_object.size,
        download_url=f"/api/files/{file_object.id}/download",
        created_at=file_object.created_at,
    )

@router.post("", response_model=ApiResponse[FileResponse])
async def upload_file(
    upload: UploadFile = File(...),
    service: FileService = Depends(build_file_service),
) -> ApiResponse[FileResponse]:
    content = await upload.read()
    file_object = await service.save_upload(
        original_name=upload.filename or "",
        content_type=upload.content_type,
        content=content,
    )
    return ApiResponse(data=to_file_response(file_object))

@router.get("/{file_id}", response_model=ApiResponse[FileResponse])
async def get_file(
    file_id: UUID,
    service: FileService = Depends(build_file_service),
) -> ApiResponse[FileResponse]:
    file_object = await service.get_file(file_id)
    return ApiResponse(data=to_file_response(file_object))

@router.get("/{file_id}/download")
async def download_file(
    file_id: UUID,
    service: FileService = Depends(build_file_service),
) -> DownloadFileResponse:
    file_object, path = await service.get_download_path(file_id)
    return DownloadFileResponse(
        path=path,
        media_type=file_object.content_type,
        filename=file_object.original_name,
    )
```

```TypeScript
import type { ApiResponse, UploadedFile } from "../types";

export async function uploadFile(file: File): Promise<UploadedFile> {
  const formData = new FormData();
  formData.append("upload", file);

  const response = await fetch("/api/files", {
    method: "POST",
    body: formData,
  });
  const payload = (await response.json()) as ApiResponse<UploadedFile>;
  if (!response.ok || payload.code >= 400) {
    throw new Error(payload.message || `HTTP ${response.status}`);
  }
  if (!payload.data) {
    throw new Error("empty response");
  }
  return payload.data;
}

export function getDownloadUrl(file: UploadedFile): string {
  return file.download_url;
}
```

### 9.1.7 关键理解
​        文件上传有两条数据线：

```Plain
文件内容线：浏览器 -> API -> /app/uploads
元数据线：浏览器 -> API -> files 表 -> 前端展示
```

​        文件内容适合放在存储系统里，元数据适合放在数据库里。
​        第二个重点是文件名不能直接信任。
​        用户上传的文件名来自浏览器，后端必须把它当作不可信输入。本节用 `Path(filename).name` 只保留文件名本身，避免路径片段影响真实保存位置。
​        第三个重点是 `FormData`。
​        JSON 请求适合普通结构化数据，文件上传需要 `multipart/form-data`。前端发送 `FormData` 时，不要手动设置 `Content-Type`。

### 9.1.8 技术难点与亮点
​        文件上传看起来只是一个接口，但真正容易出错的地方在边界上。FastAPI 接收文件依赖 `python-multipart`，浏览器提交的字段名必须和后端参数名 `upload` 一致；文件内容写入磁盘，文件元数据写入数据库，这两步还要保持事务意识，避免出现数据库没有记录但磁盘已经残留文件，或者数据库有记录但文件内容丢失的情况。
​        这一阶段的工程亮点也在于分层没有被上传功能打乱。文件模块仍然按照领域实体、Repository、应用服务和 API 路由拆开；前端上传逻辑也没有塞进页面文件，而是拆成 `file-api.ts`、`AttachmentUpload`、`AttachmentList` 和 store action。下载链接统一走 API 入口，后续无论补权限、审计还是对象存储签名，都有一个相对稳定的接入位置。

### 9.1.9 面试考点
​        面试中问到文件上传，不要只回答“用了 FastAPI 的 `UploadFile`”。更好的回答是把存储边界讲清楚：文件内容和元数据为什么分开存，`multipart/form-data` 和 JSON 请求有什么区别，前端为什么不能手动设置 `Content-Type`，后端为什么要清理浏览器传来的文件名，以及 Docker Volume 在容器重建时保护了什么。能把这些问题串起来，说明你不是只会写上传接口，而是理解了文件能力在系统中的位置。

## 9.2 会话文件与预览开卷

### 9.2.1 本节目标
​        前文已经让文件可以上传、保存和下载，但那一章里的文件仍然是独立资源。对于 Agent 工作台来说，独立文件还不够，因为用户真正关心的是“这个文件属于哪个会话”“这个会话有哪些材料”“我能不能先看一眼文件内容”。如果这些关系没有建立，后续让 Agent 读取上下文时就会缺少基础。
​        本节要把文件推进到会话上下文中。后端会新增 `session_files` 关系表，实现上传文件到指定会话、查询某个会话的文件列表，以及文本文件预览接口。前端会在右侧工作区展示会话文件列表，并提供下载和预览面板。读者在这一阶段要重点理解下载和预览的差异：下载交付的是完整文件，预览交付的是受限制、可直接展示的文本片段。

### 9.2.2 最终效果
​        本节结束后，访问：

```Plain

```

​        进入任意会话后，可以完成下面的操作：

```Plain

```

​        后端新增接口：

```Plain

```

​        前文已经有独立文件上传。本节让文件真正进入会话上下文。

### 9.2.3 本节要解决的问题
​        前文完成了文件上传、元数据保存和下载。
​        但是前文有一个明显边界：文件是独立存在的，页面只知道“刚刚上传成功了某个文件”，不知道这个文件属于哪个会话。
​        这会带来几个问题：

```Plain
刷新页面后，当前会话看不到之前上传的文件
切换会话后，不知道哪些文件属于哪个会话
后续发送消息时，很难把附件和任务上下文放在一起
文件预览没有统一入口
```

​        所以本节要给文件增加会话归属。
​        文件和会话不是一对一关系。一个会话可以有多个文件，后续一个文件也可能被多个任务引用。因此本节使用关系表：

```Plain
sessions
  |
  +-- session_files
        |
        v
      files
```

### 9.2.4 本节技术方案
​        本节采用“文件表 + 会话文件关系表”的方案。
​        可选方案有三种：
​        一种做法是在 `files` 表里直接增加 `session_id`，这样实现最短，但会把文件元数据和归属关系揉在一起。另一种做法是在消息表里直接保存附件信息，适合很轻的聊天 Demo，却不利于后续独立预览、权限控制和多次引用。课程在这里选择新增 `session_files` 关系表，让文件本身和文件归属各自保持清楚的职责。
​        本节选择第三种。
​        原因是：
​        `files` 表继续只描述文件是什么，包括原始文件名、存储文件名、类型、大小和存储路径；`session_files` 表只描述这个文件属于哪个会话，不重复保存文件内容，也不复制元数据。这样拆开后，文件下载、预览和未来权限控制仍然围绕 `file_id` 展开，而会话文件列表只需要围绕 `session_id` 查询关系表。
​        本节请求链路如下：

```Plain
浏览器选择文件
  |
  v
POST /api/sessions/{session_id}/files
  |
  v
FileService
  |
  +-- 检查会话是否存在
  +-- 保存文件内容
  +-- 写入 files 表
  +-- 写入 session_files 表
  +-- 更新会话 updated_at
  |
  v
GET /api/sessions/{session_id}/files
  |
  v
前端展示会话文件列表
```

​        预览链路如下：

```Plain
用户选择文件
  |
  v
GET /api/files/{file_id}/preview
  |
  v
只读取有限大小的文本内容
  |
  v
前端预览面板展示
```

#### 9.2.6.1 增加预览大小配置
​        打开 `backend/api/app/core/config.py`，在上传配置后加入：

```Python
max_file_preview_size: int = 64 * 1024
```

​        这个配置控制预览接口最多读取多少字节。
​        为什么需要它？
​        下载接口可以把完整文件交给浏览器，但预览接口会把文件内容放进 JSON 响应里。如果一个文件有几十 MB，直接塞进 JSON 会导致接口很慢，也会让页面卡住。
​        本节先限制为 64KB。它足够预览普通文本文件的开头，也能避免误把大文件一次性读进响应。
​        同步更新 `.env.example`：

```Plain

```

​        同步更新 `docker-compose.yml` 的 API 环境变量：


#### 9.2.6.5 实现会话文件 Repository
​        打开 `backend/api/app/infrastructure/repositories/file_repository.py`，新增 `SqlAlchemySessionFileRepository`：

```Python
class SqlAlchemySessionFileRepository(SessionFileRepository):
    def __init__(self, db_session: AsyncSession) -> None:
        self.db_session = db_session
    async def add(self, session_id: UUID, file_id: UUID) -> SessionFile:
        # 关系表只保存归属关系，不冗余保存文件内容和文件元数据。
        model = SessionFileModel(session_id=session_id, file_id=file_id)
        self.db_session.add(model)
        await self.db_session.flush()
        stmt = select(SessionFileModel).where(SessionFileModel.id == model.id)
        result = await self.db_session.execute(stmt)
        created = result.scalar_one()
        return created.to_entity()
    async def list_by_session(self, session_id: UUID) -> list[SessionFile]:
        stmt = (
            select(SessionFileModel)
            .where(SessionFileModel.session_id == session_id)
            .order_by(SessionFileModel.created_at.desc())
        )
        result = await self.db_session.execute(stmt)
        return [model.to_entity() for model in result.scalars()]
```

​        这段代码的业务流程：

```Plain
写入 session_files
  |
  v
重新查询这条关系
  |
  v
返回带 file 元数据的 SessionFile
```

​        这里写完后重新查询一次，是为了稳定拿到 `relationship` 中的文件元数据。异步数据库会话中，不建议依赖隐式加载关系数据。

#### 9.2.6.7 扩展文件应用服务
​        打开 `backend/api/app/application/file_service.py`，新增三个能力：
​        `save_session_upload()` 负责把上传文件保存下来，并在同一个业务动作里建立会话归属；`list_session_files()` 负责读取某个会话下已经绑定的文件；`preview_file()` 则负责在下载之外提供一个轻量文本预览入口。三个方法放在同一个应用服务里，是因为它们共同维护文件资源和会话上下文之间的边界。
​        关键代码如下：

```Python
async def save_session_upload(
    self,
    session_id: UUID,
    original_name: str,
    content_type: str | None,
    content: bytes,
) -> SessionFile:
    session = await self.uow.sessions.get(session_id)
    if session is None:
        raise AppException(
            message="session not found",
            code=404,
            status_code=404,
        )
    clean_name = self._clean_filename(original_name)
    stored_name, storage_path = self._write_upload_file(
        clean_name=clean_name,
        content=content,
    )
    try:
        file_object = await self.uow.files.add(
            original_name=clean_name,
            stored_name=stored_name,
            content_type=content_type or "application/octet-stream",
            size=len(content),
            storage_path=str(storage_path),
        )
        session_file = await self.uow.session_files.add(
            session_id=session_id,
            file_id=file_object.id,
        )
        await self.uow.sessions.touch(session_id)
        await self.uow.commit()
    except Exception:
        # 会话归属写入失败时也要清理文件，避免页面永远找不到这份上传内容。
        storage_path.unlink(missing_ok=True)
        await self.uow.rollback()
        raise
    return session_file
```

​        这段代码的业务流程：

```Plain
检查会话
  |
  v
写入磁盘
  |
  v
写入 files
  |
  v
写入 session_files
  |
  v
更新会话 updated_at
  |
  v
commit
```

​        为什么先检查会话？
​        如果会话不存在，就不应该保存文件内容。否则磁盘里会留下无法从页面访问的文件。
​        为什么异常时要删除文件？
​        文件写磁盘和数据库事务不是同一个系统。数据库可以回滚，但磁盘写入不会自动回滚。所以在数据库写入失败时，要手动清理文件。
​        预览代码如下：

```Python
async def preview_file(self, file_id: UUID) -> tuple[FileObject, str, bool]:
    file_object, path = await self.get_download_path(file_id)
    if not self._is_text_preview_supported(file_object):
        raise AppException(
            message="file preview is not supported",
            code=415,
            status_code=415,
        )
    # 预览只读取有限字节，避免把大文件一次性塞进接口响应。
    content = path.read_bytes()
    truncated = len(content) > settings.max_file_preview_size
    preview_bytes = content[: settings.max_file_preview_size]
    return file_object, preview_bytes.decode("utf-8", errors="replace"), truncated
```

​        预览和下载不是一回事。
​        下载可以返回完整文件流。预览需要把内容变成页面可展示的文本，所以必须限制类型和大小。

### 9.2.7 关键理解
​        第一个重点：文件和会话要通过关系表关联。

```Plain
files          文件是什么
session_files  文件属于哪个会话
```

​        第二个重点：下载和预览不是同一个接口。

```Plain
download  返回完整文件
preview   返回有限文本内容
```

​        第三个重点：前端文件状态分成两类。

```Plain
files       当前会话已经保存的文件列表
attachments 本次刚上传成功、靠近输入框展示的附件
```

​        后续章节如果要把附件真正挂到某条消息上，可以继续增加消息附件表，而不需要推翻本节结构。

### 9.2.8 技术难点与亮点
​        本节的难点不在于多写一个上传接口，而在于关系和一致性。`session_files` 不能冗余保存文件元数据，否则文件名、大小和下载地址将来会出现多处来源；上传会话文件时，又要让文件记录、关系记录和会话更新时间尽量在一次业务事务中完成。如果数据库写入失败，已经落盘的文件还要清理掉，避免留下页面永远查不到的孤立文件。
​        另一个难点是预览边界。下载接口可以交付完整文件，但预览接口会把内容塞进 JSON 响应，因此必须限制文件类型和读取大小。前端也不只是多一个按钮，它要同时处理文件列表、选中文件、预览加载、预览失败和截断提示。到这一阶段，右侧工作区已经开始形成“文件 + 事件”的双栏信息结构，项目的工作台感也更明显。

### 9.2.9 面试考点
​        这一阶段适合在面试里讲系统建模能力。你可以从为什么不用在 `files` 表里直接加 `session_id` 讲起，再解释下载接口和预览接口为什么要分开。随后补充上传成功但数据库写入失败时如何清理落盘文件、预览接口为什么限制类型和大小，以及前端为什么把文件面板拆成独立组件。这个回答的重点不是“我会上传文件”，而是“我知道文件在会话系统里如何成为可管理资源”。
