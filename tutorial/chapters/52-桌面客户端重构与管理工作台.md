# 第五十二章. 桌面客户端重构与管理工作台

## 52.1 本章目标

第四十七章做出的 Electron 客户端能跑，但它只是一个"能跑"的东西：单个 `App.tsx` 里塞了 567 行代码、所有 API 调用散落在组件里、左侧图标栏七个按钮六个点了没反应、Skill 和知识库这两块新能力在桌面端完全看不到。

这一章把它重构成一个真正的管理工作台。

完成本章后，你将能够：

- 把单文件组件按"外壳 / 视图 / API 层 / 类型"拆开，并说清每一层的边界；
- 给 Electron 主进程的 IPC 通道写**可测试**的安全校验，而不是把校验逻辑埋在闭包里；
- 实现一个完整的技能管理界面：列表、搜索、草稿编辑、发布、启停、版本历史、注入命中调试；
- 实现一个完整的知识库界面：建库、摄取、文档状态、检索验证台；
- 用一套 CSS 变量支撑三主题（墨夜 / 晨光 / 高对比），新增面板零额外主题代码；
- 处理管理界面绕不开的四件事：加载态、离线态、错误反馈、乐观刷新。

## 52.2 重构前的问题

先诚实地看一眼原来的结构：

```text
src/
├── App.tsx      567 行：外壳 + 导航 + 任务视图 + 5 个子组件 + API 调用 + 主题 hook
├── types.ts     63 行
├── main.tsx
└── styles.css   855 行
```

具体问题有四个。

**问题一：没有导航。** `IconRail` 里的七个按钮是硬编码的静态数组，只有第一个 `active: true`，点击没有任何 handler。这是典型的"设计稿实现"——看起来像个应用，实际上是张图片。

**问题二：API 调用与组件耦合。** `atlasRequest` 定义在 `App.tsx` 顶部，每个需要数据的地方现拼 URL 字符串。新增一个视图就要复制一遍这套模式，路径拼错了只能在运行时发现。

**问题三：安全校验不可测试。** 主进程的 IPC handler 里有一段路径校验：

```javascript
if (!requestPath.startsWith("/api/") || requestPath.includes("..")) {
  throw new Error("invalid Atlas API path");
}
```

这是渲染进程与后端之间的**唯一安全边界**（API Key 只存在主进程），但它埋在一个 Electron 闭包里，没有任何测试覆盖。而且它有漏洞——后面会说。

**问题四：演示数据混在业务里。** `demoCheckpoints` 这个 84 行的常量放在 `App.tsx` 顶部，和真实数据处理逻辑交织在一起。

## 52.4 统一 API 层

`src/api.ts` 把每个后端接口收敛成一个有类型的函数。调用方不再拼 URL：

```typescript
export const skillsApi = {
  list: (params: { search?: string; status?: string } = {}) => {
    const query = new URLSearchParams();
    if (params.search) query.set("search", params.search);
    if (params.status) query.set("status", params.status);
    const suffix = query.toString() ? `?${query.toString()}` : "";
    return atlasRequest<SkillList>(`/api/skills${suffix}`);
  },
  publish: (skillId: string) =>
    atlasRequest<Skill>(`/api/skills/${skillId}/publish`, { method: "POST", body: {} }),
  setEnabled: (skillId: string, enabled: boolean) =>
    atlasRequest<Skill>(`/api/skills/${skillId}/enabled`, {
      method: "POST",
      body: { enabled },
    }),
  previewContext: (query: string) =>
    atlasRequest<SkillContextPreview>(
      `/api/skills/context?query=${encodeURIComponent(query)}`,
    ),
  ...
};
```

三个收益：

1. **参数编码集中处理。** `encodeURIComponent` 和 `URLSearchParams` 只在这一层出现，视图里不会漏。中文查询词直接传进去也不会出问题。
2. **类型贯通。** `atlasRequest<SkillList>` 的泛型一路传到调用点，`data.items[0].skill_key` 有补全、拼错编译期就报。
3. **改接口只改一处。** 后端路径调整时，视图代码一行不动。

底层的 `atlasRequest` 保持双通道：Electron 下走 IPC（携带 API Key），浏览器开发环境退回 `fetch`。

```typescript
export async function atlasRequest<T>(path: string, options: AtlasRequestOptions = {}): Promise<T> {
  if (window.atlasDesktop?.request) {
    return window.atlasDesktop.request<T>(path, options);
  }
  const response = await fetch(`${API_BASE}${path}`, {...});
  const payload = (await response.json()) as ApiEnvelope<T>;
  if (!response.ok || Number(payload.code ?? response.status) >= 400) {
    throw new Error(payload.message || `Atlas API returned ${response.status}`);
  }
  if (payload.data === undefined) {
    throw new Error("Atlas API returned an empty response");
  }
  return payload.data;
}
```

注意它解包了 `ApiResponse` 信封并把非 200 的 `code` 也当作错误——后端的错误可能带 HTTP 200 但 `code: 409`，只看 HTTP 状态会漏掉。

## 52.5 把安全边界做成可测试模块

这是本章技术含量最高的一处改动。

原来的校验有两个漏洞：

```javascript
if (!requestPath.startsWith("/api/") || requestPath.includes("..")) { ... }
```

**漏洞一：CRLF 注入没有防护。** `/api/skills\nX-Injected: 1` 以 `/api/` 开头、不含 `..`，完全通过校验。虽然现代 fetch 实现通常会拒绝含控制字符的 URL，但**依赖下游实现的防护不是防护**——今天 Electron 的 `net.fetch` 挡住了，明天换个 HTTP 客户端就未必。同类问题还有反斜杠（某些解析器把 `\` 当路径分隔符）和协议相对地址 `//evil.test/...`（虽然当前前缀检查恰好能挡住，但这是巧合而非设计）。

**漏洞二：无法测试。** 逻辑埋在 `ipcMain.handle` 的回调里，要测它就得启动 Electron。结果就是没人测。

重构后抽成独立 CJS 模块：

```javascript
const ALLOWED_METHODS = new Set(["GET", "POST", "PATCH", "DELETE"]);

function normalizeApiRequest(request) {
  const requestPath = String((request && request.path) || "");
  const method = String((request && request.method) || "GET").toUpperCase();

  // 1. 必须是 /api/ 前缀的绝对路径，禁止协议相对地址（//evil.test）。
  if (!requestPath.startsWith("/api/") || requestPath.startsWith("//")) {
    throw new Error("invalid Atlas API path");
  }
  // 2. 禁止路径穿越与反斜杠绕过。
  if (requestPath.includes("..") || requestPath.includes("\\")) {
    throw new Error("invalid Atlas API path");
  }
  // 3. 禁止控制字符（CR/LF 注入）。
  if (/[\u0000-\u001f\u007f]/.test(requestPath)) {
    throw new Error("invalid Atlas API path");
  }
  // 4. 方法白名单。
  if (!ALLOWED_METHODS.has(method)) {
    throw new Error("unsupported Atlas API method");
  }

  return { path: requestPath, method, body: request ? request.body : undefined };
}
```

主进程变成三行：

```javascript
ipcMain.handle("atlas:api-request", async (_event, request) => {
  const { path: requestPath, method, body } = normalizeApiRequest(request);
  const headers = { Accept: "application/json" };
  if (API_KEY) headers["X-Atlas-API-Key"] = API_KEY;
  ...
});
```

测试直接 `createRequire` 加载 CJS 模块，不需要 Electron：

```javascript
const require = createRequire(import.meta.url);
const { normalizeApiRequest } = require("../electron/request-guard.cjs");

test("rejects paths that escape the API prefix", () => {
  const hostile = [
    "/etc/passwd",
    "api/skills",
    "//evil.test/api/steal",
    "/api/../../secret",
    "/api/skills\\..\\..",
    "/api/skills\nX-Injected: 1",
    "https://evil.test/api/skills",
  ];
  for (const path of hostile) {
    assert.throws(() => normalizeApiRequest({ path }), /invalid Atlas API path/, path);
  }
});
```

这条经验可以推广：**任何"安全校验"逻辑，如果没法在单元测试里直接调用，就等于没有校验。** 遇到这种情况，把它从框架回调里抽出来。

## 52.6 技能管理界面

`SkillsView` 是本章最复杂的视图，它要把上一章的整套生命周期做成可操作的界面。布局是经典的"列表 + 详情"两栏：

```tsx
<div className="panel-body">
  <div className="entity-list" role="list" aria-label="技能列表">...</div>
  <div className="entity-detail" aria-label="技能详情">...</div>
</div>
```

**状态可视化。** 列表项同时显示三个维度，因为上一章讲过 `status` 和 `enabled` 是正交的：

```tsx
<span className="entity-meta">
  <span className={`status-chip ${skill.status}`}>{STATUS_LABELS[skill.status]}</span>
  {skill.enabled ? <span className="status-chip enabled">已启用</span> : null}
  <span className="risk-chip">{RISK_LABELS[skill.risk_level]}</span>
</span>
```

**按状态渲染动作。** 界面不该展示会失败的按钮。草稿显示"编辑 / 发布"，已发布显示"启用/停用 / 新版本 / 废弃"：

```tsx
{selected.status === "draft" ? (
  <>
    <button onClick={...}>{editForm ? "取消编辑" : "编辑草稿"}</button>
    <button className="primary-button" onClick={() => void run(() => skillsApi.publish(selected.id), "技能已发布，内容从此冻结。")}>
      发布
    </button>
  </>
) : null}
{selected.status === "published" ? (
  <>
    <button onClick={...}>{selected.enabled ? "停用" : "启用"}</button>
    <button onClick={...}>新版本</button>
    <button className="outline-button danger" onClick={...}>废弃</button>
  </>
) : null}
```

删除按钮的显示条件直接对应后端约束（已启用的已发布技能不能删）：

```tsx
{!(selected.status === "published" && selected.enabled) ? (
  <button className="outline-button danger" onClick={...}>删除</button>
) : null}
```

**统一的动作包装。** 每个操作都要处理"成功提示 + 失败提示 + 刷新列表"，重复三十遍不现实。抽一个 `run`：

```tsx
async function run<T>(action: () => Promise<T>, successMessage: string): Promise<T | null> {
  try {
    const result = await action();
    report(successMessage);
    await refresh();
    return result;
  } catch (error) {
    report(error instanceof Error ? error.message : "操作失败", "danger");
    return null;
  }
}
```

后端的错误消息直接展示给用户。这看起来"不够友好"，但对开发者工具类应用是对的——`only draft skills can be edited; create a new version instead` 比"操作失败，请重试"有用一百倍。

**版本历史。** 同一个 `skill_key` 的所有版本列在详情下方，绿色对勾标出启用中的版本。上一章提到"发布新版本不会自动停用旧版本"，这个视图就是让那种状态一眼可见的地方：

```tsx
{versions.map((version) => (
  <li key={version.id}>
    <button className={version.id === selected.id ? "selected" : ""} onClick={() => setSelectedId(version.id)}>
      <code>{version.version}</code>
      <span className={`status-chip ${version.status}`}>{STATUS_LABELS[version.status]}</span>
      {version.enabled ? <CheckCircle size={14} weight="fill" className="ok" /> : null}
      <span className="version-time">{formatTimestamp(version.created_at)}</span>
    </button>
  </li>
))}
```

**注入命中调试。** 这是整个面板最实用的功能，直接消费上一章的 `/api/skills/context`：

```tsx
<div className="context-preview-block">
  <h3><Crosshair size={16} /> 注入命中调试</h3>
  <p className="panel-subtitle">输入一个任务描述，预览哪些已启用技能会注入 Agent 上下文。</p>
  ...
  {contextPreview.items.map((item) => (
    <div key={item.id} className="hit-card">
      <strong>{item.name}</strong>
      <code>{item.skill_key}@{item.version}</code>
      <span>相关度 {item.relevance_score.toFixed(2)}</span>
      {item.matched_terms.length ? (
        <span className="matched">命中：{item.matched_terms.slice(0, 5).join("、")}</span>
      ) : null}
    </div>
  ))}
</div>
```

调技能的相关度阈值时，不用跑真实任务，输入一句话就能看到命中了什么、因为哪些词命中。

## 52.7 知识库界面

`KnowledgeView` 的结构类似，但有三个 RAG 特有的关注点。

**摄取是长操作，需要明确反馈。** 摄取要切分、调 embedding 服务、写向量，可能几秒钟。按钮要禁用并改文案，完成后按状态给不同提示：

```tsx
const document = await ragApi.ingestDocument(selected.id, {...});
if (document.status === "ready") {
  report(`文档已摄取：切分为 ${document.chunk_count} 个 chunk 并写入向量索引。`);
} else {
  report(`摄取失败：${document.error || "未知原因"}`, "danger");
}
```

注意这里**没有 try/catch 里判断成功**——上一章说过，摄取失败返回的是 `status=failed` 的正常响应，不是异常。界面要按业务状态分支，而不是按 HTTP 异常分支。

**文档状态与错误必须可见。** 摄取失败的文档在列表里显示红色状态和具体原因，旁边就是"重建索引"按钮：

```tsx
{document.status === "failed" && document.error ? (
  <p className="error-text">{document.error}</p>
) : null}
...
<button className="outline-button" onClick={() => void reingestDocument(document)}>重建索引</button>
```

上一章设计的 `error` 字段落库，价值就体现在这里——运维不用翻服务器日志。

**检索验证台。** 建完库、灌完文档，第一件事是验证检索效果。面板内置查询框，结果展示三个分数：

```tsx
<div className="hit-card-head">
  <strong>{chunk.citation}</strong>
  <span>
    综合 {chunk.final_score.toFixed(2)} · 向量 {chunk.vector_score.toFixed(2)} · 词法 {chunk.lexical_score.toFixed(2)}
  </span>
</div>
<p>{chunk.content}</p>
```

三个分数分开显示，是为了调参时能判断问题出在哪：向量分低说明 embedding 模型不匹配领域，词法分低说明查询词与文档用词不一致，综合分都不错却排序奇怪说明权重要调。头部还显示了后端类型和候选数：

```tsx
<span>后端 {queryResult.backend}</span>
<span>候选 {queryResult.candidate_count}</span>
<span>命中 {queryResult.chunks.length}</span>
```

`候选 24 / 命中 0` 这种组合一眼就能看出是相关度阈值卡太高了。

## 52.8 管理界面绕不开的四件事

这两个视图都遵循同一套模式，值得单独总结。

**加载态。** 用一个 `loading` 布尔控制刷新图标的旋转，而不是整页 spinner——整页 spinner 会让已有内容闪烁：

```tsx
<ArrowClockwise size={18} className={loading ? "spin" : undefined} />
```

**离线态。** 桌面客户端经常在后端没起来的时候被打开。捕获失败后显示明确提示，而不是空白页：

```tsx
{offline ? <InlineNotice notice="未连接控制平面：请启动后端后重试。" tone="danger" /> : null}
```

**空状态要给下一步。** 不是"暂无数据"，而是告诉用户该做什么：

```tsx
<p className="empty-hint">还没有知识库。创建一个，把团队文档变成 Agent 可检索的证据。</p>
```

**刷新后保持选中。** 操作完成后列表会重新拉取，如果简单地 `setSelectedId(items[0].id)`，用户的选中项就跳走了。正确做法是保留有效的旧选中：

```tsx
setSelectedId((current) => {
  if (current && data.items.some((skill) => skill.id === current)) return current;
  return data.items[0]?.id ?? null;
});
```

这个细节小，但少了它，每次点"启用"焦点都会跳到列表第一项，操作第五条技能会非常痛苦。

## 52.9 三主题与样式扩展

第四十七章建立的 CSS 变量体系在这里体现了价值。新增的管理面板样式全部引用变量，没有一个硬编码颜色：

```css
.entity-item {
  border: 1px solid var(--line);
  background: var(--surface);
}
.entity-item.selected {
  border-color: var(--accent);
  background: var(--surface-raised);
}
.status-chip.published,
.status-chip.ready,
.status-chip.enabled {
  border-color: var(--success);
  color: var(--success);
  background: var(--success-soft);
}
```

三个主题（墨夜 / 晨光 / 高对比）自动生效，**新增面板没有写一行主题专属代码**。唯一的例外是高对比主题下主按钮的文字色——它的 `--accent` 是亮黄色，白字读不了：

```css
.primary-button {
  background: var(--accent);
  color: #ffffff;
}
:root[data-theme="contrast"] .primary-button {
  color: #000000;
}
```

响应式也顺手做了。窄窗口下两栏塌成一栏：

```css
@media (max-width: 1080px) {
  .panel-body {
    grid-template-columns: 1fr;
  }
}
```

`ThemeSelect` 抽成共享组件，三个视图的头部都用它，主题切换在任何页面都能操作。

- 技能：对已发布技能点编辑，应看到后端返回的 409 原文；
- 技能：注入命中调试能显示相关度与命中词；
- 知识库：建库 → 摄取 → 文档列表显示 ready 与 chunk 数 → 检索返回带引用的片段；
- 知识库：摄取一份重复内容，应看到 409 提示；
- 窄窗口下两栏塌成一栏。

类型检查是构建的一部分（`build` 脚本里 `tsc --noEmit` 在 `vite build` 之前），所以 `npm run build` 通过就意味着没有类型错误。

## 52.11 常见坑

**坑一：把 API Key 放进渲染进程。** 渲染进程加载的是网页内容，任何 XSS 或恶意依赖都能读到它。密钥只应该存在主进程，渲染进程通过 IPC 发请求。这也是 `request-guard` 存在的理由。

**坑二：`contextIsolation` 关掉图省事。** 项目保持 `contextIsolation: true` + `nodeIntegration: false` + `sandbox: true`。preload 只暴露一个 `request` 方法，且用 `Object.freeze` 冻结。

**坑三：在 `useEffect` 里直接写 async 函数。** `useEffect(async () => ...)` 返回的是 Promise，不是清理函数。项目里统一用 `void refresh()` 或内部定义 async 函数。

**坑四：刷新列表时丢失选中项。** 见 52.8。

**坑五：把演示数据当兜底逻辑散布各处。** `demoCheckpoints` 现在只存在于 `TasksView.tsx` 内部，是明确的离线兜底，不会泄漏到其他视图。新的两个视图没有演示数据——管理界面显示假数据会误导操作。

## 52.12 本章小结

这一章做的事情用一句话概括：**把一个看起来像应用的界面，变成一个能用来干活的工作台。**

三条经验值得带走：

1. **拆分的标准是职责，不是行数。** `App.tsx` 从 567 行降到 107 行不是目的，"外壳只管路由、视图只管一块业务、API 层只管协议"才是。
2. **安全逻辑必须可测试。** 埋在框架回调里的校验等于没有校验。抽成纯函数模块之后，我们不但能测，还顺手补上了 CRLF 注入这个原本存在的漏洞。
3. **管理界面的质量在细节里。** 加载态、离线态、错误原文、选中保持、空状态引导——这几件事做到位，工具才从"能看"变成"能用"。

至此，AtlasAgent 的三个客户端与后端的四类注入物（Tool / Memory / RAG / Skill）全部打通。Web 端负责完整的会话工作流，桌面端负责长时间驻留的观察与治理，TUI 负责 SSH 场景——它们共用同一套 FastAPI 控制平面，也共用同一条证据链。
