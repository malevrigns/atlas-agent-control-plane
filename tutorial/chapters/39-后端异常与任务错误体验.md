## 39.3 本章要解决的问题

​        第 3 章已经做过基础异常处理：

```Plain
AppException -> 统一 JSON 响应
HTTPException -> 统一 JSON 响应
RequestValidationError -> 统一 JSON 响应
Exception -> 500 响应
```

​        这能保证接口不会直接返回 FastAPI 默认错误页面。

​        但是成熟 Agent 产品里，错误不只是“接口失败”。

​        真实任务执行过程中，可能出现：

```Plain
LLM API Key 未配置
搜索页面 SSL 失败
Sandbox 502
浏览器截图超时
MCP Server 连接失败
A2A Agent 返回错误
上传文件太大或编码不支持
```

​        如果前端只显示：

```Plain
任务执行失败
sandbox browser request failed: timed out
```

​        用户不知道：

​        具体来说，第一，是哪个环节坏了？；第二，能不能重试？；第三，应该检查配置、网络，还是重新上传文件？；第四，开发者应该拿什么 ID 去查日志？。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        所以本章补的是“错误治理”：

```Plain
错误分类
  |
  v
结构化 API 错误
  |
  v
结构化 task_error 事件
  |
  v
前端错误卡片
```

## 39.4 本章技术方案

​        本章保留现有响应外壳：

```Plain
code
message
data
```

​        只新增一个可选字段：

```Plain
error
```

​        这样旧代码不会被破坏，新前端可以读取更详细的错误信息。

​        错误结构包含：

```Plain
type         错误类型，例如 timeout、not_found、dependency_error
source       错误来源，例如 api、agent、tool、sandbox、mcp、a2a
user_message 给用户看的错误说明
suggestion   下一步建议
request_id   HTTP 请求追踪 ID
details      给开发者排查的结构化细节
```

​        Agent 任务错误会复用同样的字段，但放进事件：

```Plain
SessionEventType.task_error
```

​        这样对话流、步骤卡片、右侧详情抽屉都能使用同一套错误信息。

​        本章暂时不做这些内容：

​        换句话说，第一，不接入 Sentry、OpenTelemetry 或 ELK；第二，不做错误告警；第三，不做用户权限和审计；第四，不做自动重试策略重构。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        这些属于生产运维体系，第 42 章最终验收会说明生产差异。

## 39.6 实施步骤
### 39.6.1 扩展 AppException 和错误分类

​        打开 `api/app/core/exceptions.py`。

​        本章新增 `ErrorType` 和 `ErrorSource`：

```Python
class ErrorType(StrEnum):
    validation = "validation_error"
    business = "business_error"
    not_found = "not_found"
    timeout = "timeout"
    dependency = "dependency_error"
    tool = "tool_error"
    internal = "internal_error"

class ErrorSource(StrEnum):
    api = "api"
    agent = "agent"
    dependency = "dependency"
    tool = "tool"
    llm = "llm"
    sandbox = "sandbox"
    mcp = "mcp"
    a2a = "a2a"
```

#### 39.6.1.1 字段含义

​        从实现顺序看，第一，`ErrorType` 表示错误是什么类型；第二，`ErrorSource` 表示错误来自哪个系统边界。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        例如：

```Plain
浏览器截图超时 -> type=timeout, source=dependency
会话不存在     -> type=not_found, source=api
MCP 连接失败   -> type=dependency_error, source=dependency
```

​        继续扩展 `AppException`：

```Python
class AppException(Exception):
    def __init__(
        self,
        message: str,
        code: int = 400,
        status_code: int = 400,
        *,
        error_type: str | ErrorType | None = None,
        source: str | ErrorSource = ErrorSource.api,
        suggestion: str | None = None,
        details: dict | None = None,
    ) -> None:
        self.message = message
        self.code = code
        self.status_code = status_code
        self.error_type = str(error_type or self._infer_error_type(status_code))
        self.source = str(source)
        self.suggestion = suggestion
        self.details = details or {}
        super().__init__(message)
```

#### 39.6.1.2 这段代码的业务流程

​        以前抛业务异常只需要：

```Python
raise AppException(message="session not found", code=404, status_code=404)
```

​        现在仍然可以这样写。

​        如果不传 `error_type`，程序会根据 HTTP 状态码自动推断：

```Plain
404 -> not_found
422 -> validation_error
500 -> internal_error
其他 4xx -> business_error
```

​        如果某个地方需要更精确，也可以手动写：

```Python
raise AppException(
    message="MCP server connection failed",
    code=502,
    status_code=502,
    error_type=ErrorType.dependency,
    source=ErrorSource.mcp,
    suggestion="请检查 MCP Server 地址和网络连接。",
)
```

#### 39.6.1.3 为什么这样设计

​        课程前面已经有很多 `AppException`。

​        如果本章强制所有地方都改，会带来很大改动，也容易引入新问题。所以这里保持向后兼容：

```Plain
旧写法仍然能用
需要更精确时再补字段
```

### 39.6.2 新增错误分类函数

​        继续在 `api/app/core/exceptions.py` 中新增：

```Python
def classify_exception(error: Exception) -> dict:
    """把 Python 异常转换成前端和日志都能理解的错误摘要。"""

    if isinstance(error, AppException):
        return {
            "error_type": error.error_type,
            "source": error.source,
            "message": error.message,
            "user_message": error.message,
            "suggestion": error.suggestion or build_error_suggestion(error.error_type),
            "retryable": error.status_code >= 500 or error.error_type == ErrorType.timeout,
            "details": error.details,
        }

    error_name = error.__class__.__name__
    error_text = str(error) or error_name
    lowered = error_text.lower()
    if isinstance(error, (TimeoutError, SocketTimeout)) or "timeout" in lowered:
        error_type = ErrorType.timeout
        source = ErrorSource.dependency
        retryable = True
    elif any(keyword in lowered for keyword in ["connection", "connect", "502", "ssl"]):
        error_type = ErrorType.dependency
        source = ErrorSource.dependency
        retryable = True
    elif isinstance(error, ValueError):
        error_type = ErrorType.validation
        source = ErrorSource.api
        retryable = False
    else:
        error_type = ErrorType.internal
        source = ErrorSource.agent
        retryable = False
```

#### 39.6.2.1 这段代码的业务流程

​        Agent 工具调用时，经常拿到的是普通异常：

```Plain
TimeoutError
RuntimeError
ValueError
ConnectionError
```

​        它们没有业务字段。

​        `classify_exception()` 负责把普通异常变成稳定结构：

```Plain
TimeoutError -> timeout + dependency + 可重试
连接失败     -> dependency_error + dependency + 可重试
ValueError   -> validation_error + api + 不建议盲目重试
其他异常     -> internal_error + agent + 需要查日志
```

#### 39.6.2.2 为什么这样设计

​        错误分类不是为了隐藏真实错误。

​        它是为了给不同使用者看不同层次的信息：

```Plain
用户：外部服务响应超时，本轮任务没有完成。
页面：可以稍后重试，或检查 Sandbox、浏览器、搜索服务和网络连接。
开发者：details.exception = TimeoutError
日志：request_id / session_id / task_id
```

### 39.6.4 升级异常 handler

​        打开 `api/app/core/handlers.py`。

​        核心函数变成：

```Python
def build_error_response(
    *,
    code: int,
    message: str,
    status_code: int,
    request: Request,
    error_type: str,
    source: str,
    suggestion: str | None = None,
    details: dict | None = None,
) -> JSONResponse:
    payload = ApiResponse[None](
        code=code,
        message=message,
        data=None,
        error=ApiError(

            source=source,
```

#### 39.6.4.1 这段代码的业务流程


### 39.6.5 生成结构化 task_error

​        继续在 `api/app/core/exceptions.py` 中新增：

```Python
def build_task_error_payload(
    error: Exception,
    *,
    session_id: UUID,
    plan_id: str | None,
    task_id: str | None = None,
    step: dict | None = None,
    step_index: int | None = None,

    payload = {
        "kind": "task_error",
        "session_id": str(session_id),
        "task_id": task_id,
        "plan_id": plan_id,
        "message": summary["message"],
        "user_message": summary["user_message"],
        "suggestion": summary["suggestion"],
        "error_type": summary["error_type"],
        "source": summary["source"],
        "retryable": summary["retryable"],
        "details": summary["details"],
```

#### 39.6.5.1 这段代码的业务流程


​        而是统一调用：

```Python

```

```Plain

payload.error_type
```

​        `message` 是兼容字段。

​        旧前端、日志和已有事件读取逻辑可能还依赖它。

​        新前端优先展示：

## 39.7 关键理解

​        本章最重要的是理解错误治理的三个层次：

```Plain
接口层错误：请求参数错、资源不存在、权限不足
任务层错误：Planner、ReAct、Tool、Sandbox、LLM 执行失败
产品层错误：用户看到什么、能不能重试、应该怎么排查
```

​        不要只做第一层。

​        Agent 产品真正麻烦的是第二层和第三层。

​        第二个重点是：

```Plain
不要把内部异常直接丢给用户
```

​        用户不需要知道 Python 栈、httpx 内部错误或某个类名。

​        用户需要知道：

```Plain
发生了什么
可能是什么原因
下一步怎么处理
```

​        第三个重点是：

```Plain
message 保留兼容
error/task_error 提供结构化信息
```

​        这样旧代码不容易坏，新体验也能继续增强。

## 39.8 技术难点与亮点

​        技术难点：

​        放到工程语境里看，第一，API 错误和 Agent 任务错误不是同一种链路；第二，SSE 中途失败时，不能只让连接断掉，要尽量发出 `task_error`；第三，错误响应要兼容旧的 `ApiResponse`；第四，前端需要同时处理普通请求错误、文件上传错误和任务事件错误。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        项目亮点：

​        展开来看，第一，错误响应包含 `request_id`，方便日志追踪；第二，任务错误事件包含 `session_id`、`plan_id`、`step_id` 和错误分类；第三，前端失败步骤有用户可读提示和建议；第四，任务查询接口开始返回真实 HTTP 404，而不是 JSON 里写 404、HTTP 还是 200。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

## 39.9 面试考点

​        具体来说，第一，为什么统一异常处理不等于好的错误体验？；第二，为什么错误响应需要 `request_id`？；第三，API 错误和 Agent 任务错误有什么区别？；第四，为什么 SSE 执行链路里要写 `task_error` 事件？；第五，为什么不能把内部异常栈直接展示给用户？；第六，为什么保留 `message` 字段，同时新增 `error` 字段？。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。
