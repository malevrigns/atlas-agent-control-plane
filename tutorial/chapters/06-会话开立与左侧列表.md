# 第六章. 会话开立与左侧列表

## 6.1 本章目标

​        第 5 章把 `sessions` 表、Repository 和 Unit of Work 都准备好了，但从用户视角看，页面还没有发生变化。数据库能存会话，不代表用户能创建会话；后端有 Repository，也不代表前端能看到列表。本章要做的，就是把上一章的数据层接到真实产品界面上。
​        完成本章后，读者应该能设计会话创建、查询和删除 API，使用 Pydantic 定义请求与响应模型，在应用服务中组织业务逻辑，并通过 Repository 和 Unit of Work 完成数据库写入与事务提交。前端部分会开始接入真实 API，左侧栏不再只是静态导航，而是能加载会话、显示空状态和错误状态，也能创建和删除会话。更重要的是，读者要理解一次“创建会话”从前端输入、后端校验、数据库写入、事务提交到页面刷新的完整链路。

## 6.2 最终效果

​        本章结束后，左侧栏不再只是静态导航，而是真实的会话列表。读者可以在页面左侧输入标题，点击创建按钮，然后看到新会话出现在列表中，右侧也会展示当前选中会话的基础信息。

```Plain
输入任务标题 -> 创建会话 -> 左侧列表出现新会话 -> 右侧展示会话详情
```

​        后端新增接口：

```Plain
POST   /api/sessions
GET    /api/sessions
DELETE /api/sessions/{session_id}
```

​        前端访问：

```Plain
http://localhost:8088
```

​        页面会展示会话创建输入框、会话列表、会话删除按钮、API 和数据库状态，以及当前选中会话详情。这些区域不再只是 UI 占位，而是开始和数据库里的 `sessions` 表发生关系。

## 6.3 本章要解决的问题

​        第 5 章已经创建了 `sessions` 表，也准备好了 Repository 和 Unit of Work。但是现在还没有业务接口使用这张表。也就是说，数据库已经能存会话，但浏览器还不能创建会话，也不能看到会话列表。
​        本章要把数据层接到产品界面上：

```Plain
用户输入标题
  |
  v
Next.js 页面提交 POST /api/sessions
  |
  v
FastAPI 路由接收请求
  |
  v
SessionService 处理业务规则
  |
  v
Repository 写入 sessions 表
  |
  v
UnitOfWork 提交事务
  |
  v
前端重新拉取 GET /api/sessions
  |
  v
左侧列表显示新会话
```

​        这条链路很重要，因为后续聊天输入、消息事件、Agent 执行和文件列表都会沿用类似模式。读者在这一章看懂“一个会话如何从页面进入数据库，再回到页面”，后面理解消息和任务事件就会顺很多。

## 6.4 本章技术方案

​        本章采用“后端接口 + 前端页面状态”的方式实现会话列表。后端继续沿用上一章的数据层边界，只是在 API 路由和 Repository 之间加入 `SessionService`，把业务规则放到应用服务里。

```Plain
API Route
  |
  v
SessionService
  |
  v
UnitOfWork
  |
  v
SessionRepository
  |
  v
sessions 表
```

​        前端从本章开始按职责拆分文件：

```Plain
frontend/web/app/page.tsx
  |
  +-- 维护页面共享状态
  +-- 调用 API 加载数据
  +-- 组合侧边栏、状态面板和详情面板

frontend/web/app/components
  |
  +-- AppSidebar
  +-- SessionList
  +-- StatusPanel
  +-- SessionPanel
  +-- TaskFlowPreview

frontend/web/app/lib
  |
  +-- requestApi()
  +-- formatDate()
```

​        这样做的原因是，会话列表、创建表单、状态面板和右侧详情已经是不同职责。如果全部写进 `page.tsx`，短期能跑，后面加入聊天输入、消息时间线和 SSE 时会很难维护。从这一章开始，前端也要逐步从“单文件页面”走向“按组件和工具函数拆分”。
​        本章会新增会话请求和响应 Schema，新增 `SessionService`，新增会话路由，并把会话路由注册到 API Router。前端会改造首页，接入真实会话接口，同时拆分类型定义、请求工具、格式化函数和页面组件。暂时不做单个会话详情页路由，不做聊天消息表、聊天输入框、SSE 流式事件、未读数更新和批量删除。这里仍然保持克制，只把“会话列表闭环”先做扎实。

## 6.6 实施步骤
### 6.6.1 定义会话接口的请求和响应结构

​        创建 `backend/api/app/schemas/session.py`：

```Python
from datetime import datetime
from uuid import UUID

from pydantic import BaseModel, Field

class SessionCreateRequest(BaseModel):
    title: str = Field(min_length=1, max_length=200)

class SessionResponse(BaseModel):
    id: UUID
    title: str
    status: str
    unread_count: int
    created_at: datetime
    updated_at: datetime

class SessionListResponse(BaseModel):
    items: list[SessionResponse]
```

#### 6.6.1.1 这段代码的业务流程

​        前端创建会话时，会向后端发送：

```JSON
{"title":"帮我整理一份调研计划"}
```

​        这个 JSON 会先进入 `SessionCreateRequest`。

​        后端写入数据库后，会把数据库里的会话转换成 `SessionResponse` 返回给前端。

​        列表接口返回多条会话，所以用 `SessionListResponse` 包一层 `items`：

```JSON
{
  "items": [
    {
      "id": "...",
      "title": "...",
      "status": "idle",
      "unread_count": 0,
      "created_at": "...",
      "updated_at": "..."
    }
  ]
}
```

#### 6.6.1.2 关键代码逐段解释

​        `SessionCreateRequest` 只允许前端传 `title`：

```Python
title: str = Field(min_length=1, max_length=200)
```

​        `min_length=1` 防止空字符串。

​        `max_length=200` 和第 5 章数据库字段 `String(200)` 保持一致。

​        `SessionResponse` 是给前端看的会话结构。它没有返回 `deleted_at`，因为已经删除的会话不会出现在列表里，前端也不需要知道软删除时间。

​        `SessionListResponse` 使用 `items`，而不是直接返回数组，是为了后续扩展分页时更稳定。后面可以变成：

```JSON
{"items":[],"total":0,"page":1}
```

​        前端调用方式不用大改。

#### 6.6.1.3 为什么这样设计

​        请求模型和响应模型分开，是为了避免前端传入不该传的字段。

​        比如创建会话时，前端不应该传：

```Plain
id
status
created_at
```

​        这些字段应该由后端或数据库决定。

#### 6.6.1.4 常见误区

​        不要直接把 ORM 模型作为接口响应。

​        ORM 模型服务于数据库，接口响应服务于前端。两者职责不同，混在一起后，数据库字段变化容易直接影响前端。

### 6.6.2 编写会话应用服务

​        创建 `backend/api/app/application/session_service.py`：

```Python
from uuid import UUID

from app.application.unit_of_work import UnitOfWork
from app.core.exceptions import AppException
from app.domain.sessions.entities import Session

class SessionService:
    def __init__(self, uow: UnitOfWork) -> None:
        self.uow = uow

    async def create_session(self, title: str) -> Session:
        clean_title = title.strip()
        if not clean_title:
            raise AppException(message="session title is required", code=400, status_code=400)

        session = await self.uow.sessions.add(title=clean_title)
        await self.uow.commit()
        return session

    async def list_sessions(self) -> list[Session]:
        return await self.uow.sessions.list_active()

    async def delete_session(self, session_id: UUID) -> None:
        session = await self.uow.sessions.get(session_id)
        if session is None:
            raise AppException(
                message="session not found",
                code=404,
                status_code=404,
            )

        await self.uow.sessions.soft_delete(session_id)
        await self.uow.commit()
```

#### 6.6.2.1 这段代码的业务流程

​        `SessionService` 是会话业务的入口。

​        创建会话时：

```Plain
路由收到 title
  |
  v
SessionService.create_session()
  |
  v
清理标题前后空格
  |
  v
Repository 写入数据库
  |
  v
UnitOfWork commit
  |
  v
返回 Session 实体
```

​        删除会话时：

```Plain
路由收到 session_id
  |
  v
先查询会话是否存在
  |
  +-- 不存在 -> 抛出 404
  |
  +-- 存在 -> soft_delete
          |
          v
        commit
```

#### 6.6.2.2 关键代码逐段解释

​        `title.strip()` 是业务规则：

```Python
clean_title = title.strip()
```

​        即使前端传来的是：

```Plain
"   "
```

​        清理后也会变成空字符串。这个时候不能创建会话。

​        `AppException` 会被第 3 章统一异常处理捕获，返回统一响应格式：

```Python
raise AppException(message="session title is required", code=400, status_code=400)
```

​        `Repository` 只负责写入数据：

```Python
session = await self.uow.sessions.add(title=clean_title)
```

​        事务提交放在服务层：

```Python
await self.uow.commit()
```

​        这样后续如果一个业务操作要同时写入会话、消息、事件，就可以在同一个 Unit of Work 中统一提交。

#### 6.6.2.3 为什么这样设计

​        业务规则不放在路由里，是为了让路由保持薄。

​        路由负责 HTTP 输入输出，服务负责业务流程，Repository 负责数据库访问。

​        这会让后续功能更容易维护：

```Plain
API 路由变化 -> 少影响业务逻辑
数据库查询变化 -> 少影响接口定义
业务规则变化 -> 集中改 Service
```

#### 6.6.2.4 常见误区

​        不要在 Repository 的 `add()` 里直接 `commit()`。

​        Repository 不知道一次业务操作是不是只写一张表。提交事务应该由 Unit of Work 或应用服务决定。

### 6.6.3 编写会话 API 路由

​        创建 `backend/api/app/api/routes/sessions.py`：

```Python
from uuid import UUID

from fastapi import APIRouter, Depends, Response
from sqlalchemy.ext.asyncio import AsyncSession

from app.application.session_service import SessionService
from app.application.unit_of_work import UnitOfWork
from app.domain.sessions.entities import Session
from app.infrastructure.database.session import get_db_session
from app.schemas.common import ApiResponse
from app.schemas.session import (
    SessionCreateRequest,
    SessionListResponse,
    SessionResponse,
)

router = APIRouter(prefix="/sessions", tags=["sessions"])

def build_session_service(
    db_session: AsyncSession = Depends(get_db_session),
) -> SessionService:
    return SessionService(UnitOfWork(db_session))

def to_session_response(session: Session) -> SessionResponse:
    return SessionResponse(
        id=session.id,
        title=session.title,
        status=session.status.value,
        unread_count=session.unread_count,
        created_at=session.created_at,
        updated_at=session.updated_at,
    )

@router.post("", response_model=ApiResponse[SessionResponse])
async def create_session(
    payload: SessionCreateRequest,
    service: SessionService = Depends(build_session_service),
) -> ApiResponse[SessionResponse]:
    session = await service.create_session(payload.title)
    return ApiResponse(data=to_session_response(session))

@router.get("", response_model=ApiResponse[SessionListResponse])
async def list_sessions(
    service: SessionService = Depends(build_session_service),
) -> ApiResponse[SessionListResponse]:
    sessions = await service.list_sessions()
    return ApiResponse(
        data=SessionListResponse(
            items=[to_session_response(session) for session in sessions],
        )
    )

@router.delete("/{session_id}", status_code=204)
async def delete_session(
    session_id: UUID,
    service: SessionService = Depends(build_session_service),
) -> Response:
    await service.delete_session(session_id)
    return Response(status_code=204)
```

#### 6.6.3.1 这段代码的业务流程

​        这份路由文件把 HTTP 请求转成业务调用。

​        创建会话：

```Plain
POST /api/sessions
  |
  v
SessionCreateRequest 校验请求体
  |
  v
SessionService.create_session()
  |
  v
SessionResponse 返回前端
```

​        查询列表：

```Plain
GET /api/sessions
  |
  v
SessionService.list_sessions()
  |
  v
SessionListResponse(items=[...])
```

​        删除会话：

```Plain
DELETE /api/sessions/{session_id}
  |
  v
SessionService.delete_session()
  |
  v
204 No Content
```

#### 6.6.3.2 关键代码逐段解释

​        `build_session_service()` 是依赖组装函数：

```Python
db_session: AsyncSession = Depends(get_db_session)
return SessionService(UnitOfWork(db_session))
```

​        FastAPI 会先创建数据库会话，再用它创建 Unit of Work，最后创建 SessionService。

​        路由函数只依赖 `SessionService`，不直接关心数据库连接如何创建。

​        `to_session_response()` 是实体到响应模型的转换：

```Python
status=session.status.value
```

​        领域实体里的 `status` 是枚举，接口返回给前端时转成字符串。

​        删除接口返回 `204`：

```Python
@router.delete("/{session_id}", status_code=204)
```

​        `204 No Content` 表示删除成功但没有响应体。前端收到成功状态后重新拉取列表即可。

#### 6.6.3.3 为什么这样设计

​        路由层不直接操作 Repository，是为了让 HTTP 逻辑和业务逻辑分开。

​        如果后续会话创建时还要自动写入第一条系统消息，只需要改 `SessionService.create_session()`，路由层可以不变。

#### 6.6.3.4 常见误区

​        不要在删除接口里返回已经删除的会话详情。

​        本章使用软删除，删除后前端真正关心的是列表刷新。返回 `204` 更简单，也更符合“删除成功但无内容”的语义。

```Plain
ApiResponse<SessionListData>
```

```Plain
SessionListData.items
```

​        然后把 `SessionItem[]` 交给会话列表组件展示。

### 6.6.6 封装 API 请求和格式化函数

​        创建 `frontend/web/app/lib/api.ts`：

```TypeScript
import type { ApiResponse } from "../types";

export async function requestApi<T>(
  url: string,
  init?: RequestInit,
): Promise<T> {
  const response = await fetch(url, {
    ...init,
    headers: {
      "Content-Type": "application/json",
      ...init?.headers,
    },
  });

  if (response.status === 204) {
    return undefined as T;
  }

  const payload = (await response.json()) as ApiResponse<T>;
  if (!response.ok || payload.code >= 400) {
    throw new Error(payload.message || `HTTP ${response.status}`);
  }
  if (payload.data === null) {
    throw new Error("empty response");
  }
  return payload.data;
}
```

​        创建 `frontend/web/app/lib/format.ts`：

```TypeScript
export function formatDate(value: string) {
  return new Intl.DateTimeFormat("zh-CN", {
    month: "2-digit",
    day: "2-digit",
    hour: "2-digit",
    minute: "2-digit",
  }).format(new Date(value));
}
```

#### 6.6.6.1 这段代码的业务流程

​        页面创建、查询、删除会话时都调用 `requestApi()`。

```Plain
page.tsx
  |
  +-- requestApi("/api/sessions")
  +-- requestApi("/api/sessions", { method: "POST" })
  +-- requestApi("/api/sessions/{id}", { method: "DELETE" })
```

​        组件展示时间时调用 `formatDate()`，不用在 JSX 中重复写日期格式化逻辑。

#### 6.6.6.2 关键代码逐段解释

​        删除接口成功时返回 `204`，没有 JSON 响应体：

```TypeScript
if (response.status === 204) {
  return undefined as T;
}
```

​        如果这里继续执行 `response.json()`，浏览器会因为空响应体报错。

​        业务错误统一转成异常：

```TypeScript
throw new Error(payload.message || `HTTP ${response.status}`);
```

​        这样页面只需要在 `catch` 中展示错误信息，不需要每个按钮都重复判断响应格式。

#### 6.6.6.3 为什么这样设计

​        请求工具和格式化函数不属于页面结构，也不属于某一个组件。

​        把它们放到 `lib/`，可以让页面和组件保持更干净。后续加入文件上传、流式接口或取消请求时，也可以继续在这里扩展。

```TypeScript
async function handleCreateSession(event: FormEvent<HTMLFormElement>) {
  event.preventDefault();
  const cleanTitle = title.trim();
  if (!cleanTitle) {
    setActionError("请输入会话标题");
    return;
  }

  setSubmitting(true);
  setActionError(null);
  try {
    const created = await requestApi<SessionItem>("/api/sessions", {
      method: "POST",
      body: JSON.stringify({ title: cleanTitle }),
    });
    setTitle("");
    setSelectedSessionId(created.id);
    await loadSessions();
  } catch (error) {
    setActionError(error instanceof Error ? error.message : "unknown error");
  } finally {
    setSubmitting(false);
  }
}
```

## 6.7 关键理解

​        本章最重要的是理解“创建会话”的完整链路：

```Plain
前端表单
  |
  v
POST /api/sessions
  |
  v
Pydantic 校验
  |
  v
SessionService 处理业务规则
  |
  v
Repository 写入 sessions 表
  |
  v
UnitOfWork commit
  |
  v
返回 SessionResponse
  |
  v
前端重新 GET /api/sessions
  |
  v
左侧列表更新
```

​        还有一个关键点：接口层、业务层、数据层各自负责不同事情。

```Plain
Route       负责 HTTP 输入输出
Service     负责业务流程
Repository  负责数据库读写
UoW         负责事务提交
```

​        这样做不是为了把代码拆复杂，而是为了后续功能增长时还能保持清楚。

## 6.8 技术难点与亮点

​        技术难点：

​        本章的技术难点，是把三个接口和前端操作对应起来。`POST /api/sessions` 对应创建，`GET /api/sessions` 对应加载列表，`DELETE /api/sessions/{session_id}` 对应删除。创建成功后重新拉取列表，是为了让页面以数据库最新结果为准；软删除后列表不再显示该会话，是因为 Repository 默认只查询 `deleted_at` 为空的记录。Service、Repository、Unit of Work 的职责边界，也会在这一章第一次被真实接口用起来。

​        项目亮点：

​        本章的项目亮点，是会话列表已经接入真实数据库，不再是静态假数据。前端从这一章开始有真实产品交互，后端接口仍然保持统一响应格式，删除操作使用软删除，为后续审计和恢复预留空间。前端操作后再以数据库最新结果刷新页面，也能降低本地状态和后端状态不一致的风险。

## 6.9 面试考点

​        面试里可以围绕这条链路展开：创建会话的请求从前端到数据库经历了哪些层，为什么创建成功后要重新请求列表，为什么删除接口可以返回 `204 No Content`，Service、Repository、Unit of Work 分别负责什么，前端为什么要区分 loading、ready、error 状态。能回答这些问题，说明你不是只写了一个按钮，而是理解了一次完整业务操作如何穿过前后端。
