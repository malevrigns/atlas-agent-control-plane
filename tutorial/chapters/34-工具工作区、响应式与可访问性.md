## 34.2 第一阶段：工具预览、浏览器 VNC 与文件工作区细琢

### 34.2.1 本阶段目标

​        学完本阶段后，你将能够：

​        换句话说，第一，理解右侧工具工作区在 AI Agent 产品中的作用；第二，把工具输出从“能显示”整理成“按类型可读”；第三，为工具调用增加类型标签、复制输出和结构化摘要；第四，让 Shell 输出使用等宽字体、长文本滚动和错误高亮；第五，让浏览器工具预览和 VNC 远程桌面联动；第六，统一文件预览和工具预览的视觉风格；第七，保持工具事件、文件预览、VNC 状态和对话时间线之间的职责边界。这些点放在一起看，构成了本阶段叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

#### 34.2.6.2 根据工具名和输出判断工具类型

​        继续在 `tool-preview-panel.tsx` 中新增：

```TypeScript
function getToolKind(toolName: string, output: string) {
  if (parseScreenshot(output)) {
    return "Browser Screenshot";
  }
  if (parseSearchResults(output) || toolName.startsWith("search_")) {
    return "Search";
  }
  if (parseMcpToolResult(output) || toolName.startsWith("mcp_")) {
    return "MCP";
  }
  if (parseA2aTaskResult(output) || toolName.startsWith("a2a_")) {
    return "A2A";
  }
  if (parseMultiAgentResult(output) || toolName.startsWith("multi_agent_")) {
    return "Multi-Agent";
  }
  if (toolName.startsWith("browser_")) {
    return "Browser";
  }
  if (toolName.startsWith("shell_")) {
    return "Shell";
  }
  if (toolName.startsWith("file_")) {
    return "File";
  }
  return "Tool";
}
```

##### 34.2.6.2.1 为什么同时看 output 和 toolName

​        有些工具输出是结构化 JSON。

​        例如截图：

```JSON
{"kind":"browser_screenshot","mime_type":"image/png","base64_data":"..."}
```

​        这种情况最可靠的判断方式是 `kind`。

​        但 Shell 工具目前输出的是普通文本：

```Plain
会话：...
命令：...
状态：...
退出码：...
```

​        它没有 JSON `kind`，所以要看 `toolName`：

```TypeScript
toolName.startsWith("shell_")
```

​        这种“双通道判断”可以兼容当前后端，也给未来结构化输出留空间。

##### 34.2.6.4.1 为什么 Shell 要单独处理

​        Shell 输出有两个特点。

​        第一，它需要等宽字体。

​        命令输出经常包含目录树、日志、表格、错误堆栈。如果用普通字体，很难看齐。

​        第二，它需要错误高亮。

​        课程里的 Shell 工具输出已经包含：

```Plain
退出码：0
```

​        或者：

```Plain
退出码：1
```

​        前端可以从文本里判断是否失败，然后给出绿色或红色状态。

##### 34.2.6.7.1 为什么 VNC 要放进工具工作区

​        截图回答的是：

```Plain
某一刻页面是什么样
```

​        VNC 回答的是：

```Plain
浏览器现在正在发生什么
```

​        当 Agent 执行浏览器任务时，两者应该在同一个观察区里出现。

### 34.2.7 关键理解

​        本阶段最重要的是“统一入口，不统一内容”。

​        右侧工具工作区要统一：

```Plain
标题
关闭
复制
展开
最近工具调用
基础视觉风格
```

​        但不同工具的内容不能强行统一。

```Plain
搜索结果要像搜索结果
Shell 输出要像终端
截图要像图片
多 Agent 要像协作记录
文件要像文件预览
VNC 要像远程桌面
```

​        第二个重点是不要为了前端好看就随便改后端协议。

​        本阶段先在前端兼容当前协议：

​        具体来说，第一，JSON `kind` 能解析就结构化展示；第二，没有 JSON 的 Shell 输出就按工具名展示；第三，解析不了就回退普通文本。这些点放在一起看，构成了本阶段叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        这样不会破坏已有工具。

​        第三个重点是工具工作区服务于真实对话。

​        本阶段没有新增孤立演示页。所有入口仍然来自：

```Plain
发送任务 -> 工具调用 -> 点击工具卡片 -> 右侧工作区
```

### 34.2.8 技术难点与亮点

​        技术难点：

​        换句话说，第一，工具输出格式不同，不能只靠一种组件展示；第二，Shell 输出是普通文本，需要前端识别退出码；第三，浏览器截图和 VNC 来自不同数据源，需要在同一工作区组合；第四，文件预览不是工具事件，但视觉上要和工具工作区一致；第五，复制按钮要处理浏览器权限失败。这些点放在一起看，构成了本阶段叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        项目亮点：

​        展开来看，第一，发消息必须绕路，`ui/app/components/chat-input.tsx:21-27` 是 `<form onSubmit>` 加 `:43` 的 `type="submit"`，但输入区是 `:31` 的 `<textarea>`，Enter 在里面只插换行，也没有 Cmd 或 Ctrl 加 Enter 的处理，键盘用户得先 Tab 出文本域再按 Enter；第二，`ui/app/components/conversation/step-detail-dialog.tsx:22` 的弹窗是手写的 `<div className="fixed inset-0">`，依赖里没有 Radix 也没用原生 `<dialog>`，因此没有 `role="dialog"`、没有 `aria-modal`、没有 Esc 关闭、没有焦点陷阱、关闭后不还原焦点，遮罩层也没有 onClick，打开后 Tab 会跑到弹窗背后的页面里，唯一的关闭途径是 Tab 到 `:38-45` 那个 X 按钮；第三，`ui/app/components/chat-workspace.tsx:190`、`:201`、`:211` 三个抽屉同理，无 Esc、无焦点转移，`onClose` 只挂在面板内部的按钮上；第四，`ui/app/components/vnc-panel.tsx:168` 的挂载点是一个没有 `tabIndex`、没有 `role`、没有可访问名的裸 `<div>`，而 `:106` 写着 `rfb.viewOnly = false;`，这是一个可交互的远程桌面，键盘焦点能不能进去完全依赖 noVNC 内部行为，本项目的代码没有任何保障。这些点放在一起看，构成了本阶段叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        `vnc-panel.tsx:168` 的原样是：

```TypeScript
<div className="h-full w-full" ref={screenRef} />
```

​        这一项判定为缺口，而且是本阶段最重的一条。四处断裂点各自的落点，一并记进 34.3.6.8。

### 34.3.7 关键理解

​        本阶段最重要的是理解「验收章的产出是结论，不是代码」。

​        第一个重点是结论必须可复现。

​        不要只说：

```Plain
移动端看起来还行
```

​        而是要有：

```Plain
验收项
命令
实测输出
判定
落点
```

​        第二个重点是数字要看构成，不能只看总量。

​        88 处 `aria-` 听起来是一份不错的成绩，拆开看是同一个 `aria-hidden` 重复 88 次。41 处断点听起来像响应式做透了，拆开看 40 处是桌面优先的向下折叠。46 处 `title=` 听起来是一层挺厚的兜底，拆开看只有 36 处落在 `<button>` 上，另外 7 处是渲染成可见标题的 React prop，1 处传给子组件，剩下 2 处在 `<label>` 和 `<a>` 上。

​        这条规矩最难的地方是对自己用。上面三个数字里，前两个本阶段一开始就拆了，第三个是差点漏掉的那个。

​        第三个重点是承诺和代码冲突时，改的是承诺。

​        本章第一阶段的预告写下了「键盘操作场景都能正常使用」，代码没做到，本阶段的责任是把这句话纠正掉，而不是替它圆场。把「本阶段会做 X」改写成「系统现在就做 X」，而代码不做 X，是这类文档最坏的一种失效。

​        第四个重点是纠正不能矫枉过正。

​        写成「键盘完全不可用」也是错的，65 个原生交互元素让 Tab 可达是事实。精确的缺口比笼统的否定更有价值，也更经得起读者自己去验。

### 34.3.8 技术难点与亮点

​        放到工程语境里看，第一，难点是把印象换成证据，每条结论都得有一条能跑的命令；第二，难点是区分「没做」和「做了一半」，本项目的可访问性属于「只做了一件事且做对了」；第三，难点是承认缺口而不伤及全书调性，第 32 章的三态记账提供了现成的体裁；第四，亮点是 design-tokens.ts 里那 4 个零引用字段，它们同时证明了规范写过和规范没落地；第五，亮点是把缺口压到文件和行，尤其是 `use-auto-scroll.ts:36` 这种「改错行就白改」的位置，让补齐变成一个明确的小任务，而不是一句愿望。这些点放在一起看，构成了本阶段叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

### 34.3.9 面试考点

​        换句话说，第一，`aria-hidden` 解决什么问题，为什么它多不代表可访问性好；第二，`title` 为什么是可访问名的末位兜底，纯图标按钮该用什么；第三，`aria-live` 在流式产品里的作用是什么；第四，`prefers-reduced-motion` 为什么管不到 `scrollIntoView`；第五，模态对话框除了视觉遮罩还必须具备哪些行为；第六，桌面优先加 `max-*` 和移动优先加 `min-*` 各自的代价；第七，`color-scheme: dark` 和 `prefers-color-scheme` 的区别是什么。这些点放在一起看，构成了本阶段叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。
