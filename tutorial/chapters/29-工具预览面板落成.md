# 第二十九章. 工具预览面板落成

## 29.1 本章目标
​        学完本章后，你应该能把前面几章分散出现的文件、Shell、浏览器截图和 VNC 观察能力，收敛到一个统一的右侧工具预览面板中。
​        第 23 章做了 FileTool，第 24 章做了 ShellTool，第 27 章让 BrowserTool 的截图进入事件记录，第 28 章又把 VNC 远程桌面接进工作台。能力越来越多以后，如果每种工具都单独占一个卡片，右侧工作区会很快变成接口演示合集。真正的 Agent 产品不应该让用户在多个演示卡片之间来回找结果，而应该围绕“当前任务正在使用什么工具、产生了什么文件、执行环境现在是什么状态”来组织界面。
​        本章的目标，就是新增 `ToolPreviewPanel`，把工具调用、会话文件和执行环境放进一个分栏面板。工具页签展示最近的 `tool_called` 事件和截图预览；文件页签复用会话文件面板；环境页签集中展示当前任务沙箱和 VNC 远程桌面。整理完这一章后，右侧工作台会更像一个真正的执行观察区，而不是多个临时章节组件的堆叠。

## 29.2 最终效果

## 29.3 本章要解决的问题
​        前面几章每加入一种能力，页面上就多一个展示入口。文件有文件面板，沙箱有沙箱状态，VNC 有远程桌面，浏览器截图又先放在事件记录里。这个阶段对于教学是有帮助的，因为每章都能独立验证自己的功能；但继续往后做，就会变成产品结构问题。
​        Agent 工作台的右侧区域应该承担“观察执行过程”的职责，而不是展示所有历史教学组件。用户关心的是：Agent 调用了什么工具，工具用了哪些参数，结果是否成功，有没有生成文件，浏览器有没有打开，远程桌面能不能观察。这些问题属于同一类信息，都应该进入工具预览区。
​        因此，本章要做的不是新增一个能力，而是整理已有能力的展示方式。`ToolPreviewPanel` 会把最近工具调用、文件工作区、沙箱状态和 VNC 画面放到同一个面板中。这个改动看起来偏前端，但它代表项目从“章节演示”向“产品工作台”过渡。

## 29.4 本章技术方案
​        本章采用“统一面板 + 页签”的方案，而不是继续新增右侧卡片。
​        工具调用、文件和执行环境虽然内容不同，但它们都服务于同一个目标：帮助用户理解 Agent 当前正在如何执行任务。工具页签关注最近一次 `tool_called` 事件，文件页签关注工作产物，环境页签关注 Sandbox 和 VNC。它们放在同一个 `ToolPreviewPanel` 中，既能节省右侧空间，也方便后续加入 SearchTool、MCP Tool、A2A Tool 等更多工具类型。
​        `ToolPreviewPanel` 自身不直接请求接口。它从 `ChatWorkspace` 接收 `events`、`files`、`preview`、`sandbox`、`vnc` 等状态，并通过回调触发刷新或文件预览。这样组件更接近纯展示层，数据加载仍然留在页面层和已有 hook 里。这个边界很重要，因为工具预览面板以后会继续变复杂，如果让它直接散落请求逻辑，后续维护会很难。
​        本章还会把 `EventTimeline` 中复杂的工具详情展示收回到 `ToolPreviewPanel`。事件时间线仍然保留，但它只显示事件流和工具名称摘要；详细参数、截图和最近工具调用列表交给工具预览面板处理。这样事件记录更像日志，工具预览更像观察面板，两个区域职责更加清晰。

### 29.6.4 展示最近工具调用
​        工具页签的核心是 `ToolCallView`。它先处理加载、错误和空状态，再展示最近一次工具调用详情和最近五次工具调用摘要：

```TypeScript
function ToolCallView({
  events,
  latestToolEvent,
  toolEvents,
}: {
  events: LoadState<SessionEventItem[]>;
  latestToolEvent: SessionEventItem | null;
  toolEvents: SessionEventItem[];
}) {
  if (events.type === "loading") {
    return <EmptyState icon={RefreshCcw} text="正在读取工具事件..." />;
  }

  if (events.type === "error") {
    return <p className="text-sm text-rose-600">{events.message}</p>;
  }

  if (!latestToolEvent) {
    return <EmptyState icon={Bot} text="执行计划后，工具调用会显示在这里。" />;
  }

  return (
    <div className="grid gap-4">
      <ToolCallDetail event={latestToolEvent} />
      <div>
        <h3 className="text-sm font-semibold text-slate-900">最近工具调用</h3>
        <div className="mt-2 grid gap-2">
          {toolEvents.slice(0, 5).map((event) => (
            <ToolCallSummary event={event} key={event.id} />
          ))}
        </div>
      </div>
    </div>
  );
}
```

​        这里的“最近工具调用”不是后端新接口，而是前端从已有事件列表里筛出来的。事件列表本来就会随着计划执行刷新，工具预览面板只是在 UI 上提取重点。
​        这种做法有一个直接好处：不用改事件模型，也不用新增工具查询接口，就能让用户看到工具执行的上下文。等后续工具事件结构更成熟时，面板可以继续从同一批事件里读取更丰富的字段。

### 29.6.5 渲染工具详情和截图

```TypeScript
function ToolCallDetail({ event }: { event: SessionEventItem }) {
  const toolName = getString(event.payload.tool_name);
  const output = getString(event.payload.output);
  const screenshot = parseScreenshot(output);
  const Icon = getToolIcon(toolName, screenshot);

  return (

      <div className="flex items-start gap-2">

          <div className="flex items-center justify-between gap-3">
            <h3 className="truncate text-sm font-semibold text-slate-950">
              {toolName || "tool_called"}
            </h3>
            <span className="shrink-0 text-xs text-slate-500">
              {formatDateTime(event.created_at)}
            </span>
          </div>
          <ToolArguments value={event.payload.arguments} />
          {screenshot ? (
            <ScreenshotPreview screenshot={screenshot} />
          ) : (
            <pre className="mt-3 max-h-56 overflow-auto whitespace-pre-wrap rounded-md bg-white p-3 text-xs leading-5 text-slate-700">
              {output || "<no output>"}
            </pre>
          )}
        </div>
      </div>
    </div>
  );
}
```

​        这一段把工具事件拆成三层：工具名称、调用参数、工具输出。普通工具输出继续用文本块展示；浏览器截图输出则会被 `parseScreenshot()` 识别成图片结构，再交给 `ScreenshotPreview`。
​        注意这里没有根据工具名直接判断截图，而是解析输出内容。原因是第 27 章的截图工具把结果以 JSON 字符串放进 `ToolCallResult.output`，只要它符合 `kind: browser_screenshot` 的结构，前端就能展示图片。这样即使以后截图工具改名，只要输出协议不变，预览仍然可用。

### 29.6.7 工具摘要、图标和截图解析
​        继续实现摘要和辅助函数：

```TypeScript
function ToolCallSummary({ event }: { event: SessionEventItem }) {
  const toolName = getString(event.payload.tool_name);
  const output = getString(event.payload.output);
  const screenshot = parseScreenshot(output);
  const Icon = getToolIcon(toolName, screenshot);

  return (
    <div className="flex items-center justify-between gap-3 rounded-md border border-slate-200 bg-white px-3 py-2 text-sm">
      <div className="flex min-w-0 items-center gap-2">
        <Icon className="shrink-0 text-slate-500" size={15} aria-hidden="true" />
        <span className="truncate font-medium text-slate-800">{toolName || "tool"}</span>
      </div>
      <span className="shrink-0 text-xs text-slate-500">{formatDateTime(event.created_at)}</span>
    </div>
  );
}

function getToolEvents(state: LoadState<SessionEventItem[]>): SessionEventItem[] {
  if (state.type !== "ready") {
    return [];
  }
  return [...state.data]
    .filter((event) => event.type === "tool_called")
    .sort((a, b) => b.created_at.localeCompare(a.created_at));
}

function getToolIcon(toolName: string, screenshot: ScreenshotPayload | null) {
  if (screenshot) {
    return Camera;
  }
  if (toolName.startsWith("browser_")) {
    return Globe;
  }
  if (toolName.startsWith("shell_")) {
    return Terminal;
  }
  if (toolName.startsWith("file_")) {
    return FileText;
  }
  if (toolName.includes("list")) {
    return FolderOpen;
  }
  return Hammer;
}
```

​        摘要列表只展示最近五次调用，避免面板无限拉长。完整事件仍然在事件记录里，工具预览面板只把最有用的部分提出来。
​        图标选择也放在这里处理。它不是核心业务逻辑，但对用户理解很有帮助：截图用相机图标，浏览器用地球图标，Shell 用终端图标，文件工具用文件图标。用户扫一眼就能知道 Agent 刚才在使用哪类工具。
​        继续实现截图解析和字符串读取：

```TypeScript
function parseScreenshot(value: string): ScreenshotPayload | null {
  try {
    const payload = JSON.parse(value) as Partial<ScreenshotPayload>;
    if (
      payload.kind === "browser_screenshot" &&
      typeof payload.mime_type === "string" &&
      typeof payload.base64_data === "string" &&
      typeof payload.size === "number"
    ) {
      return payload as ScreenshotPayload;
    }
  } catch {
    return null;
  }
  return null;
}

function getString(value: unknown): string {
  return typeof value === "string" ? value : "";
}
```

​        这里的 `catch` 直接返回 `null`，是因为普通工具输出本来就不是 JSON。解析失败不代表错误，只代表这次工具输出应该按文本展示。真正的错误事件仍然由后端 `task_error` 或工具调用异常来表达。

### 29.6.9 简化 EventTimeline 的工具展示
​        第 27 章曾经把工具参数、输出和截图都放进事件记录。现在这些详细内容已经进入 `ToolPreviewPanel`，事件记录就可以回到日志职责：显示事件发生了什么，以及大致是哪一个工具。

```TypeScript
import { Activity, Hammer } from "lucide-react";

import { formatDate } from "../lib/format";
import type { LoadState, SessionEventItem } from "../types";

export function EventTimeline({
  state,
}: {
  state: LoadState<SessionEventItem[]>;
}) {
  if (state.type === "loading") {
    return <div className="text-sm text-slate-500">事件加载中...</div>;
  }

  if (state.type === "error") {
    return <div className="text-sm text-rose-600">{state.message}</div>;
  }

  if (state.data.length === 0) {
    return <div className="text-sm text-slate-500">暂无事件</div>;
  }

  return (
    <div className="grid gap-2">
      {state.data.map((event) => (
        <div
          className="flex gap-2 rounded-md border border-slate-200 bg-slate-50 px-3 py-2"
          key={event.id}
        >
          <Activity className="mt-0.5 shrink-0 text-slate-500" size={15} />
          <div className="min-w-0">
            <div className="text-sm font-medium text-slate-800">
              {event.type}
            </div>
            <div className="mt-1 text-xs text-slate-500">
              {formatDate(event.created_at)}
            </div>
            <EventPayload event={event} />
          </div>
        </div>
      ))}
    </div>
  );
}
```

​        `EventPayload` 只保留工具名称摘要：

```TypeScript
function EventPayload({ event }: { event: SessionEventItem }) {
  if (event.type !== "tool_called") {
    return null;
  }

  const toolName = getString(event.payload.tool_name);

  return (
    <div className="mt-2 inline-flex items-center gap-1 rounded bg-white px-2 py-1 text-xs text-slate-600">
      <Hammer size={13} aria-hidden="true" />
      <span>工具：{toolName || "-"}</span>
    </div>
  );
}
```

​        这样调整后，事件记录不再承担图片预览和参数展示。它保持轻量，适合快速浏览执行轨迹；工具预览面板则承担更重的观察职责。

## 29.7 关键理解
​        本章最重要的是职责收敛。
​        工具调用详情不应该一直塞在事件记录里，文件工作区不应该和工具结果割裂，沙箱状态和 VNC 也不应该作为孤立卡片堆在右侧。它们都属于“观察 Agent 执行过程”的信息，所以应该进入工具预览面板。
​        第二个重点是事件和预览的关系。事件记录是日志，它适合展示时间线和状态变化；工具预览是工作区，它适合展示参数、结果、文件和画面。两者都需要，但不能混成一个超大的事件卡片。
​        第三个重点是组件边界。`ToolPreviewPanel` 不请求接口，不修改后端状态，它只组合已有状态和回调。这个设计让它可以承载更复杂的展示，同时保持可测试和可替换。

## 29.8 技术难点与亮点
​        本章的技术难点不是算法，而是前端信息架构。已有能力都能运行，但如何把它们放在同一个工作台里，并让用户快速理解它们的关系，是这一章要解决的核心问题。
​        `ToolPreviewPanel` 需要同时处理普通文本工具输出、浏览器截图、文件预览、沙箱状态和 VNC 画面。如果每一种输出都写成独立入口，页面会越来越散；如果全部塞进一个事件卡片，阅读又会很累。本章用页签分层解决这个问题。
​        这一章的亮点是，右侧工作台开始出现明确的信息分区：计划负责下一步，工具预览负责执行观察，上下文负责输入账单，事件记录负责历史轨迹。这个结构为后续 SearchTool、MCP、A2A 和多 Agent 协作继续扩展留出了稳定位置。

## 29.9 面试考点
​        面试里问到这一章，不要只说“我做了一个 tab 面板”。更好的回答是：随着工具类型增加，原来分散的面板不利于用户观察 Agent 执行过程，因此把工具调用、文件产物和执行环境统一收敛到 `ToolPreviewPanel`。
​        还可以继续解释事件记录和工具预览的区别。事件记录强调时间顺序，适合看 `step_started`、`tool_called`、`step_completed`；工具预览强调当前结果，适合看调用参数、截图、文件和环境状态。
​        如果被问到为什么 `ToolPreviewPanel` 不自己请求接口，可以说明这是组件职责边界：页面层管理数据加载，面板层管理展示组合，子组件管理具体视图。这样后续迁移到 store 或加入更多工具时，不会把网络请求散落到多个展示组件里。

## 29.11 常见问题
### 29.11.1 页面没有出现“工具预览”面板怎么办？
​        先确认 `ChatWorkspace` 已经导入并渲染 `ToolPreviewPanel`。如果源码已经更新，但页面仍然旧，通常是 UI 容器没有重新构建。
​        执行 `docker compose build ui`，再执行 `docker compose up -d --force-recreate ui nginx`。重新访问 `http://localhost:8088` 后，右侧工作台应该能看到“工具预览”。

### 29.11.2 工具页签一直显示空状态怎么办？
​        空状态说明当前事件列表里还没有 `tool_called`。只发送消息不会产生工具调用，必须先生成计划，再执行计划。执行后事件流中出现 `tool_called`，工具页签才会展示最近工具调用。
​        如果确认已经执行计划但仍然空，可以检查事件记录是否有 `tool_called`。如果事件记录也没有，问题在后端执行链路；如果事件记录有，问题在前端事件筛选或 UI 没有刷新。

### 29.11.3 截图没有渲染成图片怎么办？
​        截图预览依赖 `ToolCallResult.output` 中的 JSON 字符串，里面需要包含 `kind: browser_screenshot`、`mime_type`、`base64_data` 和 `size`。如果任一字段缺失，`parseScreenshot()` 会返回 `null`，面板就会按普通文本展示。
​        先查看事件 payload 中的 output，再确认 BrowserTool 的 `_format_screenshot()` 是否仍然输出这个结构。后端输出正确但前端没有变化时，重新构建 UI。

### 29.11.4 文件页签没有文件怎么办？
​        文件页签复用的是会话文件列表。只有上传附件、生成文件对象或通过后续工具把文件沉淀到会话中，列表才会有内容。Sandbox 里的临时工作目录文件，不一定都会自动成为会话文件。
​        如果你只是用 Shell 在 `/workspace` 里创建了文件，它可能还没有进入主 API 的文件对象系统。后续章节会继续完善工具产物和会话文件之间的关系。

### 29.11.5 环境页签里的 VNC 连接失败怎么办？
​        环境页签只是复用第 28 章的 `VncPanel`。先请求 `curl http://localhost:8088/sandbox-api/vnc/status`，确认 VNC 状态接口正常；再检查 Nginx 的 `/sandbox-vnc/` WebSocket 代理和 Sandbox 中的 websockify 进程。
​        如果 VNC 状态接口正常，但远程桌面无法连接，优先查看浏览器控制台和 Sandbox 容器日志，确认 WebSocket 是否成功升级。

### 29.11.6 为什么事件记录还要保留？
​        工具预览面板展示重点结果，但它不是完整日志。事件记录仍然有价值，因为它展示任务执行的时间顺序，包括消息、计划、步骤开始、工具调用、步骤完成和任务结束。
​        两个区域的职责不同：事件记录回答“发生了什么”，工具预览回答“工具做了什么、结果长什么样”。保留两者，用户既能看全局轨迹，也能看细节结果。

## 29.12 本章小结
​        本章完成了工具预览面板的第一版。我们新增了 `ToolPreviewPanel`，用“工具、文件、环境”三个页签收敛工具调用、会话文件、任务沙箱和 VNC 远程桌面。`ChatWorkspace` 不再把这些能力散落摆放，而是把它们组织成一个更稳定的右侧观察区。
​        同时，事件记录被简化回日志职责，详细的工具参数、文本输出和浏览器截图由工具预览面板承载。从这一章开始，右侧工作台不再只是章节功能的堆叠，而是形成了更接近真实 Agent 产品的执行观察结构。
