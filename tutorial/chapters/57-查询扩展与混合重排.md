# 第五十七章. 查询扩展与混合重排

## 57.1 本章目标

第五十章完成了 RAG 的基础闭环：切分、向量召回、词法重排、预算裁剪、编号引用，并把检索能力注册成了 Agent 工具 `knowledge_search`；第五十四章进一步做了自动召回与带引用作答。但真实使用一段时间后，检索质量的两块短板暴露得很明显：**用户问句和文档措辞字面不同导致漏召回**，以及**粗排分数把"沾边"的段落排在"真正回答"的段落前面**。

完成本章后，你将能够：

- 实现一条"LLM 优先、规则兜底"的查询改写链路，让离线环境也能工作；
- 用 RRF（Reciprocal Rank Fusion）把多查询的召回列表融合成单一排序；
- 用两级切分 + 父文档检索（small-to-big）解决"命中子块但上下文不够"的问题；
- 实现 LLM listwise 重排与词法降级重排，并解释"为什么重排失败要静默降级而不是报错"；
- 用相关分、文档新鲜度、来源类型三个信号合成引用置信度。

## 57.2 为什么需要这一章

向量检索的经典假设是"查询和文档在同一个语义空间里"，但真实查询往往违反这个假设。用户问"数据库连不上怎么办"，文档里写的是"数据库连接超时排查"——语义接近，字面差异不小；英文知识库配中文提问时，差异更大。单一查询向量只能命中它"看得见的"那部分空间。

工程上的标准解法是 **multi-query**：把原始查询改写成 2-3 个变体，各自召回，再融合。但 multi-query 引入了一个新问题：三个查询各召回一个有序列表，名次互相矛盾时听谁的？如果直接按"某条候选在某个列表里排第 1"来定胜负，一个偏科的变体会主导最终结果。所以需要一种**只看名次、不看分数**的融合算法——不同列表的分数本来就不可比（不同查询的向量余弦没有共同标尺），而名次是可比的最小公分母。这就是 RRF。

第二块短板在精排。粗排（向量余弦 + RRF）的目标是召回率，它允许"沾边"的段落混进来；但喂给 LLM 生成答案的 top-k 位置宝贵，需要一次精排把真正相关的段落顶上来。这里必须做一个明确的取舍：**精排可以调 LLM，但精排失败绝不能让检索失败**。检索是主链路，重排是增强项——这个原则贯穿本章所有 LLM 调用。

## 57.3 实现步骤

### 57.3.1 查询改写：LLM 优先，规则兜底

`query_processing.py` 里的 `expand_query` 是入口，两条路径：

```python
async def expand_query(query, llm=None, *, max_variants: int = 3) -> ExpandedQuery:
    ...
    if llm is not None:
        try:
            variants = await _llm_rewrite(clean, llm, max_variants)
            return ExpandedQuery(original=clean, variants=variants, method="llm")
        except Exception:
            # 降级是设计内行为：不打日志告警，避免污染检索主链路。
            pass
    return ExpandedQuery(original=clean, variants=rule_expand(clean, max_variants), method="rule")
```

LLM 路径的 prompt 明确要求三个变体分工：**同义改写、上位词扩展、子问题分解**——三个变体覆盖三种不同的漏召回模式，而不是让 LLM 自由发挥生成三个近似重复的句子。

规则路径（`rule_expand`）由三个确定性策略组成：去停用词、同义词表替换（"错误"→"异常"这类同义词组）、中英扩展（查询只出现中文主题词时，把 glossary 里的英文词补在句尾，保证中英文档都能被字面命中）。这条路径没有外部依赖，是离线/无密钥部署的默认路径。

一个细节是 `_parse_string_list` 的容错：用正则先把输出里的 JSON 数组抠出来再 `json.loads`，容忍 LLM 在数组外面加解释文字或代码围栏；解析失败或变体全被去重过滤时抛 `ValueError`，由 `expand_query` 统一吞掉降级。**改写是增强项，任何失败都不得阻塞主检索链路**——这是有意的设计决策：宁可少两个变体，不能因为一次改写失败让用户等一个报错。

### 57.3.2 RRF 融合：只看名次，不看分数

```python
def reciprocal_rank_fuse(ranked_lists: list[list[Any]], *, k: int = 60) -> list[tuple[Any, float]]:
    scores: dict[Any, float] = {}
    first_seen: dict[Any, int] = {}
    for position, ranked in enumerate(ranked_lists):
        for rank, chunk_id in enumerate(ranked, start=1):
            scores[chunk_id] = scores.get(chunk_id, 0.0) + 1.0 / (k + rank)
            first_seen.setdefault(chunk_id, position)
    fused = sorted(scores, key=lambda chunk_id: (-scores[chunk_id], first_seen[chunk_id]))
    return [(chunk_id, round(scores[chunk_id], 6)) for chunk_id in fused]
```

三个设计点：

- **k=60**：Cormack 2009 论文的经典取值。k 越大名次差异被平滑得越多——排第 1 和第 10 的得分差距被压得很小，避免"某条候选恰好是每个列表的第 1 名但每个列表都只沾一点边"这种刷分情况。
- **缺席列表得 0 分**：只被一个变体召回的候选不会被惩罚性淘汰，它的分数只是低一些——这正是 multi-query 想要的"并集召回、融合排序"。
- **同分时 `first_seen` 决胜**：先出现的列表排前面，保证多次运行结果确定，可复现、可审计。

### 57.3.3 父文档检索：small-to-big

"命中子块但上下文不够"是切分粒度两难的另一面：子块切得细，向量召回精确，但答案经常横跨两个子块。`chunking.py` 的 `split_with_parents` 用两级切分解开这个矛盾：

```python

    ...
```

**只把子块写进向量存储**，子块 metadata 里冻结所属父块的全文（`PARENT_TEXT_KEY = "parent_text"`）。检索时命中子块，`parent_context.py` 把它换算回父块上下文，三条路径按优先级回退：

1. 直接读 metadata 里的父块全文——零额外查询；
2. 子块带 `parent_seq` 但 metadata 没有父块文本（旧数据补录）：按 `parent_seq` 把兄弟子块排序拼接；
3. 更老的单级切分文档：按 `seq` 向前后各扩展 `neighbor_count` 个邻块，模拟一个更大的阅读窗口。

这里有个容易忽略的取舍：路径 2 和 3 都要拿整文档的 chunk 表做计算，是一次数据库查询换来的"近似父块"。路径 1 把成本付在入库时（metadata 存全文，有存储冗余），换取检索时零查询。我选了**新文档走路径 1，旧文档容忍路径 2/3 的开销**，不为存量数据做一次性回填——回填本身也是一次全库重读，不如让它随文档重新摄取自然升级。

### 57.3.4 重排：LLM listwise，词法降级

`reranking.py` 的重排入口只对粗排前 `top_n`（默认 10）个候选算分，其余保持原序——重排成本随 top_n 线性增长，而粗排第 10 名之后的候选本来就进不了答案引用区。

LLM 路径是 **listwise**：整组候选一次喂给 LLM 打 0-10 分，而不是 pairwise 逐对比较。取舍在于调用次数——pairwise 对 10 个候选理论上是 45 次比较，listwise 恒定 1 次；而且 LLM 在 listwise 下能看到候选间的相对差异，打分反而更稳定。每个候选正文截断到 300 字（`_CANDIDATE_SNIPPET_CHARS`），够判断相关性又不爆 token。

LLM 输出不可解析、调用超时、返回分数全被过滤——全部走同一条降级路径，切到词法重排：

```python
def _lexical_rerank_scores(query, chunks) -> list[float]:
    # TF-IDF 加权 + 短语匹配加分 + 位置衰减
    idf = math.log(1.0 + document_count / doc_freq.get(term, 1))
    ...
    phrase = _phrase_bonus(query, candidate_texts[position])
    decay = 1.0 / (1.0 + 0.1 * position)
    scores.append(round(max(0.0, min(0.7 * tfidf_norm + 0.3 * phrase, 1.0)) * decay, 4))
```

词法路径三个信号：**TF-IDF 加权**缓解常见词刷分；**短语加分**看查询词在正文中是否成簇出现（`_phrase_bonus` 用"词首现位置跨度"衡量紧凑度，紧凑得像原句命中给 1.0）；**位置衰减**让粗排名次信息不浪费。纯函数、确定性，离线环境行为可复现。

这里回到 57.2 的取舍：**为什么重排失败要静默降级而不是报错？** 因为重排的失败模式（LLM 超时、输出格式漂移）和用户查询本身无关，报错只会把"检索成功但精排不可用"误报成"检索失败"，误导上游重试逻辑。降级后的词法重排仍然产出一个可用排序，`rerank_score` 字段有值，审计日志里能看到 method 从 `llm` 变成了 `lexical`——可观测，但不阻断。

### 57.3.5 引用置信度

重排分数回答"和相关吗"，引用置信度（`confidence_score`）回答"这条引用有多可信"，三者加权：

```python
confidence = 0.6 * max(0.0, min(final_score, 1.0)) + 0.25 * freshness + 0.15 * weight
```

新鲜度按半衰期指数衰减（`0.5 ** (age_days / 180)`），来源类型权重区分人工沉淀（1.0）和外部网页（0.85）。相关分权重最大（0.6），但新鲜度和来源各占一截——一条三个月前从网页抓的、只沾边的引用，置信度会被压到很低，前端展示时排到后面。

## 57.4 本章小结

本章给 RAG 检索管线补上了两段：前端的**查询扩展**（multi-query + RRF 融合扩大召回面）和后端的**重排与置信度**（listwise LLM 精排 + 词法降级 + 三维引用置信度）。贯穿两者的原则是"增强项失败静默降级，主链路永不因增强项挂掉"——查询改写失败退回单查询，重排失败退回词法，都有审计痕迹可查。

父文档检索用两级切分把"召回精度"和"上下文完整性"解耦：向量索引细粒度保证召回，父块全文保证生成质量，成本在入库时一次性付清。
