# 第七章. 数据库、迁移与会话模型立制

## 7.1 本章目标

​        前面几章已经让 AtlasAgent 有了后端、前端和统一网关，但系统仍然没有真正记住任何东西。状态接口返回的是写在代码里的固定信息，页面刷新后也不会出现业务数据。一个 Agent 工作台如果不能保存会话，就只能停留在演示壳阶段；用户创建过哪些任务、每次对话的标题是什么、执行状态有没有变化、哪些会话已经删除，这些信息都必须进入数据库。
​        本章的目标，就是让后端从“只有接口”进入“有数据层”。读者会使用 SQLAlchemy 2.x 编写异步 ORM 模型，用 asyncpg 连接 PostgreSQL，用 Alembic 管理表结构迁移，并创建第一张业务表 `sessions`。同时，本章会开始引入领域实体、Repository 和 Unit of Work。它们现在看起来比直接写 SQL 多绕了一层，但后面会话、消息、文件、任务事件逐步加入后，这些边界会让业务代码更容易维护。

## 7.2 最终效果

​        本章结束后，后端会具备最小数据层能力。数据库中会新增第一张业务表：

```Plain
sessions
```

​        这张表暂时只描述会话的基本状态，字段包含：

```Plain
id
title
status
unread_count
created_at
updated_at
deleted_at
```

​        执行迁移后，可以通过网关验证数据库连接：

```Plain
http://localhost:8088/api/status/database
```

​        正常情况下会返回：

```JSON
{
  "code": 200,
  "message": "success",
  "data": {
    "status": "ok"
  }
}
```

​        需要注意，本章只完成数据库模型、迁移和数据访问骨架，不做创建会话接口，也不做前端会话列表。第 08 章会基于本章继续实现会话创建、查询和删除。这样安排是为了让读者先看清数据层的结构，再把它接到真实业务接口上。

## 7.3 本章要解决的问题

​        第 06 章完成了统一网关入口，浏览器已经可以通过 Nginx 访问 UI 和 API。但目前 API 还没有业务数据。状态接口每次返回的内容都是代码里写死的，服务重启之后也不会有任何业务状态被保留下来。对一个 Agent 工作台来说，这显然不够。
​        从会话功能开始，数据必须存进 PostgreSQL。用户创建了哪些会话，每个会话的标题是什么，会话当前是空闲、运行中、停止还是失败，有多少未读消息，是否已经被软删除，这些都不是临时变量能解决的问题。它们需要有稳定的表结构，也需要有明确的数据访问边界。
​        如果直接在接口里手写 SQL，前期确实很快。但项目一变大，问题也会变得明显：表结构变化不好管理，业务代码和 SQL 细节耦合太强，创建、查询、删除等逻辑容易散落在不同接口里，多个接口一起修改数据时也很难统一提交或回滚事务。笔者不想等这些问题全部出现之后再重构，所以从第一张业务表开始，就把数据层的基本秩序立起来。
​        本章因此引入四个概念。SQLAlchemy 用来在 Python 中描述表结构和查询，Alembic 用来管理数据库结构变更，Repository 用来封装会话数据访问，Unit of Work 用来统一管理一次业务操作中的事务提交和回滚。本章完成后，后端就不再只是能返回 JSON 的接口服务，而是开始拥有可持续演进的数据层。

## 7.4 本章技术方案

​        本章选择 SQLAlchemy 2.x 作为 ORM，asyncpg 作为 PostgreSQL 异步驱动，Alembic 作为迁移工具。直接使用 SQL 字符串当然可以，SQLAlchemy Core 也能更接近 SQL 表达；但本项目后续会有会话、消息、文件、任务事件等多张表，ORM 更适合表达对象关系，也方便后续在 Repository 中组合查询。
​        这里还有一个设计取舍：领域实体和 ORM 模型分开定义。`Session` 领域实体表达业务世界里的会话，`SessionModel` ORM 模型表达数据库里的 `sessions` 表。它们字段目前很接近，但语义不一样。领域实体不应该被数据库细节绑死，ORM 模型也不应该承担业务规则。这个边界看起来有些“工程化”，但它会让后续业务服务更容易测试，也更容易替换底层存储实现。
​        本章会增加数据库相关依赖，加入 `DATABASE_URL` 和 `DATABASE_ECHO` 配置，创建数据库连接和异步 Session 工厂，定义领域层 `Session` 实体和基础 Repository 协议，再创建 `SessionModel` ORM 模型、SQLAlchemy 版会话 Repository、Unit of Work、Alembic 配置和迁移文件。最后还会增加数据库状态检查接口，并更新 Dockerfile，让 API 镜像包含迁移文件。
​        本章暂时不做会话创建接口、会话列表接口和前端会话列表，也不接入消息表、Redis 任务或复杂事务场景。这些能力会在后续章节逐步接上。本章先把模块关系打稳：

```Plain
API 路由
  |
  v
Application / UnitOfWork
  |
  v
Domain Repository 协议
  |
  v
Infrastructure Repository 实现
  |
  v
SQLAlchemy ORM Model
  |
  v
PostgreSQL
```

## 7.6 开始前理解：为什么需要迁移

​        数据库表结构不是一次写完就永远不变。会话表一开始可能只有几个字段：

```Plain
id
title
created_at
```

​        后面随着业务推进，又可能增加状态、未读数和软删除时间：

```Plain
status
unread_count
deleted_at
```

​        如果每个人都手动在数据库里执行 SQL，很容易出现环境不一致：

```Plain
你的数据库有 status 字段
另一台电脑没有 status 字段
服务器数据库字段类型又不一样
```

​        Alembic 的作用，就是把表结构变化写成可以被版本管理的迁移文件。每次升级数据库时执行：

```Bash
uv run alembic upgrade head
```

​        数据库就会按迁移文件一步步更新到最新结构。这样本地、测试环境和服务器都可以按照同一套迁移历史前进，而不是靠每个人记住自己执行过哪些 SQL。

## 7.7 实施步骤
### 7.7.1 增加数据库依赖

​        先进入 `api` 目录：

```Bash
cd api
```

​        使用 uv 增加依赖：

```Bash
uv add "sqlalchemy[asyncio]>=2.0,<3.0" "asyncpg>=0.30,<1.0" "alembic>=1.16,<2.0"
```

​        这条命令会更新：

```Plain
api/pyproject.toml
api/uv.lock
```

​        `sqlalchemy[asyncio]` 提供异步 ORM 能力，`asyncpg` 是连接 PostgreSQL 的异步驱动，`alembic` 负责数据库迁移。不要混用其他安装命令，后端依赖统一由 uv 管理，这样 `pyproject.toml` 和 `uv.lock` 才能保持一致。

### 7.7.2 增加数据库配置

​        打开 `api/app/core/config.py`，在 `Settings` 中增加数据库配置：

```Python
database_url: str = (
    "postgresql+asyncpg://postgres:postgres@localhost:5432/atlas_agents"
)
database_echo: bool = False
```

​        `database_url` 是数据库连接地址，格式是：

```Plain
postgresql+asyncpg://用户名:密码@主机:端口/数据库名
```

​        本地默认值使用 `localhost`，适合在宿主机能访问 PostgreSQL 时使用。Docker Compose 中，API 容器要访问 PostgreSQL 容器，不能写 `localhost`，要写服务名 `postgres`。所以还要打开根目录 `docker-compose.yml`，在 `api.environment` 中加入：

```YAML
DATABASE_URL: ${DATABASE_URL:-postgresql+asyncpg://postgres:postgres@postgres:5432/atlas_agents}
DATABASE_ECHO: ${DATABASE_ECHO:-false}
```

​        这里的 `postgres` 是 Docker Compose 服务名，不是数据库名。继续更新 `.env.example`：

```Plain
DATABASE_URL=postgresql+asyncpg://postgres:postgres@postgres:5432/atlas_agents
```

### 7.7.3 创建数据库基础模块

​        创建 `api/app/infrastructure/database/base.py`：

```Python
from sqlalchemy.orm import DeclarativeBase


class Base(DeclarativeBase):
    pass
```

​        `Base` 是所有 ORM 模型的基类。后续所有数据库表模型都会继承它。

​        Alembic 也会通过它收集表结构。

​        创建 `api/app/infrastructure/database/session.py`：

```Python
from collections.abc import AsyncGenerator

from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine

from app.core.config import settings

engine = create_async_engine(
    settings.database_url,
    echo=settings.database_echo,
    pool_pre_ping=True,
)

AsyncSessionLocal = async_sessionmaker(
    bind=engine,
    class_=AsyncSession,
    expire_on_commit=False,
)


async def get_db_session() -> AsyncGenerator[AsyncSession]:
    async with AsyncSessionLocal() as session:
        yield session
```

​        这里有三个关键点。`create_async_engine()` 创建异步数据库引擎，后续所有 SQLAlchemy 异步操作都要通过它连接数据库；`async_sessionmaker()` 创建数据库会话工厂，接口处理请求时会从这里拿到一个 `AsyncSession`；`get_db_session()` 是 FastAPI 依赖函数，后续接口可以通过 `Depends(get_db_session)` 获取数据库会话。
​        `pool_pre_ping=True` 会在连接被使用前检查连接是否可用，可以减少数据库连接断开导致的偶发错误。数据库连接池不是业务功能，但它会直接影响服务稳定性。现在先把这个细节放好，后续接口使用数据库时就不需要重复考虑连接如何创建。

### 7.7.4 定义领域实体

​        接下来创建领域实体。打开 `api/app/domain/sessions/entities.py`，先用 Python 自身的类型系统描述业务中的会话。

```Python
from dataclasses import dataclass
from datetime import datetime
from enum import StrEnum
from uuid import UUID


class SessionStatus(StrEnum):
    idle = "idle"
    running = "running"
    stopped = "stopped"
    failed = "failed"


@dataclass(slots=True)
class Session:
    id: UUID
    title: str
    status: SessionStatus
    unread_count: int
    created_at: datetime
    updated_at: datetime
    deleted_at: datetime | None = None
```

​        这里的 `Session` 是领域实体，不是数据库模型。领域实体关心业务含义：会话标题是什么，会话当前处于什么状态，未读数量是多少，是否已经被删除。它不关心数据库字段类型、索引、表名，也不关心 SQLAlchemy 的映射配置。
​        `SessionStatus` 使用字符串枚举，是为了让数据库里保存的值更直观，比如：

```Plain
idle
running
stopped
failed
```

​        对后续业务来说，`idle`、`running`、`stopped`、`failed` 比数字状态码更容易阅读，也更容易在日志和调试过程中判断含义。

### 7.7.5 定义 Repository 协议

​        然后定义 Repository 协议。打开 `api/app/domain/sessions/repositories.py`，这里只写接口形状，不写 SQLAlchemy 细节。

```Python
from typing import Protocol
from uuid import UUID

from app.domain.sessions.entities import Session


class SessionRepository(Protocol):
    async def add(self, title: str) -> Session:
        raise NotImplementedError

    async def get(self, session_id: UUID) -> Session | None:
        raise NotImplementedError

    async def list_active(self) -> list[Session]:
        raise NotImplementedError

    async def soft_delete(self, session_id: UUID) -> None:
        raise NotImplementedError
```

​        Repository 的作用是封装数据访问。后续业务代码不直接写：

```Python
select(SessionModel)
```

​        而是调用：

```Python
uow.sessions.list_active()
```

​        这样做的好处，是查询逻辑集中管理，业务层不依赖 SQLAlchemy 细节，后续如果要调整查询条件、加缓存，甚至更换存储实现，影响范围都会更小。这里使用 `Protocol`，是为了让领域层只声明“我需要什么能力”，而不是绑定“这个能力必须由哪个具体类提供”。

### 7.7.6 创建 ORM 模型

​        领域实体描述业务，会话表还需要 ORM 模型来描述数据库结构。创建 `api/app/infrastructure/database/models/session.py`：

```Python
from datetime import datetime
from uuid import UUID, uuid4

from sqlalchemy import DateTime, Integer, String, func
from sqlalchemy.dialects.postgresql import UUID as PgUUID
from sqlalchemy.orm import Mapped, mapped_column

from app.domain.sessions.entities import Session, SessionStatus
from app.infrastructure.database.base import Base


class SessionModel(Base):
    __tablename__ = "sessions"

    id: Mapped[UUID] = mapped_column(PgUUID(as_uuid=True), primary_key=True, default=uuid4)
    title: Mapped[str] = mapped_column(String(200), nullable=False)
    status: Mapped[str] = mapped_column(String(32), nullable=False, default=SessionStatus.idle.value)
    unread_count: Mapped[int] = mapped_column(Integer, nullable=False, default=0)
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        nullable=False,
        server_default=func.now(),
    )
    updated_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        nullable=False,
        server_default=func.now(),
        onupdate=func.now(),
    )
    deleted_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True))

    def to_entity(self) -> Session:
        return Session(
            id=self.id,
            title=self.title,
            status=SessionStatus(self.status),
            unread_count=self.unread_count,
            created_at=self.created_at,
            updated_at=self.updated_at,
            deleted_at=self.deleted_at,
        )
```

​        `SessionModel` 是 ORM 模型，负责描述数据库表。这里 `id` 使用 PostgreSQL UUID，`title` 限制长度为 200，`status` 保存字符串，`unread_count` 默认是 0，`deleted_at` 用于软删除。`to_entity()` 则把 ORM 模型转换成领域实体，让上层业务拿到的是 `Session`，而不是带着 SQLAlchemy 状态的数据库对象。
​        软删除表示不直接删除数据库记录，而是给 `deleted_at` 填入时间。这样后续如果需要恢复、审计或排查问题，仍然能找到历史数据。对于 Agent 工作台来说，用户任务和会话往往带有调试价值，直接物理删除并不适合早期系统。

​        创建 `api/app/infrastructure/database/models/__init__.py`：

```Python
from app.infrastructure.database.models.session import SessionModel

__all__ = ["SessionModel"]
```

​        这个文件会让 Alembic 能导入所有模型。如果模型没有被导入，`Base.metadata` 里就不会出现对应表，迁移工具也就不知道应该管理这张表。

### 7.7.7 实现 Repository

​        协议定义好之后，再写 SQLAlchemy 版本的具体实现。创建 `api/app/infrastructure/repositories/session_repository.py`：

```Python
from datetime import UTC, datetime
from uuid import UUID

from sqlalchemy import Select, select
from sqlalchemy.ext.asyncio import AsyncSession

from app.domain.sessions.entities import Session, SessionStatus
from app.domain.sessions.repositories import SessionRepository
from app.infrastructure.database.models.session import SessionModel


class SqlAlchemySessionRepository(SessionRepository):
    def __init__(self, db_session: AsyncSession) -> None:
        self.db_session = db_session

    async def add(self, title: str) -> Session:
        model = SessionModel(
            title=title,
            status=SessionStatus.idle.value,
            unread_count=0,
        )
        self.db_session.add(model)
        await self.db_session.flush()
        await self.db_session.refresh(model)
        return model.to_entity()

    async def get(self, session_id: UUID) -> Session | None:
        stmt = self._active_stmt().where(SessionModel.id == session_id)
        result = await self.db_session.execute(stmt)
        model = result.scalar_one_or_none()
        return model.to_entity() if model else None

    async def list_active(self) -> list[Session]:
        stmt = self._active_stmt().order_by(SessionModel.updated_at.desc())
        result = await self.db_session.execute(stmt)
        return [model.to_entity() for model in result.scalars()]

    async def soft_delete(self, session_id: UUID) -> None:
        stmt = self._active_stmt().where(SessionModel.id == session_id)
        result = await self.db_session.execute(stmt)
        model = result.scalar_one_or_none()
        if model is not None:
            model.deleted_at = datetime.now(UTC)

    @staticmethod
    def _active_stmt() -> Select[tuple[SessionModel]]:
        return select(SessionModel).where(SessionModel.deleted_at.is_(None))
```

​        这里先实现四个基础能力：新增会话、查询单个会话、查询未删除会话列表、软删除会话。`_active_stmt()` 把“只查询未删除记录”这个条件集中起来，避免每个查询方法都重复写 `deleted_at.is_(None)`。
​        `flush()` 会把新增对象发送到数据库，但不提交事务。这样可以让数据库生成默认字段，也能让后续 `refresh()` 拿到完整模型；真正提交事务则交给 Unit of Work 统一处理。这个分工很重要，Repository 负责数据访问，事务边界不应该散落在每一个 Repository 方法里。

### 7.7.8 创建 Unit of Work

​        有了 Repository 之后，还需要一个事务边界。创建 `api/app/application/unit_of_work.py`：

```Python
from sqlalchemy.ext.asyncio import AsyncSession

from app.infrastructure.repositories.session_repository import SqlAlchemySessionRepository


class UnitOfWork:
    def __init__(self, db_session: AsyncSession) -> None:
        self.db_session = db_session
        self.sessions = SqlAlchemySessionRepository(db_session)

    async def commit(self) -> None:
        await self.db_session.commit()

    async def rollback(self) -> None:
        await self.db_session.rollback()
```

​        Unit of Work 用来管理一次业务操作中的事务。后续会话接口会像这样使用：

```Python
uow = UnitOfWork(db_session)
session = await uow.sessions.add(title="新的任务")
await uow.commit()
```

​        如果中间出现异常，就可以统一回滚：

```Python
await uow.rollback()
```

​        本章先只放最小结构，第 08 章会真正接入接口。这个类现在看起来很短，但它已经把事务提交和回滚放到了应用层边界。后续当一次业务操作同时涉及会话、消息、文件和任务事件时，Unit of Work 的价值会更明显。

### 7.7.9 创建 Alembic 配置

​        接下来创建 Alembic 配置。在 `api/` 目录创建 `alembic.ini`：

```TOML
[alembic]
script_location = migrations
prepend_sys_path = .
path_separator = os
```

​        这个文件告诉 Alembic：迁移脚本放在 `migrations`，Python 导入路径从当前目录开始。随后创建 `api/migrations/env.py`，让 Alembic 能读取项目配置并找到 ORM 元数据。核心配置是：

```Python
config.set_main_option("sqlalchemy.url", settings.database_url)
target_metadata = Base.metadata
```

​        `settings.database_url` 让 Alembic 读取项目配置，`Base.metadata` 让 Alembic 知道当前有哪些 ORM 模型。还需要导入模型：

```Python
from app.infrastructure.database.models import SessionModel
```

​        如果不导入模型，`Base.metadata` 里就没有 `sessions` 表。很多迁移文件生成不出来，问题都出在这里：模型类写好了，但没有在迁移环境中被导入。

### 7.7.10 创建 sessions 表迁移

​        现在创建真正的迁移文件：

```Plain
api/migrations/versions/202606030001_create_sessions.py
```

​        升级逻辑负责创建 `sessions` 表：

```Python
def upgrade() -> None:
    op.create_table(
        "sessions",
        sa.Column("id", postgresql.UUID(as_uuid=True), nullable=False),
        sa.Column("title", sa.String(length=200), nullable=False),
        sa.Column("status", sa.String(length=32), nullable=False),
        sa.Column("unread_count", sa.Integer(), nullable=False),
        sa.Column("created_at", sa.DateTime(timezone=True), server_default=sa.func.now(), nullable=False),
        sa.Column("updated_at", sa.DateTime(timezone=True), server_default=sa.func.now(), nullable=False),
        sa.Column("deleted_at", sa.DateTime(timezone=True), nullable=True),
        sa.PrimaryKeyConstraint("id"),
    )
    op.create_index("ix_sessions_deleted_at", "sessions", ["deleted_at"])
    op.create_index("ix_sessions_updated_at", "sessions", ["updated_at"])
```

​        降级逻辑负责回退这次迁移：

```Python
def downgrade() -> None:
    op.drop_index("ix_sessions_updated_at", table_name="sessions")
    op.drop_index("ix_sessions_deleted_at", table_name="sessions")
    op.drop_table("sessions")
```

​        `upgrade()` 表示升级数据库，`downgrade()` 表示回退数据库。`deleted_at` 和 `updated_at` 建索引，是因为后续会经常查询未删除会话，并按更新时间排序。现在提前建好索引，后面实现会话列表时就不需要重新回来补这个基础结构。

### 7.7.11 增加数据库状态接口

​        数据层建好后，需要一个最小验证入口。创建 `api/app/infrastructure/database/health.py`：

```Python
from sqlalchemy import text
from sqlalchemy.ext.asyncio import AsyncSession


async def check_database(db_session: AsyncSession) -> bool:
    result = await db_session.execute(text("select 1"))
    return result.scalar_one() == 1
```

​        这个函数只做一件事：向数据库发送 `select 1`。如果数据库连接正常，会返回 `1`。它不检查业务表，也不写入数据，只用于确认 API 能不能连到 PostgreSQL。

​        接着更新 `api/app/schemas/status.py`，增加数据库状态响应模型：

```Python
class DatabaseStatusData(BaseModel):
    status: str
```

​        再更新 `api/app/api/routes/status.py`，增加数据库状态接口：

```Python
@router.get("/database", response_model=ApiResponse[DatabaseStatusData])
async def get_database_status(
    db_session: AsyncSession = Depends(get_db_session),
) -> ApiResponse[DatabaseStatusData]:
    is_ready = await check_database(db_session)
    return ApiResponse(data=DatabaseStatusData(status="ok" if is_ready else "error"))
```

​        最终访问路径是：

```Plain
/api/status/database
```

​        这个接口是本章验证数据库连接的最小入口。它不会替代后续监控系统，但在教程阶段很有用：读者可以直接通过网关确认 API、Nginx、数据库连接和依赖注入是否都已经打通。

## 7.8 关键理解

​        本章最重要的是区分三组概念。第一组是 ORM 模型和领域实体。

```Plain
SessionModel  负责数据库表结构
Session       负责业务含义
```

​        ORM 模型知道表名、字段类型、索引和 SQLAlchemy 配置。领域实体只表达业务对象，不关心数据库实现。两者短期看字段相似，长期看职责完全不同。
​        第二组是 Repository 和 Unit of Work。

```Plain
Repository    封装数据访问
UnitOfWork    管理事务提交和回滚
```

​        Repository 不应该自己随便提交事务。事务由 Unit of Work 统一提交，这样多个 Repository 操作可以放进同一个事务里。以后一次用户请求可能同时创建会话、写入消息、记录事件，如果每个 Repository 自己提交，失败后的回滚就会很难处理。
​        第三组是宿主机地址和容器地址。在宿主机里，可能会写：

```Plain
localhost:5432
```

​        在 API 容器里，要访问 PostgreSQL 容器，应该写：

```Plain
postgres:5432
```

​        所以 Docker Compose 中的 `DATABASE_URL` 使用：

```Plain
postgresql+asyncpg://postgres:postgres@postgres:5432/atlas_agents
```

## 7.9 技术难点与亮点

​        本章的技术难点不在某一行代码，而在几个边界。Alembic 迁移文件和 ORM 模型不是同一个东西：ORM 模型描述当前代码认为表应该是什么样，迁移文件描述数据库从一个版本变到另一个版本应该执行什么操作。异步 SQLAlchemy 也需要读者注意，连接引擎、Session 工厂和接口依赖都要使用异步版本。
​        容器里的数据库地址也容易出错。API 容器访问 PostgreSQL 容器时，要使用 Compose 服务名 `postgres`，不是 `localhost`。Repository 不直接提交事务，迁移文件也要被拷贝进 API 镜像，这些都是工程细节，但它们会决定项目能不能稳定运行。
​        本章的亮点，是数据层从一开始就有迁移版本管理，会话表支持软删除和更新时间排序，领域实体和 ORM 模型分离，Repository 和 Unit of Work 为复杂业务事务预留了清晰边界，数据库状态接口也让数据库链路可以被直接验证。这些设计都不夸张，但它们让后续业务不会从一开始就陷进混乱的数据访问里。

## 7.10 面试考点

​        面试里如果聊到这一章，重点通常会落在几个问题上：为什么项目需要 Alembic，而不是手动建表；SQLAlchemy ORM 模型和领域实体有什么区别；Repository 模式解决什么问题；Unit of Work 为什么要统一管理 commit 和 rollback；Docker Compose 中为什么数据库地址写 `postgres:5432`，不是 `localhost:5432`。
​        这些问题考察的是你对数据层边界的理解。能把表建出来只是第一步，真正重要的是表结构如何演进，业务代码如何避免直接依赖数据库细节，事务如何在一次业务操作里保持一致。

## 7.12 常见问题

### 7.12.1 `uv run alembic heads` 找不到迁移配置怎么办

​        确认当前目录是 `api/`，并且 `api/alembic.ini` 已经创建。Alembic 会从当前目录寻找配置文件，如果站在项目根目录直接执行，就可能找不到它。

### 7.12.2 容器里执行迁移时提示找不到 `alembic.ini` 怎么办

​        确认 `api/Dockerfile` 已经拷贝 `alembic.ini` 和 `migrations/`，然后重新执行 `docker compose build api`。Docker 镜像不会自动拥有你本地新增的文件，必须在 Dockerfile 中显式复制并重新构建。

### 7.12.3 迁移时报 `could not translate host name "postgres"` 怎么办

​        `postgres` 这个主机名只能在 Docker Compose 网络里使用。请用 `docker compose exec api uv run alembic upgrade head` 在 API 容器中执行迁移，不要直接在宿主机用 `postgres` 这个主机名。如果要在宿主机直接执行迁移，就要把连接地址改成宿主机能访问的数据库地址。

### 7.12.4 数据库状态接口返回 500 怎么办

​        先检查迁移是否执行成功，再查看 API 日志：`docker compose logs --tail=80 api`。还要确认 `DATABASE_URL` 是否指向 `postgres:5432`。如果 API 容器连不上数据库，状态接口自然会返回错误。

### 7.12.5 为什么本章不直接实现会话创建接口

​        本章目标是数据层和迁移闭环。会话接口会涉及请求参数、响应结构、事务提交、前端列表联动，放到第 08 章更清晰。先把数据层打稳，下一章实现接口时才不会一边写业务一边补基础设施。

## 7.13 本章小结

​        本章完成了 AtlasAgent 的数据库基础。我们加入 SQLAlchemy、asyncpg 和 Alembic，增加数据库配置，创建异步数据库连接，定义会话领域实体和 Repository 协议，再实现 `sessions` ORM 模型、SQLAlchemy Repository、Unit of Work、Alembic 配置和迁移文件。最后，数据库状态检查接口让整个连接链路可以通过网关直接验证。
