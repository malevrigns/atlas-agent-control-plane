# 第五十八章. 记忆生命周期与冲突消解

## 58.1 本章目标

第二十七章和第四十五章把记忆系统搭了起来：类型化事实（subject-predicate-value）、candidate/verified 生命周期、Write Gate、supersede 链。但当时有一个刻意没做的事：**记忆只进不出**。几个月后，库里会堆满"当时正确、现在过期"的事实——三个月前的部署偏好、已经修掉的缺陷教训、被新版本文档推翻的项目事实。它们还带着当年的高置信度躺在检索结果里，污染每一次决策。

完成本章后，你将能够：

- 实现艾宾浩斯式遗忘曲线，并按记忆类型区分衰减系数 λ；
- 设计"检索命中驱动的巩固"机制，让常用记忆越用越稳；
- 用纯函数检测同 subject + 同 predicate 的记忆冲突；
- 用三种策略（latest_wins / authority_wins / manual_review）消解冲突，并复用 superseded 链保持历史可追溯；
- 理解"衰减 + 巩固"这对看似矛盾的设计为什么必须同时存在。

本章新增代码集中在：

```text
backend/api/app/domain/memories/lifecycle.py    衰减 + 巩固
backend/api/app/domain/memories/conflicts.py    冲突检测 + 三策略消解
```

## 58.2 为什么需要这一章

记忆系统最大的风险不是"记不住"，而是"记错了还很有信心"。一条置信度 0.9 的旧事实被注入上下文，模型会把它当当前事实引用——比"什么都没召回"危害大得多。

工程上有两种朴素解法，都有问题：

- **定期批量删除低置信度记忆**：太粗暴。"项目使用 PostgreSQL"和"上次发布回滚了三次"不该用同一把尺子量，前者是长期事实，后者是事件经验，过期速度差一个量级。
- **全部保留，靠检索分数自然淘汰**：检索分数反映的是"和当前查询相关"，不是"和当前现实一致"。过期事实和当前查询高度相关时，它照样排第一。

所以需要一个**按时间 + 类型维度主动贬值**的机制（衰减），同时防止误伤真正有用的记忆——被反复检索命中的记忆恰恰是"仍然有用"的最强信号（巩固）。衰减管"忘"，巩固管"记牢"，两者共用同一个扫描入口，互为闸门。

冲突消解解决的是另一类腐化：**同一条事实被新证据改写**。旧记忆说"项目使用 SQLite"，新证据说"项目使用 PostgreSQL"——两条记忆的 subject 和 predicate 相同，value 不同。如果不处理，检索会把两条都召回，模型看到自相矛盾的事实后行为不可预测。

## 58.3 实现步骤

### 58.3.1 艾宾浩斯式衰减：一条公式，三个 λ

`lifecycle.py` 的核心是一条指数衰减公式：

```python
new_confidence = confidence * exp(-λ * days_since_last_access)
```

λ 按记忆类型分三档（`decay_lambda`）：

```python
_PREFERENCE_KINDS = frozenset({MemoryKind.user_preference})     # λ = 0.005，偏好最稳定
_EVENT_KINDS = frozenset({                                       # λ = 0.05，事件类遗忘最快
    MemoryKind.episode, MemoryKind.task_experience, MemoryKind.bug_lesson,
})
# 其余类型（项目事实、代码事实、约束、决策）按一般事实处理，λ = 0.01
```

这里有个容易做错的细节：**时间锚点优先取 `last_accessed_at`，而不是 `created_at`**。一条去年创建、上周还被检索命中的记忆，遗忘应该从"上周"重新计时——这正是"间隔重复"的直觉。从未被命中的记忆才从创建时间开始遗忘。

两个保护参数值得单独说：

- **`memory_decay_floor`（默认 0.05）**：衰减有下限，记忆不会衰减到零。宁可留着一条 0.05 的旧记忆，也不做不可逆删除——删除是审计灾难，低置信度只是检索排序问题。
- **`memory_decay_min_drop`（默认 0.005）**：单次衰减幅度小于阈值就不写库。衰减是每天跑的后台任务，如果每次扫描都更新几万条"从 0.9 变成 0.899"的记录，数据库写入放大了但记忆行为没变——这类无意义更新必须拦在事务外面。

### 58.3.2 巩固：让常用记忆越用越稳

衰减天然是无差别的——用得多用得少，公式不区分。巩固机制补上这个区分：

```python
@staticmethod
def is_consolidation_eligible(memory, *, min_accesses: int = 3) -> tuple[bool, list[str]]:
    if memory.access_count < min_accesses:
        return False, [f"检索命中次数不足（{memory.access_count}/{min_accesses}）"]
    if memory.status is not MemoryStatus.verified:
        return False, ["记忆状态不是 verified"]
    if not memory.provenance:
        return False, ["缺少来源 provenance，无法视为通过验证"]
    if memory.authority is not MemoryAuthority.suggested:
        return False, [f"当前权威度 {memory.authority.value} 无需巩固晋升"]
    return True, []
```

条件链是"命中 ≥3 次 + 已过 Write Gate（verified + 有 provenance）+ authority 仍是 suggested"。满足后，`consolidate` 把 authority 从 `suggested` 晋升为 `verified`，同时把置信度抬到巩固下限（0.9），并写 `memory_consolidated` 审计事件。

两个刻意的限制：**`agent_inferred` 不参与自动晋升**——Agent 自己推断的记忆需要外部证据复验，不能靠"自己反复查到"自证；**巩固只抬不降**（`max(memory.confidence, ...)`）——衰减刚把一条记忆压到 0.6，巩固不该把它瞬间抬回 0.9 制造震荡。

`run_lifecycle` 把衰减和巩固串成一个可被后台定时任务调度的入口，单次执行失败不影响下一次调度——衰减是"迟早会做对"的幂等操作，不需要 at-least-once 之外的保证。

### 58.3.3 冲突检测：纯函数，先看后动

`conflicts.py` 的 `detect_conflicts` 是纯函数，只依赖领域实体：

```python
def detect_conflicts(new_memory, existing_memories) -> list[MemoryConflict]:
    ...
    for existing in existing_memories:
        if existing.id == new_memory.id:
            continue
        if existing.deleted_at is not None:
            continue
        if existing.status is MemoryStatus.superseded:
            continue
        if existing.subject != new_memory.subject or existing.predicate != new_memory.predicate:
            continue
        if _canonical_value(existing.value) == new_value:
            continue
        conflicts.append(MemoryConflict(...))
    return conflicts
```

三个细节：

- **`_canonical_value` 用 `json.dumps(sort_keys=True)` 归一化 value**。value 是自由 dict，`{"a":1,"b":2}` 和 `{"b":2,"a":1}` 是同一个事实，键序不同不该算冲突。
- **已 superseded 的记忆不参与检测**。它是历史版本，新事实取代它的后继者时，不应再和它"冲突"一次——否则 supersede 链越深，检测越膨胀。
- **没有 subject 的记忆直接跳过**。无 subject 就没有"同一条事实"的判定基础，宁可漏检不可误杀。

### 58.3.4 三策略消解

```python
class MemoryConflictStrategy(StrEnum):
    latest_wins = "latest_wins"        # 默认：时间戳新的胜出
    authority_wins = "authority_wins"  # 权威度高的胜出，平级退回 latest_wins
    manual_review = "manual_review"    # 不动状态，双方挂 conflict_review 标记
```

权威度排序是显式表：`explicit_user(5) > verified(4) > tool_verified/test_verified(3) > suggested(2) > agent_inferred(1)`。

`resolve` 对每个冲突执行策略，`latest_wins` 和 `authority_wins` 殊途同归：输的一方走 `mark_superseded(loser_id, replacement_id=winner_id)`——**复用第四十五章建好的 superseded 链，而不是新增一个 `lost_in_conflict` 状态**。这是本章最重要的复用决策：supersede 链已经承担了"谁替代了谁"的语义，冲突只是 supersede 的一个触发来源。加新状态意味着检索过滤、前端展示、审计回放全部要改一遍，收益却是零。

`manual_review` 策略只写标记不动状态：双方 metadata 挂上 `conflict_review`（含对手方 id 和检测时间），留审计事件。为什么留这个策略？高权威度记忆的冲突（比如用户明确说过的偏好 vs 工具验证的新事实）机器不该自动判输——自动判错一条 `explicit_user` 记忆的代价，远高于挂起等人看一眼。

## 58.4 本章小结

本章给记忆系统补上了时间维度：**衰减**用一条指数公式 + 三个 λ 分类型贬值过期事实，下限和最小跌幅两个参数拦住"不可逆"和"无意义写入"；**巩固**用检索命中次数反向认证，让常用记忆从 suggested 晋升 verified，两个机制共用 `run_lifecycle` 一个调度入口。

**冲突消解**把"同事实新证据"场景收敛成纯函数检测 + 三策略消解，消解动作全部落在既有的 superseded 链上，零新增状态机。
