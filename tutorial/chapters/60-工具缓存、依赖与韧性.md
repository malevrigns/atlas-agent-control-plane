# 第六十章. 工具缓存、依赖与韧性

## 60.1 本章目标

前面的章节反复出现一个事实：Agent 一轮之内经常请求多个工具调用——搜索一下、再读个文件、然后基于前两个结果去浏览器里核实。这些调用之间**有的互相独立，有的依赖前面调用的产物**；有的失败了值得重试，有的重试一百次也不会成功；有的调用重复执行是浪费，有的重复执行是灾难。第四十六章给工具加了权限、幂等与审计，本章补上执行层的四件事。

完成本章后，你将能够：

- 为低风险幂等工具实现带版本号的 LRU+TTL 结果缓存，理解 key 设计里每个字段的必要性；
- 用 `provides` / `requires` 能力标签把一轮工具调用拓扑排序成并行批次；
- 设计"可重试性判定 + 指数退避 + fallback"三层韧性，并解释哪些错误重试了也没用；
- 用三维度预算约束单步工具调用，并理解"超预算为什么是回喂结果而不是抛异常"。

本章新增代码集中在：

```text
backend/api/app/domain/agent_core/tool_cache.py       结果缓存
backend/api/app/domain/agent_core/tool_deps.py        依赖分批
backend/api/app/domain/agent_core/tool_resilience.py  重试与降级
backend/api/app/domain/agent_core/tool_budget.py      预算控制
```

## 60.2 为什么需要这一章

Agent 的工具调用和人工写的函数调用有一个本质区别：**调用方是概率性的**。模型同一类任务里会反复发起参数几乎相同的搜索（换个措辞、补个关键词），也会在一轮里同时发三个调用"碰运气"。四件事缺了会怎样：

- **没缓存**：同一轮任务里三次几乎相同的搜索，三次真实的网络往返，三次计费。搜索类工具是典型的高频低风险调用，重复率惊人。
- **没依赖编排**："先打开页面再截图"这类有数据流依赖的调用被并行发出，截图拍到空白页；反过来，如果为了安全把整轮调用串行化，无依赖的搜索也排在前面之后干等。
- **没韧性**：一次网络抖动让整轮工具调用失败，模型重试整个步骤，上下文翻倍。
- **没预算**：模型对某类工具"上头"（反复搜索同一个词、反复读同一个文件），单步跑几十次调用，token 账单和延迟一起失控。

四件事的共同点是：**都发生在"执行层"，都不该让模型或领域实体感知**。模型只看到"调用成功/失败"，领域实体只知道能力标签——编排细节被封装在执行入口里。

## 60.3 实现步骤

### 60.3.1 结果缓存：key 里的每个字段都不是装饰

`tool_cache.py` 是一个纯内存 LRU+TTL 缓存（默认 256 条、TTL 300 秒）。真正的决策在 key 的生成上：

```python
@staticmethod
def build_key(tool_name, arguments, *, version: str = "1.0.0") -> str:
    body = json.dumps(
        {"tool": tool_name, "version": version, "arguments": arguments},
        sort_keys=True, ensure_ascii=False, separators=(",", ":"), default=str,
    ).encode("utf-8")
    return f"toolcache:{hashlib.sha256(body).hexdigest()}"
```

三个设计点：

- **`sort_keys=True`**：`{"a": 1, "b": 2}` 和 `{"b": 2, "a": 1}` 必须是同一个 key。模型的 function call 参数顺序不保证稳定，不排序的话命中率会被参数顺序的偶然差异打成零。
- **`version` 进 key**：工具实现升级（字段含义变了、输出结构变了）后，旧缓存自动失效，不需要运维手动清缓存。
- **哪些工具允许缓存，key 层管不了**——这是工具定义层的事。`ToolDefinition` 上声明 `cacheable=True` 且必须是低风险 + 幂等才能进缓存；写文件、发请求这类有副作用的工具天然不满足。缓存"能不能存"和"存成什么 key"是两层决策，分开了才安全。

线程安全的取舍值得说：这个缓存面向单事件循环的协程场景，`get`/`put` 之间没有 await 点，不需要加锁。多进程部署时它是进程私有的——这是接受的：缓存是加速器不是事实源，命中率低一点不影响正确性，换来的是零基础设施依赖。

### 60.3.2 依赖分批：能力标签 + 拓扑排序

工具通过 `ToolDefinition` 的 `provides` / `requires` 声明能力标签（capability tags，如 `web_content`、`file_path`、`page_opened`）。`tool_deps.py` 的 `plan_parallel_batches` 做一件事：把一轮调用拓扑排序成批次。

```python
def plan_parallel_batches(calls: list[ToolCall]) -> list[list[ToolCall]]:
    ...
    # tag -> 提供该 tag 的调用下标
    providers: dict[str, list[int]] = {}
    for index, call in enumerate(calls):
        for tag in call.provides:
            providers.setdefault(tag, []).append(index)
    # 下标 -> 必须先于它执行的下标集合（只统计列表内的依赖边）
    depends_on: list[set[int]] = [set() for _ in calls]
    for index, call in enumerate(calls):
        for tag in call.requires:
            for provider in providers.get(tag, ()):
                if provider != index:
                    depends_on[index].add(provider)
    ...
```

关键取舍是**只统计列表内的依赖边**：调用 B `requires "page_opened"`，但本轮列表里没有任何调用 `provides "page_opened"`——视为外部已满足（比如上一步的浏览器状态留下来的），不构成本轮内的排序约束。这一条让工具可以跨轮次协作，而不是每轮都要求"打开页面"和"截图"必须成对出现。

批次内无相互依赖，调用方用 `asyncio.gather` 并行执行；批间串行等待。发现循环依赖时抛 `ToolDependencyError` 并**附带环路径**（DFS 三色标记找环，如 `search -> scrape -> search`）——标签是人工声明的，声明错成环是真实会发生的事，报错里必须直接指出是哪几个标签转圈，否则排查全靠猜。

### 60.3.3 重试与降级：先判定值不值得重试

`tool_resilience.py` 的第一层是 `is_retryable_error`——这一步比重试本身更重要，因为**重试参数类错误是纯浪费**：

```python
def is_retryable_error(error: BaseException) -> bool:
    if isinstance(error, AppException):
        if error.error_type == ErrorType.timeout:
            return True
        if error.status_code in (408, 429) or error.status_code >= 500:
            return True
        return False
    if isinstance(error, (ValueError, KeyError, TypeError)):
        return False                          # 参数类错误，永不重试
    if isinstance(error, (TimeoutError, ConnectionError, socket.timeout)):
        return True
    return is_retryable_error_text(str(error)) # 兜底：按错误文本关键词
```

规则很直白：4xx 参数类错误重试一百次也是 4xx，立即失败；超时、5xx、408/429 是"系统暂时不行"，值得等一等。429（限流）被划进可重试一侧——它的语义本来就是"稍后再试"。

第二层是指数退避：`retry_delay(attempt) = base * factor^(attempt-1)`，默认 base 1.5 秒、factor 2.0、最多重试 2 次——总等待 1.5s + 3s = 4.5s，给网络抖动留了窗口，又不至于让一次失败的调用阻塞步骤 30 秒。每次重试前产生一个 `RetryEvent`（attempt、delay、错误摘要）进 `retry_events`，ToolRuntime 把它写进审计——"这次结果为什么比平时慢了 4 秒"在审计里一行就能查到。

第三层是 fallback：重试耗尽后若提供了 `fallback` 可调用对象，调用它产出降级结果并标记 `fell_back=True`；没提供则重新抛出最后一个错误，由上层决定是否切换到 `AgentTool.fallback_tool` 声明的替代工具。**降级结果和真实结果的区分靠 `fell_back` 标记**——模型不应该把降级产物当权威事实，审计也不该把它和正常成功混在一起。

### 60.3.4 预算：超限时回喂结果，不抛异常

`tool_budget.py` 管三个维度：单步总调用次数（默认 12）、单工具单步次数（默认 4）、工具输出累计 token 估算（默认 10 万）。token 用 `ceil(len(text) / 2)` 粗估——中英文混合的保守值，不引 tokenizer，误差在预算场景可接受。

最反直觉的设计在超预算时：

```python
def build_exceeded_result(self, tool_name, check, arguments) -> ToolCallResult:
    payload = {
        "budget_exceeded": True,
        "reason": check.reason,
        "detail": check.detail,
        "suggestion": "请停止调用工具，基于已获得的结果直接给出本步骤的结论。",
    }
    return ToolCallResult(tool_name=tool_name, ..., status=ToolInvocationStatus.failed,
                          audit={"budget_exceeded": check.reason, "budget": self.to_audit()})
```

**不抛异常，返回一个结构化的 failed 结果回喂给模型**。为什么？抛异常意味着步骤中断、任务挂起，用户看到的是"出错了"——但预算超限不是错误，是"该收手了"的信号。回喂结构化 JSON 后，模型能解析 `reason` 和 `suggestion`，自己决定基于已有结果收尾，步骤正常结束。把"管束"表达成"信息"，让概率性的调用方参与管束，而不是被管束打断。

另外两个细节：**失败调用也记账**（`record_call` 对失败同样计数——失败的调用消耗了模型的轮次，不记账等于给失败调用开绿灯）；**预算对象生命周期是单步骤**，每个 `run_step` 新建实例，额度不跨步骤泄漏。

## 60.4 本章小结

本章给工具执行层装了四个阀门：**缓存**用带版本号的规范化 key 拦掉重复调用，只放行低风险幂等工具；**依赖分批**用能力标签 + 拓扑排序让该并行的并行、该串行的串行，环依赖直接报出路径；**韧性**用"先判可重试性、再指数退避、最后降级标记"三层结构吸收网络抖动；**预算**用三维度限额管住单步调用量，超限时回喂结构化结果让模型自己收尾而不是抛异常打断任务。

四个模块都是纯 domain 层实现，不依赖数据库和网络，由 ToolRuntime / StepAgentLoop 在执行入口接线——执行层的复杂性被挡在了模型视野之外。

至此，RAG 的检索增强、记忆的生命周期治理、工具的执行层管控三条线的核心机制全部落地。这四章是这轮升级的收尾，也是这套系统从"能跑"走向"跑得久"的底盘。
