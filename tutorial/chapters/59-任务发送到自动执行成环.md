### 59.6.1 确认后端统一流式入口

​        打开 `api/app/presentation/http/routes/sessions.py`，确认存在：

```Python
@router.post("/{session_id}/messages/stream")
async def stream_message(
    session_id: UUID,
    payload: MessageCreateRequest,
    runner: AgentRunnerService = Depends(build_agent_runner_service),
) -> StreamingResponse:
    async def event_stream():
        # ===================== 第1步：Runner 统一产出 SSE 需要的状态和事件 =====================
        async for item in runner.stream_user_message(
            session_id=session_id,
            content=payload.content,
        ):
            yield encode_sse(item.name, to_runner_stream_payload(item))

    return StreamingResponse(
        event_stream(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",
        },
    )
```

#### 59.6.1.1 这段代码在流程中的位置

​        这是前端发送任务时调用的唯一主入口。

​        它不是普通 `POST JSON -> 返回 JSON` 接口，而是 SSE 流式接口。前端请求发出后，连接不会马上关闭，后端会不断推送事件：

```Plain
session_status
message_created
plan_created
step_started
tool_called
step_completed
task_done
stream_done
```

#### 59.6.1.2 输入和输出

​        输入：

​        换句话说，第一，`session_id`：当前会话 ID；第二，`payload.content`：用户在输入框里写的任务内容。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        输出：

​        从实现顺序看，第一，一串 SSE 事件；第二，每条事件都有 `event` 名称和 JSON 数据。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

#### 59.6.1.3 为什么这样设计

​        Agent 任务不是一次普通请求。

​        如果使用普通 JSON 接口，前端只能等任务全部结束后一次性显示结果。这样用户看不到执行过程，也无法知道 Agent 当前正在搜索、浏览网页、执行 Shell，还是等待工具返回。

​        SSE 更适合本项目当前阶段：

​        放到工程语境里看，第一，浏览器原生支持；第二，比 WebSocket 更简单；第三，适合服务端单向推送任务过程；第四，能和 Nginx 网关自然配合。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

### 59.6.2 理解 Runner 自动闭环

​        打开 `api/app/application/agent_runner_service.py`，关注 `stream_user_message()`。

​        核心流程如下：

```Python
async def stream_user_message(
    self,
    *,
    session_id: UUID,
    content: str,
):
    """把用户消息转换成可流式观察的 Agent 执行过程。"""

    # 1. 会话先进入 running，前端可以立即展示任务开始。
    running_session = await self.session_service.mark_running(session_id)
    yield AgentRunnerStreamItem(
        name="session_status",
        payload=running_session,
    )

    # 2. 写入用户消息，并把 message_created 推给前端时间线。
    message, message_event = await self.session_service.create_user_message(
        session_id=session_id,
        content=content,
    )
    yield AgentRunnerStreamItem(
        name=message_event.type.value,
        payload=message_event,
    )

    # 3. 生成计划。Planner 内部会读取上下文快照和长期记忆。
    _plan, plan_event = await self.planner_service.create_plan(
        session_id=session_id,
        task=content,
    )
    yield AgentRunnerStreamItem(
        name=plan_event.type.value,
        payload=plan_event,
    )

    # 4. 执行计划。ReAct 内部会持续写 step/tool/task 事件。
    async for event in self.react_service.stream_latest_plan(session_id):
        yield AgentRunnerStreamItem(
            name=event.type.value,
            payload=event,
        )

    # 5. 推送最终会话状态和 stream_done，前端据此收尾 loading 状态。
    final_session = await self.session_service.get_session(session_id)
    yield AgentRunnerStreamItem(
        name="session_status",
        payload=final_session,
    )
    yield AgentRunnerStreamItem(
        name="stream_done",
        payload={
            "session_id": str(session_id),
            "message_id": str(message.id),
            "message": {
                "id": str(message.id),
                "session_id": str(message.session_id),
                "role": message.role.value,
                "content": message.content,
                "created_at": message.created_at.isoformat(),
            },
        },
    )
```

#### 59.6.2.1 这段代码在流程中的位置

​        `AgentRunnerService` 是本章的核心业务编排层。

​        调用链路是：

```Plain
Route -> AgentRunnerService -> SessionService
                         -> PlannerService
                         -> ReActAgentService
```

#### 59.6.2.2 关键代码逐段解释

​        第一段先把会话标记为 `running`。前端收到 `session_status` 后，就可以显示“正在执行任务”。

​        第二段写入用户消息。这里不只是保存聊天内容，还会写入 `message_created` 事件。前端时间线依赖事件来统一展示过程。

​        第三段调用 Planner 生成计划。这个计划会变成 `plan_created` 事件，前端根据它渲染步骤列表。

​        第四段调用 ReAct 执行计划。每个步骤开始、工具调用、步骤完成、任务完成都会写成事件，再通过 SSE 推给前端。

​        第五段发送 `stream_done`。这个事件告诉前端本次流结束，可以关闭 loading，并刷新会话列表和上下文。

#### 59.6.2.3 小白最容易困惑的点

​        `stream_user_message()` 不是“只发送消息”。

​        它代表一次完整 Agent 任务：

```Plain
消息 -> 计划 -> 执行 -> 工具 -> 总结
```

​        所以前端主流程只需要调用它，不需要再单独调用 `/{session_id}/plan` 或 `/{session_id}/plan/execute`。

### 59.6.3 让前端 store 只调用流式入口

​        打开 `ui/app/stores/session-store.ts`，确认 `sendMessage()` 中使用的是 `streamMessage()`。

​        核心代码如下：

```TypeScript
sendMessage: async () => {
  const sessionId = get().selectedSessionId;
  const content = get().draft.trim();
  if (!sessionId) {
    set({ actionError: "请先选择一个会话" });
    return;
  }
  if (!content) {
    set({ actionError: "请输入消息内容" });
    return;
  }

  set({
    actionError: null,
    currentTask: null,
    executingPlan: false,
    latestPlan: null,
    planning: true,
    sendingMessage: true,
  });
  try {
    set({ draft: "" });
    // ===================== 第1步：通过统一 SSE 发送任务并接收执行过程 =====================
    // 后端会依次推送 message_created、plan_created、step/tool/task 事件。
    await streamMessage(sessionId, content, async (event) => {
      await sleep(getPresentationDelay(event.event));
      const session = toSessionItem(event);
      if (session) {
        set((state) => ({
          sessions:
            state.sessions.type === "ready"
              ? {
                  type: "ready",
                  data: updateSession(state.sessions.data, session),
                }
              : state.sessions,
        }));
      }

      const sessionEvent = toSessionEventItem(event);
      if (!sessionEvent) {
        return;
      }
      set((state) => {
        const currentEvents =
          state.events.type === "ready" ? state.events.data : [];
        const events = [...currentEvents, sessionEvent];
        const currentMessages =
          state.messages.type === "ready" ? state.messages.data : [];
        const streamMessageItem = toChatMessageItem(sessionEvent);
        const messages =
          streamMessageItem &&
          !currentMessages.some((message) => message.id === streamMessageItem.id)
            ? [...currentMessages, streamMessageItem]
            : currentMessages;
        const latestPlan = applyExecutionEvents(getLatestPlan(events), events);
        return {
          events: {
            type: "ready",
            data: events,
          },
          executingPlan:
            sessionEvent.type === "task_done" ||
            sessionEvent.type === "task_error"
              ? false
              : state.executingPlan || sessionEvent.type === "plan_created",
          latestPlan,
          messages: {
            type: "ready",
            data: messages,
          },
          planning:
            sessionEvent.type === "plan_created" ? false : state.planning,
        };
      });
    });
    await Promise.all([
      get().loadSessionDetail(sessionId),
      get().refreshSessions(),
      get().loadSessionContext(sessionId),
    ]);
  } catch (error) {
    set({ actionError: getErrorMessage(error) });
  } finally {
    set({
      executingPlan: false,
      planning: false,
      sendingMessage: false,
    });
  }
}
```

#### 59.6.3.1 这段代码在流程中的位置

​        这是前端任务发送的状态管理入口。

​        调用链路是：

```Plain
ChatInput -> onSend -> workspace.sendMessage -> streamMessage -> SSE -> store
```

#### 59.6.3.2 输入和输出

​        输入：

​        展开来看，第一，`selectedSessionId`：当前会话；第二，`draft`：输入框里的任务文本。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        输出：

​        具体来说，第一，更新 `messages`；第二，更新 `events`；第三，更新 `latestPlan`；第四，更新 `planning` 和 `executingPlan`；第五，刷新会话列表和上下文。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

#### 59.6.3.3 为什么这样设计

​        前端不直接拼装“假步骤”。

​        步骤、工具、任务结果都来自后端事件。这样后续接搜索、浏览器、Shell、文件、MCP、A2A、多 Agent 时，前端只需要继续消费统一事件流，不需要为每种工具写一条独立主流程。

#### 59.6.3.4 本章保留的小节奏延迟

​        `getPresentationDelay()` 会给不同事件加一点展示节奏。

​        这不是伪造执行结果，而是避免本地开发环境中后端太快，浏览器一次性把所有事件刷出来，用户完全看不到“任务正在推进”的过程。

## 59.7 关键理解

​        本章最重要的是“主路径只有一条”。

```Plain
sendMessage -> streamMessage -> AgentRunnerService.stream_user_message
```

​        旧接口仍然可以保留：

```Plain
POST /api/sessions/{session_id}/plan
POST /api/sessions/{session_id}/plan/execute
POST /api/sessions/{session_id}/plan/tasks
```

​        但它们是调试、兼容和后台任务能力，不是首页主流程。

## 59.11 常见问题

- 问题：为什么页面上找不到“生成计划”按钮？

​        解释：这是本章的目标。生成计划已经进入 `sendMessage -> streamMessage -> Runner` 主链路，不再作为用户要手动点击的按钮。

- 问题：发送后还是一次性全部出来怎么办？

​        解释：先确认请求走的是 `/messages/stream`，而不是普通 `/messages`。如果后端执行太快，本地可能看起来接近一次性输出；第 60 章会继续优化步骤卡片的流式节奏和展开方式。

- 问题：为什么首页不再加载 MCP、A2A、多 Agent 面板？

​        解释：这些属于设置和工具详情，不应该常驻在主对话区。任务真的调用到对应工具时，结果会通过工具节点和右侧详情展示。

- 问题：这是不是已经完全最终 UI？

​        解释：不是。本章完成主流程闭环。第 60 章整理步骤卡片，第 61 章整理右侧详情抽屉，第 62 章做最终清理、文件任务和发布验收。
