.1.6.3.1 字段含义

​        从实现顺序看，第一，`TimelineItem`：页面时间线的统一条目。它把消息和计划事件放进同一个列表，方便按时间排序展示；第二，`StepView`：前端真正展示的步骤结构。它不是后端原始 `PlanStep`，而是在 `PlanStep` 基础上补充了开始时间、完成时间、工具事件和摘要；第三，`MultiAgentInlineResult`：多 Agent 工具输出的前端解析结果。步骤卡片和最终回答都会读取它；第四，`AgentRunViewModel`：`ConversationTimeline` 最终需要的数据结构。入口组件拿到它之后，只需要负责渲染。这些点放在一起看，构成了本节叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

#### 33.1.6.4 抽出 view-model 转换逻辑

​        创建 `frontend/web/app/components/conversation/view-model.ts`。

​        这个文件负责把后端消息和事件转换成前端展示模型。

​        核心职责有三个：

​        放到工程语境里看，第一，构建时间线条目；第二，根据事件更新步骤状态；第三，解析工具输出中的多 Agent 结果。这些点放在一起看，构成了本节叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

```TypeScript
export function buildAgentRunViewModel(
  messages: ChatMessage[],
  events: SessionEventItem[],
  plan: AgentPlan | null,
): AgentRunViewModel {
  const timelineItems = buildTimelineItems(messages, events);
  const latestPlan = plan ?? getLatestPlanFromEvents(events);
  const finalEvent =
    [...events]
      .reverse()
      .find((event) => event.type === "task_done" || event.type === "task_error") ??
    null;

  return {
    finalEvent,
    latestPlan,
    timelineItems,
  };
}
```

.1.6.4.1 这段代码在流程中的位置

​        调用链路是：

```Plain
useSessionStore
  |
  | messages / events / latestPlan
  v
ConversationTimeline
  |
  v
buildAgentRunViewModel()
  |
  v
AgentRunBlock / MessageBubble / StepCard
```

​        也就是说，`view-model.ts` 是 store 和组件之间的转换层。

​        store 不需要知道页面具体怎么画。

​        组件也不需要自己到处解析事件。

.1.6.4.2 为什么这样设计

​        后端事件是业务事实：

```Plain
plan_created
step_started
tool_called
step_completed
task_done
```

​        前端展示需要的是 UI 状态：

```Plain
哪个步骤 running
哪个步骤 completed
哪个步骤绑定了工具事件
最终回答是什么
```

​        这两者不是同一个东西。

​        把转换逻辑抽到 `view-model.ts`，后续本章后文做动画和状态回放时，只需要扩展这一层，不需要在 JSX 里到处加判断。

#### 33.1.6.6 收敛 ConversationTimeline 入口

​        修改 `frontend/web/app/components/conversation-timeline.tsx`。

​        重构后，它只做五件事：

1. 处理 loading。
2. 处理 error。

4. 调用 `buildAgentRunViewModel()`。
5. 组合消息、计划块和步骤详情弹层。

```TypeScript
export function ConversationTimeline({
  events,
  messages,
  onSelectToolEvent,
  plan,
  planning,
  executing,
  selectedToolEventId,
  task,
}: ConversationTimelineProps) {
  const [detailStep, setDetailStep] = useState<StepView | null>(null);

  if (messages.type === "loading" || events.type === "loading") {
    return <TimelineLoadingState />;
  }

  if (messages.type === "error") {
    return <ErrorBlock message={messages.message} />;
  }

  if (events.type === "error") {
    return <ErrorBlock message={events.message} />;
  }

  const viewModel = buildAgentRunViewModel(messages.data, events.data, plan);

  if (viewModel.timelineItems.length === 0) {
    return <TimelineEmptyState />;
  }

  return (
    <>
      <div className="flex-1 overflow-y-auto px-8 py-8 max-md:px-4">
        <div className="mx-auto grid max-w-3xl gap-7">
          {viewModel.timelineItems.map((item) =>
            item.kind === "message" ? (
              <MessageBubble key={item.id} message={item.message} />
            ) : viewModel.latestPlan ? (
              <AgentRunBlock
                events={events.data}
                finalEvent={viewModel.finalEvent}
                key={item.id}
                onSelectToolEvent={onSelectToolEvent}
                onOpenStep={setDetailStep}
                plan={viewModel.latestPlan}
                planning={planning}
                selectedToolEventId={selectedToolEventId}
              />
            ) : null,
          )}
          <TaskStatusCard task={task} />
          {planning || executing ? (
            <RunningBlock
              text={
                planning
                  ? "正在理解任务并生成计划..."
                  : "正在执行计划并同步工具结果..."
              }
            />
          ) : null}
        </div>
      </div>
      {detailStep ? (
        <StepDetailDialog
          onClose={() => setDetailStep(null)}
          onSelectToolEvent={onSelectToolEvent}
          step={detailStep}
        />
      ) : null}
    </>
  );
}
```

### 33.1.7 关键理解

​        本节最重要的是理解“组件拆分不是按 UI 长相随便切”。

​        一个好的拆分应该回答三个问题：

```Plain
这个组件负责什么？
它从哪里拿数据？
它通过什么事件通知上层？
```

​        如果一个组件既解析事件、又维护弹层、又展示步骤、又处理工具输出，它就太重了。

​        第二个重点是理解 `view-model`。

​        后端给的是事件事实，前端要的是展示状态。中间需要一层转换逻辑。把这层放进 `view-model.ts`，比散落在 JSX 中更容易测试和维护。

​        第三个重点是设计 token 要克制。

​        本节不追求抽象所有 className，只抽最常重复、最能表达语义的样式。这样既能减少重复，又不会把 Tailwind 写法复杂化。

### 33.1.8 技术难点与亮点

​        技术难点：

​        从实现顺序看，第一，拆组件时不能改变 props 数据流；第二，拆 view-model 时不能改变事件排序和步骤状态判断；第三，设计 token 不能过度抽象，否则反而更难读；第四，重构后要确保 TypeScript 能发现漏掉的 import 和 props。这些点放在一起看，构成了本节叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        项目亮点：

#### 33.2.6.1 新增自动滚动 Hook

​        创建 `frontend/web/app/hooks/use-auto-scroll.ts`：

```TypeScript
import { useCallback, useEffect, useRef, useState } from "react";

type UseAutoScrollOptions = {
  threshold?: number;
  watchKey: string;
};

// ===================== 第1步：管理对话时间线的自动滚动状态 =====================
export function useAutoScroll({
  threshold = 96,
  watchKey,
}: UseAutoScrollOptions) {
  const bottomRef = useRef<HTMLDivElement | null>(null);
  const scrollRef = useRef<HTMLDivElement | null>(null);
  const [pinnedToBottom, setPinnedToBottom] = useState(true);

  const scrollToBottom = useCallback((behavior: ScrollBehavior = "smooth") => {
    bottomRef.current?.scrollIntoView({ behavior, block: "end" });
  }, []);

  const handleScroll = useCallback(() => {
    const element = scrollRef.current;
    if (!element) {
      return;
    }

    // ===================== 第2步：判断用户是否还停留在底部附近 =====================
    // 如果用户主动向上看旧步骤，就暂停自动滚动；否则新事件进入时继续贴底展示。
    const distanceToBottom =
      element.scrollHeight - element.scrollTop - element.clientHeight;
    setPinnedToBottom(distanceToBottom <= threshold);
  }, [threshold]);

  useEffect(() => {
    if (pinnedToBottom) {
      scrollToBottom("smooth");
    }
  }, [pinnedToBottom, scrollToBottom, watchKey]);

  return {
    bottomRef,
    handleScroll,
    pinnedToBottom,
    scrollRef,
    scrollToBottom,
  };
}
```

.2.6.1.1 代码讲解

​        这段代码做了三件事。

​        第一，`scrollRef` 指向真正滚动的容器。

```TypeScript
const scrollRef = useRef<HTMLDivElement | null>(null);
```

​        第二，`bottomRef` 指向时间线最底部的一个空节点。

```TypeScript
const bottomRef = useRef<HTMLDivElement | null>(null);
```

​        滚动到底部时，不直接计算 `scrollTop`，而是让底部节点进入视口：

```TypeScript
bottomRef.current?.scrollIntoView({ behavior, block: "end" });
```

​        第三，`pinnedToBottom` 表示当前是否还贴着底部。

​        用户向上滚动时，`distanceToBottom` 会变大。只要超过 `threshold`，前端就认为用户正在查看历史内容，暂停自动滚动。

.2.6.1.2 为什么需要 watchKey

​        `watchKey` 是外部传进来的变化标记。

​        对话时间线会把消息数量、事件数量、计划 ID、任务状态拼成一个字符串。只要这些内容变化，`useEffect` 就会触发一次。

```Plain
消息数量变化 -> 可能有新消息
事件数量变化 -> 可能有新步骤或工具结果
任务状态变化 -> 可能完成、失败或停止
```

​        这样 hook 不需要知道业务细节，只负责滚动行为。

}

function getPresentationDelay(eventName: string) {
  // ===================== 第1步：给不同事件留出可感知的展示节奏 =====================

  if (eventName === "step_started") {
    return 560;
  }
  if (eventName === "tool_called") {
    return 720;
  }
  if (eventName === "step_completed") {
    return 460;

.2.6.8.1 为什么现在就补这些状态

### 33.2.7 关键理解

​        本节最重要的是理解“流式体验”和“真实流式能力”的区别。

​        后端已经通过 SSE 推送事件，这是数据层的流式。

​        前端还需要把这些事件变成用户能理解的节奏，这是体验层的流式。

```Plain
数据流式：事件一条条到达
体验流式：用户一眼能看懂 Agent 正在做什么
```

​        第二个重点是不要展示隐藏推理。

​        本节展示的是任务执行过程：

```Plain
计划
步骤
工具
结果
```

​        不是展示模型内部不可见的推理文本。

​        第三个重点是尊重用户阅读。

​        自动滚动不是永远滚动。用户主动上滑，就说明用户正在阅读历史内容。此时要暂停自动滚动，让用户自己决定什么时候回到底部。

### 33.2.8 技术难点与亮点

​        技术难点：

​        换句话说，第一，SSE 事件来得很快，前端需要控制展示节奏；第二，消息、事件和计划来自不同状态，需要避免重复插入；第三，自动滚动要兼顾最新进度和历史阅读；第四，当前步骤高亮不能在任务结束后继续误导用户；第五，步骤折叠不能影响打开详情和工具预览。这些点放在一起看，构成了本节叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        项目亮点：

​        从实现顺序看，第一，对话区更像真实任务执行工作台；第二，用户消息能在 `message_created` 到达时立即出现；第三，当前步骤会自动展开并高亮；第四，长任务可以暂停自动滚动再回到底部；第五，状态体系开始覆盖等待、重试、停止等复杂任务状态。这些点放在一起看，构成了本节叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

### 33.2.9 面试考点

​        放到工程语境里看，第一，SSE 已经能流式推送，为什么前端还要做展示节奏？；第二，自动滚动为什么不能简单地每次都滚到底部？；第三，如何避免流式事件重复插入消息列表？；第四，为什么最终仍然要重新加载数据库结果？；第五，AI 产品中“执行过程展示”和“隐藏推理内容”有什么区别？。这些点放在一起看，构成了本节叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。
