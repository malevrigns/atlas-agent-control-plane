## 58.3 本章要解决的问题

​        第 30 章已经加入了 `SearchTool`，并设计了两种模式：

```Plain
有 BING_SEARCH_API_KEY -> 调用官方 Bing Search API
没有 BING_SEARCH_API_KEY -> 抓取 Bing 搜索结果页
```

​        但是之前的页面搜索降级实现比较轻，只用 Python 标准库 `HTMLParser` 识别：

```Plain
li.b_algo
h2 > a
p
```

​        真实 Bing 页面会因为地区、语言、浏览器 User-Agent、A/B 实验和验证码策略返回不同结构。结果是：工具被调用了，但解析不到结果，前端看起来像搜索失败。

​        本章把无 Key 搜索降级改成更稳的版本：

```Plain
请求 Bing 搜索页
  |
  v
使用 BeautifulSoup 解析 HTML
  |
  v
多路径提取标题、链接、摘要
  |
  v
返回统一 search_results JSON
```

#### 58.6.1.1 为什么使用 BeautifulSoup

​        搜索结果页不是稳定 API。

​        如果继续用标准库 `HTMLParser` 手写状态机，代码会很脆弱：

```Plain
进入 li -> 进入 a -> 收集标题 -> 进入 p -> 收集摘要
```

​        只要页面结构变成：

```HTML
<div class="b_caption">
  <p>摘要内容</p>
</div>
```

​        或者标题不在 `h2` 里，解析就容易失败。

​        BeautifulSoup 更适合这种 HTML 页面解析。它可以用 CSS 选择器查找元素，也可以在结构变化时增加兜底逻辑。

def _is_bing_challenge_page(html: str) -> bool:
    """判断 Bing 是否返回验证码或验证页面。"""

    lower_html = html.lower()
    return (
        "captcha" in lower_html
        or "unusual traffic" in lower_html
        or "verify you are a human" in lower_html

​        验证码页不是搜索结果页。

### 58.6.4 使用 BeautifulSoup 解析搜索结果

​        新增 `_parse_bing_results()`：

```Python
def _parse_bing_results(html: str) -> list[SearchResult]:
    """从 Bing 搜索结果页中解析自然结果。

    Bing 搜索页不是稳定 API，页面结构可能因为地区、登录状态或 A/B
    实验变化。这里参考真实 Agent 项目常用做法，不只依赖单一 DOM
    路径，而是按“结果块 -> 标题链接 -> 摘要文本”的顺序做多层兜底。
    """

    soup = BeautifulSoup(html, "html.parser")
    results: list[SearchResult] = []

    # ===================== 第1步：定位 Bing 自然搜索结果块 =====================
    # 常规结果一般在 li.b_algo 中。这里保留 CSS 选择器，后续如果 Bing
    # DOM 变化，只需要补充选择器，不影响上层 SearchTool。
    for item in soup.select("li.b_algo"):
        if not isinstance(item, Tag):
            continue

        # ===================== 第2步：提取标题和链接 =====================
        # 首选 h2 > a，这是 Bing 自然结果最常见结构。
        title = ""
        url = ""
        title_link = item.select_one("h2 a")
        if isinstance(title_link, Tag):
            title = _clean_text(title_link.get_text(" ", strip=True))
            url = str(title_link.get("href") or "")

        # 如果 h2 缺失，退化为寻找结果块中第一个“像标题”的链接。
        # 这能覆盖部分特殊卡片或区域差异导致的结构变化。
        if not title:
            for link in item.find_all("a"):
                if not isinstance(link, Tag):
                    continue
                text = _clean_text(link.get_text(" ", strip=True))
                href = str(link.get("href") or "")
                if len(text) > 10 and href:
                    title = text
                    url = href
                    break

        if not title or not url:
            continue

        # ===================== 第3步：提取摘要 =====================
        # Bing 的摘要可能在 p、b_caption、b_descript、b_lineclamp 等位置。
        snippet = _extract_snippet(item, title)
        results.append(
            SearchResult(
                title=title,
                url=_normalize_bing_url(url),
                snippet=snippet,
            )
        )

    return results
```

#### 58.6.4.1 代码讲解

​        这段代码分三步。

​        第一步，找到结果块：

```Python
soup.select("li.b_algo")
```

​        Bing 的自然搜索结果通常放在 `li.b_algo` 中。我们只解析自然结果，不解析广告、侧边栏和推荐问题。

​        第二步，提取标题和链接。

​        首选：

```Python
h2 a
```

​        如果没有 `h2`，就遍历结果块里的 `a` 标签，找一个文本较长、链接存在的元素作为标题。

​        第三步，提取摘要。

​        摘要不一定在同一个位置，所以交给 `_extract_snippet()` 继续兜底。

def _extract_snippet(item: Tag, title: str) -> str:
    """从一个搜索结果块中提取摘要文本。"""

    # 1. 优先找 Bing 常见的摘要容器。
    snippet_selector = (
        ".b_caption p, .b_caption, .b_descript, .b_lineclamp, p"

def _clean_text(value: str) -> str:
    """压缩空白字符，避免前端摘要出现奇怪换行。"""

    return re.sub(r"\s+", " ", value).strip()

#### 58.6.5.1 为什么要拆成辅助函数

​        搜索结果解析看起来只是几行 HTML 处理，但实际会不断遇到边界情况：

```Plain

链接是相对路径
文本里有很多换行
标题和摘要重复
```

​        拆成辅助函数后，每个函数只处理一个问题：

​        具体来说，第一，`_extract_snippet()`：负责找摘要；第二，`_normalize_bing_url()`：负责整理链接；第三，`_clean_text()`：负责清洗文本；第四，`_is_bing_challenge_page()`：负责识别验证页。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

## 58.7 关键理解

​        本章最重要的是理解：

```Plain
不配置 API Key 也能搜索
```

​        不等于：

```Plain
不需要搜索服务
```

​        无 Key 搜索本质上是在请求 Bing 搜索结果页，然后解析 HTML。它适合课程、本地开发和低成本验证，但稳定性永远不如官方 API 或专门的搜索服务。

​        所以本项目最终保留两条路：

```Plain
有 Key：走官方 Bing Web Search API
无 Key：走 Bing 页面搜索降级
```

​        这样既方便本地学习，又保留生产扩展空间。

## 58.11 常见问题

- 问题：没有 `BING_SEARCH_API_KEY`，为什么还能搜索？

​        解释：这是页面搜索降级方案。后端请求 `https://www.bing.com/search`，再解析 HTML 中的自然搜索结果。

- 问题：为什么之前不配 Key 时搜索结果为空？

​        解释：之前只用标准库 `HTMLParser` 识别少量 DOM 结构。Bing 根据请求头返回的页面结构不同，解析器可能找不到 `li.b_algo` 或摘要节点。

- 问题：为什么本章不直接配置官方 Bing API Key？

​        解释：课程环境不应该强依赖外部付费 Key。本章先保证无 Key 也能低成本验证，生产环境可以再配置官方或第三方搜索服务。

- 问题：返回 `bing page search returned a verification page` 怎么办？

​        解释：说明 Bing 返回了验证码或验证页面。可以稍后重试、切换网络，或者配置正式搜索 API Key。

- 问题：为什么前端不用改？

​        解释：工具输出仍然是 `kind=search_results`。前端只关心统一结构，不关心后端是官方 API 还是页面搜索降级。
