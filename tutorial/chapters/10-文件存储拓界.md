# 第十章. 文件存储拓界

## 10.1 本章目标
​        第 9 章已经把文件上传、会话文件和文本预览跑通了，但那时 `FileService` 同时负责业务流程和本地磁盘读写。早期这样写没有问题，因为先让功能成立最重要；可是一旦项目要接入 COS、S3、MinIO 这类对象存储，所有磁盘细节都留在应用服务里，就会让后续改造变得很重。
​        本章要做的是一次后端内部重构。用户看到的上传、列表、预览和下载能力保持不变，但文件内容的保存、读取、删除和路径判断会被抽到 `FileStorage` 协议里。`LocalFileStorage` 继续提供本地磁盘实现，工厂函数根据 `FILE_STORAGE_BACKEND` 创建具体存储对象。读者需要理解的是：文件元数据仍然属于数据库和 Repository，文件内容读写则交给存储层。

## 10.2 最终效果
​        本章结束后，页面功能和第 9 章保持一致：

```Plain
上传附件 -> 会话文件列表出现文件 -> 文本文件可以预览 -> 文件可以下载
```

​        但是后端文件结构发生变化：

```Plain
FileService
  |
  v
FileStorage 协议
  |
  v
LocalFileStorage
```

​        以前 `FileService` 直接使用 `Path.write_bytes()`、`Path.read_bytes()` 操作本地磁盘。
​        现在 `FileService` 只调用：

```Plain
storage.save()
storage.delete()
storage.exists()
storage.read_bytes()
storage.get_local_path()
```

​        也就是说，业务服务不再关心文件到底保存在本地磁盘、对象存储还是其他系统。

## 10.3 本章要解决的问题
​        第 12、13 章已经完成文件上传、会话文件列表和文本预览。
​        但是当前实现还有一个工程问题：本地磁盘操作写在 `FileService` 里。
​        这在早期没有问题，因为先让上传功能跑通最重要。
​        但项目继续发展后，会出现新需求：

```Plain
开发环境使用本地磁盘
生产环境使用对象存储
文件下载可能需要签名地址
文件预览可能需要从远程对象读取部分内容
上传失败时需要删除远程对象
```

​        如果所有存储细节都写在 `FileService`，以后切换存储方式时，上传、下载、预览、会话文件逻辑都要一起改。
​        所以本章要把“文件存储”单独抽出来。

## 10.4 本章技术方案
​        本章采用“协议 + 本地实现 + 工厂函数”的方案。
​        可选方案有三种：
​        一个选择是继续把本地磁盘逻辑放在 `FileService` 里，这样短期最省事，但会让业务服务越来越知道存储细节。另一个选择是直接接入对象存储，不过那会立刻引入密钥、桶名、地域、网络权限和签名下载等问题。课程在这里采用第三种方案：先抽象 `FileStorage`，保留本地实现，把边界整理清楚。
​        本章选择第三种。
​        原因是：
​        当前文件能力已经可以使用，因此不应该为了未来扩展而改动用户可见流程。抽象之后，`FileService` 继续编排上传、会话关系、数据库提交和异常清理；`FileStorage` 只处理文件内容。本地存储仍然保留，开发和验证方式不变。等后续真的接入对象存储时，只需要新增实现类和工厂分支，而不是重写会话文件业务。
​        重构后的调用关系：

```Plain
API Route
  |
  v
FileService
  |
  +-- UnitOfWork       负责数据库
  |
  +-- FileStorage      负责文件内容
        |
        v
      LocalFileStorage
```

​        本章会做这些内容：
​        本章会新增 `api/app/domain/files/storage.py` 定义协议和存储结果对象，新增 `api/app/infrastructure/storage/local.py` 实现本地存储，再通过 `api/app/infrastructure/storage/factory.py` 按配置创建存储实例。配置层会增加 `FILE_STORAGE_BACKEND`，`FileService` 会从直接调用 `Path.write_bytes()` 改成依赖 `FileStorage`。这些变化都发生在后端内部，现有文件接口保持不变。
​        本章暂时不做这些内容：
​        本章不会真正接入 COS、S3 或 MinIO，也不会修改数据库表结构、前端页面、图片预览和文件删除接口。这里先把接口边界抽出来，让后续扩展有位置可放，而不是在功能还不稳定时一次性引入太多外部依赖。

### 10.6.2 定义 FileStorage 协议
​        创建 `api/app/domain/files/storage.py`：

```Python
from dataclasses import dataclass
from pathlib import Path
from typing import Protocol

@dataclass(slots=True)
class StoredFile:
    stored_name: str
    storage_path: str

class FileStorage(Protocol):
    def save(self, clean_name: str, content: bytes) -> StoredFile:
        raise NotImplementedError

    def delete(self, storage_path: str) -> None:
        raise NotImplementedError

    def exists(self, storage_path: str) -> bool:
        raise NotImplementedError

    def read_bytes(self, storage_path: str, max_size: int | None = None) -> bytes:
        raise NotImplementedError

    def get_local_path(self, storage_path: str) -> Path:
        raise NotImplementedError
```

​        这段代码的业务流程：

```Plain
FileService 想保存文件
  |
  v
调用 FileStorage.save()
  |
  v
得到 StoredFile
  |
  v
把 stored_name 和 storage_path 写入数据库
```

​        `StoredFile` 是存储层返回给业务层的结果。
​        它有两个字段：
​        `stored_name` 是存储层真正使用的文件名，通常由 UUID 和原始后缀组合而成，用来避免同名文件互相覆盖；`storage_path` 是后续读取、下载和删除时需要使用的存储位置。对本地存储来说，它是一个文件路径；对对象存储来说，将来可以变成对象 key。
​        为什么要有 `FileStorage` 协议？
​        因为 `FileService` 只需要知道“能保存、能删除、能读取、能判断是否存在”。它不应该知道本地磁盘如何创建目录，也不应该知道对象存储如何生成 key。
​        这里的 `get_local_path()` 是当前阶段为了配合 FastAPI 的 `FileResponse`。
​        本地存储可以返回一个真实路径。对象存储不一定有本地路径，后续接入对象存储时，下载接口可能会改成重定向签名 URL 或流式响应。

### 10.6.3 实现本地存储类
​        创建 `api/app/infrastructure/storage/local.py`：

```Python
from pathlib import Path
from uuid import uuid4

from app.domain.files.storage import FileStorage, StoredFile

class LocalFileStorage(FileStorage):
    def __init__(self, upload_root: str) -> None:
        self.upload_root = Path(upload_root)

    def save(self, clean_name: str, content: bytes) -> StoredFile:
        stored_name = self._build_stored_name(clean_name)
        storage_path = self.upload_root / stored_name
        self.upload_root.mkdir(parents=True, exist_ok=True)
        storage_path.write_bytes(content)
        return StoredFile(
            stored_name=stored_name,
            storage_path=str(storage_path),
        )

    def delete(self, storage_path: str) -> None:
        Path(storage_path).unlink(missing_ok=True)

    def exists(self, storage_path: str) -> bool:
        return Path(storage_path).is_file()

    def read_bytes(self, storage_path: str, max_size: int | None = None) -> bytes:
        if max_size is None:
            return Path(storage_path).read_bytes()
        # 预览只需要读取文件开头；本地文件可以直接按字节数读取。
        with Path(storage_path).open("rb") as file:
            return file.read(max_size)

    def get_local_path(self, storage_path: str) -> Path:
        return Path(storage_path)

    @staticmethod
    def _build_stored_name(filename: str) -> str:
        suffix = Path(filename).suffix
        return f"{uuid4().hex}{suffix}"
```

​        这段代码的业务流程：

```Plain
LocalFileStorage.save()
  |
  +-- 生成随机文件名
  +-- 创建上传目录
  +-- 写入文件内容
  +-- 返回 stored_name 和 storage_path
```

​        为什么文件名要重新生成？
​        因为用户上传的原始文件名可能重复。
​        例如两个用户都上传：

```Plain
README.md
```

​        如果直接用原始文件名保存，后上传的文件可能覆盖先上传的文件。
​        这里保留原始后缀，是为了让本地排查时还能大概看出文件类型。
​        代码里这条注释是有必要的：

```Python
# 预览只需要读取文件开头；本地文件可以直接按字节数读取。
```

​        它解释的是读取边界，不是把代码翻译成中文。预览不需要读取整个文件，所以 `max_size` 会影响实际读取量。

### 10.6.4 创建存储工厂函数
​        创建 `api/app/infrastructure/storage/factory.py`：

```Python
from app.core.config import settings
from app.core.exceptions import AppException
from app.domain.files.storage import FileStorage
from app.infrastructure.storage.local import LocalFileStorage

def build_file_storage() -> FileStorage:
    if settings.file_storage_backend == "local":
        return LocalFileStorage(settings.upload_dir)

    # 这里先明确失败，避免配置了未实现的对象存储后静默写入本地目录。
    raise AppException(
        message=f"unsupported file storage backend: {settings.file_storage_backend}",
        code=500,
        status_code=500,
    )
```

​        这段代码的业务流程：

```Plain
FileService 初始化
  |
  v
build_file_storage()
  |
  +-- local -> LocalFileStorage
  |
  +-- 其他值 -> 明确报错
```

​        为什么不在配置错误时自动退回本地存储？
​        因为文件存储是重要数据路径。
​        如果生产环境本来想用对象存储，但因为配置写错，系统悄悄把文件写到容器本地目录里，后果会很严重。容器重建后文件可能丢失。
​        所以这里选择“明确失败”，让问题尽早暴露。

### 10.6.5 改造 FileService 初始化
​        打开 `api/app/application/file_service.py`，把初始化改成：

```Python
class FileService:
    def __init__(self, uow: UnitOfWork, storage: FileStorage | None = None) -> None:
        self.uow = uow
        self.storage = storage or build_file_storage()
```

​        这里有两个参数：
​        `uow` 继续负责数据库事务和 Repository 访问，`storage` 则负责文件内容。如果调用方没有显式传入存储实例，`FileService` 会通过 `build_file_storage()` 创建默认实现。这样既保留了业务层的使用便利，也让测试或后续扩展可以注入不同的存储实现。
​        为什么 `storage` 可以传入？
​        这样后续写测试时，可以传一个假的存储实现，不需要真的写磁盘。
​        如果没有传入，就用 `build_file_storage()` 根据配置创建真实存储。
​        这一步以后，`FileService` 的职责就清楚了：

```Plain
FileService 负责编排业务流程
UnitOfWork 负责数据库事务
FileStorage 负责文件内容读写
```

### 10.6.6 改造上传逻辑
​        第 9 章的上传逻辑里，`FileService` 会自己生成文件名、创建目录、写入文件。
​        本章改成调用：

```Python
stored_file = self._write_upload_file(
    clean_name=clean_name,
    content=content,
)
```

​        然后把存储结果写入数据库：

```Python
file_object = await self.uow.files.add(
    original_name=clean_name,
    stored_name=stored_file.stored_name,
    content_type=content_type or "application/octet-stream",
    size=len(content),
    storage_path=stored_file.storage_path,
)
```

​        这里的关键变化是：

```Plain
以前：FileService 自己决定文件怎么保存
现在：FileStorage 决定文件怎么保存
```

​        异常清理也从：

```Python
storage_path.unlink(missing_ok=True)
```

​        改成：

```Python
self.storage.delete(stored_file.storage_path)
```

​        这样做是为了让清理逻辑也跟着存储实现走。
​        本地存储删除本地文件。
​        对象存储以后可以删除远程对象。

### 10.6.7 改造下载和预览逻辑
​        下载逻辑现在先问存储层文件是否存在：

```Python
if not self.storage.exists(file_object.storage_path):
    raise AppException(
        message="file content not found",
        code=404,
        status_code=404,
    )
path = self.storage.get_local_path(file_object.storage_path)
return file_object, path
```

​        当前 `FileResponse` 仍然需要本地路径，所以本地存储可以直接返回 `Path`。
​        预览逻辑从读取完整文件改成读取有限字节：

```Python
preview_bytes = self.storage.read_bytes(
    file_object.storage_path,
    max_size=settings.max_file_preview_size + 1,
)
truncated = len(preview_bytes) > settings.max_file_preview_size
preview_bytes = preview_bytes[: settings.max_file_preview_size]
return file_object, preview_bytes.decode("utf-8", errors="replace"), truncated
```

​        为什么多读 1 个字节？
​        因为这样可以判断文件是否被截断。
​        如果只读 `max_file_preview_size`，无法知道文件刚好等于上限，还是超过上限。
​        这个细节对页面展示很重要。前端需要知道是否提示：

```Plain
内容较长，已截断显示。
```

### 10.6.8 对照最终 FileService
​        打开 `api/app/application/file_service.py`，最终完整文件如下：

```Python
from pathlib import Path
from uuid import UUID

from app.application.unit_of_work import UnitOfWork
from app.core.config import settings
from app.core.exceptions import AppException
from app.domain.files.entities import FileObject, SessionFile
from app.domain.files.storage import FileStorage, StoredFile
from app.infrastructure.storage.factory import build_file_storage

TEXT_PREVIEW_TYPES = {
    "application/json",
    "application/xml",
    "application/yaml",
    "text/csv",
}

class FileService:
    def __init__(self, uow: UnitOfWork, storage: FileStorage | None = None) -> None:
        self.uow = uow
        self.storage = storage or build_file_storage()

    async def save_upload(
        self,
        original_name: str,
        content_type: str | None,
        content: bytes,
    ) -> FileObject:
        clean_name = self._clean_filename(original_name)
        if not clean_name:
            raise AppException(
                message="file name is required",
                code=400,
                status_code=400,
            )
        if not content:
            raise AppException(
                message="file content is required",
                code=400,
                status_code=400,
            )
        if len(content) > settings.max_upload_size:
            raise AppException(
                message="file is too large",
                code=413,
                status_code=413,
            )

        stored_file = self._write_upload_file(
            clean_name=clean_name,
            content=content,
        )

        try:
            file_object = await self.uow.files.add(
                original_name=clean_name,
                stored_name=stored_file.stored_name,
                content_type=content_type or "application/octet-stream",
                size=len(content),
                storage_path=stored_file.storage_path,
            )
            await self.uow.commit()
        except Exception:
            # 元数据写入失败时清理已落盘文件，避免出现没有数据库记录的孤立文件。
            self.storage.delete(stored_file.storage_path)
            await self.uow.rollback()
            raise
        return file_object

    async def save_session_upload(
        self,
        session_id: UUID,
        original_name: str,
        content_type: str | None,
        content: bytes,
    ) -> SessionFile:
        session = await self.uow.sessions.get(session_id)
        if session is None:
            raise AppException(
                message="session not found",
                code=404,
                status_code=404,
            )

        clean_name = self._clean_filename(original_name)
        stored_file = self._write_upload_file(
            clean_name=clean_name,
            content=content,
        )

        try:
            file_object = await self.uow.files.add(
                original_name=clean_name,
                stored_name=stored_file.stored_name,
                content_type=content_type or "application/octet-stream",
                size=len(content),
                storage_path=stored_file.storage_path,
            )
            session_file = await self.uow.session_files.add(
                session_id=session_id,
                file_id=file_object.id,
            )
            await self.uow.sessions.touch(session_id)
            await self.uow.commit()
        except Exception:
            # 会话归属写入失败时也要清理文件，避免页面永远找不到这份上传内容。
            self.storage.delete(stored_file.storage_path)
            await self.uow.rollback()
            raise
        return session_file

    async def list_session_files(self, session_id: UUID) -> list[SessionFile]:
        session = await self.uow.sessions.get(session_id)
        if session is None:
            raise AppException(
                message="session not found",
                code=404,
                status_code=404,
            )
        return await self.uow.session_files.list_by_session(session_id)

    async def get_file(self, file_id: UUID) -> FileObject:
        file_object = await self.uow.files.get(file_id)
        if file_object is None:
            raise AppException(
                message="file not found",
                code=404,
                status_code=404,
            )
        return file_object

    async def get_download_path(self, file_id: UUID) -> tuple[FileObject, Path]:
        file_object = await self.get_file(file_id)
        if not self.storage.exists(file_object.storage_path):
            raise AppException(
                message="file content not found",
                code=404,
                status_code=404,
            )
        path = self.storage.get_local_path(file_object.storage_path)
        return file_object, path

    async def preview_file(self, file_id: UUID) -> tuple[FileObject, str, bool]:
        file_object, path = await self.get_download_path(file_id)
        if not self._is_text_preview_supported(file_object):
            raise AppException(
                message="file preview is not supported",
                code=415,
                status_code=415,
            )

        # 预览只读取有限字节，避免把大文件一次性塞进接口响应。
        preview_bytes = self.storage.read_bytes(
            file_object.storage_path,
            max_size=settings.max_file_preview_size + 1,
        )
        truncated = len(preview_bytes) > settings.max_file_preview_size
        preview_bytes = preview_bytes[: settings.max_file_preview_size]
        return file_object, preview_bytes.decode("utf-8", errors="replace"), truncated

    @staticmethod
    def _clean_filename(filename: str) -> str:
        # 只保留文件名本身，避免用户传入 ../ 这类路径片段。
        return Path(filename).name.strip()

    def _write_upload_file(self, clean_name: str, content: bytes) -> StoredFile:
        if not clean_name:
            raise AppException(
                message="file name is required",
                code=400,
                status_code=400,
            )
        if not content:
            raise AppException(
                message="file content is required",
                code=400,
                status_code=400,
            )
        if len(content) > settings.max_upload_size:
            raise AppException(
                message="file is too large",
                code=413,
                status_code=413,
            )

        return self.storage.save(clean_name, content)

    @staticmethod
    def _is_text_preview_supported(file_object: FileObject) -> bool:
        content_type = file_object.content_type.split(";")[0].lower()
        if content_type.startswith("text/") or content_type in TEXT_PREVIEW_TYPES:
            return True
        return Path(file_object.original_name).suffix.lower() in {
            ".json",
            ".md",
            ".py",
            ".txt",
            ".ts",
            ".tsx",
            ".yaml",
            ".yml",
        }
```

​        这份最终代码里，最关键的变化不是函数数量，而是依赖方向。
​        第 9 章的 `FileService` 同时关心业务流程和本地磁盘细节。
​        本章的 `FileService` 仍然关心业务流程，但文件内容操作都交给 `self.storage`。
​        如果后续新增对象存储，`save_session_upload()` 不需要知道对象存储 SDK 怎么用，它仍然只拿到 `StoredFile`，然后写数据库。

### 10.6.9 理解重构后的完整职责
​        本章完成后，文件模块分工如下：

```Plain
api/app/domain/files/entities.py
  |
  +-- 文件领域数据结构

api/app/domain/files/repositories.py
  |
  +-- 文件元数据仓库协议

```

​        最重要的是看清楚这条边界：

```Plain
数据库保存文件记录
存储层保存文件内容
应用服务负责把两者串起来
```

​        这就是本章重构的核心。

## 10.7 关键理解
​        本地存储和对象存储的差异：

```Plain
本地存储
  |
  +-- 可以直接拿到本地路径
  +-- 适合开发环境
  +-- 容器重建时需要 Volume 保留数据

对象存储
  |
  +-- 通常没有本地路径
  +-- 适合生产环境和多实例部署
  +-- 下载可能使用签名 URL 或流式代理
```

​        所以本章没有直接接入对象存储。
​        直接接入会引入密钥、桶名、地域、网络权限、签名 URL 等新问题。当前阶段先把接口边界整理清楚，后面接入会更稳。

## 10.8 技术难点与亮点
​        这一章的难点是抽象边界要刚好。`FileStorage` 只能负责文件内容，不能顺手接管数据库元数据；`FileService` 仍然要负责业务事务、异常清理和会话文件关系。下载接口当前依赖本地路径，所以协议里暂时保留了 `get_local_path()`，但文档也要明确：未来对象存储可能会改成签名 URL、重定向或流式代理。
​        项目亮点在于用户可见功能没有变化，内部结构却变成了可替换形态。配置错误时，工厂函数会明确抛出 `unsupported file storage backend`，不会静默退回本地存储。这种失败方式更适合工程调试，也符合本项目一贯的原则：配置错了就暴露出来，不要假装运行成功。

## 10.9 面试考点
​        面试里可以把这一章讲成一次“稳定功能上的边界重构”。先说明为什么要抽象 `FileStorage`，再区分 `FileRepository` 和 `FileStorage` 的职责：前者处理数据库里的文件记录，后者处理文件内容。接着解释为什么配置错误不能自动降级、为什么预览时要多读 1 个字节判断截断，以及本地存储和对象存储在下载接口上的差异。这样的回答能体现你对扩展点和失败暴露的理解。
