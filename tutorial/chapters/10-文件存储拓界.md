# 第十章. 文件存储拓界

上一章把文件落到本地盘。这在单机和 Compose 里够用：API 容器挂 `api_uploads` 卷，进程重启文件还在。一旦要多副本，本地盘就变成「哪台机器接了上传、哪台才能下载」。

现行 `backend/api-ts` 仍然只有本地后端。`FILE_STORAGE_BACKEND` 这个名字从旧配置里留下来，这一章先把边界讲清楚，免得有人把 `storage_path` 当成可移植的 URL。

`storage_path` 是容器内的文件系统路径，例如 `/app/uploads/<uuid>.pdf`。对外永远暴露 `/api/files/:id/download` 或网关的 `/uploads/<stored_name>`。预览接口读盘、截断、当文本返回；它不关心文件以后会不会上对象存储。将来若换成 S3，改的是 `FileService` 里 `writeFile` / `readFile` 那一层，表结构不用动——id、原名、content_type、size 仍然够用。

![仓库过道：对象可以换地方，编号不能乱](../assets/ch10-archive.jpg)

沙箱里的文件是另一件事。用户附件在 API 的 uploads；Agent 用工具写出来的东西在 sandbox 的 `/workspace`。两边不要共用一个目录。会话上的 `workspace_dir` 只告诉沙箱「从挂载根往哪走」，API 上传目录不是工作区。

下载沙箱文件走 `GET /api/sessions/:id/sandbox-files/download?path=`，由控制平面带着密钥去问 `sandbox-ts`。现在这条在 TypeScript API 里还没接上，工作台里的下载链接触的是已经落到 `files` 表的对象。缺的那截补上之前，不要让前端对沙箱路径发裸请求，密钥会漏到浏览器。

这一章没有新表。你要带走的只有一句：元数据在库，字节在可替换的存储，对外只给经过鉴权的 URL。
