# 第五十九章. 记忆图谱与上下文扩展

## 59.1 本章目标

到上一章为止，每条记忆都是孤岛：衰减公式只看它自己的类型和时间，冲突检测只看它自己的 subject/predicate。但真实记忆里，事实之间是有结构的——"项目使用 PostgreSQL"这条项目事实**支撑**着"迁移必须用 pg_dump 而非 SQLite 导出"这条决策；"缓存击穿导致数据库雪崩"的缺陷教训**扩展自**某次具体的事故情景。孤岛模型下，检索命中其中一条，另一条就石沉大海。

完成本章后，你将能够：

- 设计四类记忆关联边（supports / contradicts / extends / duplicates）及其存储位置；
- 解释"关联类型为什么不单独建表、而是写进双方 metadata"这个取舍；
- 实现检索命中时的一跳上下文扩展，并理解深度硬上限与条数上限如何防止上下文爆炸；
- 给 `GraphNeighbour` 加属性委托，让扩展结果无缝替换 `AgentMemory` 用进既有注入管线。

本章新增代码集中在：

```text
backend/api/app/domain/memories/graph.py    关联边读写 + 一跳扩展
```

## 59.2 为什么需要这一章

先看一个具体的失败场景。Agent 在排查一个数据库慢查询时，检索命中记忆"项目使用 PostgreSQL"。它的正确答案其实藏在另一条记忆里："这个项目的连接池上限是 50，压测时超过 30 就开始排队"。两条记忆内容上互不重复、关键词重叠几乎为零——纯检索手段找不到关联。但人知道它们是一组：前者是事实，后者是约束，一起用才完整。

这就是需要**关联边**的原因：让"命中 A 时顺带想起 B"成为可能。

但设计上有两个明显的诱惑，我都拒绝了：

**诱惑一：上专用图数据库（Neo4j 之类）。** 记忆图谱的规模是"几百到几千条节点、每条出边个位数"，连 PG 的一张边表都嫌重，图数据库纯属杀鸡用牛刀，还多一个基础设施依赖。

**诱惑二：多跳扩散检索。** "命中 A，找 A 的邻居 B，再找 B 的邻居 C……"听起来更智能，但每一跳都会把"弱相关"的记忆稀释进上下文。一跳之内还是"强关联的佐证"，两跳之后大概率是"沾亲带故的噪音"。上下文预算是有限的公共资源，不该为图谱扩张买单。

所以本章的方案收敛得很紧：**边存 metadata，扩展只跳一跳，条数有硬上限**。

## 59.3 实现步骤

### 59.3.1 关联边：四类关系，双向可见

`graph.py` 定义了四种关联类型：

```python
class MemoryRelation(StrEnum):
    supports = "supports"        # A 支撑 B（事实支撑决策）
    contradicts = "contradicts"  # A 与 B 矛盾（冲突消解的输入信号）
    extends = "extends"          # A 扩展自 B（教训扩展自事故情景）
    duplicates = "duplicates"    # A 与 B 重复（后续合并的依据）
```

边的存储位置是本章最关键的取舍。实体上已有 `related_ids: list[UUID]` 存 id 集合，关联类型则写在**双方** metadata 的 `graph_relations` 映射里（key 为对方记忆的 uuid 字符串）：

```python
metadata_a["graph_relations"] = { "<memory_b.id>": "supports", ... }
```

为什么不单独建一张 `memory_edges` 边表？三个理由：

1. **规模不配**。边数量上限被 `memory_graph_max_links`（默认 3）钳制在节点数的常数倍内，边表能解决的性能问题在这里根本不存在。
2. **事务简单**。边和节点在同一个 update 里改完（`related_ids` + `metadata` 一次 `repository.update`），不需要跨表事务一致性。
3. **读路径零额外查询**。扩展上下文时，关联类型直接从已取出的源记忆 metadata 里读，不用 JOIN。

代价是 metadata 里多了一个约定键（`graph_relations`），靠契约注释和测试钉死读写两侧的行为。规模上来之后（比如上万条记忆、边数破千），这张"边表"随时可以迁出去——读路径只有 `expand_context` 一个函数，写路径只有 `link_memories` 一个函数。

### 59.3.2 建边：幂等、防爆炸、单侧容忍

`link_memories` 的入参设计值得看：接受"实体或 id"，实体免去一次仓库回读；`relation` 只能按关键字传入（`*,` 分隔），避免两个实体参数换位导致关系写反——这种参数顺序 bug 在"双向"语义下尤其致命，因为 `supports` 写反和没写是两种不同的错误。

```python
existing_a = memory_a.id in memory_b.related_ids
existing_b = memory_b.id in memory_a.related_ids
if existing_a and existing_b:
    return memory_a, memory_b            # 已双向关联：幂等返回，不重写关系类型
...
if not existing_b and len(memory_a.related_ids) < self.settings.memory_graph_max_links:
    ...
```

三个防御：

- **已双向关联时直接返回**，且不重写关系类型——幂等。重复建边如果允许覆盖类型，后台扫描任务跑两遍就会把 `supports` 漂成 `extends`。
- **单侧关联（历史脏数据）自动补齐另一侧**。边必须是双向的，否则扩展上下文时"A 认得 B、B 不认得 A"，从两边检索命中拿到的邻居集合不一致。
- **任一侧边数达到 `memory_graph_max_links` 时该侧不再追加，另一侧照常记录**。这是防上下文爆炸的第一道闸：不允许任何一条记忆成为"枢纽"，邻居表永远有上界。注意这里不对称地继续记录另一侧——宁可留下待补齐的单向边（下次 `link_memories` 调用会补），也不静默丢弃关系。

### 59.3.3 一跳扩展：检索命中时的上下文补全

`expand_context` 是检索管线的出口，设计成"宁缺毋滥"：

```python
bounded_depth = max(0, min(depth, self.settings.memory_graph_expand_depth))   # 硬上限 1
bounded_limit = limit or self.settings.memory_graph_max_links                 # 默认 3
...
for related_id in memory.related_ids:
    ...
    if related.deleted_at is not None or not related.enabled:
        continue
    if related.status is MemoryStatus.superseded:
        continue
    if not related.is_retrievable():
        continue
    ...
    neighbours.append(GraphNeighbour(memory=related, relation=relation))
return neighbours[:bounded_limit]
```

三道过滤对应三种"看起来在关联边上、实际不该进上下文"的情况：禁用/软删除（显式失效）、`superseded`（被第五十八章的冲突消解或版本替代判过输的过期事实）、`is_retrievable()` 不通过（置信度低于检索下限——衰减机制的下游受益者）。

`depth` 参数保留了扩展性，但被 `min(depth, memory_graph_expand_depth)` 钳死在 1——**上限是配置项，不是调用方自觉**。留参数是为了以后真要两跳时只改配置和测试，不改签名；钳制是为了防止哪个新同事的调用方传个 `depth=3` 就把上下文预算打穿。

条数上限默认 3 且保持 `related_ids` 既有顺序截断。顺序在这里是功能不是巧合：写入方的添加顺序隐含重要性排序（最先被关联的邻居最相关），截断时保留的就是前 3 个——用零成本的约定换了一个可用的排序信号。

### 59.3.4 GraphNeighbour：让扩展结果无缝进管线

`expand_context` 返回的不是裸 `AgentMemory`，而是包了一层 `GraphNeighbour`：

```python
@dataclass(slots=True)
class GraphNeighbour:
    memory: AgentMemory
    relation: MemoryRelation | None

    def __getattr__(self, name: str):
        # 未显式定义的属性直接委托给被关联的记忆实体
        return getattr(self.memory, name)

    def __iter__(self):
        yield self.memory
        yield self.relation
```

为什么要包？因为调用方需要两个信息：**这条邻居是谁**（`memory`），以及**它和源记忆是什么关系**（`relation`，用于给注入 prompt 加"以下事实支撑该决策"这类措辞）。但下游的注入管线是按 `AgentMemory` 写的——取 `.content`、`.confidence`、`.kind` 的地方有一堆。如果 `expand_context` 返回裸实体，关系信息就丢了；如果返回 tuple，所有下游都要解包。`__getattr__` 委托让 `GraphNeighbour` 在读取场景下可以**当 `AgentMemory` 用**，同时 `.relation` 仍可取——零迁移成本地给管线加了关系感知。

## 59.4 本章小结

本章的记忆图谱是"轻量图谱"的样板：**不引新存储、不建新表、不扩深度**。边存双方 metadata，规模由 `memory_graph_max_links` 钳死；扩展只跳一跳，过滤掉失效、superseded、低置信度的邻居，条数上限 3。

它和前一章形成了闭环：衰减把过期记忆压到不可检索，冲突消解把输家标成 superseded——这两道机制保证了图谱扩展不会把"历史上关联过、现在已失效"的记忆重新拽回上下文。**图谱是记忆的放大器，放大什么取决于生命周期治理有多严。**
