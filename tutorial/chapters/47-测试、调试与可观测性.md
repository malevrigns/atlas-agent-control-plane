​        完整代码如下：

```Python
import re
import unittest

from fastapi import FastAPI
from fastapi.testclient import TestClient

from app.core.request_id import RequestIdMiddleware


class RequestIdMiddlewareTest(unittest.TestCase):
    # ===================== 第1步：没有传入请求 ID 时，服务端应自动生成一个 =====================
    def test_generates_request_id_response_header(self) -> None:
        app = FastAPI()
        app.add_middleware(RequestIdMiddleware)

        @app.get("/ping")
        async def ping():
            return {"ok": True}

        response = TestClient(app).get("/ping")

        self.assertEqual(response.status_code, 200)
        self.assertRegex(
            response.headers["X-Request-ID"],
            re.compile(r"^[0-9a-f-]{36}$"),
        )

    # ===================== 第2步：调用方传入请求 ID 时，应保持同一个 ID 贯穿响应 =====================
    def test_reuses_incoming_request_id(self) -> None:
        app = FastAPI()
        app.add_middleware(RequestIdMiddleware)

        @app.get("/ping")
        async def ping():
            return {"ok": True}

        response = TestClient(app).get(
            "/ping",
            headers={"X-Request-ID": "debug-request-001"},
        )

        self.assertEqual(response.headers["X-Request-ID"], "debug-request-001")
```

#### 47.6.1.1 代码讲解

​        这个测试只创建一个最小 FastAPI 应用，不启动完整项目。

​        它验证两个行为：

​        展开来看，第一，浏览器或 curl 没有传 `X-Request-ID` 时，服务端自动生成；第二，调用方已经传了 `X-Request-ID` 时，服务端沿用它。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        这样用户在排查问题时，可以主动传一个固定 ID：

```Bash
curl -H "X-Request-ID: debug-001" http://localhost:8088/api/status
```

​        后端响应也会返回同一个 ID。

### 47.6.2 实现 RequestIdMiddleware

​        创建：

```Plain
api/app/core/request_id.py
```

​        完整代码如下：

```Python
import logging
from uuid import uuid4

from starlette.middleware.base import BaseHTTPMiddleware
from starlette.requests import Request
from starlette.responses import Response

logger = logging.getLogger(__name__)

REQUEST_ID_HEADER = "X-Request-ID"


class RequestIdMiddleware(BaseHTTPMiddleware):
    """为每个 HTTP 请求补充可追踪的 request id。"""

    async def dispatch(self, request: Request, call_next) -> Response:
        # ===================== 第1步：读取调用方传入的请求 ID，或生成一个新的 =====================
        request_id = request.headers.get(REQUEST_ID_HEADER) or str(uuid4())
        request.state.request_id = request_id

        # ===================== 第2步：继续处理请求 =====================
        response = await call_next(request)

        # ===================== 第3步：把请求 ID 放回响应头，方便前端和 curl 排查 =====================
        response.headers[REQUEST_ID_HEADER] = request_id
        logger.debug(
            "request completed: method=%s path=%s request_id=%s status=%s",
            request.method,
            request.url.path,
            request_id,
            response.status_code,
        )
        return response
```

```Plain
api/app/main.py
```

#### 47.6.2.1 业务流程

​        一次请求进入 API 后：

```Plain
请求进入 FastAPI
  |
  v
RequestIdMiddleware
  |
  +-- 读取或生成 request_id
  +-- 放入 request.state
  |
  v
路由和应用服务继续执行
  |
  v
响应头写入 X-Request-ID
```

#### 47.6.2.2 为什么这样做

​        请求 ID 是最小但很有用的可观测性能力。

​        它让排查路径变成：

```Plain
用户截图里的 X-Request-ID
  |
  v
Nginx / API 日志搜索同一个 request_id
  |
  v
定位对应接口、状态码和错误
```

​        Agent 系统的链路比普通 CRUD 更长：

## 47.9 常见问题

- 问题：`curl -i` 看不到 `X-Request-ID` 怎么办？

​        解释：确认 API 镜像已经重新构建，并且容器运行的是第 47 章代码。执行 `BUILD=true ./scripts/start.sh`。

- 问题：诊断清单接口正常，但某条命令执行失败怎么办？

​        解释：诊断清单只负责告诉你该查哪里。具体失败要看那条命令的响应、对应容器日志和服务状态。

- 问题：为什么不直接在接口里自动探测所有系统？

​        解释：自动探测可能很慢，也可能因为某个外部服务卡住导致诊断接口本身不可用。本章先做结构化清单，后续可以逐步加入轻量探测。

- 问题：`TestClient` 输出 deprecation warning 怎么办？

​        解释：这是 Starlette/FastAPI 依赖栈的提示，不影响本章测试结果。后续统一升级依赖时再处理。
