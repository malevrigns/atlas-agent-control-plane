# 第十二章. 文件上传与本地存储

## 12.1 本章目标
​        从这一章开始，AtlasAgent 不再只处理文本输入。真实的 Agent 工作台里，用户经常会把需求文档、截图、表格、代码文件或压缩包交给系统，希望后续任务可以围绕这些材料继续展开。因此，文件上传不是一个孤立的按钮，而是 Agent 输入能力的一部分。
​        本章要带读者完成文件上传的第一条基础链路：浏览器通过 `multipart/form-data` 把文件传给 FastAPI，后端使用 `UploadFile` 读取内容，把真实文件写入 API 服务的上传目录，再把文件名、大小、类型、下载地址和创建时间写入 PostgreSQL。前端则在聊天工作台里增加附件上传区，让用户可以看到上传结果并下载原始文件。读到这里，读者需要特别注意两条边界：文件内容保存在哪里，文件元数据又由谁负责维护。

## 12.2 最终效果
​        本章结束后，访问：

```Plain
http://localhost:8088
```

​        进入任意会话后，可以在聊天输入框上方看到附件上传区。
​        选择一个本地文件后：
​        浏览器会把文件提交到后端，API 服务把文件内容保存到 `/app/uploads`，同时在 `files` 表里记录这次上传的元数据。页面拿到响应后，会把文件名、文件大小、上传时间和下载入口展示在附件列表里。用户此时看到的不是一个临时文件名，而是一条可以被后续功能继续引用的文件记录。
​        同时后端新增接口：

```Plain
POST /api/files
GET  /api/files/{file_id}
GET  /api/files/{file_id}/download
```

​        本章先完成独立文件能力。文件暂时不绑定到会话消息里。第 13 章会继续加入会话文件列表和文件预览。

## 12.3 本章要解决的问题
​        第 11 章已经完成会话状态、停止任务、未读清理和 SSE 状态流。
​        但是一个真实的 Agent 工作台不能只接收文本。用户常常需要上传：

```Plain
需求文档
截图
表格
压缩包
代码文件
```

​        这些文件后续可能会被 Agent 读取、分析、预览或作为工具输入。
​        文件上传不能只把文件放到某个目录里。因为页面还需要知道：

```Plain
文件原始名称是什么
文件类型是什么
文件大小是多少
文件如何下载
文件什么时候上传
```

​        所以本章把文件拆成两部分处理：

```Plain
文件内容 -> 保存到本地存储目录
文件元数据 -> 保存到 PostgreSQL
```

## 12.4 本章技术方案
​        本章采用“本地磁盘 + 数据库元数据”的方案。
​        可选方案有三种：
​        最简单的做法是只把文件保存到磁盘，不写数据库；这种方式实现快，但页面很难稳定查询文件列表，也无法给后续权限、预览和引用关系留下位置。另一个极端是把文件二进制内容直接写进数据库；它看起来统一，但会让数据库备份、迁移和查询压力变重。课程项目在这里选择中间方案：文件内容落在磁盘，文件元数据进入 PostgreSQL。
​        本章选择第三种。
​        原因是：
​        这样做的好处是边界清楚。文件内容通常比较大，适合交给文件系统或后续对象存储；元数据体积小、结构稳定，适合交给数据库负责查询和关联。本章先使用本地磁盘，是为了让开发环境容易验证；等项目进入部署或生产语境时，`FileService` 这层还可以继续演进，把本地目录替换成 S3、MinIO 或其他对象存储。
​        本章请求链路如下：

```Plain
浏览器选择文件
  |
  v
POST /api/files
  |
  v
FileService
  |
  +-- 清理文件名
  +-- 检查文件大小
  +-- 写入 /app/uploads
  +-- 写入 files 表
  |
  v
前端展示附件和下载链接
```

​        本章会做这些内容：
​        后端部分会从依赖开始，加入 `python-multipart`，让 FastAPI 能够解析浏览器提交的文件表单。随后新增 `files` 表迁移、文件领域实体、Repository、应用服务和 API 路由，让上传、查询和下载都经过清楚的分层。Docker Compose 还会给 API 服务挂载上传目录，避免容器重建后丢失已经保存的文件。
​        前端部分会新增 `file-api.ts`、附件上传组件和附件列表组件，zustand store 负责保存当前页面已经上传成功的附件。这里暂时还不讨论 Agent 如何读取文件内容，重点先放在“文件能可靠上传、保存、查询、下载”这条底层链路上。
​        本章暂时不做这些内容：
​        本章不会把文件绑定到具体消息，也不会做文件分页、文件预览、对象存储、权限控制和 Agent 文件读取。这些能力都需要更完整的上下文关系。课程在这里先把文件模块站稳，下一章再把文件接入会话维度，并继续处理预览和上下文组织问题。

## 12.6 实施步骤
### 12.6.1 安装文件上传依赖
​        进入后端目录：

```Bash
cd api
```

​        安装 `python-multipart`：

```Bash
uv add python-multipart
```

​        FastAPI 接收 `multipart/form-data` 表单上传时需要这个依赖。浏览器上传文件时，请求体不是普通 JSON，而是带边界分隔的表单数据。
​        安装后，`api/pyproject.toml` 会出现：

```TOML
"python-multipart>=0.0.30",
```

​        `api/uv.lock` 也会同步更新。
​        常见误区是手动在 `pyproject.toml` 里加依赖，但没有更新锁文件。后续 Docker 构建或其他机器安装时就可能出现版本不一致。

### 12.6.2 配置上传目录和大小限制
​        打开 `api/app/core/config.py`，在数据库配置后加入：

```Python
upload_dir: str = "uploads"
max_upload_size: int = 10 * 1024 * 1024
```

​        这两个配置分别表示：
​        `upload_dir` 决定文件内容写入哪个目录，`max_upload_size` 决定单个文件允许的最大字节数，默认是 10MB。把这两个值放进配置层，可以让本地开发、Docker Compose 和后续部署环境使用不同取值，而不用修改路由或应用服务代码。
​        本地直接运行 API 时，文件会保存到 `api/uploads`。Docker Compose 运行时，会通过环境变量改成 `/app/uploads`。
​        这里把限制放进配置，而不是写死在路由里，是为了后续部署时可以按机器磁盘和业务需求调整。

### 12.6.5 实现文件 Repository
​        创建 `api/app/infrastructure/repositories/file_repository.py`：

```Python
from uuid import UUID

from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

from app.domain.files.entities import FileObject
from app.domain.files.repositories import FileRepository
from app.infrastructure.database.models.file_object import FileObjectModel


class SqlAlchemyFileRepository(FileRepository):
    def __init__(self, db_session: AsyncSession) -> None:
        self.db_session = db_session

    async def add(
        self,
        original_name: str,
        stored_name: str,
        content_type: str,
        size: int,
        storage_path: str,
    ) -> FileObject:
        model = FileObjectModel(
            original_name=original_name,
            stored_name=stored_name,
            content_type=content_type,
            size=size,
            storage_path=storage_path,
        )
        self.db_session.add(model)
        await self.db_session.flush()
        await self.db_session.refresh(model)
        return model.to_entity()

    async def get(self, file_id: UUID) -> FileObject | None:
        stmt = select(FileObjectModel).where(FileObjectModel.id == file_id)
        result = await self.db_session.execute(stmt)
        model = result.scalar_one_or_none()
        return model.to_entity() if model else None
```

​        Repository 只负责数据库读写，不负责保存文件内容。
​        这样做的原因是：文件内容属于存储层操作，元数据属于数据库操作。把两件事拆开后，后续把本地磁盘替换成对象存储时，数据库 Repository 不需要跟着大改。

### 12.6.6 实现文件应用服务
​        创建 `api/app/application/file_service.py`：

```Python
from pathlib import Path
from uuid import UUID, uuid4

from app.application.unit_of_work import UnitOfWork
from app.core.config import settings
from app.core.exceptions import AppException
from app.domain.files.entities import FileObject


class FileService:
    def __init__(self, uow: UnitOfWork) -> None:
        self.uow = uow
        self.upload_root = Path(settings.upload_dir)

    async def save_upload(
        self,
        original_name: str,
        content_type: str | None,
        content: bytes,
    ) -> FileObject:
        clean_name = self._clean_filename(original_name)
        if not clean_name:
            raise AppException(
                message="file name is required",
                code=400,
                status_code=400,
            )
        if not content:
            raise AppException(
                message="file content is required",
                code=400,
                status_code=400,
            )
        if len(content) > settings.max_upload_size:
            raise AppException(
                message="file is too large",
                code=413,
                status_code=413,
            )

        stored_name = self._build_stored_name(clean_name)
        storage_path = self.upload_root / stored_name
        self.upload_root.mkdir(parents=True, exist_ok=True)
        storage_path.write_bytes(content)

        try:
            file_object = await self.uow.files.add(
                original_name=clean_name,
                stored_name=stored_name,
                content_type=content_type or "application/octet-stream",
                size=len(content),
                storage_path=str(storage_path),
            )
            await self.uow.commit()
        except Exception:
            # 元数据写入失败时清理已落盘文件，避免出现没有数据库记录的孤立文件。
            storage_path.unlink(missing_ok=True)
            await self.uow.rollback()
            raise
        return file_object

    async def get_file(self, file_id: UUID) -> FileObject:
        file_object = await self.uow.files.get(file_id)
        if file_object is None:
            raise AppException(
                message="file not found",
                code=404,
                status_code=404,
            )
        return file_object

    async def get_download_path(self, file_id: UUID) -> tuple[FileObject, Path]:
        file_object = await self.get_file(file_id)
        path = Path(file_object.storage_path)
        if not path.is_file():
            raise AppException(
                message="file content not found",
                code=404,
                status_code=404,
            )
        return file_object, path

    @staticmethod
    def _clean_filename(filename: str) -> str:
        # 只保留文件名本身，避免用户传入 ../ 这类路径片段。
        return Path(filename).name.strip()

    @staticmethod
    def _build_stored_name(filename: str) -> str:
        suffix = Path(filename).suffix
        return f"{uuid4().hex}{suffix}"
```

​        这段代码的业务流程：

```Plain
路由读取上传内容
  |
  v
FileService.save_upload
  |
  +-- 清理原始文件名
  +-- 检查空文件
  +-- 检查文件大小
  +-- 生成磁盘文件名
  +-- 写入上传目录
  +-- 写入 files 表
  +-- commit
```

​        这里有一个有意加入的注释：

```Python
# 只保留文件名本身，避免用户传入 ../ 这类路径片段。
# 元数据写入失败时清理已落盘文件，避免出现没有数据库记录的孤立文件。
```

​        这是安全边界和一致性边界，不是普通代码翻译。文件上传场景里，用户传来的文件名不可信。如果直接拼接路径，可能造成路径穿越风险。文件写入磁盘后，如果数据库提交失败，也需要清理已落盘文件，否则后续很难判断这个文件是否仍然有效。

### 12.6.7 把文件 Repository 接入 Unit of Work
​        打开 `api/app/application/unit_of_work.py`，最终文件如下：

```Python
from sqlalchemy.ext.asyncio import AsyncSession

from app.infrastructure.repositories.file_repository import SqlAlchemyFileRepository
from app.infrastructure.repositories.session_repository import (
    SqlAlchemySessionEventRepository,
    SqlAlchemySessionMessageRepository,
    SqlAlchemySessionRepository,
)


class UnitOfWork:
    def __init__(self, db_session: AsyncSession) -> None:
        self.db_session = db_session
        self.files = SqlAlchemyFileRepository(db_session)
        self.sessions = SqlAlchemySessionRepository(db_session)
        self.session_messages = SqlAlchemySessionMessageRepository(db_session)
        self.session_events = SqlAlchemySessionEventRepository(db_session)

    async def commit(self) -> None:
        await self.db_session.commit()

    async def rollback(self) -> None:
        await self.db_session.rollback()
```

​        这样 `FileService` 就可以通过：

```Python
self.uow.files.add(...)
```

### 12.6.8 实现文件接口
​        创建 `api/app/schemas/file.py`：

```Python
from datetime import datetime
from uuid import UUID

from pydantic import BaseModel


class FileResponse(BaseModel):
    id: UUID
    original_name: str
    content_type: str
    size: int
    download_url: str
    created_at: datetime
```

​        创建 `api/app/api/routes/files.py`：

```Python
from uuid import UUID

from fastapi import APIRouter, Depends, File, UploadFile
from fastapi.responses import FileResponse as DownloadFileResponse
from sqlalchemy.ext.asyncio import AsyncSession

from app.application.file_service import FileService
from app.application.unit_of_work import UnitOfWork
from app.domain.files.entities import FileObject
from app.infrastructure.database.session import get_db_session
from app.schemas.common import ApiResponse
from app.schemas.file import FileResponse

router = APIRouter(prefix="/files", tags=["files"])


def build_file_service(
    db_session: AsyncSession = Depends(get_db_session),
) -> FileService:
    return FileService(UnitOfWork(db_session))


def to_file_response(file_object: FileObject) -> FileResponse:
    return FileResponse(
        id=file_object.id,
        original_name=file_object.original_name,
        content_type=file_object.content_type,
        size=file_object.size,
        download_url=f"/api/files/{file_object.id}/download",
        created_at=file_object.created_at,
    )


@router.post("", response_model=ApiResponse[FileResponse])
async def upload_file(
    upload: UploadFile = File(...),
    service: FileService = Depends(build_file_service),
) -> ApiResponse[FileResponse]:
    content = await upload.read()
    file_object = await service.save_upload(
        original_name=upload.filename or "",
        content_type=upload.content_type,
        content=content,
    )
    return ApiResponse(data=to_file_response(file_object))


@router.get("/{file_id}", response_model=ApiResponse[FileResponse])
async def get_file(
    file_id: UUID,
    service: FileService = Depends(build_file_service),
) -> ApiResponse[FileResponse]:
    file_object = await service.get_file(file_id)
    return ApiResponse(data=to_file_response(file_object))


@router.get("/{file_id}/download")
async def download_file(
    file_id: UUID,
    service: FileService = Depends(build_file_service),
) -> DownloadFileResponse:
    file_object, path = await service.get_download_path(file_id)
    return DownloadFileResponse(
        path=path,
        media_type=file_object.content_type,
        filename=file_object.original_name,
    )
```

### 12.6.9 给 Docker Compose 增加上传目录
​        打开 `docker-compose.yml`，在 `api` 服务里加入：

```TypeScript
import type { ApiResponse, UploadedFile } from "../types";

export async function uploadFile(file: File): Promise<UploadedFile> {
  const formData = new FormData();
  formData.append("upload", file);

  const response = await fetch("/api/files", {
    method: "POST",
    body: formData,
  });
  const payload = (await response.json()) as ApiResponse<UploadedFile>;
  if (!response.ok || payload.code >= 400) {
    throw new Error(payload.message || `HTTP ${response.status}`);
  }
  if (!payload.data) {
    throw new Error("empty response");
  }
  return payload.data;
}

export function getDownloadUrl(file: UploadedFile): string {
  return file.download_url;
}
```

​        这里没有手动设置 `Content-Type`。
​        原因是 `FormData` 请求需要浏览器自动生成边界。如果手动写成 `multipart/form-data`，边界可能缺失，后端会解析失败。

    month: "2-digit",
    day: "2-digit",

  }).format(new Date(value));

export function formatDateTime(value: string) {
  return new Intl.DateTimeFormat("zh-CN", {
    year: "numeric",
    month: "2-digit",
    day: "2-digit",
    hour: "2-digit",
    minute: "2-digit",
  }).format(new Date(value));

export function formatBytes(value: number) {
  if (value < 1024) {
    return `${value} B`;
  }

uploadAttachment: async (file) => {
  if (!get().selectedSessionId) {

## 12.7 关键理解
​        文件上传有两条数据线：

```Plain
文件内容线：浏览器 -> API -> /app/uploads
元数据线：浏览器 -> API -> files 表 -> 前端展示
```

​        文件内容适合放在存储系统里，元数据适合放在数据库里。
​        第二个重点是文件名不能直接信任。
​        用户上传的文件名来自浏览器，后端必须把它当作不可信输入。本章用 `Path(filename).name` 只保留文件名本身，避免路径片段影响真实保存位置。
​        第三个重点是 `FormData`。
​        JSON 请求适合普通结构化数据，文件上传需要 `multipart/form-data`。前端发送 `FormData` 时，不要手动设置 `Content-Type`。

## 12.8 技术难点与亮点
​        文件上传看起来只是一个接口，但真正容易出错的地方在边界上。FastAPI 接收文件依赖 `python-multipart`，浏览器提交的字段名必须和后端参数名 `upload` 一致；文件内容写入磁盘，文件元数据写入数据库，这两步还要保持事务意识，避免出现数据库没有记录但磁盘已经残留文件，或者数据库有记录但文件内容丢失的情况。
​        这一章的工程亮点也在于分层没有被上传功能打乱。文件模块仍然按照领域实体、Repository、应用服务和 API 路由拆开；前端上传逻辑也没有塞进页面文件，而是拆成 `file-api.ts`、`AttachmentUpload`、`AttachmentList` 和 store action。下载链接统一走 API 入口，后续无论补权限、审计还是对象存储签名，都有一个相对稳定的接入位置。

## 12.9 面试考点
​        面试中问到文件上传，不要只回答“用了 FastAPI 的 `UploadFile`”。更好的回答是把存储边界讲清楚：文件内容和元数据为什么分开存，`multipart/form-data` 和 JSON 请求有什么区别，前端为什么不能手动设置 `Content-Type`，后端为什么要清理浏览器传来的文件名，以及 Docker Volume 在容器重建时保护了什么。能把这些问题串起来，说明你不是只会写上传接口，而是理解了文件能力在系统中的位置。

## 12.11 常见问题

### 12.11.1 启动 API 时报 `python-multipart` 相关错误怎么办
​        这是文件上传依赖没有安装或镜像仍然使用旧依赖导致的。进入 `api` 目录执行 `uv sync` 可以同步本地依赖；Docker 环境下需要重新执行 `docker compose build api`，再启动 API 容器，让镜像里的依赖和 `uv.lock` 保持一致。

### 12.11.2 页面还是旧界面，看不到“选择附件上传”怎么办
​        本章改了前端组件和页面组合，如果 UI 容器没有重建，浏览器看到的仍然会是旧页面。执行 `docker compose build ui` 后，再执行 `docker compose up -d ui nginx`。如果页面仍旧没有变化，再刷新浏览器或清理缓存。

### 12.11.3 上传时返回 `field required` 怎么办
​        这个错误通常说明上传字段名写错了。本章后端参数名是 `upload`，所以 `curl` 命令必须写成 `-F "upload=@README.md"`。如果前端自己构造 `FormData`，也必须使用 `formData.append("upload", file)`。

### 12.11.4 上传后查询有记录，但下载返回 `file content not found` 怎么办
​        这说明数据库里有元数据，但磁盘上的文件内容已经找不到。优先检查 `UPLOAD_DIR` 和 Docker Volume 配置，再执行 `docker compose config` 确认 `api_uploads` 是否挂载到了 `/app/uploads`。如果上传目录没有持久化，容器重建后就可能只剩数据库记录。

### 12.11.5 页面选择文件后没有反应怎么办
​        先确认页面已经选中一个会话。当前章节的附件区仍然放在会话工作台里，没有选中会话时，上传入口会被禁用，store 也不会发起 `uploadAttachment`。

### 12.11.6 上传大文件返回 `file is too large` 怎么办
​        当前默认限制是 10MB，对应配置是 `MAX_UPLOAD_SIZE`。如果课程验证需要上传更大的文件，可以调整这个环境变量并重启 API。这里要注意，放大限制只是允许请求进入后端，不等于已经解决存储、预览和后续处理成本。

## 12.12 本章小结
​        本章完成了文件上传的基础闭环。后端可以接收浏览器上传的文件，把文件内容保存到本地上传目录，把元数据写入 `files` 表，并提供元数据查询和下载接口；Docker Compose 给 API 配置了上传 Volume，让容器内的文件目录具备持久化能力；前端聊天工作台新增附件上传和附件列表，上传相关逻辑继续保持组件化和 store 管理。
