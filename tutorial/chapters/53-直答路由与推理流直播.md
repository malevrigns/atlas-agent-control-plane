# 第五十三章. 直答路由与推理流直播

## 53.1 本章目标

前面五十二章把 AtlasAgent 的能力铺满了：Planner、ReAct、工具运行时、记忆、RAG、Skill、三个客户端。但有一件事一直没做对——**它不像一个能聊天的产品**。

问它"什么是闭包"，后端老老实实走 Planner 生成四步计划，再让 ReAct 挨个执行工具，十几秒后返回一段带"## 总结 / ## 证据与引用 / ## 产物"的任务报告。用户想要一段解释，拿到的是一份工单。

这一章做两件事：把"对话"和"任务"分成两条路径，并把模型的推理过程实时播给用户看。

完成本章后，你将能够：

- 写出一个不会误判的意图路由，并说清为什么"强关键词 + 动词宾语共现"比一张关键词表可靠；
- 实现直答路径：上下文快照 → 多轮 messages → 流式产出 → **回答落库** → 写 task_done；
- 在 OpenAI 兼容协议上解析 `reasoning_content`，用 `extra_body` 传 `enable_thinking`，并在模型不支持时自动降级重试一次；
- 把规划阶段和最终回答阶段的思考流统一转发成 SSE 增量，让三个阶段都能"直播"；
- 定义 `answer_started / thinking_delta / answer_delta` 三个增量事件，并在前端正确缓冲与清空；
- 定位并解决"后端明明在流、前端却一次性收到"的代理缓冲问题——这是本章最难查的一个坑。

## 53.2 改造前的四个问题

先诚实地看一眼原来的执行链路：

```text
用户消息
  → mark_running
  → create_user_message
  → PlannerService.create_plan            ← 不管你问的是什么
  → ReActAgentService.execute_latest_plan ← 挨个调工具
  → task_done
```

**问题一：所有消息都走流水线。** "什么是控制反转"这种问题，Planner 会拆出"明确任务目标 / 拆解执行步骤 / 逐步实现和检查 / 总结结果"四步，ReAct 再挨个找工具执行。第一，慢——四次模型调用加若干次工具调用；第二，答非所问——最终总结器被要求"根据可观察的工具输出写最终回复正文，不要编造未执行的动作"，而这个任务压根没有工具输出，于是它只能写一段空话。

**问题二：助手的回答没有落库。** 最终回答只写进 `task_done` 事件的 `final_answer` 字段。事件时间线能看到，消息列表看不到。刷新页面后对话区只剩用户自己的提问。`react_agent_service.py` 里那段注释就是这个教训的原文：

```python
"""把最终回答落库成 assistant 消息并返回 message_created 事件。

消息列表是客户端刷新后的事实源。回答只存在 task_done 事件里时，
刷新后消息列表只剩用户消息，对话看起来像“没有人回复”。
"""
```

**问题三：模型的推理过程完全看不到。** 思考型模型（Qwen、DeepSeek-R1 这类）在 `delta.reasoning_content` 里输出一大段推理，我们的 SSE 客户端直接丢掉了。用户面对的是一个转了十几秒的加载态，然后"啪"地弹出结果。对一个以"可观察"为卖点的 Agent 控制平面来说，这很讽刺。

**问题四：会话状态会卡在 running。** 用户关标签页或网络断开时，SSE 连接断掉，`stream_user_message` 这个 async generator 在当前 `yield` 处被关闭，后面的 `update_status(idle)` 永远不会执行。会话列表里那一条从此显示"运行中"，只能手工改数据库。

四个问题的共同点：**执行链路只有一种形状，而且这个形状假设了"一切都会正常走完"。**

## 53.3 路由分流：needs_agent_pipeline

分流函数放在 `backend/api/app/application/agent_runner_service.py` 的模块顶层，是一个纯函数——没有依赖、没有 IO、可以直接单测。

### 53.3.1 为什么不是一张关键词表

最直觉的写法是列一批词：`["搜索", "文件", "运行", "执行", "查找", "保存"]`，命中就进流水线。这个写法第一天就会崩，因为编程问答里这些词的密度极高：

- "二分**查找**怎么写" → 命中"查找"
- "如何**保存** Python 字典到变量里" → 命中"保存"
- "怎么**运行** Python 脚本" → 命中"运行"

三个都是纯问答，三个都会被误送进 Planner + ReAct。**误判进流水线的代价（慢十倍 + 答非所问）远大于误判进直答的代价（少调一次工具，用户再说一句就行），所以路由必须偏向直答。**

### 53.3.2 强信号词表

第一档是**歧义极小**的词，出现在句子里几乎不可能是在问概念：

```python
# 强信号：命中即进入“计划 + 工具”执行流水线。
# 注意只放歧义极小的词——“查找/保存/运行”这类词在编程问答里太常见
# （“二分查找怎么写”），会把本该像 GPT 一样直接回答的问题误送进流水线。
_PIPELINE_STRONG_KEYWORDS = (
    # 沙箱与环境
    "沙箱", "sandbox", "Sandbox",
    # 搜索与资讯
    "搜索", "检索一下", "新闻", "资讯",
    # 浏览器与网页操作
    "浏览器", "网页", "网站", "截图", "爬取", "抓取",
    # 文件动作短语（区别于“读取列表元素”这类编程语义）
    "写入文件", "保存到", "保存为", "存到", "导出到",
    "读取文件", "创建文件", "生成文件",
    # 终端
    "终端", "命令行", "shell", "Shell",
    # 外部集成与多 Agent
    "MCP", "mcp", "A2A", "a2a",
    "多 Agent", "多Agent", "远程 Agent", "远程智能体",
)
```

（源码里每个字面量占一行，这里为了排版合并了。）

注意文件那一组的处理方式：**放的不是"文件"，而是"写入文件""保存到""读取文件"这样的动作短语。** "文件"单独出现太常见了（"怎么用 Python 遍历文件夹"），而"写入文件"几乎一定是在让 Agent 干活。这是本节的核心手法——**当一个词有歧义时，不要放宽它，而是把它扩成一个更长的短语。**

大小写是显式枚举的，没有做 `content.lower()`：中文混排下小写化对中文无效，多列两个字面量比引入归一化更好读。

### 53.3.3 弱信号：动词与宾语必须共现

第二档处理"执行 / 运行"这类动词。它们单独出现不可靠，但和执行对象共现时几乎一定是任务：

```python
# 弱信号动词：必须与执行对象共现才算工具任务。
# “执行任务”“运行脚本”是流水线；“怎么运行 Python”单靠动词不触发。
_PIPELINE_ACTION_VERBS = ("执行", "运行", "跑一下", "跑个")
_PIPELINE_ACTION_OBJECTS = (
    "任务", "脚本", "命令", "代码", "程序", "测试", "pytest", "文件",
)
```

"文件"在强信号里被拆成了短语，但在宾语表里可以原样出现——它必须和"执行/运行"共现才生效，"运行文件"不会是概念提问。

### 53.3.4 判定顺序

```python
def needs_agent_pipeline(content: str) -> bool:
    """判断一条用户消息是否需要完整的计划执行流水线。

    默认走直接问答（像 GPT 一样流式回答）——这是对话产品的主路径。
    只有出现明确的工具意图（沙箱、搜索、网页、文件动作、终端、集成），
    或“执行/运行 + 对象”的组合语义时，才启动 Planner + ReAct。
    URL 一律按工具任务处理。
    """

    if "http://" in content or "https://" in content:
        return True
    if any(keyword in content for keyword in _PIPELINE_STRONG_KEYWORDS):
        return True
    if any(verb in content for verb in _PIPELINE_ACTION_VERBS) and any(
        target in content for target in _PIPELINE_ACTION_OBJECTS
    ):
        return True
    return False
```

四步，顺序有讲究：

1. **URL 优先。** 用户贴链接的唯一意图就是让 Agent 去看那个链接。这一条放最前面，因为它最确定也最便宜。
2. **强关键词。** 命中即进流水线。
3. **动词 + 宾语共现。** 两个 `any()` 用 `and` 连接，缺一不可。
4. **默认返回 False。** 这是整个函数最重要的一行——**没有明确证据时走直答**。

**这个函数刻意没有调用 LLM。** 用模型做意图分类当然更准，但要多花一次往返，而这条路径的全部意义就是快。规则跑偏时用户可以换个说法，模型调用超时了用户只能干等。

## 53.4 直答路径：_stream_direct_answer

分流之后，`stream_user_message` 的主体变成了一个 if/else：

```python
if needs_agent_pipeline(content):
    # 3a. 工具任务：流式生成计划——规划阶段的模型思考实时推给前端。
    async for kind, value in self.planner_service.stream_plan(...):
        ...
else:
    # 3b. 普通问答：跳过计划和工具，直接流式回答。
    async for item in self._stream_direct_answer(
        session_id=session_id,
        content=content,
    ):
        yield item
```

### 53.4.1 先发 answer_started，再组装上下文

```python
yield AgentRunnerStreamItem(
    name="answer_started",
    payload={"session_id": str(session_id), "mode": "chat"},
)

uow = self.session_service.uow
snapshot = await self.context_service.build_snapshot(session_id, task=content)
attachment_excerpts = await self._load_attachment_excerpts(session_id)
rag_context, rag_sources = await self._load_rag_context(content)
chat_messages = self._build_chat_messages(
    snapshot, content, attachment_excerpts, rag_context
)
```

`answer_started` 不带内容，它只做一件事：**告诉前端这一轮是对话不是任务**。前端收到它就收掉"正在生成计划"的加载态，并清空上一轮残留的流式缓冲。

后面四行说明**直答不等于裸调模型**：会话概要、长期记忆、附件正文节选、知识库自动检索全都复用前面章节的能力，唯一的区别是没有计划和工具。`_load_rag_context` 里那句注释值得单拎出来：

```python
except Exception:  # noqa: BLE001 —— RAG 是增强项，失败不影响直答。
    return "", []
```

知识库没建、向量服务挂了、测试环境根本没有数据库，统统静默降级。**增强能力失败时应该降级，而不是让主功能一起失败。**

### 53.4.2 把快照还原成多轮对话

`_build_chat_messages` 决定模型看到什么。核心判断是：哪些内容进 system，哪些还原成对话轮次。

```python
def _build_chat_messages(self, snapshot, content, attachment_excerpts=None, rag_context=""):
    """把上下文快照转换成多轮对话消息。

    最近消息按原始角色还原成对话轮次；长期记忆和附件内容
    进入 system 提示，模型可以引用但不会把它们误当成用户发言。
    """

    sections: list[str] = [
        "你是 AtlasAgent，一个严谨的中文 AI 助手。"
        "请直接回答用户的问题：答案准确、结构清晰，可以使用 Markdown。"
        "不知道就说不知道，不要编造。",
    ]
    if snapshot.summary:
        sections.append(f"会话概要：{snapshot.summary}")
    if snapshot.memory_context.items:
        memory_lines = "\n".join(
            f"- [{item.kind.value}] {item.content}"
            for item in snapshot.memory_context.items
        )
        sections.append(f"长期记忆（可参考，不要复述）：\n{memory_lines}")
    # …… rag_context 与 attachment_excerpts 同样进 sections ……

    messages: list[LLMMessage] = [
        LLMMessage(role="system", content="\n\n".join(sections)),
    ]
    for context_message in snapshot.messages:
        if context_message.role not in {"user", "assistant"}:
            continue
        messages.append(
            LLMMessage(role=context_message.role, content=context_message.content)
        )

    # 快照为空时兜底，保证至少携带当前问题。
    if len(messages) == 1 or messages[-1].role != "user":
        messages.append(LLMMessage(role="user", content=content))
    return messages
```

两个细节：

**记忆和附件进 system，不进 user。** 拼进用户消息，模型会以为用户刚说了这些话，然后开始回应记忆内容本身。放在 system 里并标注"可参考，不要复述"，模型才当它是背景。

**最后那个兜底是必需的。** 正常情况下 `snapshot.messages` 已包含刚落库的用户消息，不会重复追加。但上下文预算把消息裁光、或快照构建降级返回空时，如果不兜底，发给模型的就只有一条 system。**"正常路径下永远不触发"的兜底代码，价值就在那个不正常的路径上。**

### 53.4.3 流式产出与降级重试

```python
answer_parts: list[str] = []
reasoning_parts: list[str] = []
# 第一轮按配置请求思考过程；模型不支持 enable_thinking 而在
# 任何输出产生前报错时，自动降级为普通流式重试一次。
attempts: list[bool | None] = [None]
if self.llm_service.thinking_enabled():
    attempts.append(False)

for attempt_index, thinking in enumerate(attempts):
    try:
        async for delta in self.llm_service.chat_stream(
            chat_messages,
            thinking=thinking,
        ):
            if delta.kind == "reasoning":
                reasoning_parts.append(delta.text)
                yield AgentRunnerStreamItem(
                    name="thinking_delta",
                    payload={"session_id": str(session_id), "delta": delta.text},
                )
            else:
                answer_parts.append(delta.text)
                yield AgentRunnerStreamItem(
                    name="answer_delta",
                    payload={"session_id": str(session_id), "delta": delta.text},
                )
        break
    except AppException as error:
        if answer_parts or reasoning_parts:
            # 已经流出部分内容后 provider 中断，按任务错误处理。
            raise
        if attempt_index + 1 < len(attempts):
            continue
        # 模型没配置或不可达时，用明确的提示回复，而不是让请求失败。
        fallback = self._build_llm_unavailable_answer(error)
        answer_parts = [fallback]
        yield AgentRunnerStreamItem(
            name="answer_delta",
            payload={"session_id": str(session_id), "delta": fallback},
        )
```

`attempts` 把"重试策略"表达成了数据：配置里 `thinking: false` 时 `attempts == [None]`，只试一次；`thinking: true` 时 `attempts == [None, False]`，第一次按配置请求思考，失败后显式关闭再试一次。

`thinking=None` 表示"用配置决定"，`thinking=False` 表示"明确不要思考"。**三态在这里不是啰嗦，而是必需的**——只有区分了"没指定"和"明确关闭"，降级重试才能表达出来。

`if answer_parts or reasoning_parts: raise` 划出了重试的边界：**只有一个字都还没吐出来时，重试才是安全的。** 已经流出半段回答再重试，用户会看到内容从头开始，比直接报错更糟。

最后的兜底不抛 500，而是把排查指引当成回答流出去：

```python
@staticmethod
def _build_llm_unavailable_answer(error: AppException) -> str:
    """模型不可用时给用户可执行的排查指引。"""

    return (
        "当前无法调用模型服务，所以这条消息没有得到 AI 回答。\n\n"
        f"- 原因：{error.message}\n"
        "- 请在服务端配置 `LLM_API_KEY` 环境变量（OpenAI 兼容服务的密钥），"
        "并确认 `backend/api/config/llm.yaml` 中的 `base_url` 与 `default_model` 正确。\n"
        "- 配置完成后重启 API 服务，再发送一条消息即可。"
    )
```

第一次跑起来还没配 Key 的人，看到的是三行可执行的指引，而不是一个红色的 500。

### 53.4.4 落库：这一章最关键的十行

```python
final_answer = "".join(answer_parts).strip() or "模型没有返回内容，请重试。"
reasoning = "".join(reasoning_parts).strip()

# 回答落库：消息列表和事件时间线都能看到这轮回答。
message, message_event = await self.session_service.create_assistant_message(
    session_id=session_id,
    content=final_answer,
)
yield AgentRunnerStreamItem(name=message_event.type.value, payload=message_event)

done_event = await uow.session_events.add(
    session_id=session_id,
    event_type=SessionEventType.task_done,
    payload={
        "mode": "chat",
        "final_answer": final_answer,
        # 思考过程与回答消息关联，客户端刷新后仍能展开查看。
        "reasoning": reasoning,
        "message_id": str(message.id),
        "message": "问答完成。",
        "memory_ids": [str(item.id) for item in snapshot.memory_context.items],
        "memory_count": len(snapshot.memory_context.items),
        # 本轮自动检索命中的知识库文档，便于前端展示引用来源。
        "rag_sources": rag_sources,
    },
)
await uow.sessions.update_status(session_id, SessionStatus.idle.value)
await uow.sessions.touch(session_id)
await uow.commit()
```

`create_assistant_message` 是"刷新后还能看到历史"的**唯一**保证。流式增量是一次性的：它经 SSE 推给当前这个标签页，谁也没存。刷新后前端重新拉 `/api/sessions/{id}/messages`，那里必须已经有一条 assistant 消息，否则对话就断了。

`task_done` 里 `message_id` 和 `reasoning` 是一对：前者把这条事件和刚落库的消息绑定，后者存着完整思考文本。前端刷新后拿到消息列表 + 事件列表两份数据，靠 `message_id` 缝起来，就能在那条回答下面重新挂上可折叠的"推理过程"。**流式内容要想在刷新后还在，就必须在流结束时找一个地方落库，并留下能重新关联的键。**

`"模型没有返回内容，请重试。"` 这个兜底也不多余——53.10 会讲，某些中转模型会把全部输出额度用在思考上，正文真的是空的。

## 53.5 让 LLM 层支持推理流

上面用到的 `delta.kind == "reasoning"`，是这一章在基础设施层新加的能力。

### 53.5.1 增量对象与开放透传字段

`backend/api/app/domain/llm/entities.py`：

```python
# ===================== 第2.5步：定义流式输出的一段增量 =====================
@dataclass(slots=True)
class LLMStreamDelta:
    """一段流式增量。kind 为 content（正文）或 reasoning（思考过程）。"""

    kind: str
    text: str
```

同一个文件里，`LLMChatRequest` 加了一个字段：

```python
# 附加到请求体的服务商专有字段（如 DashScope 的 enable_thinking）。
extra_body: dict | None = None
```

**为什么是 `extra_body` 而不是一个 `enable_thinking: bool` 字段？** 因为"请求思考过程"没有统一标准：DashScope 用 `enable_thinking`，别家可能叫 `thinking`、`reasoning_effort`，或者干脆不需要参数。做成开放的字典透传通道，领域层就不用为每一家服务商改一次数据结构。

### 53.5.2 解析 reasoning_content

`backend/api/app/infrastructure/llm/openai_compatible.py` 的 `chat_stream`，先把 `extra_body` 合进请求体，再逐行解析 SSE：

```python
"""以流式方式调用 /chat/completions，逐段产出增量。

OpenAI 兼容协议在 stream=true 时返回 SSE：每行 `data: {json}`，
正文增量位于 choices[0].delta.content；思考型模型（Qwen/DeepSeek-R1 等）
会先在 delta.reasoning_content 输出思考过程。`data: [DONE]` 表示结束。
"""
if request.extra_body:
    payload.update(request.extra_body)
...
        async for line in response.aiter_lines():
            clean_line = line.strip()
            if not clean_line.startswith("data:"):
                continue
            data_text = clean_line.removeprefix("data:").strip()
            if data_text == "[DONE]":
                return
            try:
                chunk = json.loads(data_text)
            except json.JSONDecodeError:
                continue
            choices = chunk.get("choices") or []
            if not choices:
                continue
            delta = choices[0].get("delta") or {}
            reasoning = delta.get("reasoning_content")
            if isinstance(reasoning, str) and reasoning:
                yield LLMStreamDelta(kind="reasoning", text=reasoning)
            content = delta.get("content")
            if isinstance(content, str) and content:
                yield LLMStreamDelta(kind="content", text=content)
```

三个健壮性细节，每一个都对应过一次真实的崩溃：

1. **`JSONDecodeError` 直接 `continue`。** 中转服务偶尔插入非标准的心跳行，一行脏数据不该让整条流挂掉。
2. **`isinstance(reasoning, str) and reasoning`。** 有的服务商在没有思考内容时返回 `null`，有的返回 `""`，两个条件一起判。
3. **reasoning 与 content 是两个独立 `if`，不是 `elif`。** 同一帧里两个字段可以同时有值（思考结束、正文开始的那一帧），用 `elif` 会丢掉正文。

### 53.5.3 应用层开关与默认关闭的理由

```python
def thinking_enabled(self) -> bool:
    """流式对话是否默认请求思考过程。"""

    return bool(self.config.llm.thinking)

async def chat_stream(self, messages, ..., thinking: bool | None = None):
    """流式模型调用，逐段产出 LLMStreamDelta（reasoning / content）。

    thinking 为 None 时使用 llm.yaml 的 thinking 配置；
    开启时向服务商附加 enable_thinking（DashScope/Qwen 约定）。
    """

    effective_thinking = self.thinking_enabled() if thinking is None else thinking
    request, client = self._prepare_request(
        messages, provider, model, temperature, max_tokens,
        extra_body={"enable_thinking": True} if effective_thinking else None,
    )
    async for delta in client.chat_stream(request):
        yield delta
```

配置在 `backend/api/config/llm.yaml`：

```yaml
llm:
  default_provider: openai_compatible
  default_model: deepseek-chat
  temperature: 0.2
  max_tokens: 1024
  # 流式对话是否请求模型思考过程（Qwen/DashScope 的 enable_thinking）。
  # 开启后前端可实时查看推理过程；模型不支持时自动降级为普通流式回答。
  thinking: false
```

默认关闭，原因很直接：项目默认模型 `deepseek-chat` 不吃 `enable_thinking`，默认打开会让每次对话都先失败一次再降级，白白多一个往返。**换成百炼的 qwen-plus 或任何思考型模型时，把 `thinking` 改成 `true` 即可。**

### 53.5.4 真实踩过的坑：max_tokens 必须调高

这是本章代价最大的一个发现。

`max_tokens: 1024` 对普通对话够用。但开了思考之后，Planner 开始随机返回 fallback 计划——那个写死的四步模板。看日志，`_parse_llm_plan` 里的 `json.JSONDecodeError` 被吞了，直接走了 `_build_fallback_plan`。

原因是：**思考型模型的 reasoning 计入输出 token 额度。** 模型先花八百多个 token 思考"这个任务该怎么拆"，剩下不到两百个 token 写 JSON，写到一半被截断。截断的 JSON 解析失败，于是走 fallback。表现出来就是"计划质量时好时坏"——特别难查，因为 fallback 计划本身合法，接口不报错。

修法是把所有需要模型输出结构化内容的地方额度调高，并把原因写进注释：

```python
# planner_service.py：流式与非流式两条规划路径都是 3000
temperature=0.2,
# 思考型模型的 reasoning 计入输出额度，给足空间避免 JSON 被截断。
max_tokens=3000,

# tool_selection_service.py：工具选择器
temperature=0.1,
# 思考型模型的 reasoning 计入输出额度，给足空间避免 JSON 被截断。
max_tokens=2400,

# react_agent_service.py：最终回答总结器
temperature=0.2,
# 思考型模型的 reasoning 计入输出额度，给足空间避免总结被截断。
max_tokens=2500,
```

**判断标准很简单：任何一处"模型输出会被程序解析"的调用（JSON 计划、工具选择、结构化总结），都不能用默认额度。** 这些地方截断的后果不是"回答短了一点"，而是解析失败后静默降级，你根本不知道发生过什么。

## 53.6 三阶段推理直播

直答路径能看到思考了，工具路径还不行。难点在于：`PlannerService` 和 `ReActAgentService` 原本产出的是**完整结果**（`(plan, event)` 和 `SessionEvent`），现在要它们中途还能产出**文本增量**。两种东西类型完全不同，得混在同一个异步生成器里。

### 53.6.1 Planner：("thinking", 文本) 与 ("result", 结果)

```python
# ===================== 第2.5步：流式规划——思考过程实时可见 =====================
async def stream_plan(self, session_id: UUID, task: str):
    """流式生成计划：先逐段产出思考增量，最后产出 (plan, event)。

    产出协议：("thinking", 文本增量) × N，最后一条 ("result", (plan, event))。
    规划的思考过程会写入 plan_created 事件 payload，供事后回看。
    """
    ...
    reasoning_parts: list[str] = []
    content_parts: list[str] = []
    try:
        async for delta in self.llm_service.chat_stream(
            self._build_planning_messages(clean_task, agent_context),
            temperature=0.2,
            max_tokens=3000,
        ):
            if delta.kind == "reasoning":
                reasoning_parts.append(delta.text)
                yield ("thinking", delta.text)
            else:
                content_parts.append(delta.text)
        plan = (
            self._parse_llm_plan(task=clean_task, content="".join(content_parts))
            if content_parts
            else self._build_fallback_plan(clean_task)
        )
    except AppException:
        plan = self._build_fallback_plan(clean_task)

    payload = self._plan_to_payload(...)
    reasoning = "".join(reasoning_parts).strip()
    if reasoning:
        payload["reasoning"] = reasoning
    event = await self.uow.session_events.add(
        session_id=session_id,
        event_type=SessionEventType.plan_created,
        payload=payload,
    )
    await self.uow.sessions.touch(session_id)
    await self.uow.commit()
    yield ("result", (plan, event))
```

注意 `content_parts` 只累积不 yield。**规划阶段的正文是给程序解析的 JSON，不是给人看的**，流出去只会让用户看到一堆花括号。只有 reasoning 值得直播。和直答路径同构，思考文本最后进了 `plan_created` 的 `payload["reasoning"]`，刷新后仍能展开。

### 53.6.2 ReAct：SessionEvent 与元组混流

ReAct 的最终回答阶段是唯一需要"两种类型混在一起 yield"的地方：

```python
answer_parts: list[str] = []
reasoning_parts: list[str] = []

```

同一个生成器，前面的步骤循环 yield 的是 `SessionEvent` 对象，这里 yield 的是 `("answer_delta", "文本")` 元组。

### 53.6.3 Runner 统一转发并打 phase

ReAct 那一半用 `isinstance` 分流：

```python
# 4a. 执行计划。ReAct 持续产出 step/tool/task 事件；
#     最终回答阶段还会产出 (thinking_delta|answer_delta, 文本) 增量元组，
#     让流水线的收尾也像 GPT 一样打字机输出。
async for item in self.react_service.stream_latest_plan(session_id):
    if isinstance(item, tuple):
        kind, text = item
        yield AgentRunnerStreamItem(
            name=kind,
            payload={
                "session_id": str(session_id),
                "delta": text,
                "phase": "final_answer",
            },
        )
        continue
    yield AgentRunnerStreamItem(name=item.type.value, payload=item)
```

Planner 那一半用 `kind` 字符串分流：

```python
async for kind, value in self.planner_service.stream_plan(
    session_id=session_id,
    task=content,
):
    if kind == "thinking":
        yield AgentRunnerStreamItem(
            name="thinking_delta",
            payload={
                "session_id": str(session_id),
                "delta": value,
                "phase": "planning",
            },
        )
        continue
    _plan, plan_event = value
    yield AgentRunnerStreamItem(name=plan_event.type.value, payload=plan_event)
```

**为什么用元组和 `isinstance` 这种朴素做法，而不是定义一个统一的联合类型？** 三条理由。第一，这是**跨服务的内部协议**，只有 Runner 一个消费者，加一层类型定义要让三个文件同时引入它，收益和成本不成正比。第二，Runner 已经有 `AgentRunnerStreamItem` 这一层了——它才是对外的公共契约，内部再叠一层同构的东西是重复。第三，两种分流方式都在十行以内一眼看完，注释写清了产出协议。**朴素设计的代价要和它承载的复杂度匹配。** 增量种类涨到五六种时再抽象也不迟，现在抽象只是给自己找活干。

`phase` 字段是给排查用的：`planning` 来自规划，`final_answer` 来自流水线收尾，直答路径不带 `phase`。前端目前不区分它们（都当思考流渲染），但打开 DevTools 看 SSE 时，一眼就知道当前这段思考是哪个阶段产生的。

### 53.7.2 零延迟通道

`frontend/web/app/stores/session-store.ts` 里有一个 `getPresentationDelay`，给不同事件安排展示节奏：

```typescript
function getPresentationDelay(eventName: string) {
  // ===================== 第1步：给不同事件留出可感知的展示节奏 =====================
  // 这里不是伪造后端耗时，而是避免浏览器把 SSE 瞬间批量刷出，导致用户看不清执行顺序。
  // 直接问答的流式增量必须零延迟，否则上百个 delta 会把回答拖慢十几秒。
  if (
    eventName === "answer_started" ||
    eventName === "answer_delta" ||
    eventName === "thinking_delta"
  ) {
    return 0;
  }
  if (eventName === "message_created") return 120;
  if (eventName === "plan_created") return 460;
  if (eventName === "step_started") return 560;
  if (eventName === "tool_called") return 720;
  ...
}
```

任务类事件保留几百毫秒是刻意的，让用户看清"生成计划 → 执行步骤 → 调用工具"的顺序。但**流式增量必须零延迟**：一次回答动辄两三百个 `answer_delta`，每个哪怕只等 50 毫秒，回答就要拖十几秒。

关键在于零延迟不是"等 0 毫秒"，而是**根本不进定时器**：

```typescript
// 零延迟事件（流式增量）不进定时器：后台标签页的 setTimeout
// 会被浏览器钳制到 1 秒以上，逐字流会被拖成龟速。
const presentationDelay = getPresentationDelay(event.event);
if (presentationDelay > 0) {
  await sleep(presentationDelay);
}
```

`if (presentationDelay > 0)` 不能省成 `await sleep(delay)`。理由在注释里：**浏览器把后台标签页的 `setTimeout` 最小间隔钳制到 1 秒。** 用户发完消息切走，`await sleep(0)` 会变成实打实的一秒，两百个 delta 就是三分多钟。

### 53.7.3 缓冲与清空

```typescript
// 直接问答路径：answer_started 表示模型开始作答，
// thinking_delta 是思考过程增量，answer_delta 是正文增量。
if (event.event === "answer_started") {
  set({ liveAnswer: "", liveThinking: "", planning: false });
  return;
}
if (event.event === "thinking_delta") {
  const delta = typeof event.data.delta === "string" ? event.data.delta : "";
  if (delta) {
    set((state) => ({ liveThinking: state.liveThinking + delta }));
  }
  return;
}
if (event.event === "answer_delta") {
  const delta = typeof event.data.delta === "string" ? event.data.delta : "";
  if (delta) {
    set((state) => ({ liveAnswer: state.liveAnswer + delta }));
  }
  return;
}
```

三个 handler 都以 `return` 结尾，不往下走通用的事件处理逻辑——它们不是会话事件，不该进事件时间线。

清空缓冲的时机是最容易写错的地方：

```typescript
// 回答已经落库成正式消息，流式缓冲随即清空；
// 计划生成后，规划阶段的思考流也随之收起（已存入 plan_created 事件）。
liveAnswer:
  streamMessageItem?.role === "assistant" ? "" : state.liveAnswer,
liveThinking:
  streamMessageItem?.role === "assistant" ||
  sessionEvent.type === "plan_created"
    ? ""
    : state.liveThinking,
```

**触发点是 `message_created`（assistant 角色），不是 `task_done`。** 回答落库的那一刻正式消息已经进了消息列表，不同时清掉 `liveAnswer`，屏幕上会同时出现两份一模一样的回答——一份来自流式缓冲，一份来自正式消息。这个重影只在最后一帧闪一下，开发时很容易忽略。

`plan_created` 单独清 `liveThinking` 同理：规划思考已存进事件，任务卡片会负责展示它，流式缓冲该退场。`finally` 里还有一道兜底，处理流被中断的情况：

```typescript
} finally {
  set({
    executingPlan: false,
    liveAnswer: "",
    liveThinking: "",
    planning: false,
    sendingMessage: false,
  });
}
```

### 53.7.4 打字机节流与可折叠推理块

思考流不是均匀到达的，模型经常憋一会儿然后一次性推来两三百个字，直接渲染就是刷屏。`useTypewriter` 把它匀开，实现有两条要点（都写在源码注释里）：

- **interval 常驻，tick 里经 ref 读最新文本。** 绝不能把 interval 挂在依赖 `text` 的 effect 上——流式 delta 每几十毫秒更新一次 `text`，定时器会被反复重建，50 毫秒的 interval 永远活不到第一次触发，界面上一个字都不动。
- **用实际耗时 `dt` 推进而非固定步长。** 后台标签页定时器被钳制时，每次 tick 放出的字变多，整体速度仍稳定；`dt` 设上限避免深度节流唤醒后瞬间倾泻全部积压：

```typescript
const dt = Math.min((now - lastTickRef.current) / 1000, 2);
```

展示组件是可折叠的 `ReasoningBlock`：

```typescript
export function ReasoningBlock({ reasoning, streaming = false }: ReasoningBlockProps) {
  const [expanded, setExpanded] = useState<boolean | null>(null);
  const open = expanded ?? streaming;
  ...
      <span>{streaming ? "正在思考…" : "推理过程"}</span>
      <span className="text-(--text-5)">{reasoning.length} 字</span>
```

`useState<boolean | null>(null)` 加 `expanded ?? streaming` 是个小巧的三态：用户没点过时跟随 `streaming`（流式中自动展开，结束后自动折叠），一旦点过就以他的选择为准。**用 `null` 表示"用户还没表态"，比额外加一个 `touched` 布尔干净。**

流式中的调用点：

```typescript

  <div className="stream-in ml-11 max-w-4xl">
    <ReasoningBlock reasoning={pacedThinking} streaming={!liveAnswer} />
  </div>
) : null}
```

`streaming={!liveAnswer}` 表达的是"正文还没开始 = 还在思考"。正文一开始流，思考块自动折叠让位。

### 53.7.5 刷新后的回看

## 53.8 会话卡死的兜底修复

回到 53.2 的问题四。`stream_user_message` 正常结束时会把会话置回 idle，但客户端中断 SSE 时，Python 在当前 `yield` 处关闭这个 async generator，后面的代码一行都不执行。

修法是把主体拆出去，外层只做兜底：

```python
async def stream_user_message(self, *, session_id: UUID, content: str):
    """把用户消息转换成可流式观察的 Agent 执行过程。

    finally 兜底：客户端中断 SSE 时 async generator 在当前 yield 处
    被关闭，正常收尾不再执行；这里保证会话不会永远停在 running。
    """

    try:
        async for item in self._stream_user_message_inner(
            session_id=session_id,
            content=content,
        ):
            yield item
    finally:
        await self._reset_running_session(session_id)
```

`finally` 在 generator 被关闭时也会执行（`GeneratorExit` 也是异常），所以能拦住中断。

```python
async def _reset_running_session(self, session_id: UUID) -> None:
    """把仍处于 running 的会话恢复为 idle（尽力而为）。

    客户端中断 SSE 时，async generator 在当前 yield 处被关闭，
    正常收尾逻辑不再执行；不做兜底会话就永远停在“运行中”。
    """

    try:
        uow = self.session_service.uow
        session = await uow.sessions.get(session_id)
        if session is not None and session.status is SessionStatus.running:
            await uow.sessions.update_status(session_id, SessionStatus.idle.value)
            await uow.commit()
    except Exception:
        # 连接可能已随请求关闭；兜底失败不影响主流程。
        return
```

两个设计点：

**只在状态确实是 `running` 时才改。** 正常走完的会话已经是 `idle`，失败的会话是 `failed`，都不该被兜底覆盖。少了这个判断，任务失败后的 `failed` 会被改成 `idle`，错误就被抹掉了。

**整个函数吞掉所有异常。** SSE 中断往往伴随请求作用域被销毁，数据库会话可能已经关了。兜底本身失败是可接受的——它只是"尽力而为"。让它的异常冒出去，会把一个"用户关了标签页"变成一条服务端 ERROR 日志。

```python
class NeedsAgentPipelineTest(unittest.TestCase):
    def test_plain_questions_go_direct(self) -> None:
        for content in (
            "你好",
            "Python 的 GIL 是什么？",
            "帮我解释一下这段报错的含义",
            "什么是控制反转",
            # 编程问答里的“查找/写/验证”不该误触流水线——
            # 这类问题应该像 GPT 一样直接流式回答。
            "帮我写一个二分查找函数，并验证空数组等边界情况",
            "怎么读取列表的最后一个元素",
            "如何保存 Python 字典到变量里",
        ):
            self.assertFalse(needs_agent_pipeline(content), content)

    def test_tool_intents_go_pipeline(self) -> None:
        for content in (
            "搜索最近的 FastAPI 版本变化",
            "打开 https://example.com 并截图",
            "把结果写入文件 report.md",
            "执行 pytest 并总结失败原因",
            "请执行一个测试任务",
            "在沙箱里运行这个脚本",
            "把统计结果保存到 result.txt",
        ):
            self.assertTrue(needs_agent_pipeline(content), content)
```

`assertFalse(..., content)` 第二个参数把消息本身作为失败信息传进去——七个用例挂了哪一个，报错信息直接告诉你，不用数下标。

流程测试用两个替身做**否定断言**，比"断言 Planner 没被调用"更直接：路由一旦退化，测试会在退化的那一行炸掉，堆栈直接指向问题。

```python
class UnusedPlannerService:
    async def stream_plan(self, session_id: UUID, task: str):
        raise AssertionError("普通问答不应触发 Planner")
        yield  # pragma: no cover
```

（那个够不着的 `yield` 是为了让 Python 把方法识别成异步生成器，否则 `async for` 会先报类型错误。）

主流程测试断言了完整的事件序列和落库结果：

```python
names = [item.name for item in items]
self.assertEqual(
    names,
    [
        "session_status", "message_created", "answer_started",

```

思考流测试断言了顺序和归属：

```python
self.assertEqual(names.count("thinking_delta"), 2)
# 思考增量必须在正文增量之前。
self.assertLess(names.index("thinking_delta"), names.index("answer_delta"))
# task_done 关联了 assistant 消息 id，刷新后客户端可以据此展示推理过程。
```

最后一条尤其重要：**推理过程不能混进正式回答。** 少了 `if delta.kind == "reasoning"` 的分支，用户会看到模型自言自语的草稿被当成答案存进消息列表。

### 53.9.2 手工验收

```bash
# 后端
cd backend/api && uvicorn app.main:app --reload --port 8000

# 前端（注意这个环境变量，理由见 53.10 坑一）
cd frontend/web
NEXT_PUBLIC_STREAM_BASE=http://127.0.0.1:8000 pnpm dev
```

逐项确认：

1. **直答不进流水线。** 问"什么是闭包"，界面上**不应该**出现任务卡片，回答应该逐字流出；后端日志里不应有 Planner 相关调用。
2. **工具意图进流水线。** 问"在沙箱里执行这个脚本"，应该先出现任务卡片和步骤列表，再执行工具。
3. **推理流在几秒内逐段出现。** 前提是 `llm.yaml` 里 `thinking: true` 且模型支持。用户消息下方出现"正在思考…"折叠块，文字持续增长，**第一段应在两三秒内出现，而不是憋十秒后一次性弹出**。
4. **正文开始时思考块自动折叠**，标题变成"推理过程 N 字"。
5. **刷新后历史还在。** F5 刷新，那条助手回答仍在消息列表里，下面挂着可点开的"推理过程"。这一条同时验证了"回答落库"和"reasoning 关联 message_id"两件事。
6. **工具路径的两段思考也可回看。** 跑一个工具任务，刷新后展开任务卡片能看到规划阶段的推理，展开最终回答能看到总结阶段的推理。
7. **中断不卡死。** 模型还在流的时候直接关掉标签页，重新打开，会话列表里那一条应该是"空闲"而不是"运行中"。
8. **没配 Key 也不报错。** 临时清掉 `LLM_API_KEY` 重启后端再发消息，应该得到那段三行的排查指引，而不是 500。

第 3 条如果不达标——推理确实出现了，但憋很久一次性出现——**先别怀疑后端**，直接看下一节。

## 53.10 常见坑

**坑一：Next dev 的 rewrite 代理会把 SSE 整条缓冲。**

这是本章最难查的问题，因为它的表现完全指向后端：前端等六七秒，然后一次性收到全部推理和回答。

但后端一切正常。加日志，`yield` 是逐条发出去的，间隔几十毫秒。`curl` 直连后端也是逐段到达：

```bash
curl -N -X POST http://127.0.0.1:8000/api/sessions/$SESSION_ID/messages/stream \
  -H "Content-Type: application/json" \
  -d '{"content":"什么是闭包"}'
```

问题出在中间。本地开发时前端请求 `/api/...`，走的是 `next.config.ts` 里的 rewrite：

```typescript
async rewrites() {
  return [
    {
      source: "/api/:path*",
      destination:
        process.env.API_PROXY_URL ?? "http://localhost:8000/api/:path*",
    },
```

**Next 的开发服务器代理会把响应体整体缓冲后再转发。** 后端流了 6.9 秒，代理攒够了才一次性交给浏览器。

定位方法是在浏览器控制台给 `fetch` 装个间谍，数 chunk 个数和到达时间：

```javascript
// 浏览器控制台执行，然后正常发一条消息
const origFetch = window.fetch;
window.fetch = async (...args) => {
  const response = await origFetch(...args);
  if (!String(args[0]).includes("/messages/stream")) return response;
  const t0 = performance.now();
  let count = 0;
  const reader = response.body.getReader();
  const spied = new ReadableStream({
    async pull(controller) {
      const { done, value } = await reader.read();
      if (done) {
        console.log(`[spy] 结束 chunks=${count} 总耗时=${(performance.now() - t0).toFixed(0)}ms`);
        controller.close();
        return;
      }
      count += 1;
      console.log(`[spy] chunk #${count} @ ${(performance.now() - t0).toFixed(0)}ms  ${value.length}B`);
      controller.enqueue(value);
    },
  });
  return new Response(spied, response);
};
```

结论一目了然：

```text
[spy] chunk #1 @ 6912ms  18437B
[spy] 结束 chunks=1 总耗时=6913ms
```

**一个 chunk、18KB、6.9 秒。** 这不是"推理不流式"，这是整条流被攒成了一个包。正常应该看到几十上百个几百字节的 chunk。

解法是让流式端点绕过代理直连后端：

```typescript
// 本地开发时 Next 的 rewrite 代理会把 SSE 整体缓冲，逐字流会退化成
// “憋很久然后一次性弹出”。设置 NEXT_PUBLIC_STREAM_BASE（如
// http://127.0.0.1:8000）让流式端点直连后端绕过代理；后端 CORS 已放行
// localhost:3000。生产环境不设置该变量，走 Nginx（已配 proxy_buffering off）。
const STREAM_BASE = process.env.NEXT_PUBLIC_STREAM_BASE ?? "";

const response = await fetch(
  `${STREAM_BASE}/api/sessions/${sessionId}/messages/stream`,
  ...
```

只有这一个端点带 `STREAM_BASE`，其他 REST 请求继续走代理（它们本来就是一次性响应）。跨域由后端 CORS 兜住，`backend/api/app/core/config.py` 默认就放行了本地前端：

```python
cors_allow_origins: list[str] = [
    "http://localhost:3000",
    "http://127.0.0.1:3000",
]
```

**生产环境不设这个变量**，因为走的是 Nginx，而 `nginx/default.conf` 早就配好了：

```nginx
location /api/ {
    proxy_buffering off;
    proxy_cache off;
    proxy_set_header X-Accel-Buffering no;
    proxy_pass http://api:8000;
}
```

这条经验可以推广：**任何"后端在流、前端不流"的问题，先用 `curl -N` 直连后端确认后端没问题，再沿链路一段一段找缓冲点。** 开发代理、Nginx、CDN、企业代理甚至杀毒软件的 HTTPS 扫描，任何一环都可能把流攒成包。后端能做的只是发出 `X-Accel-Buffering: no` 这个信号，但不是所有代理都听。

**坑二：前端处理流式事件时 `await sleep(0)`。**

`sleep(0)` 内部是 `window.setTimeout(resolve, 0)`，而**浏览器把非活动标签页的 `setTimeout` 最小间隔钳制到 1 秒**。用户发完消息切走，两百个 `answer_delta` 就是三分多钟。正确写法是**跳过定时器**，而不是把延迟设成 0：

```typescript
if (presentationDelay > 0) {
  await sleep(presentationDelay);
}
```

同一个陷阱在 `useTypewriter` 里换了个形式：定时器被钳制后如果按固定步长推进，速度会掉到二十分之一。那里的解法是按实际耗时 `dt` 推进并给 `dt` 设上限。

**坑三：中转服务和第三方模型的行为差异极大。**

同样是"OpenAI 兼容"，实际表现能差出三个档：

- **有的模型原生输出 `reasoning_content`，根本不需要 `enable_thinking`。** DeepSeek-R1 系列就是这样，给它传这个参数反而可能报 400。这就是 `llm.yaml` 默认 `thinking: false` 的原因——**默认不发送非标准参数，需要时再打开。**
- **有的模型把额度全用在思考上，正文是空的。** 尤其在 `max_tokens` 偏小时。这时 `answer_parts` 是空列表，所以才有 `"".join(answer_parts).strip() or "模型没有返回内容，请重试。"` 这个兜底；没有它，落库的就是一条空消息。
- **有的中转服务不返回 `reasoning_content`，只是把思考混进 `content`。** 这种情况下 `<think>...</think>` 会原样出现在回答里。我们没有在解析层做剥离——那需要猜测标签格式，猜错了会吃掉正常内容。更稳的做法是换一个规范的服务商。

排查顺序：先用 `curl` 直接打服务商的 `/chat/completions`，看原始 SSE 帧里到底有没有 `reasoning_content`，再决定是配置问题还是代码问题。**不要在应用层猜服务商的行为，去看原始响应。**

**坑四：把 `enable_thinking` 写进 `LLMChatRequest` 的具名字段。** 看起来更类型安全，实际是把一个服务商的私有约定固化进了领域模型。换成需要 `reasoning_effort` 的服务商时，三层都要改。

**坑五：用 `elif` 处理 reasoning 和 content。** 思考结束、正文开始的那一帧两个字段可能同时有值，`elif` 会静默吃掉那一小段正文，表现是回答开头缺几个字——非常难发现。

**坑六：清空流式缓冲的时机绑到 `task_done`。** `message_created`（assistant）比 `task_done` 早一帧，绑到 `task_done` 意味着中间这一帧屏幕上同时存在两份相同内容，重影闪一下。

## 53.11 本章小结

这一章做的事情用一句话概括：**让这个 Agent 平台在"能干活"之外，也真正会说话。**

四条经验值得带走：

1. **路由的偏向性要和误判代价匹配。** `needs_agent_pipeline` 默认返回 `False`，因为误判进流水线的代价是慢十倍加答非所问，误判进直答的代价只是少调一次工具。有歧义的词不要放宽，把它扩成更长的短语。
2. **流式内容想活过刷新，必须在流结束时落库并留下关联键。** 直答路径的 `create_assistant_message` 加上 `task_done` 里的 `message_id + reasoning`，就是"刷新后推理过程还能展开"的全部秘密。三个阶段的思考落在三个不同事件里，前端用同一套 map 缝回去。
3. **思考型模型的 reasoning 计入输出额度。** 任何"模型输出会被程序解析"的调用都必须调高 `max_tokens`，否则 JSON 被截断后静默走 fallback，你根本不知道发生过什么。这是本章代价最大的一个教训。
4. **"后端在流、前端不流"，先怀疑链路。** 用 `curl -N` 确认后端，再用 fetch 间谍数 chunk。开发代理、Nginx、CDN 任何一环都可能把流攒成包，而后端发出的 `X-Accel-Buffering: no` 不是所有代理都听。

顺带说一句朴素设计的价值。Planner 用 `("thinking", text)` 元组、ReAct 用 `isinstance(item, tuple)` 分流，两处风格还不完全一致——这在代码审查里一定会被挑。但它们各自十行以内、注释写清了产出协议、只有一个消费者。**在只有一个消费者的内部协议上做类型抽象，成本立刻发生，收益要等到第三个消费者出现。** 那一天来了再抽也不迟。

至此，AtlasAgent 的一次用户消息有了两条完全不同的命运：一句"什么是闭包"在一秒内开始逐字回答，一句"在沙箱里跑这个脚本"照旧走完整的计划-执行-总结。而无论走哪条路，模型在想什么，用户都看得见。
