# 第二十一章. 上下文工程

## 21.1 本章目标
​        第 20 章让 Agent 执行进入了后台任务模型，但后台任务能跑起来并不代表它总能拿到合适的上下文。长任务执行到后半段时，系统可能已经积累了大量消息、事件和文件引用，如果把所有内容原样塞给模型，很快就会遇到上下文窗口、噪声干扰和文件内容过长的问题。
​        本章会实现上下文工程的第一版闭环。后端会定义会话上下文快照，对消息做数量限制和单条内容裁剪，对事件按类型聚合摘要，把文件作为引用放入上下文，而不是直接塞入完整文件内容。前端会新增“上下文工程”面板，让读者能看到 Agent 继续执行时到底会带入哪些消息、事件摘要、文件引用和预算信息。

## 21.2 最终效果
​        本章结束后，后端新增接口：

```Plain
GET /api/sessions/{session_id}/context
```

​        这个接口会返回当前会话的上下文快照：

```JSON
{
  "summary": "当前会话共有 3 条消息、8 条事件、1 个文件引用...",
  "messages": [],
  "event_summaries": [],
  "files": [],
  "budget": {}
}
```

​        前端会新增“上下文工程”面板，展示上下文摘要、纳入和省略的消息数量、纳入和省略的事件数量、最近消息、事件摘要和文件引用。这个面板不是给用户继续聊天用的，而是帮助开发者观察 Agent 下一步执行时会参考什么材料。

## 21.3 本章要解决的问题
​        前面章节已经有了：

```Plain
消息列表
事件列表
文件列表
PlannerAgent
ReActAgent
后台任务 Runner
```

​        但还缺一个关键能力：Agent 下一次继续执行时，到底应该带哪些上下文？
​        一个简单做法是把所有历史消息、所有事件和所有文件内容都塞给模型。但真实项目不能这样做。
​        原因很直接：模型上下文窗口有限，内容太多会超出限制；很多旧事件只是过程记录，不需要原样进入模型；文件内容可能非常长，如果直接塞入消息列表，会让对话上下文被文件噪声淹没。上下文工程要做的不是“尽量多塞”，而是把下一步执行真正需要的信息整理出来。
​        所以本章引入“上下文工程”：

```Plain
原始会话数据
  |
  +-- 消息：保留最近几条，过长内容裁剪
  +-- 事件：按类型聚合成摘要
  +-- 文件：只放引用和使用提示
  |
  v
上下文快照
```

## 21.4 本章技术方案
​        后端调用链路：

```Plain

  |

  +-- 读取 session_events
  +-- 读取 session_files
  +-- 裁剪消息
  +-- 聚合事件

```

```Plain

  v

```

​        本章暂时不使用 LLM 生成自然语言摘要，不把完整文件内容直接塞入上下文，也不做向量检索、跨会话长期记忆或 token 精确计算。这里先用确定性规则建立上下文工程的结构，后续再把摘要、检索、压缩和长期记忆逐步替换成更智能的实现。

## 21.7 实施步骤
### 21.7.1 增加上下文预算配置
​        打开 `api/app/core/config.py`，在 `Settings` 中加入：

```Python
context_message_limit: int = 8
context_event_limit: int = 20
context_max_message_chars: int = 1200
```

​        同时打开 `.env.example`，加入：

```Plain
# Context engineering defaults.
CONTEXT_MESSAGE_LIMIT=8
CONTEXT_EVENT_LIMIT=20
CONTEXT_MAX_MESSAGE_CHARS=1200
```

​        打开 `docker-compose.yml`，在 `api.environment` 中加入：

```YAML
CONTEXT_MESSAGE_LIMIT: ${CONTEXT_MESSAGE_LIMIT:-8}
CONTEXT_EVENT_LIMIT: ${CONTEXT_EVENT_LIMIT:-20}
CONTEXT_MAX_MESSAGE_CHARS: ${CONTEXT_MAX_MESSAGE_CHARS:-1200}
```

#### 21.7.1.1 代码讲解
​        这三个配置是本章的上下文预算。
​        `context_message_limit` 表示最多放多少条最近消息。
​        `context_event_limit` 表示最多参考多少条最近事件。注意，这里不是把事件原样返回给模型，而是先取最近事件，再按类型压缩成摘要。
​        `context_max_message_chars` 表示单条消息最多保留多少字符。用户可能粘贴很长内容，如果不裁剪，一条消息就可能占满上下文。
​        这一步先用字符数估算预算。后续接入更完整的模型上下文管理时，可以替换成 token 计算。

### 21.7.2 定义上下文工程领域模型
​        创建 `api/app/domain/context_engineering/__init__.py`：

```Python
"""Context engineering domain objects."""
```

​        创建 `api/app/domain/context_engineering/entities.py`：

```Python
from dataclasses import dataclass
from datetime import datetime
from uuid import UUID


@dataclass(slots=True)
class ContextMessage:
    role: str
    content: str
    original_chars: int  # 保留原始长度，方便判断内容被裁剪了多少。
    truncated: bool  # 标记 content 是否已经按上下文预算裁剪。
    created_at: datetime


@dataclass(slots=True)
class ContextEventSummary:
    type: str
    count: int  # 同类型事件在最近事件窗口里出现了多少次。
    latest_at: datetime  # 这个事件类型最近一次出现的时间。


@dataclass(slots=True)
class ContextFileReference:
    id: UUID
    name: str
    content_type: str
    size: int
    usage_hint: str  # 提醒 Agent 后续应该如何使用这个文件。


@dataclass(slots=True)
class ContextBudget:
    message_limit: int  # 配置允许纳入的最大消息条数。
    event_limit: int  # 配置允许参考的最大事件条数。
    max_message_chars: int  # 单条消息允许保留的最大字符数。
    included_messages: int  # 本次快照实际纳入的消息条数。
    omitted_messages: int  # 因预算限制被省略的历史消息条数。
    included_events: int  # 本次快照参考的最近事件数量。
    omitted_events: int  # 因预算限制被省略的历史事件数量。
    total_message_chars: int  # 裁剪后消息内容的总字符数。


@dataclass(slots=True)
class SessionContextSnapshot:
    session_id: UUID
    summary: str
    messages: list[ContextMessage]
    event_summaries: list[ContextEventSummary]
    files: list[ContextFileReference]
    budget: ContextBudget
```

#### 21.7.2.1 这段代码在流程中的位置
​        这些 dataclass 是上下文快照的领域对象。
​        它们不直接关心 HTTP，也不直接关心前端展示。它们只描述一件事：当前会话整理后能给 Agent 使用的上下文是什么样。

#### 21.7.2.2 输入和输出
​        输入来自三类原始数据：

```Plain
SessionMessage
SessionEvent
SessionFile
```

​        输出是：

```Plain
SessionContextSnapshot
```

#### 21.7.2.3 关键对象解释
​        `ContextMessage` 是裁剪后的消息。它保留 `original_chars` 和 `truncated`，是为了让前端知道这条消息是不是被裁剪过。
​        `ContextEventSummary` 是事件摘要。事件表可能有很多条 `step_started`、`tool_called`，上下文里不一定需要每一条的完整 payload，所以先按类型聚合。
​        `ContextFileReference` 是文件引用。文件内容可能很长，本章只把文件名、类型、大小和使用提示放进上下文。
​        `ContextBudget` 是预算报告。它告诉页面本次纳入了多少消息，省略了多少消息，纳入了多少事件，省略了多少事件。

#### 21.7.2.4 字段含义
​        `ContextMessage.role` 表示消息角色，后续组装 LLM 消息时会用它决定内容放到哪个角色下；`ContextMessage.content` 是已经处理过的消息内容，可能是原文，也可能是裁剪后的文本。`original_chars` 和 `truncated` 是一组配套字段：前者保留原始长度，后者说明内容是否已经被裁剪，前端可以据此显示“已按预算裁剪”的提示。
​        `ContextEventSummary` 用来压缩事件。`type` 表示事件类型，例如 `message_created`、`tool_called`、`task_done`；`count` 表示最近事件窗口里这种事件出现了多少次；`latest_at` 表示这种事件最近一次发生的时间。这样 Agent 看到的是过程密度和最近变化，而不是一堆重复的原始 payload。
​        `ContextFileReference.usage_hint` 是文件使用提示，它不是文件内容，而是告诉 Agent 这个文件应该被读取、下载，还是只作为引用保留。`ContextBudget.omitted_messages` 和 `ContextBudget.omitted_events` 则负责让“省略了什么”可见。上下文工程如果只告诉你纳入了什么，却不告诉你丢掉了什么，后续调试会非常困难。

#### 21.7.2.5 为什么这样设计
​        上下文工程不是简单地“查数据库然后返回”。
​        它要做筛选、裁剪、摘要和引用管理。所以单独定义领域对象，可以让后续替换摘要策略或文件检索策略时，不影响 API 层和前端组件。

### 21.7.3 编写 ContextEngineeringService
​        创建 `api/app/application/context_engineering_service.py`：

```Python
from collections import Counter
from uuid import UUID

from app.application.unit_of_work import UnitOfWork
from app.core.config import settings
from app.core.exceptions import AppException
from app.domain.context_engineering.entities import (
    ContextBudget,
    ContextEventSummary,
    ContextFileReference,
    ContextMessage,
    SessionContextSnapshot,
)
from app.domain.files.entities import SessionFile
from app.domain.sessions.entities import SessionEvent, SessionMessage


class ContextEngineeringService:
    """生成会话上下文快照。

    上下文快照不是把所有历史内容原样塞给 Agent。
    它会按预算裁剪消息、压缩事件、只引用文件清单，为后续长任务执行打基础。
    """

    def __init__(self, uow: UnitOfWork) -> None:
        # ===================== 第1步：保存数据库事务入口 =====================
        self.uow = uow

    # ===================== 第2步：构建当前会话上下文快照 =====================
    async def build_snapshot(self, session_id: UUID) -> SessionContextSnapshot:
        """读取会话数据，并转换成适合 Agent 继续执行的上下文。"""

        session = await self.uow.sessions.get(session_id)
        if session is None:
            raise AppException(
                message="session not found",
                code=404,
                status_code=404,
            )

        messages = await self.uow.session_messages.list_by_session(session_id)
        events = await self.uow.session_events.list_by_session(session_id)
        files = await self.uow.session_files.list_by_session(session_id)

        context_messages = self._build_messages(messages)
        event_summaries = self._build_event_summaries(events)
        file_references = self._build_file_references(files)
        budget = self._build_budget(
            all_messages=messages,
            included_messages=context_messages,
            all_events=events,
        )
        summary = self._build_summary(
            message_count=len(messages),
            event_count=len(events),
            file_count=len(files),
            budget=budget,
        )

        return SessionContextSnapshot(
            session_id=session_id,
            summary=summary,
            messages=context_messages,
            event_summaries=event_summaries,
            files=file_references,
            budget=budget,
        )

    # ===================== 第3步：裁剪消息上下文 =====================
    def _build_messages(self, messages: list[SessionMessage]) -> list[ContextMessage]:
        """只保留最近几条消息，并裁剪过长内容。"""

        recent_messages = messages[-settings.context_message_limit :]
        context_messages: list[ContextMessage] = []
        for message in recent_messages:
            content = message.content
            truncated = len(content) > settings.context_max_message_chars
            if truncated:
                content = content[: settings.context_max_message_chars] + "\n...[内容已裁剪]"
            context_messages.append(
                ContextMessage(
                    role=message.role.value,
                    content=content,
                    original_chars=len(message.content),
                    truncated=truncated,
                    created_at=message.created_at,
                )
            )
        return context_messages

    # ===================== 第4步：压缩事件上下文 =====================
    def _build_event_summaries(
        self,
        events: list[SessionEvent],
    ) -> list[ContextEventSummary]:
        """把大量事件压缩成按类型聚合的摘要。"""

        recent_events = events[-settings.context_event_limit :]
        counts = Counter(event.type.value for event in recent_events)
        latest_by_type: dict[str, SessionEvent] = {}
        for event in recent_events:
            latest_by_type[event.type.value] = event

        return [
            ContextEventSummary(
                type=event_type,
                count=count,
                latest_at=latest_by_type[event_type].created_at,
            )
            for event_type, count in counts.items()
        ]

    # ===================== 第5步：把文件变成引用清单 =====================
    def _build_file_references(
        self,
        files: list[SessionFile],
    ) -> list[ContextFileReference]:
        """上下文中只放文件引用，不直接塞入完整文件内容。"""

        return [
            ContextFileReference(
                id=session_file.file.id,
                name=session_file.file.original_name,
                content_type=session_file.file.content_type,
                size=session_file.file.size,
                usage_hint=self._build_file_usage_hint(session_file),
            )
            for session_file in files
        ]

    # ===================== 第6步：计算上下文预算 =====================
    def _build_budget(
        self,
        all_messages: list[SessionMessage],
        included_messages: list[ContextMessage],
        all_events: list[SessionEvent],
    ) -> ContextBudget:
        total_chars = sum(len(message.content) for message in included_messages)
        return ContextBudget(
            message_limit=settings.context_message_limit,
            event_limit=settings.context_event_limit,
            max_message_chars=settings.context_max_message_chars,
            included_messages=len(included_messages),
            omitted_messages=max(len(all_messages) - len(included_messages), 0),
            included_events=min(len(all_events), settings.context_event_limit),
            omitted_events=max(len(all_events) - settings.context_event_limit, 0),
            total_message_chars=total_chars,
        )

    def _build_summary(
        self,
        message_count: int,
        event_count: int,
        file_count: int,
        budget: ContextBudget,
    ) -> str:
        return (
            f"当前会话共有 {message_count} 条消息、{event_count} 条事件、"
            f"{file_count} 个文件引用；本次上下文纳入 {budget.included_messages} 条最近消息，"
            f"压缩 {budget.included_events} 条最近事件。"
        )

    @staticmethod
    def _build_file_usage_hint(session_file: SessionFile) -> str:
        file = session_file.file
        if file.content_type.startswith("text/") or file.content_type in {
            "application/json",
            "application/xml",
            "application/yaml",
        }:
            return "可在需要时读取文本预览或下载内容。"
        return "当前只作为文件引用放入上下文，暂不直接读取内容。"
```

#### 21.7.3.1 这段代码在流程中的位置
​        `ContextEngineeringService` 位于应用服务层。
​        调用链路是：

```Plain
Route -> ContextEngineeringService -> UnitOfWork -> Repository -> Database
```

#### 21.7.3.2 输入和输出
​        输入是一个 `session_id`。
​        输出是一个 `SessionContextSnapshot`，里面已经包含裁剪后的消息、聚合后的事件摘要、文件引用和预算统计。路由层拿到这个对象后，只需要把它转换成 Pydantic 响应模型即可，不再关心具体裁剪和聚合规则。

#### 21.7.3.3 关键代码逐段解释
​        `build_snapshot()` 先检查会话是否存在。如果会话不存在，直接抛出 404，避免继续查询消息、事件和文件。
​        然后读取三类数据：

```Python
messages = await self.uow.session_messages.list_by_session(session_id)
events = await self.uow.session_events.list_by_session(session_id)
files = await self.uow.session_files.list_by_session(session_id)
```

​        这三类数据就是上下文工程的原材料。
​        `_build_messages()` 使用：

```Python
messages[-settings.context_message_limit :]
```

​        只保留最近几条消息。长任务中，越新的消息通常越接近当前目标，旧消息可以被摘要替代。
​        如果单条消息太长，会追加：

```Plain
...[内容已裁剪]
```

​        这样前端和后续 Agent 都能知道这不是完整内容。
​        `_build_event_summaries()` 用 `Counter` 按事件类型计数。例如最近事件里有 3 次 `tool_called`，上下文里就不需要放 3 个完整 payload，而是放：

```Plain
tool_called：3 次
```

​        `_build_file_references()` 不读取文件内容，只返回文件引用。这是本章一个重要取舍：文件系统可以替代消息列表承载长内容，消息上下文里只放“有哪些文件、需要时怎么用”。
​        `_build_budget()` 不只是为了展示数字。它是后续调试 Agent 的依据。比如上下文面板显示 `omitted_messages=12`，就说明当前模型没有看到 12 条更早的消息。如果 Agent 漏掉了早期需求，就可以从这里判断是否需要摘要旧消息。
​        `_build_file_usage_hint()` 是文件上下文的第一版策略。文本类文件会提示“可读取文本预览或下载内容”；非文本文件先只作为引用。这样做是为了避免把图片、压缩包、二进制文件硬塞进文本上下文。

#### 21.7.3.4 小白最容易困惑的点
​        上下文快照不是页面展示用的普通详情接口。
​        它的目标是回答：

```Plain
如果 Agent 下一步继续执行，应该带什么信息？
```

​        所以它不会把所有历史内容原样返回，而是主动做取舍。

### 21.7.4 增加 API 响应模型
​        打开 `api/app/schemas/session.py`，新增：

```Python
class ContextMessageResponse(BaseModel):
    role: str
    content: str
    original_chars: int
    truncated: bool
    created_at: datetime


class ContextEventSummaryResponse(BaseModel):
    type: str
    count: int
    latest_at: datetime


class ContextFileReferenceResponse(BaseModel):
    id: UUID
    name: str
    content_type: str
    size: int
    usage_hint: str


class ContextBudgetResponse(BaseModel):
    message_limit: int
    event_limit: int
    max_message_chars: int
    included_messages: int
    omitted_messages: int
    included_events: int
    omitted_events: int

class SessionContextResponse(BaseModel):
    session_id: UUID

    event_summaries: list[ContextEventSummaryResponse]

```

#### 21.7.4.1 代码讲解
​        这些 Pydantic 模型是接口返回给前端的数据结构。
​        领域层用 dataclass，API 层用 Pydantic。这样领域对象可以保持简单，API 响应结构也更清晰，同时 FastAPI 文档能自动展示字段。以后如果内部快照对象发生变化，接口层仍然可以通过转换函数保持对前端稳定。
​        `ContextBudgetResponse` 很重要。它让前端不只看到“返回了什么”，还能看到“省略了什么”。
​        上下文工程一定要让省略可见，否则调试 Agent 时会很难判断模型为什么漏掉某些历史信息。

#### 21.7.4.2 字段含义
​        `summary` 是给人看的上下文概览，不是模型最终回答，而是说明这次快照纳入了多少消息、事件和文件。`messages` 是裁剪后的最近消息列表，前端用它展示“模型能看到的对话内容”。`event_summaries` 是压缩后的事件摘要，不展示每一条事件 payload，而是展示事件类型和出现次数。`files` 是文件引用列表，只放文件名、类型、大小和使用提示，不放完整文件内容。`budget` 是预算统计，让用户知道当前上下文纳入了多少内容，也省略了多少内容。

## 21.8 关键理解
​        本章最重要的是理解：上下文不是越多越好。
​        Agent 长任务里常见的问题不是“信息不够”，而是“信息太乱”。旧消息可能干扰新任务，工具结果可能过长，事件 payload 可能又碎又重复，文件内容如果直接塞进消息列表，模型反而更难找到真正的任务目标。上下文工程要解决的就是这些噪声管理问题。
​        所以需要上下文工程。
​        本章先做了三个确定性策略：

```Plain
消息裁剪：保留最近 N 条，单条超长裁剪
事件压缩：最近事件按类型聚合
文件引用：上下文只放文件信息，不直接放完整内容
```

​        这三个策略简单，但已经能建立正确的工程边界。
​        更重要的是，这一章开始把“模型输入”从临时拼接字符串变成了可以被观察、被调试、被配置的工程对象。以后 Agent 回答不准确时，开发者不必只猜提示词哪里写得不好，而是可以先看上下文快照：最近消息是否被纳入，旧消息是否被省略，事件是否被压缩，文件是否只是引用，预算是否过小。这个视角会让后续调试长任务稳定性时更有抓手。

## 21.9 技术难点与亮点
​        本章的技术难点在于上下文快照不是普通详情接口，它要主动裁剪、压缩和引用。消息、事件和文件来自不同表，需要在应用服务中汇总；文件内容不能随便塞进消息上下文，否则很容易污染任务；前端还要展示省略数量，让上下文取舍变得可见。
​        项目亮点在于 Agent 执行开始具备上下文预算意识。前端能直观看到“模型下一步会参考什么”，文件系统也开始从附件展示升级为上下文来源。后续接入 LLM 摘要、向量检索和长期记忆时，可以沿用这一章建立的快照结构。

## 21.10 面试考点
​        面试里可以从“为什么不能把所有历史消息都放进模型上下文”讲起。消息裁剪解决的是窗口限制和近期目标优先级，事件摘要解决的是过程事件过多和 payload 过碎的问题，文件引用解决的是大文件不能直接塞进对话消息的问题。上下文预算要让省略数量可见，是为了让调试时能判断模型漏掉信息到底是能力问题，还是上下文没有带进去。上下文工程和 RAG 的关系也可以顺带说明：RAG 是上下文来源的一种，上下文工程负责决定这些来源如何进入模型输入。

## 21.12 常见问题

### 21.12.1 上下文面板为空怎么办
​        先确认已经选择会话，并且会话里有消息、事件或文件。也可以直接请求 `GET /api/sessions/{session_id}/context` 检查后端返回。如果接口有数据但页面为空，重点检查 `session-store.ts` 是否在加载会话详情时同步请求了上下文。

### 21.12.2 为什么文件面板有文件但上下文里只显示文件名
​        本章只把文件作为引用放入上下文，不直接读取完整文件内容。这样可以避免大文件污染消息上下文，也能让 Agent 在需要时再通过文件工具读取具体内容。文件名、类型、大小和使用提示已经足够作为下一步执行的引用线索。

### 21.12.3 为什么不用 LLM 做摘要
​        本章先建立上下文工程的数据结构和预算规则。LLM 摘要还涉及成本、失败、缓存、可重复性和提示词稳定性，如果在这一章直接加入，会把“上下文结构”这条主线打散。后续可以在 `ContextEngineeringService` 内部替换事件摘要或旧消息摘要策略。

### 21.12.4 为什么按字符数裁剪不按 token
​        字符数裁剪实现简单，适合先理解流程，也不依赖具体模型 tokenizer。真实生产环境可以换成模型 tokenizer 做 token 级预算，或者根据不同 provider 使用不同的估算器。本章保留 `context_max_message_chars`，是为了先让预算配置和裁剪机制可见。

## 21.13 本章小结
​        本章完成了上下文工程的第一版闭环。后端新增上下文预算配置，定义上下文快照领域模型，并通过 `ContextEngineeringService` 汇总消息、事件和文件，生成裁剪后的消息、聚合后的事件摘要、文件引用和预算统计；接口层新增会话上下文接口，前端新增上下文类型、API helper、store 状态和上下文工程面板。
​        从这一章开始，Agent 不再只是执行步骤，而是开始有意识地管理“下一步要带什么上下文”。这会直接影响后续长任务、文件工具、沙箱工具和浏览器工具的稳定性。后续要加入 LLM 摘要、向量检索或长期记忆，也都会建立在这一章的上下文快照结构之上，并继续沿用这种可观察的上下文边界。
​        对一个可维护的 Agent 系统来说，上下文快照也相当于一次执行前的“输入账单”。它让开发者知道模型看到了什么、没看到什么，以及这些取舍来自哪条预算规则。
