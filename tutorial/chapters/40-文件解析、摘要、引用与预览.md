## 40.3 本章要解决的问题

​        第 12-14 章已经完成文件上传、下载、会话文件和本地存储抽象。

​        第 16 章以后，Agent 也能通过 FileTool 读取文件内容。

​        但是仅仅“能读取文件”还不够。真实任务里，用户可能上传：

```Plain

接口返回.json
页面组件.tsx
销售数据.csv
产品白皮书.pdf
```

​        如果后端只返回一大段 raw text，会有几个问题：

​        具体来说，第一，前端不知道文件解析是否成功；第二，用户不知道 Agent 看到了哪些关键片段；第三，长文件容易撑爆上下文；第四，最终回答很难引用“第几行、哪个标题、哪个字段”；第五，PDF、CSV、代码文件应该有不同展示方式。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        所以本章把文件预览升级成结构化解析结果：

```Plain
文件内容
  |
  v
识别文件类型
  |
  v
按类型解析文本
  |
  v
生成摘要和引用片段
  |
  v
前端展示为文件资料卡
```

## 40.4 本章技术方案

​        本章不引入重型文档解析系统，只做课程项目需要的轻量解析。


#### 40.6.1.1 为什么使用 pypdf

​        `pypdf` 可以读取普通 PDF 中的文本层。

#### 40.6.2.1 字段含义

​        从实现顺序看，第一，`content`：裁剪后的原文预览；第二，`file_type`：后端识别出的文件类型，例如 `markdown`、`code`、`csv`、`pdf`；第三，`language`：前端展示或后续代码高亮用的语言；第四，`line_count`：当前预览内容的行数；第五，`parse_status`：解析状态，例如 `parsed`、`unsupported`、`empty`；第六，`parse_message`：给用户看的解析说明；第七，`summary`：低成本结构摘要；第八，`references`：可引用片段，包含标签、片段内容和行号；第九，`truncated`：预览是否因为长度限制被裁剪。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

#### 40.6.2.2 为什么这样设计

​        前端不能只拿 `content`。

​        文件解析成功、文件不支持、PDF 没有文本层，这些状态都需要明确展示。后续最终回答也需要知道“哪些片段可以引用”，所以本章先把引用片段结构稳定下来。

### 40.6.4 实现文件类型识别

​        在 `FileService` 中新增文件类型判断：

```Python
CODE_EXTENSIONS = {
    ".css": "css",
    ".html": "html",
    ".js": "javascript",
    ".jsx": "jsx",
    ".py": "python",
    ".ts": "typescript",
    ".tsx": "tsx",
}

@staticmethod
def _detect_file_type(file_object: FileObject) -> str:
    suffix = Path(file_object.original_name).suffix.lower()
    content_type = file_object.content_type.split(";")[0].lower()
    if content_type == "application/pdf" or suffix == ".pdf":
        return "pdf"
    if content_type == "text/csv" or suffix == ".csv":
        return "csv"
    if suffix in {".md", ".markdown"}:
        return "markdown"
    if suffix in CODE_EXTENSIONS:
        return "code"
    if content_type.startswith("text/") or suffix in {".txt", ".json", ".yaml", ".yml"}:
        return "text"
    return "binary"
```

#### 40.6.4.1 这段代码做了什么

​        后端会同时看两个信息：

​        放到工程语境里看，第一，上传时浏览器传来的 `content_type`；第二，文件名后缀。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        原因是浏览器传的 `content_type` 不一定准确。例如 `.md` 文件可能被识别成 `application/octet-stream`。所以这里会用后缀兜底。

### 40.6.5 重写预览主流程

​        把 `preview_file()` 改成返回 `FilePreview`：

```Python
async def preview_file(self, file_id: UUID) -> FilePreview:
    # ===================== 第1步：读取文件元数据和本地路径 =====================
    file_object, path = await self.get_download_path(file_id)

    # ===================== 第2步：识别文件类型 =====================
    file_type = self._detect_file_type(file_object)

    if file_type == "pdf":
        return self._preview_pdf(file_object, path)

    if not self._is_text_preview_supported(file_object):
        return FilePreview(
            file=file_object,
            content="",
            file_type=file_type,
            language=None,
            line_count=0,
            parse_status="unsupported",
            parse_message="当前文件类型暂不支持文本解析，可以先下载原文件查看。",
            references=[],
            summary="该文件暂不支持在线解析。",
            truncated=False,
        )

    # ===================== 第3步：读取可控大小的文本内容 =====================
    preview_bytes = self.storage.read_bytes(
        file_object.storage_path,
        max_size=settings.max_file_preview_size + 1,
    )
    truncated = len(preview_bytes) > settings.max_file_preview_size
    preview_bytes = preview_bytes[: settings.max_file_preview_size]
    content = preview_bytes.decode("utf-8", errors="replace")

    # ===================== 第4步：生成摘要、引用片段和最终响应对象 =====================
    return self._build_text_preview(
        file_object=file_object,
        content=content,
        file_type=file_type,
        truncated=truncated,
    )
```

#### 40.6.5.1 业务流程

​        这段代码是本章的主线：

```Plain
文件 ID
  |
  v
查数据库和本地路径
  |
  v
识别文件类型
  |
  +-- PDF -> pypdf 解析
  |
  +-- 文本类 -> 读取有限字节
  |
  +-- 不支持 -> 返回 unsupported
  |
  v
生成摘要和引用片段
```

#### 40.6.5.2 为什么要限制读取大小

​        文件可能很大。

​        如果预览接口一次性读取完整文件，会出现：

​        展开来看，第一，接口响应过大；第二，页面渲染卡顿；第三，后续上下文注入成本太高。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        所以预览只读取 `MAX_FILE_PREVIEW_SIZE` 限制内的内容，并通过 `truncated` 告诉前端内容被裁剪。

### 40.6.6 解析 PDF

​        新增 `_preview_pdf()`：

```Python
def _preview_pdf(self, file_object: FileObject, path: Path) -> FilePreview:
    """抽取 PDF 文本并生成摘要。

    这里只做课程项目需要的轻量解析：读取前几页文本，生成摘要和引用片段。
    复杂版式、扫描件 OCR、表格识别会在真实生产项目中交给专门文档解析服务。
    """

    try:
        reader = PdfReader(str(path))
        page_texts: list[str] = []
        for index, page in enumerate(reader.pages[:8], start=1):
            text = (page.extract_text() or "").strip()
            if text:
                page_texts.append(f"[第 {index} 页]\n{text}")
    except Exception as exc:
        raise AppException(
            message=f"pdf preview failed: {exc}",
            code=415,
            status_code=415,
            suggestion="请确认 PDF 不是损坏文件；扫描件 PDF 需要 OCR 服务才能解析。",
        ) from exc
```

​        如果没有抽取到文本，返回：

```Python
parse_status="empty"
parse_message="PDF 未抽取到文本，可能是扫描件或图片型 PDF。"
```

#### 40.6.6.1 为什么只读前 8 页

​        PDF 可能有几十页甚至几百页。

​        本章的目标是预览和引用准备，不是完整文档检索。读取前 8 页足够验证链路，也能避免一个 PDF 把接口响应拖得很慢。

### 40.6.7 生成摘要和引用片段

​        新增 `_build_text_preview()`：

```Python
def _build_text_preview(
    self,
    *,
    file_object: FileObject,
    content: str,
    file_type: str,
    truncated: bool,
) -> FilePreview:
    # 1. 按行拆分内容。引用片段需要行号，前端也会展示文件大致行数。
    lines = content.splitlines()

    # 2. 从文本里提取适合引用的片段，例如 Markdown 标题、代码符号、CSV 表头。
    references = self._build_references(lines, file_type)

    # 3. 汇总成统一的 FilePreview。路由层只负责把它转换成 Pydantic 响应。
    return FilePreview(
        file=file_object,
        content=content,
        file_type=file_type,
        language=self._detect_language(file_object, file_type),
        line_count=len(lines),
        parse_status="parsed",
        parse_message=(
            "文件已解析，预览内容已裁剪。"
            if truncated
            else "文件已解析，可以用于 Agent 上下文和最终回答引用。"
        ),
        references=references,
        summary=self._build_summary(file_object, content, file_type, references),
        truncated=truncated,
    )
```

#### 40.6.7.1 引用片段策略

​        本章使用规则解析，不调用 LLM：

```Plain
CSV      -> 第一行表头
Markdown -> 标题行
代码文件 -> class / def / function / export function / const
普通文本 -> 较长自然段
```

​        这样做成本低、速度快、可解释。后续如果要做更智能的引用，可以接入向量检索或 LLM 摘要，但不影响本章的响应结构。

## 40.7 关键理解

​        本章最重要的是理解：文件预览不是把文件内容原样贴出来。

​        文件能力应该分成三层：

```Plain
原文内容：用户或 Agent 需要时查看
结构摘要：快速知道文件大概是什么
引用片段：最终回答和任务过程可以引用的证据
```

​        第二个重点是理解“解析状态”。

​        解析失败不一定是系统错误。例如扫描件 PDF 没有文本层，这属于“文件内容不适合当前解析器”。前端应该明确告诉用户原因，而不是只显示空白。

​        第三个重点是理解本章边界。

​        本章完成“文件解析结果可展示、可引用、可传递”。第 41 章会继续让最终回答真正使用这些引用片段。

## 40.8 技术难点与亮点

​        技术难点：

​        具体来说，第一，PDF 文本层和扫描件 PDF 是两回事；第二，文件 `content_type` 不一定可靠，需要结合后缀判断；第三，长文件不能全部塞进预览接口；第四，代码、Markdown、CSV 的引用片段提取规则不同；第五，前端要同时处理已解析、不支持、空内容和错误状态。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        项目亮点：

​        换句话说，第一，文件预览从 raw text 升级为结构化资料卡；第二，引用片段带行号，为最终回答引用打基础；第三，PDF 解析能力进入后端文件服务；第四，上传错误和预览错误都接入统一错误体验。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。
