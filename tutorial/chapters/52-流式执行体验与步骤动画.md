## 52.3 本章要解决的问题

​        第 51 章已经把对话时间线拆成了多个组件，代码边界更清楚了。

​        但是执行体验还有三个问题。

​        第一个问题是事件容易“一次性出现”。

​        后端通过 SSE 持续推送：

```Plain
message_created
plan_created
step_started
tool_called
step_completed
task_done
```

​        如果前端不做呈现节奏，浏览器可能会在很短时间内把这些事件全部刷出来，用户看起来就像页面突然变了一大块。

​        第二个问题是用户消息出现得太晚。

​        后端在 `message_created` 事件里已经返回了消息内容，但前端如果只在最后重新加载 `messages`，用户会感觉发送后没有立刻进入对话。

​        第三个问题是长任务需要可控滚动。

​        AI Agent 的执行过程通常比较长。用户可能正在阅读上面的某个步骤，这时新事件继续到来。如果页面强行滚到底部，会打断阅读；如果永远不滚到底部，又会错过最新进度。

​        所以本章做一个更像真实产品的流式体验：

​        放到工程语境里看，第一，默认贴底展示最新事件；第二，用户主动上滑时暂停自动滚动；第三，提供回到底部按钮；第四，当前步骤高亮；第五，步骤可以折叠和展开；第六，工具调用继续内联在对应步骤下方。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

### 52.6.1 新增自动滚动 Hook

​        创建 `ui/app/hooks/use-auto-scroll.ts`：

```TypeScript
import { useCallback, useEffect, useRef, useState } from "react";

type UseAutoScrollOptions = {
  threshold?: number;
  watchKey: string;
};

// ===================== 第1步：管理对话时间线的自动滚动状态 =====================
export function useAutoScroll({
  threshold = 96,
  watchKey,
}: UseAutoScrollOptions) {
  const bottomRef = useRef<HTMLDivElement | null>(null);
  const scrollRef = useRef<HTMLDivElement | null>(null);
  const [pinnedToBottom, setPinnedToBottom] = useState(true);

  const scrollToBottom = useCallback((behavior: ScrollBehavior = "smooth") => {
    bottomRef.current?.scrollIntoView({ behavior, block: "end" });
  }, []);

  const handleScroll = useCallback(() => {
    const element = scrollRef.current;
    if (!element) {
      return;
    }

    // ===================== 第2步：判断用户是否还停留在底部附近 =====================
    // 如果用户主动向上看旧步骤，就暂停自动滚动；否则新事件进入时继续贴底展示。
    const distanceToBottom =
      element.scrollHeight - element.scrollTop - element.clientHeight;
    setPinnedToBottom(distanceToBottom <= threshold);
  }, [threshold]);

  useEffect(() => {
    if (pinnedToBottom) {
      scrollToBottom("smooth");
    }
  }, [pinnedToBottom, scrollToBottom, watchKey]);

  return {
    bottomRef,
    handleScroll,
    pinnedToBottom,
    scrollRef,
    scrollToBottom,
  };
}
```

#### 52.6.1.1 代码讲解

​        这段代码做了三件事。

​        第一，`scrollRef` 指向真正滚动的容器。

```TypeScript
const scrollRef = useRef<HTMLDivElement | null>(null);
```

​        第二，`bottomRef` 指向时间线最底部的一个空节点。

```TypeScript
const bottomRef = useRef<HTMLDivElement | null>(null);
```

​        滚动到底部时，不直接计算 `scrollTop`，而是让底部节点进入视口：

```TypeScript
bottomRef.current?.scrollIntoView({ behavior, block: "end" });
```

​        第三，`pinnedToBottom` 表示当前是否还贴着底部。

​        用户向上滚动时，`distanceToBottom` 会变大。只要超过 `threshold`，前端就认为用户正在查看历史内容，暂停自动滚动。

#### 52.6.1.2 为什么需要 watchKey

​        `watchKey` 是外部传进来的变化标记。

​        对话时间线会把消息数量、事件数量、计划 ID、任务状态拼成一个字符串。只要这些内容变化，`useEffect` 就会触发一次。

```Plain
消息数量变化 -> 可能有新消息
事件数量变化 -> 可能有新步骤或工具结果
任务状态变化 -> 可能完成、失败或停止
```

​        这样 hook 不需要知道业务细节，只负责滚动行为。

### 52.6.4 让 SSE 消息即时进入消息流

```TypeScript
function toChatMessageItem(event: SessionEventItem): ChatMessage | null {
  if (event.type !== "message_created") {
    return null;
  }
  const messageId = event.payload.message_id;
  const role = event.payload.role;
  const content = event.payload.content;
  if (
    typeof messageId !== "string" ||
    typeof content !== "string" ||
    !["user", "assistant", "system"].includes(String(role))
  ) {
    return null;
  }
  return {
    content,
    created_at: event.created_at,
    id: messageId,
    role: role as ChatMessage["role"],
    session_id: event.session_id,
  };
}
```

### 52.6.5 优化事件呈现节奏

​        继续在 `ui/app/stores/session-store.ts` 中调整：

```TypeScript
function getPresentationDelay(eventName: string) {
  // ===================== 第1步：给不同事件留出可感知的展示节奏 =====================
  // 这里不是伪造后端耗时，而是避免浏览器把 SSE 瞬间批量刷出，导致用户看不清执行顺序。
  if (eventName === "message_created") {
    return 120;
  }
  if (eventName === "plan_created") {
    return 460;
  }
  if (eventName === "step_started") {
    return 560;
  }
  if (eventName === "tool_called") {
    return 720;
  }
  if (eventName === "step_completed") {
    return 460;
  }
  if (eventName === "task_done" || eventName === "task_error") {
    return 280;
  }
  return 120;
}
```

#### 52.6.5.1 为什么每种事件延迟不同

​        不同事件的信息量不一样。

​        `message_created` 很简单，用户只需要看到消息进入时间线。

​        `plan_created` 信息更多，它会出现计划标题和步骤列表。

​        `tool_called` 通常会出现工具卡片、调用参数或输出摘要，用户需要更明显地感知它。

​        所以它们使用不同的展示延迟。

​        这不是后端执行时间，只是前端展示节奏。

## 52.7 关键理解

​        本章最重要的是理解“流式体验”和“真实流式能力”的区别。

​        后端已经通过 SSE 推送事件，这是数据层的流式。

​        前端还需要把这些事件变成用户能理解的节奏，这是体验层的流式。

```Plain
数据流式：事件一条条到达
体验流式：用户一眼能看懂 Agent 正在做什么
```

​        第二个重点是不要展示隐藏推理。

​        本章展示的是任务执行过程：

```Plain
计划
步骤
工具
结果
```

​        不是展示模型内部不可见的推理文本。

​        第三个重点是尊重用户阅读。

​        自动滚动不是永远滚动。用户主动上滑，就说明用户正在阅读历史内容。此时要暂停自动滚动，让用户自己决定什么时候回到底部。

## 52.8 技术难点与亮点

​        技术难点：

​        换句话说，第一，SSE 事件来得很快，前端需要控制展示节奏；第二，消息、事件和计划来自不同状态，需要避免重复插入；第三，自动滚动要兼顾最新进度和历史阅读；第四，当前步骤高亮不能在任务结束后继续误导用户；第五，步骤折叠不能影响打开详情和工具预览。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        项目亮点：

​        从实现顺序看，第一，对话区更像真实任务执行工作台；第二，用户消息能在 `message_created` 到达时立即出现；第三，当前步骤会自动展开并高亮；第四，长任务可以暂停自动滚动再回到底部；第五，状态体系开始覆盖等待、重试、停止等复杂任务状态。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

## 52.11 常见问题

- 问题：发送任务后还是一次性全部出现怎么办？

​        解释：先确认请求走的是 `/messages/stream`，再检查浏览器 Network 中是否是 `text/event-stream`。如果后端执行本身非常快，本章的展示延迟也只会让事件稍微分开，不会伪造很长的执行过程。

- 问题：为什么没有逐字输出？

​        解释：本章做的是事件级流式体验。模型 token 级逐字输出需要后端 LLM 调用也按 token 或 chunk 推送，属于后续可扩展方向。

- 问题：为什么不展示完整思维链？

​        解释：产品展示的是可观察的任务执行过程，包括计划、步骤、工具调用和结果，不展示模型内部隐藏推理。

- 问题：为什么用户消息会先从事件生成，最后还要重新加载？

​        解释：事件生成用于即时展示，重新加载用于和数据库最终结果对齐。

- 问题：回到底部按钮不出现怎么办？

​        解释：只有用户向上滚动，并且距离底部超过阈值时才会出现。如果内容不够长，滚动距离不够，它不会出现。
