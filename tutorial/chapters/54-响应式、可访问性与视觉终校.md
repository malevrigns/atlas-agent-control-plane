### 54.6.4 验收长任务下的播报与动效

​        `ui/app/components/conversation-timeline.tsx:84-88` 是滚动容器：

```TypeScript
<div
  className="h-full overflow-y-auto px-8 py-8 max-md:px-4"
  onScroll={handleScroll}
  ref={scrollRef}
>
```

​        流式追加消息和运行块的地方在它里面，`:89-94`：

```TypeScript
<div className="mx-auto grid max-w-3xl gap-7">
  {viewModel.timelineItems.map((item) =>
    item.kind === "message" ? (
      <div className="stream-in" key={item.id}>
        <MessageBubble message={item.message} />
      </div>
```

#### 54.6.4.1 为什么这一项判定为缺口

​        这里没有 `aria-live`，也没有 `role="status"`。

​        意味着长任务跑起来时，屏幕阅读器完全静默。一个流式 Agent 产品最该有的播报，恰恰没有。

​        动效降级只覆盖了一个，见 `ui/app/globals.css:50`：

```CSS
@media (prefers-reduced-motion: reduce) {
  .stream-in {
    animation: none;
  }
}
```

​        没被覆盖的是 6 处 `animate-spin`、1 处 `animate-pulse`，以及最要紧的 JS 平滑滚动，见 `ui/app/hooks/use-auto-scroll.ts:17-19`：

```TypeScript
const scrollToBottom = useCallback((behavior: ScrollBehavior = "smooth") => {
  bottomRef.current?.scrollIntoView({ behavior, block: "end" });
}, []);
```

​        这里的 `"smooth"` 是默认参数，不是硬编码，调用方可以传 `"auto"`。问题在于全项目两个调用点都显式传了 `"smooth"`，没有一处传 `"auto"`：一处是 `use-auto-scroll.ts:34-38` 的 `useEffect`，另一处是 `conversation-timeline.tsx:125` 的「回到底部」按钮。

```TypeScript
useEffect(() => {
  if (pinnedToBottom) {
    scrollToBottom("smooth");
  }
}, [pinnedToBottom, scrollToBottom, watchKey]);
```

​        这个 `useEffect` 依赖 `watchKey`，长任务持续追加事件时它一直在跑。CSS 媒体查询管不到 `scrollIntoView`，而真正决定行为的实参在 `:36`——改默认值没用，会被实参盖掉。

​        前庭敏感用户感受最强的那个动效，正好是唯一没关掉的。

​        这一项判定为缺口。

## 54.7 关键理解

​        本章最重要的是理解「验收章的产出是结论，不是代码」。

​        第一个重点是结论必须可复现。

​        不要只说：

```Plain
移动端看起来还行
```

​        而是要有：

```Plain
验收项
命令
实测输出
判定
落点
```

​        第二个重点是数字要看构成，不能只看总量。

​        88 处 `aria-` 听起来是一份不错的成绩，拆开看是同一个 `aria-hidden` 重复 88 次。41 处断点听起来像响应式做透了，拆开看 40 处是桌面优先的向下折叠。46 处 `title=` 听起来是一层挺厚的兜底，拆开看只有 36 处落在 `<button>` 上，另外 7 处是渲染成可见标题的 React prop，1 处传给子组件，剩下 2 处在 `<label>` 和 `<a>` 上。

​        这条规矩最难的地方是对自己用。上面三个数字里，前两个本章一开始就拆了，第三个是差点漏掉的那个。

​        第三个重点是承诺和代码冲突时，改的是承诺。

​        第 53 章的预告写下了「键盘操作场景都能正常使用」，代码没做到，本章的责任是把这句话纠正掉，而不是替它圆场。把「第 54 章会做 X」改写成「系统现在就做 X」，而代码不做 X，是这类文档最坏的一种失效。

​        第四个重点是纠正不能矫枉过正。

​        写成「键盘完全不可用」也是错的，65 个原生交互元素让 Tab 可达是事实。精确的缺口比笼统的否定更有价值，也更经得起读者自己去验。

## 54.8 技术难点与亮点

​        放到工程语境里看，第一，难点是把印象换成证据，每条结论都得有一条能跑的命令；第二，难点是区分「没做」和「做了一半」，本项目的可访问性属于「只做了一件事且做对了」；第三，难点是承认缺口而不伤及全书调性，第 49 章的三态记账提供了现成的体裁；第四，亮点是 design-tokens.ts 里那 4 个零引用字段，它们同时证明了规范写过和规范没落地；第五，亮点是把缺口压到文件和行，尤其是 `use-auto-scroll.ts:36` 这种「改错行就白改」的位置，让补齐变成一个明确的小任务，而不是一句愿望。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

## 54.9 面试考点

​        换句话说，第一，`aria-hidden` 解决什么问题，为什么它多不代表可访问性好；第二，`title` 为什么是可访问名的末位兜底，纯图标按钮该用什么；第三，`aria-live` 在流式产品里的作用是什么；第四，`prefers-reduced-motion` 为什么管不到 `scrollIntoView`；第五，模态对话框除了视觉遮罩还必须具备哪些行为；第六，桌面优先加 `max-*` 和移动优先加 `min-*` 各自的代价；第七，`color-scheme: dark` 和 `prefers-color-scheme` 的区别是什么。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

## 54.11 常见问题

- 问题：为什么本章不顺手把键盘导航补上？

​        解释：本章目标是收敛和验收。补齐 Esc、焦点陷阱、`aria-live` 会牵动弹窗、三个抽屉和时间线容器，属于一次独立的功能迭代。验收章的职责是把缺口记准、记全、给落点，然后交给后续迭代，而不是在验收里夹带改造。

- 问题：既然第 53 章的预告写错了，是不是应该回去改掉？

​        解释：预告写下的是当时的计划，本章给出的是实际结论，两者不一致本身就是有价值的记录。正确的做法是在本章正面写明哪句没兑现、为什么没兑现、缺口在哪，而不是回头抹掉痕迹。

- 问题：88 处 `aria-hidden` 是不是白做了？

​        解释：不是。它完整解决了装饰性 SVG 被读成噪声的问题，这一项判定为通过。问题只在于不能把它当成可访问性覆盖率来汇报。

- 问题：为什么不改成移动优先？

​        解释：本项目是一个桌面形态的 AI 工作台，600px 的工具抽屉和 VNC 远程桌面在手机上没有合理形态。40 处 `max-*` 保证的是窄屏不崩，不是窄屏好用。这是一个明确的取舍，不是疏漏。

- 问题：第 51 章说要把 token 扩展成更完整的规范，本章为什么没扩展？

​        解释：本章不产出代码，扩展规范在本章不可能发生。而且 54.6.6 给出的实证说明，现在也不该急着扩展——已经写下的 8 个字段里有 4 个零引用，先把写过的接上去，比再写一批没人用的字段更有意义。
