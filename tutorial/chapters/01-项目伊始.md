# 第一章. 项目伊始

## 1.1 本章目标

​        学完本章后，你应该能够完成四件事：

​        展开来看，第一，说明 AtlasAgent 为什么采用当前的顶层目录划分；第二，创建一个适合后端、前端、沙箱和网关共同开发的 monorepo 项目结构；第三，准备根目录 README、模块 README、`.env.example` 和 `.gitignore`；第四，理解后续章节会如何在这些目录里逐步补充代码。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

## 1.3 本章要解决的问题

​        当前仓库还没有统一的项目结构。如果直接开始写后端、前端或沙箱代码，文件很快会混在一起，后续章节也很难说明每段代码属于哪个模块。

​        所以第一章先不写业务代码，而是完成项目地基：

​        具体来说，第一，划分服务目录；第二，放置基础说明文件；第三，准备配置模板；第四，建立 Git 忽略规则。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        AtlasAgent 不是一个单体脚本，而是一个由多个服务协作的全栈 Agent 工作台。先把目录边界定清楚，后面的代码才不会越写越乱。

## 1.4 本章技术方案

​        本章采用 monorepo 结构，也就是用一个 Git 仓库管理多个服务。

​        常见做法有两种：

​        换句话说，第一，多仓库：`api`、`ui`、`sandbox` 分别放在独立仓库；第二，单仓库：所有服务放在同一个仓库中，用目录区分边界。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        本项目选择单仓库。课程前期更需要清晰的整体视角，后端、前端、沙箱、网关、文档和 Docker 配置会频繁一起变化，放在一个仓库里更容易同步演进。

​        本章只创建目录和说明文件，不安装依赖，也不启动服务。这样可以先把系统边界讲清楚，再在后续章节逐步加入 Docker、FastAPI、Next.js 和沙箱代码。

## 1.6 目录职责

| 目录 | 后续职责 |
| --- | --- |
| `api/` | 后端 API、数据库访问、Agent 调度、SSE 事件和 VNC 代理 |

## 1.7 实施步骤

### 1.7.1 创建顶层目录

​        先创建四个核心模块目录：

```text

ui/
sandbox/

```

​        这几个目录在当前章节只放 README，真正的代码会在后续章节逐步加入。这样做有两个好处：

​        从实现顺序看，第一，一开始就能看到系统边界；第二，后续每一章都可以清楚地说明自己在哪个模块里工作。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

### 1.7.2 加入 README 文件

​        根目录 README 负责回答三个问题：

​        放到工程语境里看，第一，这个项目是什么；第二，它由哪些服务组成；第三，当前章节做到什么程度。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        各模块目录下的 README 则只说明该模块未来的职责。早期 README 不需要假装项目已经完整运行，而是要诚实说明当前只是初始化骨架。

### 1.7.3 准备环境变量模板

​        本章创建 `.env.example`，但不创建真实 `.env`。

​        真实密钥不能提交到 Git 仓库。后续接入 LLM、搜索、MCP 或对象存储时，都应该通过环境变量注入。

​        本章先放一些未来会用到的变量名：

```text
LLM_API_KEY=
NGINX_PORT=8088
POSTGRES_USER=postgres
POSTGRES_PASSWORD=postgres
POSTGRES_DB=atlas_agents
```

​        这些变量现在不会被代码读取，但提前定义可以让你知道后续部署会依赖哪些配置。

### 1.7.4 准备 `.gitignore`

​        `.gitignore` 的目标是避免把本地环境、依赖目录、构建产物、上传文件和真实配置提交进去。

​        第一章至少应该忽略这些内容：

​        展开来看，第一，`.env`；第二，`node_modules/`；第三，Python 虚拟环境目录；第四，上传文件目录；第五，构建产物目录。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        这是课程项目从第一章就要养成的工程习惯。

## 1.8 关键理解

​        本章没有复杂代码，但它决定了项目后续的生长方向。

​        一个全栈 Agent 系统通常不只是“一个后端加一个页面”。它还会包含任务队列、数据库、沙箱、浏览器、远程桌面、部署网关等模块。

​        所以从一开始就使用 monorepo 结构，把相关服务放在一个仓库中管理：

```text
一个仓库，多套服务，统一开发节奏。
```

## 1.10 常见问题

### 1.10.1 为什么第一章只创建目录和说明文件？

​        解释：项目初期最重要的是先确定模块边界。目录结构清楚后，后续加入 Docker、后端、前端和沙箱代码时才不会混在一起。

### 1.10.2 为什么本章不启动服务？

​        解释：如果一开始就引入 Docker、FastAPI、Next.js 和数据库，信息量会太大。第 02 章会先处理 Docker 基础设施，第 03 章再实现后端最小服务。

### 1.10.3 为什么 `.env.example` 可以提交，而 `.env` 不提交？

​        解释：`.env.example` 是配置模板，不包含真实密钥；`.env` 通常包含本地真实配置和密钥，必须忽略。
