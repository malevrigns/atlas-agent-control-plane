## 65.8 本章要解决的问题

​        前面章节已经把 Agent 执行过程做出来了：

```Plain
用户发任务
  |
  v
Planner 生成计划
  |
  v
ReAct 执行步骤
  |
  v
工具调用产生观察结果
  |
  v
task_done
```

​        但是用户真正关心的不是“系统内部完成了 task_done 事件”，而是：

​        从实现顺序看，第一，最后结论是什么？；第二，依据哪些搜索来源？；第三，引用了哪个上传文件的哪一段？；第四，有没有生成文件、截图或报告？；第五，下一步我该怎么做？。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        如果最终回答没有这些内容，就会出现一种很尴尬的体验：

```Plain
中间过程很热闹，最后答案很空。
```

​        所以本章专门收敛最终回答质量。

## 65.9 本章技术方案

​        最终回答生成分两层：

```Plain
规则兜底总结
  |
  v
LLM 总结器增强
```

​        规则兜底总结负责保证系统在 LLM 不可用时也能输出稳定结构：

```Plain
## 总结
## 执行结果
## 证据与引用
## 产物
## 下一步建议
```

​        LLM 总结器负责在可用时把工具观察材料写得更自然。

​        但 LLM 不能直接拿一大段 raw JSON。后端会先把工具输出整理成：

```Plain
工具名
调用参数
摘要
引用
产物
原始观察摘录
```

​        这样模型更容易写出结构化、可读、少幻觉的最终回答。

​        本章暂时不做这些内容：

​        放到工程语境里看，第一，不新增数据库表；第二，不做引用点击跳转到原文行号；第三，不做 PDF 引用定位到具体页码；第四，不做最终回答导出 PDF。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        这些可以作为后续产品增强。

```Python
import json
import unittest
from datetime import UTC, datetime
from uuid import uuid4

from app.application.react_agent_service import ReActAgentService
from app.domain.sessions.entities import SessionEvent, SessionEventType


def build_tool_event(
    step_id: str,
    tool_name: str,
    output: str,
    arguments: dict | None = None,
) -> SessionEvent:
    return SessionEvent(
        id=uuid4(),
        session_id=uuid4(),
        type=SessionEventType.tool_called,
        payload={
            "plan_id": "plan-1",
            "step_id": step_id,
            "tool_name": tool_name,
            "arguments": arguments or {},
            "output": output,
        },
        created_at=datetime.now(UTC),
    )
```

#### 65.11.1.1 代码讲解

​        这个测试不连数据库，不调用 LLM。

#### 65.11.3.2 为什么要保留规则兜底

​        LLM 可能因为这些原因不可用：


​        如果没有规则兜底，任务已经执行完了，却无法给用户最终回答。

​        规则兜底不如 LLM 自然，但它稳定、可测试、不会编造。

​        新增 `_build_final_answer_reference_lines()`：

```Python
def _build_final_answer_reference_lines(
    self,
    *,
    title: str,
    tool_name: str,
    output: str,
) -> list[str]:
    """从工具输出中提取最终回答可展示的证据引用。

    这里仍然只使用可观察输出，不输出隐藏推理。搜索结果引用标题和 URL；
    文件工具引用文件名和行号；浏览器工具引用页面标题和地址。
    """
```

​        搜索结果提取：

```Python
parsed = self._parse_json_object(output)
if parsed and parsed.get("kind") == "search_results":
    items = parsed.get("items") if isinstance(parsed.get("items"), list) else []
    lines: list[str] = []
    for item in items[:5]:
        if not isinstance(item, dict):
            continue
        item_title = str(item.get("title") or "").strip()
        url = str(item.get("url") or "").strip()
        snippet = str(item.get("snippet") or "").strip()
        if item_title and url:
            suffix = f"：{self._trim_text(snippet, 90)}" if snippet else ""
            lines.append(f"- **{item_title}**（{url}）{suffix}")
    return lines
```

​        文件引用提取：

```Python
if tool_name.startswith("file_"):
    useful_lines = [
        line.strip()
        for line in output.splitlines()
        if line.strip()
        and (
            line.startswith(("文件：", "路径：", "第 "))
            or "行" in line
            or Path(line.strip()).suffix
        )
    ][:4]
    if useful_lines:
        return [f"- **{title}**：{self._trim_text(line, 160)}" for line in useful_lines]
```

#### 65.11.4.1 为什么只取前几条

​        最终回答不是工具详情页。

​        搜索结果可能有 10 条，文件内容可能有几百行。最终回答只展示最有代表性的证据，完整内容仍然放在右侧工具详情里。

#### 65.11.6.1 为什么还保留原始观察摘录

​        模型需要一些原始上下文来写自然语言总结。

​        但这个摘录会被裁剪到 900 字以内，而且前面已经有摘要、引用和产物结构，模型不会被一大坨 JSON 带偏。

## 65.12 关键理解

​        本章最重要的是理解：最终回答不是事件日志。

​        事件日志回答的是：

```Plain
系统发生了什么？
```

​        最终回答回答的是：

```Plain
用户拿到了什么？
为什么可信？
下一步怎么用？
```

​        第二个重点是：引用必须来自可观察证据。

​        Agent 不应该编造来源。搜索来源来自搜索工具返回的 URL；文件引用来自文件工具输出；产物路径来自 Shell 或文件工具输出。

​        第三个重点是：LLM 总结器只能润色和组织，不能替代证据提取。

​        证据提取先用确定性规则完成，LLM 再基于这些证据写最终回复。

## 65.13 技术难点与亮点

​        技术难点：

​        具体来说，第一，不同工具输出格式不同，不能用一套字符串截断解决；第二，最终回答要可读，但不能编造未执行的动作；第三，LLM 不可用时仍然要输出稳定结果；第四，搜索来源、文件片段、截图和产物路径要被归入不同章节。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        项目亮点：

​        换句话说，第一，`task_done.final_answer` 成为真正对话正文；第二，最终回答具备“总结、证据、产物、下一步”结构；第三，搜索来源标题和 URL 会进入最终回答；第四，文件名、行号和上传内容片段能进入最终回答；第五，Shell / Browser 工具结果能提炼成产物或观察结果。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

## 65.16 常见问题

- 问题：最终回答没有 `## 证据与引用` 怎么办？

​        解释：本轮任务可能没有搜索、文件或浏览器等可引用工具输出。可以用搜索任务或上传文件任务验证。

- 问题：最终回答没有 `## 产物` 怎么办？

​        解释：如果任务没有生成文件、截图或下载地址，LLM 总结器会写“本次任务没有生成新的文件产物”。规则兜底只有在检测到产物路径时才展示产物段落。

- 问题：为什么最终回答还需要右侧工具详情？

​        解释：最终回答是交付摘要，右侧详情是完整证据。二者职责不同，不能互相替代。

- 问题：为什么不用 LLM 直接从所有事件生成最终回答？

​        解释：直接塞全部事件容易混入 raw JSON、内部字段和冗余日志。先整理证据，再让 LLM 写答案，更稳定也更可控。
