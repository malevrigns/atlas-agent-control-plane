# 第四十九章. 迁移、测试与交付验收

## 49.1 本章目标

本章不再增加功能，而是将 Memory Control Plane、Tool Runtime 和 TUI 收敛成一套可重复的迁移与交付流程。

## 49.2 升级前检查

执行数据库升级前，先完成：

1. 备份 PostgreSQL 数据库与上传文件卷；
2. 记录当前 Alembic revision；
3. 确认未运行旧版 API 容器与新版共用数据库；
4. 为 `ARTIFACT_DIR` 准备可持久、不对公网直接暴露的存储路径；
5. 核对 `TOOL_AUTO_APPROVE_RISK`、`TOOL_DEFAULT_TIMEOUT_SECONDS` 和 `TOOL_OUTPUT_INLINE_LIMIT`。

## 49.3 数据库迁移

```bash
cd backend/api
uv sync --frozen
uv run alembic current
uv run alembic upgrade head
```

升级 migration 为：

```text
202608010001_memory_tool_control_plane.py
```

它会扩展 `agent_memories`，并新建任务、需求、决策、Checkpoint、Artifact、记忆关系、环境快照、Skill 执行、检索轨迹和工具审计等表。

为避免到生产环境才发现 SQL 方言问题，使用离线生成先检查迁移 SQL：

```bash
uv run alembic upgrade head --sql > /tmp/atlas-migration.sql
```

离线 SQL 用于审查，不代替真实数据库的升级验证。

## 49.4 自动化测试

后端：

```bash
cd backend/api
uv run python -m unittest discover -s tests
```

重点用例：

- `test_memory_control_plane.py`：写入门、验证、替代与检索上下文；
- `test_checkpoint_service.py`：稳定哈希、证据完整性、约束继承；
- `test_checkpoint_restore.py`：哈希复验、乐观锁恢复与 resume；
- `test_auth_middleware.py` / `test_runtime_hardening.py`：认证、模块策略、密钥与外部执行边界；
- `test_tool_runtime.py`：权限、审批、幂等、超时、脱敏和 Artifact；
- 原有 Agent Runner、搜索、安全、可观测与产品验收测试：保证兼容性。

TUI：

```bash
cd frontend/tui
uv sync --frozen
uv run python -m unittest discover -s tests
```

## 49.5 手工端到端验收

自动测试通过后，按以下顺序做一次真实链路：

1. 创建一个带验收标准和 `must_preserve` 的任务；
2. 为它捕获环境快照；
3. 上传一个测试报告 Artifact；
4. 创建 Checkpoint，确认 `validator_report.valid=true`；
5. 修改任务后调用 restore，确认错误版本返回 409、正确版本恢复成功；
6. 新建候选记忆，带 provenance 验证；
7. 执行一个低风险工具，然后用相同幂等键再调用一次；
8. 查看工具审计，确认第二次为 `deduplicated`；
9. 在 Web 和 TUI 中查看同一任务状态。

## 49.6 交付包卫生

交付源码不应包含：

```text
.venv/
node_modules/
dist/
release/
__pycache__/
.pytest_cache/
.mypy_cache/
本地 Artifact 实例
测试过程产生的截图与临时文件
```

必须包含：

- 依赖锁文件；
- `.env.example`，但不包含真实 `.env`；
- Alembic migration；
- 后端和 TUI 测试；
- 运行文档、教程更新和交付说明。

## 49.7 持续集成与依赖门禁

仓库的 `.github/workflows/ci.yml` 在每次推送和 Pull Request 上从全新环境运行以下门禁：

- API、Sandbox、TUI 与根目录 Python 测试；
- UI 依赖审计、类型检查和生产构建；

- `docker compose config` 与 Nginx 配置语法校验。

CI 中必须使用锁文件安装：Python 使用 `uv sync --frozen`，UI 使用 `pnpm install --frozen-lockfile`。`pnpm audit` 的 high 漏洞应直接阻断交付；依赖升级后要同时更新清单和锁文件，不能只改 `package.json`。

本次加固基线为 API 50 项、Sandbox 1 项、TUI 3 项、根目录 4 项测试，UI 审计为 0 个已知漏洞。数字只是当前证据，README、教程和 CI 应从实际命令得到结果，不能长期手工维护成宣传口径。

CI 不能替代真实服务验收：没有 PostgreSQL/Redis 的单元测试无法证明迁移、Consumer Group 恢复或完整 Agent 链路。发布前仍需按 49.5 在真实 Compose 环境跑一次端到端流程。

## 49.8 回滚策略

数据库结构回滚不等于数据回滚。如果新版已经产生 Checkpoint、Artifact 和工具审计数据，直接 downgrade 可能丢失这些记录。正式环境应优先：

1. 停止写入；
2. 备份升级后数据；
3. 回滚应用并恢复升级前数据库快照；
4. 将升级期间的新数据另行导出审查。

不要在没有备份时直接对生产数据库执行 `alembic downgrade`。

## 49.9 最终验收清单

- [ ] 迁移可从旧 revision 升级到 head；
- [ ] 后端全部测试通过；
- [ ] TUI 无头测试通过；


- [ ] 高风险工具未审批不执行；
- [ ] 幂等调用不产生二次副作用；
- [ ] Checkpoint 丢失约束时不可验证；
- [ ] Checkpoint 哈希不匹配时不可恢复，正确版本可 restore/resume；
- [ ] 未认证请求不能访问控制面、Sandbox 或 noVNC；
- [ ] API 重启后旧任务仍可由 Consumer Group 认领，取消会停止执行协程；
- [ ] GitHub Actions 在全新环境中通过测试、构建、audit 与配置校验；
- [ ] 过期/被替代/敏感记忆不进入普通上下文；
- [ ] 交付包不包含虚拟环境、依赖目录、密钥或运行产物。

## 49.10 本章小结

到这里，AtlasAgent 从“可以调工具的 Web Agent”演进成“有事实源、可恢复、可追溯、可审批、有多客户端的 Agent Control Plane”。交付的完成标准不是文件数量，而是迁移、测试、手工链路和交付包卫生都有明确证据。
