# 第五十六章. 任务卡片、锚定滚动与界面主题化

## 56.1 本章目标

前面几章一直在给后端加能力：直答路由、知识库召回、浏览器读页。能力够了，但把界面交给真人用一天，反馈全是界面问题，而且每一条都很扎心：

- "你任务框和展示的东西重复了，严重问题"——同一次任务在时间线里画了一排步骤卡片，底部又挂了一条计划进度条。
- "我问了一个你好，但是你对你好的回复为什么还有上一个任务的任务栏呢"——任务卡固定挂在时间线末尾，新提的问题被上一轮的任务卡压在下面。
- "为什么他自动给我从上面滑到下面，而不是一直锁定在我当前消息的位置"——追问之后视图自己滑到底部。
- "你的思考直播太快了，给我放慢一点"——推理流瞬间刷屏。
- 还有一串"小事"：输入框巨大、侧栏占死屏幕、原生滚动条丑、代码块不能复制、主题切换点了没反应。

这些都不是后端问题，是**前端把"过程"呈现错了**。这一章把对话区从头改一遍。

完成本章后，你将能够：

- 把"一次任务运行"建模成时间线里的一条独立项，让任务卡属于触发它的那一轮对话；
- 用 `plan_id` 精确匹配终结事件，并给旧数据设计时间窗兜底，避免一张卡吞掉另一次运行的结果；
- 实现 ChatGPT 式锚定滚动：切会话跳底部、发追问锁顶部、流式期间绝不跟滚，并说清四个必踩的坑；
- 写一个真正能跑的打字机节流 hook，理解"定时器不能挂在依赖流式文本的 effect 上"这条铁律；
- 用 CSS 变量 + `data-theme` + `beforeInteractive` 脚本做出不闪白的主题系统；
- 处理一批决定"这个界面是否像成品"的细节：自动伸缩输入框、中文输入法回车、可隐藏侧栏、自定义滚动条、代码块复制、品牌图标。

## 56.2 一次任务被画了两遍

旧的视图模型大意是这样：

```typescript
// 旧实现的结构（示意）
return {
  plan: getLatestPlan(events),        // 整个会话只取"最新的那一个"计划
  timelineItems: messages.map(...),   // 时间线里只有消息
};
```

时间线只承载消息；计划被单独拎出来，由外层组件追加渲染在**整条时间线的末尾**，底部还有一条常驻 `PlanProgressBar` 显示 n/m 进度。

**问题一：同一件事画了两遍。** 步骤卡片列表和底部进度条消费同一份 `buildStepViews` 结果，一个展开成一排卡片，一个压缩成一条进度。用户看到的是"上面刚说第 3 步完成，下面又说一遍 3/5"。这不是冗余，是**噪音**——它让人怀疑是不是有两个任务在跑。

**问题二：任务卡不属于任何一轮对话。** `getLatestPlan` 只返回最新的计划，渲染位置又固定在末尾，于是"计划"和"提出这个计划的那句话"彻底脱钩。用户发一句"你好"，得到一条直答气泡，**下面却还挂着上一个任务的卡片**。

两个问题的根因相同：**计划不是时间线里的一等公民**。

### 把 plan_created 变成时间线项

`frontend/web/app/components/conversation/types.ts`：

```typescript
export type TimelineItem =
  | { kind: "message"; id: string; created_at: string; message: ChatMessage }
  | { kind: "plan"; id: string; created_at: string; event: SessionEventItem };
```

`frontend/web/app/components/conversation/view-model.ts`：

```typescript
function buildTimelineItems(
  messages: ChatMessage[],
  events: SessionEventItem[],
): TimelineItem[] {
  const planEvents = events.filter((event) => event.type === "plan_created");

  // 计划执行路径的最终回答由 AgentRunBlock 的 FinalAnswer 展示；
  // 同一内容的 assistant 消息不再重复渲染成气泡。
  // 只统计流水线运行（mode 非 chat）的 task_done——直接问答的回答
  // 没有 AgentRunBlock，它们的气泡必须保留。
  const finalAnswers = new Set(
    events
      .filter(
        (event) =>
          event.type === "task_done" && getString(event.payload.mode) !== "chat",
      )
      .map((event) => getString(event.payload.final_answer))
      .filter(Boolean),
  );
  const visibleMessages = planEvents.length
    ? messages.filter(
        (message) =>
          message.role !== "assistant" || !finalAnswers.has(message.content),
      )
    : messages;

  return [
    ...visibleMessages.map((message) => ({
      kind: "message" as const,
      id: `message-${message.id}`,
      created_at: message.created_at,
      message,
    })),
    ...planEvents.map((event) => ({
      kind: "plan" as const,
      id: `plan-${event.id}`,
      created_at: event.created_at,
      event,
    })),
  ].sort((left, right) => left.created_at.localeCompare(right.created_at));
}
```

**`created_at` 排序解决了归属问题。** 计划事件一定晚于触发它的用户消息、早于下一条用户消息，排序之后任务卡自然落在正确位置，不需要额外维护"这个计划属于哪条消息"的字段——**时间本身就是关联**。

**去重要挑对象。** 流水线路径的最终回答由 `FinalAnswer` 渲染，同内容的 assistant 消息再画成气泡就重复了。但过滤条件里的 `mode !== "chat"` 不能少：直答路径也发 `task_done`，而直答**没有** `AgentRunBlock`，气泡是它唯一的显示位置。少了这个条件，用户会发现"问'你好'居然什么都没回"。

### 一张卡只负责一次运行

`AgentRunBlock` 不能再自己去"找最新的计划"，而要接收**属于自己的那个** `planEvent`：

```tsx
type AgentRunBlockProps = {
  /** 仅最新一张卡在会话执行中时为 true——历史卡片永远是 false。 */
  executing: boolean;
  /** store 里实时更新的计划（执行中步骤状态来自 SSE），仅当 id 匹配时覆盖事件快照。 */
  livePlan: AgentPlan | null;
  /** 本卡片对应的 plan_created 事件——一张卡只负责一次任务运行。 */
  planEvent: SessionEventItem;
  // ...events / planning / selectedToolEventId / onSelectToolEvent
};

const plan = useMemo(() => {
  const parsed = parsePlanPayload(planEvent.payload);
  return livePlan && livePlan.id === parsed.id ? livePlan : parsed;
}, [livePlan, planEvent]);
```

**只有 id 匹配才用 `livePlan` 覆盖事件快照**——历史卡片解析出的 plan id 与当前 live plan 不同，于是永远显示自己那次运行的最终状态，不会被新任务的进度污染。`parsePlanPayload` 是纯解析，把可能缺字段的 payload 补齐成 `AgentPlan`，其中 `id: getString(payload.id) || getString(payload.plan_id)` 兼容了后端两个版本的字段名——这类兼容代码写在解析层，比散在业务逻辑里好得多。

### 终结事件归谁：plan_id 精确匹配 + 时间窗兜底

`task_done` / `task_error` 在事件流里是平铺的，怎么知道哪个属于哪张卡？

```tsx
// 只认属于本次运行的终结事件：优先按 plan_id 匹配；
// 旧数据没有 plan_id 时退回时间窗（本计划之后、下一个计划之前），
// 并排除直答路径的 task_done（mode=chat），避免旧任务卡吞掉新对话的结果。
const finalEvent = useMemo(() => {
  const terminals = events.filter(
    (event) => event.type === "task_done" || event.type === "task_error",
  );
  if (plan.id) {
    const byPlanId = terminals.find(
      (event) => getString(event.payload.plan_id) === plan.id,
    );
    if (byPlanId) {
      return byPlanId;
    }
  }
  const nextPlanAt = events.find(
    (event) =>
      event.type === "plan_created" && event.created_at > planEvent.created_at,
  )?.created_at;
  return (
    terminals.find(
      (event) =>
        event.created_at > planEvent.created_at &&
        (!nextPlanAt || event.created_at < nextPlanAt) &&
        getString(event.payload.mode) !== "chat",
    ) ?? null
  );
}, [events, plan.id, planEvent]);
```

三层逻辑缺一不可：

1. **优先按 `plan_id` 精确匹配。** 新数据都带这个字段，一句 `find` 搞定。
2. **旧数据用时间窗兜底。** 改造前落库的事件没有 `plan_id`，"晚于本计划、早于下一个计划"物理上就是这次运行的区间。
3. **兜底时必须排除 `mode === "chat"`。** 这条是踩出来的：会话里先跑了一次任务，然后用户问"你好"走直答。直答也发 `task_done`，它晚于本计划，而且后面**没有新的计划**，`nextPlanAt` 是 undefined、时间窗没有右边界——那条 `task_done` 就被上一张任务卡认领了，现象是任务卡下面挂着一句莫名其妙的"你好呀"作为 Final Answer。

### running 判定：不能靠步骤反推

```tsx
const runningStep = steps.find((step) => step.status === "running") ?? null;
const failed = finalEvent?.type === "task_error";
// 不用 steps.some(pending) 推断运行中——被中断的历史任务没有终结事件，
// 会导致旧卡片永远转圈；执行态只信当前会话的 planning/executing。
const running = !finalEvent && (planning || executing || Boolean(runningStep));
```

直觉写法是"还有 pending 的步骤就是在跑"。这对**正常结束**的任务成立，对**被中断**的任务完全错误：用户点了停止、或者后端挂了，那次运行既没有 `task_done` 也没有 `task_error`，步骤永远停在 pending，于是每次打开这个会话，那张三个月前的历史卡片都在兴致勃勃地转圈。

正确的心智模型是：**"正在运行"是当前会话的实时状态，不是历史数据能推导出来的属性。** 执行态从外部传入，而且只授予最新一张卡（`frontend/web/app/components/conversation-timeline.tsx`）：

```tsx
// 执行态只属于最新的任务卡；历史卡片一律静止。
const lastPlanItemId =
  [...viewModel.timelineItems]
    .reverse()
    .find((item) => item.kind === "plan")?.id ?? null;

<AgentRunBlock
  executing={executing && item.id === lastPlanItemId}
  planning={planning && item.id === lastPlanItemId}
  planEvent={item.event}
  livePlan={plan}
  events={events.data}
  ...
/>
```

这个写法把"全局执行态"降级成了"这一张卡的执行态"，历史卡片拿到的永远是 `false`。

## 56.3 TaskRunCard：把一次运行收进一张卡

旧实现有三个组件分摊同一件事：`StepCard`（每个步骤一张独立卡片）、`StepDetailDialog`（点步骤弹模态框）、`PlanProgressBar`（底部常驻进度条）。新实现只有一个 `TaskRunCard`：头部是状态图标 + 标题 + `n/m` 计数 + 折叠箭头，展开区逐条列出步骤和一行摘要。

```tsx
export function TaskRunCard({ title, steps, running, failed, ... }: TaskRunCardProps) {
  const [expanded, setExpanded] = useState(true);
  const completedCount = steps.filter((step) => step.status === "completed").length;
  const headline = failed ? "任务执行失败" : running ? "正在执行任务" : "任务已完成";

  return (
    <div className="overflow-hidden rounded-2xl border border-(--line) bg-(--surface) shadow-xl">
      <button aria-expanded={expanded} onClick={() => setExpanded((value) => !value)} type="button">
        <HeadIcon failed={failed} running={running} />
        <div className="text-[15px] font-semibold text-(--text-1)">{headline}</div>
        <div className="mt-0.5 truncate text-xs text-(--text-4)">{title}</div>
        <span>{completedCount} / {steps.length}</span>
        <ChevronDown className={`transition-transform ${expanded ? "rotate-180" : ""}`} size={16} />
      </button>
      ...
```

步骤行本身是个 `<button>`，点击打开右侧工具详情面板——**不是模态框**。模态框会遮住对话，用户想边看详情边对照上下文就得反复开关；侧边面板可以常驻：

```tsx
{steps.map((step, index) => {
  const toolEventId = step.toolEvent?.id ?? null;
  const selected = Boolean(toolEventId) && toolEventId === selectedToolEventId;
  return (
    <button
      className={`flex items-start gap-3 rounded-xl p-1.5 text-left transition ${
        selected
          ? "bg-(--accent)/10 ring-1 ring-(--accent)/40"
          : toolEventId
            ? "hover:bg-(--fill-1)"
            : "cursor-default"
      }`}
      key={step.id}
      onClick={() => {
        if (toolEventId) onSelectToolEvent(toolEventId);
      }}
      title={toolEventId ? "查看该步骤的工具详情" : undefined}
      type="button"
    >
      <StepIcon status={step.status} />
      <div className="min-w-0 flex-1">
        <div className="text-sm font-semibold leading-6 text-(--text-1)">
          {index + 1}. {step.title}
        </div>
        <p className="mt-0.5 line-clamp-2 text-sm leading-6 text-(--text-4)">
          {getStepDisplaySummary(step)}
        </p>
      </div>
    </button>
  );
})}
```

注意三态样式：**选中**（accent 底色 + ring）、**可点**（hover 反馈）、**不可点**（`cursor-default`，没有工具事件的步骤不该给点击暗示）。少了第三种，用户会一直点一个毫无反应的行。摘要来自 `getStepDisplaySummary`，它按状态给不同文案，失败时把后端的 `user_message` 和 `suggestion` 拼在一起显示。

**删代码也是重构成果。** 这次净删掉三个组件文件，`ConversationTimeline` 的渲染分支从"消息 / 步骤卡 / 进度条 / 详情弹窗"简化成"消息 / 任务卡"。

删组件时别忘了顺着往上删：`view-model.ts` 里的 `buildPlanProgressView` 和 `types.ts` 里的 `PlanProgressView` 都是专为 `PlanProgressBar` 写的，组件没了它们就成了死代码——TypeScript 不会报错，测试也不会失败，只有搜一遍调用方才发现。**删一个组件，要连它的视图模型、类型和未用导入一起清掉**，否则下一个读代码的人会以为这套进度条模型还在用。

## 56.4 ChatGPT 式锚定滚动

这是本章技术含量最高的部分。先把**目标行为**定义清楚，因为大部分实现问题都源于目标本身没想明白：

1. **切换会话**：直接跳到底部。
2. **发出追问**：把这条用户消息滚到视口顶部并锁住，回答在下方生长。
3. **流式期间**：绝不自动跟滚，用户滚到哪就停在哪。
4. **兜底**：不在底部时显示"回到底部"按钮。

第 3 条是关键。很多聊天界面的做法是"如果用户贴着底部就跟滚"，但这条规则和第 2 条直接冲突：锚定之后用户其实没有滚动，若内容不足一屏，视口物理上仍然贴底，跟滚逻辑立刻把刚锚好的位置推走。所以这里**彻底放弃自动跟滚**，只留按钮兜底。

完整实现在 `frontend/web/app/hooks/use-auto-scroll.ts`：

```typescript
export function useAutoScroll({ threshold = 96, sessionKey, lastUserMessageId }: UseAutoScrollOptions) {
  const bottomRef = useRef<HTMLDivElement | null>(null);
  const scrollRef = useRef<HTMLDivElement | null>(null);
  const [pinnedToBottom, setPinnedToBottom] = useState(true);
  // 锚定后在时间线尾部垫一段空白，保证"锚到视口顶部"物理上可达
  //（否则新消息下方内容不足一屏时滚不上去）。ChatGPT 同款行为。
  const [anchorSpacer, setAnchorSpacer] = useState(false);
  const anchoredMessageRef = useRef<string | null>(null);
  const sessionRef = useRef<string | null>(null);

  const scrollToBottom = useCallback((behavior: ScrollBehavior = "smooth") => {
    bottomRef.current?.scrollIntoView({ behavior, block: "end" });
  }, []);

  const handleScroll = useCallback(() => {
    const element = scrollRef.current;
    if (!element) return;
    // 以"内容末尾"（bottomRef，位于锚定空白之前）为贴底基准：
    // 锚定空白只是滚动缓冲，视口越过内容末尾就算到底。
    const bottomElement = bottomRef.current;
    const distanceToBottom = bottomElement
      ? bottomElement.getBoundingClientRect().top -
        element.getBoundingClientRect().top -
        element.clientHeight
      : element.scrollHeight - element.scrollTop - element.clientHeight;
    setPinnedToBottom(distanceToBottom <= threshold);
  }, [threshold]);

  // 会话切换：跳到底部；同时重置锚定记录（避免把历史消息当新消息锚定）。
  useEffect(() => {
    if (sessionRef.current === sessionKey) return;
    sessionRef.current = sessionKey;
    anchoredMessageRef.current = lastUserMessageId;
    setAnchorSpacer(false);
    // 用 setTimeout 而非 requestAnimationFrame：后台/隐藏标签页的 rAF
    // 会被浏览器冻结，导致滚动永远不执行。
    window.setTimeout(() => scrollToBottom("auto"), 0);
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, [sessionKey]);

  // 新的用户消息出现：把它锚定到视口顶部（问题固定，回答向下生长）。
  useEffect(() => {
    if (!lastUserMessageId || anchoredMessageRef.current === lastUserMessageId) return;
    anchoredMessageRef.current = lastUserMessageId;
    setAnchorSpacer(true);
    // 等 spacer 渲染进 DOM 再滚动，否则底部空间不足仍会滚不到位。
    window.setTimeout(() => {
      const element = scrollRef.current?.querySelector(
        `[data-message-anchor="${lastUserMessageId}"]`,
      );
      element?.scrollIntoView({ behavior: "smooth", block: "start" });
    }, 50);
  }, [lastUserMessageId]);

  return { anchorSpacer, bottomRef, handleScroll, pinnedToBottom, scrollRef, scrollToBottom };
}
```

代码不长。难的是下面四个坑，每一个都能让这段代码"看起来写对了但行为不对"。

### 坑一：浏览器有自己的滚动锚定，它会覆盖你

写完 hook，切会话正常、锚定也正常，但一到流式回答视图还是慢慢往下爬。断点全打在 hook 里，没有任何自定义滚动被触发。

原因是浏览器的原生 **scroll anchoring**：滚动容器接近底部、内容在下方增长时，浏览器会自动调整 `scrollTop` 保持视觉稳定，表现出来就是"自动跟滚"。这是规范行为，跟你的 JS 无关，也不经过任何事件回调。解法是在滚动容器上关掉它：

```tsx
{/* overflow-anchor:none 关掉浏览器原生滚动锚定——
    否则视口贴底时流式内容增长，浏览器会自动跟滚到底部，
    覆盖我们"锁定在用户消息"的滚动策略。 */}
<div
  className="h-full overflow-x-hidden overflow-y-auto px-8 py-8 [overflow-anchor:none] max-md:px-4"
  onScroll={handleScroll}
  ref={scrollRef}
>
```

Tailwind 没有现成的 `overflow-anchor` 工具类，用任意属性语法 `[overflow-anchor:none]`。**任何自定义滚动策略的第一行代码，都应该是关掉 `overflow-anchor`**，否则你是在和浏览器抢方向盘。

### 坑二：锚定需要尾部空白

第二个现象更隐蔽：`scrollIntoView({ block: "start" })` 明明调用了，消息却只往上挪了一点，没顶到视口顶部。

原因是物理限制——容器最多只能滚到 `scrollHeight - clientHeight`。新消息下面的内容不足一屏时，那条消息**根本没有可能**出现在视口顶部，不是代码没生效，是空间不够。ChatGPT 的做法是在时间线尾部垫一段空白，我们照做：

```tsx
{/* bottomRef 标记内容末尾（在锚定空白之前）：
    贴底判断与"回到底部"都以它为准，空白只是滚动缓冲。 */}
<div ref={bottomRef} />
{/* 锚定后的尾部空白：保证最新提问能顶到视口顶部，回答在下方生长。 */}
{anchorSpacer ? (
  <div aria-hidden className="h-[calc(100dvh-360px)] shrink-0" />
) : null}
```

三个细节：**空白只在锚定后出现**（`anchorSpacer` 控制），会话刚打开时不该有一大片留白；**`bottomRef` 放在空白之前**，否则贴底判断会把空白算进内容，用户永远"到不了底"，按钮一直挂着；**先 `setAnchorSpacer(true)` 再滚动，中间隔 50ms**，空白得先进 DOM 才能提供滚动空间。

### 坑三：静默刷新——"自动从上面滑到下面"的真正根因

这是最花时间的一个。现象：追问锚定成功，回答流式生长，一切正常；**但回答结束的一瞬间，视图唰地滑到底部**。前两个坑都排除了，问题只出在"结束的那一刻"。

根因在 store 里。流结束后要以服务端为准刷新一次会话详情，保证消息 id、事件时间戳跟数据库一致。原来的 `loadSessionDetail` 一进来就把四份数据置成 `loading`，而 `ConversationTimeline` 的第一行就是 `if (messages.type === "loading" || events.type === "loading") return <TimelineLoadingState />;`。

这条链路是致命的：置 loading → 时间线返回另一个组件 → **整棵子树卸载** → `useAutoScroll` 里的 ref 全部重置 → 数据回来后重新挂载 → `sessionRef.current` 是 `null`，跟 `sessionKey` 不相等 → hook 判定"这是切换会话" → 跳到底部。

**用户看到的"自动滑到底部"，本质是一次组件重挂被误判成了会话切换。**

修法是给 `loadSessionDetail` 加 `silent` 选项，静默刷新时保留旧数据、原地替换（`frontend/web/app/stores/session-store.ts`）：

```typescript
loadSessionDetail: (sessionId: string, options?: { silent?: boolean }) => Promise<void>;

loadSessionDetail: async (sessionId, options) => {
  // silent：流结束后的静默刷新。保留旧数据直接原地替换，
  // 不置 loading——否则时间线会卸载重挂，滚动位置被重置到底部。
  if (!options?.silent) {
    set({
      context: { type: "loading" },
      events: { type: "loading" },
      files: { type: "loading" },
      messages: { type: "loading" },
      filePreview: { type: "ready", data: null },
      selectedFile: null,
    });
  }
  const [messages, events, files, context] = await Promise.all([...]);
  set({ /* 四份数据一律置 ready，原地替换 */ });
},
```

调用点在 `sendMessage` 的收尾：`get().loadSessionDetail(sessionId, { silent: true })`。

这条经验值得记住：**加载态不是免费的**。`{ type: "loading" }` 会让消费它的组件走另一条渲染分支，挂在那棵子树上的 ref、DOM 位置、滚动状态、`useState` 全部归零。判断标准很简单：**这次请求会不会让屏幕上已有的东西消失？** 会，就用 loading；不会，就用 silent。

### 坑四：后台标签页里 rAF 与 smooth 动画会被冻结

最后一个坑只在特定场景暴露：把标签页切到后台，任务跑完再切回来，滚动位置完全没变。

浏览器对不可见页面有两套限制：`requestAnimationFrame` **完全不执行**（不是变慢，是根本不调）；CSS 平滑滚动动画同样被冻结，`scrollIntoView({ behavior: "smooth" })` 发出去了但动画不推进。前者决定触发方式——所有滚动用 `window.setTimeout`，不用 rAF；后者决定 `behavior`——需要"立刻到位"的场景一律用瞬时滚动。切会话就是这么写的：

```tsx
timeline.scrollTo({ top: timeline.scrollHeight, behavior: "instant" as ScrollBehavior });
```

Web 端切会话用 `scrollToBottom("auto")`（同样瞬时），只有用户主动点"回到底部"才用 `smooth`。**写自动化测试时这条尤其重要**：Playwright 的无头浏览器里 smooth 动画时序不可靠，断言 `scrollTop` 经常读到动画中间的值，测试随机失败。要验证滚动策略，就在测试路径上用 `behavior: "instant"`，滚完立刻断言。

### 收口：锚点属性与 scroll-mt

锚定靠 DOM 查询定位，每条消息都要带一个稳定标记：

```tsx
<div
  className="stream-in scroll-mt-2"
  data-message-anchor={item.message.id}
  key={item.id}
>
```

`data-message-anchor` 用于查询；`scroll-mt-2` 给 `scroll-margin-top` 留 8px，避免消息紧贴视口边缘看起来像被裁掉。"回到底部"按钮绝对定位在滚动容器上，`{!pinnedToBottom ? <button .../> : null}` 控制显隐，`onClick={() => scrollToBottom("smooth")}`——这是全局唯一用 `smooth` 的地方，因为它是用户主动发起的。

## 56.5 打字机节流：让"思考直播"慢下来

模型的思考流不是匀速到达的。后端一次 flush 可能带来几百个字符，前端直接渲染就是一整屏文字瞬间砸下来，然后卡住几秒，再砸一屏。要的效果是：**按稳定速度把已到达的文本放出去；落后太多时加速追平**。

`frontend/web/app/hooks/use-typewriter.ts`：

```typescript
export function useTypewriter(
  text: string,
  { charsPerSecond = 45, catchUpThreshold = 400 }: UseTypewriterOptions = {},
) {
  const [visibleLength, setVisibleLength] = useState(0);
  const textRef = useRef(text);
  const progressRef = useRef(0);
  const lastTickRef = useRef(0);

  textRef.current = text;

  useEffect(() => {
    if (text.length < progressRef.current) {
      progressRef.current = 0;
      setVisibleLength(0);
    }
  }, [text]);

  useEffect(() => {
    lastTickRef.current = performance.now();
    const timer = window.setInterval(() => {
      const now = performance.now();
      const dt = Math.min((now - lastTickRef.current) / 1000, 2);
      lastTickRef.current = now;
      const full = textRef.current;
      if (progressRef.current >= full.length) {
        return;
      }
      const behind = full.length - progressRef.current;
      const rate = charsPerSecond + Math.max(0, behind - catchUpThreshold) * 2;
      progressRef.current = Math.min(full.length, progressRef.current + rate * dt);
      setVisibleLength(Math.floor(progressRef.current));
    }, 50);
    return () => window.clearInterval(timer);
  }, [charsPerSecond, catchUpThreshold]);

  return text.slice(0, visibleLength);
}
```

### 最大的坑：定时器不能挂在依赖流式文本的 effect 上

第一版是这么写的：

```typescript
// 错误写法
useEffect(() => {
  const timer = window.setInterval(() => { /* 推进一格 */ }, 50);
  return () => window.clearInterval(timer);
}, [text]);          // ← 依赖 text
```

看起来天经地义：文本变了，重新起一个定时器继续推进。实际现象是**一个字都不出来**。

推理一遍就清楚了：流式 delta 每几十毫秒更新一次 `text`，effect 的清理函数随即 `clearInterval`，然后重新计时。50ms 的 interval 撞上 30ms 一次的 delta，**永远活不到第一次触发**。整个流结束前，回调一次都没跑过。这类 bug 的信号很典型：**"完全没反应"而不是"反应不对"**——看到定时器一次都没触发，第一件事就是查它挂在什么依赖上。

正确写法有三条：**interval 常驻**，依赖数组里只有几乎不变的速度参数，定时器实际只创建一次；**用 ref 读最新文本**，`textRef.current = text` 写在组件函数体里每次渲染同步更新，tick 里读到的永远是最新值；**进度也放 ref**，`progressRef` 是浮点数，`visibleLength` 只是它取整后的展示副本——用 state 存进度，每次 tick 触发的重渲染会反过来影响下一次计算，逻辑立刻绕不清楚。

### 按 dt 推进，且给 dt 设上限

固定步长（每次放 3 个字）在后台标签页会出问题：浏览器把 `setInterval` 钳制到 1 秒以上，固定步长意味着速度掉到原来的二十分之一。改成按**实际耗时**推进后，tick 变稀疏时每次多放几个字，单位时间的字数不变，**整体速度稳定**。

```typescript
const dt = Math.min((now - lastTickRef.current) / 1000, 2);
```

`Math.min(..., 2)` 这个上限也是必需的。标签页被深度节流几分钟后切回来，`now - lastTick` 可能是 300 秒，乘以速率就是几万个字——一次 tick 把全部积压倾泻出来，节流的意义荡然无存。截到 2 秒，最坏情况也只是"回来时快进了一小段"。

追赶策略是 `rate = charsPerSecond + Math.max(0, behind - catchUpThreshold) * 2`：基础速度 45 字/秒约等于舒适阅读速度的上限，积压超过 400 字后每多积压 1 个字加 2 字/秒，保证**展示进度不会和真实进度脱节太远**。文本变短意味着新一轮流开始，立刻把进度归零。

消费端只有一行 `const pacedThinking = useTypewriter(liveThinking);`。**只对思考流节流，不对正文回答节流**——正文是用户真正在等的东西，人为放慢等于故意让人等；思考过程是辅助信息，慢一点反而看得清。

## 56.6 推理块：可折叠、有字数、能渲染 Markdown

推理过程如果只是一坨灰色纯文本，读起来很痛苦——模型的思考里经常带列表和代码。用户的要求很具体："推理过程的内容需要渲染，代码要放进代码块。"

`frontend/web/app/components/conversation/reasoning-block.tsx`：

```tsx
export function ReasoningBlock({ reasoning, streaming = false }: ReasoningBlockProps) {
  const [expanded, setExpanded] = useState<boolean | null>(null);
  const open = expanded ?? streaming;

  if (!reasoning) return null;

  return (
    <div className="mb-2 overflow-hidden rounded-2xl border border-(--line) bg-(--fill-1)">
      <button aria-expanded={open} onClick={() => setExpanded(!open)} type="button">
        <Brain className={streaming ? "animate-pulse text-(--accent)" : "text-(--text-4)"} size={14} />
        <span>{streaming ? "正在思考…" : "推理过程"}</span>
        <span className="text-(--text-5)">{reasoning.length} 字</span>
        <ChevronDown className={`ml-auto transition-transform ${open ? "rotate-180" : ""}`} size={14} />
      </button>
      {open ? (
        <div className="max-h-64 overflow-y-auto border-t border-(--line-soft) px-4 py-3">
          <MarkdownContent compact content={reasoning} />
        </div>
      ) : null}
    </div>
  );
}
```

四个设计点：

**`useState<boolean | null>(null)` 表示"用户还没表态"。** `open = expanded ?? streaming` 的效果是：流式中默认展开（让人看到进展），结束后默认折叠（结论已出，过程收起来）；一旦用户手动点过，完全尊重用户的选择。普通布尔做不到这种"默认值跟随状态、手动值优先"的语义。

**字数统计给的是预期。** "推理过程 1284 字"和"推理过程"是两种体验。

**流式脉冲。** `animate-pulse` 加在大脑图标上配 accent 色，一眼区分"还在想"和"想完了"。

**内容走 Markdown 的 compact 变体。** `MarkdownContent` 的 `compact` 开关把正文从 `text-[15px] leading-7 text-(--text-3)` 换成 `text-[13px] leading-6 text-(--text-4)`，代码块字号同步收紧。推理块和正文回答**共用一套 Markdown 组件**，但视觉层级明确区分；`max-h-64 overflow-y-auto` 再给个高度上限，避免超长思考把整个对话撑开。

## 56.7 主题系统：变量分层、防闪白、自定义下拉

用户点主题切换没反应，是因为原来根本没有完整的主题系统——只有一套写死的暗色。

### CSS 变量分层

`frontend/web/app/globals.css` 的令牌不按颜色命名，而是**按用途分层**：

```css
:root,
:root[data-theme="dark"] {
  color-scheme: dark;
  /* 页面与分层表面：从页面底色到卡片逐级抬升 */

  --surface-2: #0b0d14;
  --surface-3: #111421;
  --surface-4: #151722;

  /* 分隔线与填充 */

  --line-soft: rgba(255, 255, 255, 0.05);

  --fill-2: rgba(255, 255, 255, 0.09);
  --fill-3: rgba(255, 255, 255, 0.15);

```

关键在于**暗色用半透明白、亮色用半透明黑**。`--fill-1: rgba(255,255,255,0.04)` 在暗色下是"轻微提亮"，对应的亮色值 `rgba(15,23,42,0.045)` 是"轻微压暗"，两者在各自主题里语义相同。这样组件层不需要任何主题分支。`color-scheme` 也别漏——它决定浏览器原生控件（滚动条默认样式、`<input>` 内部渲染、聚焦环）用哪套配色。

### Tailwind 4 的变量语法

Tailwind 4 消费 CSS 变量的写法和 3.x 不同，这是升级时最容易踩的地方：

```tsx
className="border border-(--line) bg-(--surface) text-(--text-1)"   // 括号语法
className="bg-(--accent)/10 ring-1 ring-(--accent)/40"              // 带透明度修饰符
className="bg-(--surface-2)/95 backdrop-blur-xl"
className="[overflow-anchor:none]"                                  // 任意属性
```

`bg-(--accent)/10` 这种"变量 + 透明度"特别好用：一个 accent 变量派生出边框（`/30`）、底色（`/10`）、选中环（`/40`）三档，主题切换时全部跟着变。如果你还在写 `bg-[var(--accent)]`，那是 3.x 的写法——4.x 下它也能工作，但**接不了透明度修饰符，而且不会报错**。另外 Tailwind 4 不再需要 `tailwind.config.js` 声明这些变量。

### 防 FOUC：beforeInteractive 注入初始化脚本

主题存在 localStorage 里，而 localStorage 只能在客户端读。等 React 挂载后再设 `data-theme`，亮色用户会先看到一帧暗色再闪成亮色。解法是在 body 最前面同步执行一小段脚本（`frontend/web/app/layout.tsx`）：

```tsx
// 首帧前从 localStorage 恢复主题，避免亮色用户看到暗色闪烁。
// system 或未设置时跟随操作系统配色。
const themeInitScript = `(function(){try{var p=localStorage.getItem("atlas-web-theme");var t=p==="light"||p==="dark"?p:(window.matchMedia("(prefers-color-scheme: light)").matches?"light":"dark");document.documentElement.dataset.theme=t;}catch(e){document.documentElement.dataset.theme="dark";}})();`;

export default function RootLayout({ children }: Readonly<{ children: React.ReactNode }>) {
  return (
    <html lang="zh-CN" suppressHydrationWarning>
      <body>
        <Script id="atlas-theme-init" strategy="beforeInteractive">
          {themeInitScript}
        </Script>
        {children}
      </body>
    </html>
  );
}
```

四个要点：**`strategy="beforeInteractive"`** 让 Next.js 把脚本放在任何水合之前执行，这是它区别于普通 `<script>` 的关键；**`suppressHydrationWarning` 加在 `<html>` 上**，因为脚本改了 `documentElement` 的属性，服务端 HTML 和客户端首帧必然不一致；**`try/catch` 兜底**，隐私模式下 `localStorage` 可能直接抛异常；**脚本写成压缩的一行**，它会内联进 HTML，可读性让位于体积。

运行时的偏好管理在 `frontend/web/app/lib/theme.ts`：`applyTheme` 把解析后的主题写进 `document.documentElement.dataset.theme`，`update` 同时写 localStorage。此外还有一个容易漏的 effect：

```typescript
useEffect(() => {
  if (preference !== "system") return;
  const media = window.matchMedia("(prefers-color-scheme: light)");
  const onChange = () => applyTheme("system");
  media.addEventListener("change", onChange);
  return () => media.removeEventListener("change", onChange);
}, [preference]);
```

`system` 不是"初始化时读一次系统配色"，而是**持续跟随**：用户在操作系统里切换深浅色，界面实时跟着变。

### 自定义下拉替代原生 select

主题选择器最初用的是原生 `<select>`。问题是**原生下拉的弹出层由操作系统渲染，CSS 完全管不到**：暗色界面上弹出一个白底黑字的系统列表，刺眼且割裂，不同平台样式还各不相同。

所以抽了通用的 `SelectMenu` 和专用的 `ThemeMenu`，共用同一套交互骨架：

```tsx
useEffect(() => {
  if (!open) return;
  function onPointerDown(event: PointerEvent) {
    if (!rootRef.current?.contains(event.target as Node)) setOpen(false);
  }
  function onKeyDown(event: KeyboardEvent) {
    if (event.key === "Escape") setOpen(false);
  }
  window.addEventListener("pointerdown", onPointerDown);
  window.addEventListener("keydown", onKeyDown);
  return () => {
    window.removeEventListener("pointerdown", onPointerDown);
    window.removeEventListener("keydown", onKeyDown);
  };
}, [open]);
```

三个必备行为：**点击外部关闭**、**Escape 关闭**、**只在打开时挂监听**（`if (!open) return` 提前返回，避免永久挂着两个全局监听器）。无障碍属性也要给全，否则自定义下拉对屏幕阅读器就是一堆匿名按钮：触发按钮挂 `aria-expanded` / `aria-haspopup="listbox"` / `aria-label`，弹层挂 `role="listbox"`，每个选项挂 `role="option"` + `aria-selected`。`ThemeMenu` 在此之上给三个选项各配了图标、一句 hint（"随操作系统自动切换" / "明亮环境下使用" / "默认的深色工作台"）和选中标记——用户不用猜"跟随系统"到底跟随什么。

### 自定义滚动条

原生滚动条在暗色主题下是一条突兀的灰白色带。改造分两条路径：

```css
/* Chromium：细圆角滑块悬浮在透明轨道上，隐藏两端箭头按钮。 */
::-webkit-scrollbar { width: 10px; height: 10px; }
::-webkit-scrollbar-track { background: transparent; }
::-webkit-scrollbar-button { display: none; width: 0; height: 0; }

::-webkit-scrollbar-thumb {
  min-height: 32px;
  background: var(--scrollbar);
  background-clip: padding-box;
  border: 3px solid transparent;
  border-radius: 999px;
}

/* Firefox 没有 ::-webkit-scrollbar，用标准属性给出等效的细滚动条。
   注意不能对 Chromium 应用这两个标准属性——它们会禁用上面的自定义样式。 */
@supports not selector(::-webkit-scrollbar) {
  * {
    scrollbar-width: thin;
    scrollbar-color: var(--scrollbar) transparent;
  }
}
```

`border: 3px solid transparent` + `background-clip: padding-box` 是让滑块"变细并留出内边距"的经典技巧——直接改 `width` 会连轨道一起变窄，热区太小不好抓；hover 时把边框收到 2px，滑块视觉上变粗，是个很轻的反馈。而 Chromium 同时支持两套语法，一旦设了 `scrollbar-width`/`scrollbar-color`，它就会**放弃 `::-webkit-scrollbar` 的自定义样式**回退到原生细滚动条，所以必须用 `@supports not selector(...)` 做特性检测，让两套样式各管各的浏览器。

### 代码块复制按钮

Agent 的回答里经常有命令和代码，不能复制就得手动框选。`MarkdownContent` 给 `pre` 换了个带复制按钮的容器：

```tsx
/** 代码块容器：右上角悬浮复制按钮，点击复制整段代码。 */
function PreBlock({ children }: { children?: React.ReactNode }) {
  const preRef = useRef<HTMLPreElement>(null);
  const [copied, setCopied] = useState(false);

  async function copy() {
    const text = preRef.current?.innerText ?? "";
    if (!text) return;
    try {
      await navigator.clipboard.writeText(text);
      setCopied(true);
      window.setTimeout(() => setCopied(false), 1600);
    } catch {
      // 剪贴板不可用（如非安全上下文）时静默失败。
    }
  }

  return (
    <div className="group relative my-4">
      <pre className="overflow-x-auto" ref={preRef}>{children}</pre>
      <button className="... opacity-0 focus-visible:opacity-100 group-hover:opacity-100" onClick={copy} type="button">
        {copied ? "已复制" : "复制"}
      </button>
    </div>
  );
}
```

四个细节：**从 `innerText` 取值**而不是拼 children（children 是 React 节点树，`innerText` 直接拿到用户看到的纯文本）；**`opacity-0 group-hover:opacity-100`** 平时隐藏不干扰阅读，并用 `focus-visible:opacity-100` 照顾键盘用户；**`navigator.clipboard` 在非安全上下文不可用**，整段包 try/catch 静默失败，总比抛异常炸掉整条回答强；**成功状态 1.6 秒后自动复位**，不需要额外的 toast 系统。

## 56.8 输入框与侧栏

两个小改动，但对"是否像成品"的影响很大。

### 输入框自动伸缩

原来的输入框固定 `rows`，永远占着四五行高度。改成单行起步、随内容长高、到上限后内部滚动（`frontend/web/app/components/chat-input.tsx`）：

```tsx
const MAX_INPUT_HEIGHT = 176;

// 随内容自动伸缩：先归零再按内容高度设置，超过上限后内部滚动。
useEffect(() => {
  const element = textareaRef.current;
  if (!element) {
    return;
  }
  element.style.height = "auto";
  element.style.height = `${Math.min(element.scrollHeight, MAX_INPUT_HEIGHT)}px`;
  element.style.overflowY =
    element.scrollHeight > MAX_INPUT_HEIGHT ? "auto" : "hidden";
}, [draft]);
```

**`element.style.height = "auto"` 这行不能省。** `scrollHeight` 包含当前设定的高度，不先归零的话删字时高度只增不减——输入框会越写越高，删空了还停在原来的高度。`overflowY` 也要手动切，没到上限时设 `hidden`，否则某些浏览器会常驻一条滚动条槽位。

### Enter 发送与中文输入法

```tsx
onKeyDown={(event) => {
  // Enter 直接发送，Shift+Enter 换行；输入法候选确认的 Enter 不触发。
  if (
    event.key === "Enter" &&
    !event.shiftKey &&
    !event.nativeEvent.isComposing
  ) {
    event.preventDefault();
    if (!disabled && !sending && draft.trim()) {
      onSend();
    }
  }
}}
```

`event.nativeEvent.isComposing` 是重点。中文、日文输入法在选字时，回车是用来**确认候选词**的。没有这个判断，用户打"你好"按回车选词，消息就直接发出去了，输入框里还留着拼音——中文用户几乎百分之百会踩到。React 的合成事件对象上没有 `isComposing`，要从 `event.nativeEvent` 拿。

### 可隐藏侧栏

侧栏固定 300px，小屏笔记本上把对话区压得很窄。加一个折叠开关，偏好持久化（`frontend/web/app/page.tsx`）：

```tsx
// 左侧导航可隐藏：隐藏时对话区自动铺满整个宽度，偏好持久化。
const [sidebarOpen, setSidebarOpen] = useState(true);

useEffect(() => {
  if (window.localStorage.getItem("atlas-sidebar-open") === "0") {
    setSidebarOpen(false);
  }
}, []);

function toggleSidebar() {
  setSidebarOpen((open) => {
    window.localStorage.setItem("atlas-sidebar-open", open ? "0" : "1");
    return !open;
  });
}
```

布局用 grid 列定义切换，收起时变成单列，对话区自然铺满：

```tsx
className={`grid h-full min-h-0 ${
  sidebarOpen
    ? "grid-cols-[300px_1fr] max-lg:grid-cols-1 max-lg:grid-rows-[auto_1fr]"
    : "grid-cols-1"
}`}
```

**注意默认值是 `true` 而不是从 localStorage 初始化。** 服务端渲染读不到 localStorage，把读取放进 `useState` 初始化函数会导致 hydration 错误。正确做法是给确定的默认值，挂载后在 effect 里纠正。代价是收起状态的用户会看到一帧侧栏，但这比 hydration 报错好。另外别忘了在侧栏收起时于左上角渲染一个绝对定位的展开按钮，否则就没法再打开了。

## 56.9 品牌图标

浏览器标签页上一直是 Next.js 的默认图标，看起来像个没做完的脚手架项目。

Next.js 的 app 目录有一套**文件约定**：把特定文件名放进 `app/` 根目录，框架自动生成对应的 `<link>` 标签，不需要写任何 metadata 配置。

```text
frontend/web/app/
├── icon.svg          浏览器标签页图标（矢量，优先级最高）
├── favicon.ico       传统 ICO，兼容老浏览器与部分工具链
└── apple-icon.png    iOS 添加到主屏幕时使用
```

注意路径是 `app/icon.svg`，**不是 `app/app/icon.svg`，也不是 `public/`**。放进 `public/` 需要手写 metadata，放进 app 目录才走约定。

图标是手写的 SVG（`frontend/web/app/icon.svg`）：

```xml
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 64 64">
  <!-- 底座：圆角方形，蓝(#4E8CFF)→紫(#7C5CFC)对角渐变 + 顶部白色高光 -->
  <rect x="1" y="1" width="62" height="62" rx="16" fill="url(#bg)"/>
  <rect x="1" y="1" width="62" height="62" rx="16" fill="url(#shine)"/>
  <!-- 天线 -->
  <rect x="30.4" y="14.5" width="3.2" height="7" rx="1.6" fill="#FFFFFF"/>
  <circle cx="32" cy="12.2" r="3.4" fill="#FFFFFF"/>
  <!-- 两侧耳块 -->
  <rect x="7.6" y="31" width="4.6" height="13" rx="2.3" fill="#FFFFFF" opacity="0.92"/>
  <rect x="51.8" y="31" width="4.6" height="13" rx="2.3" fill="#FFFFFF" opacity="0.92"/>
  <!-- 机器人头与胶囊竖眼 -->
  <rect x="14" y="23" width="36" height="29" rx="11" fill="#FFFFFF"/>
  <rect x="22.2" y="31" width="6.2" height="13" rx="3.1" fill="#4C63F2"/>
  <rect x="35.6" y="31" width="6.2" height="13" rx="3.1" fill="#4C63F2"/>
</svg>
```

设计约束只有一条：**16px 下还能认出来**。这条约束推出了所有决策——圆角方底 + 高饱和渐变，保证图标在亮色暗色标签栏上都有明确边界；只用三种颜色（渐变底、白色、深蓝眼睛），缩小时颜色越少越清晰；形状极简，没有描边、阴影和细节，那些东西在 16px 下全糊成脏点；元素占满画布，留白太多会让图标显得比别人小一号。

## 56.11 本章验收

```bash
cd frontend/web
pnpm install
pnpm typecheck        # tsc --noEmit，应无输出
pnpm build            # Next.js 生产构建，应全绿
pnpm dev
```

界面上逐项确认。

**任务卡片**

- 发一条会触发计划执行的任务，时间线里**只出现一张任务卡**，底部没有额外进度条；
- 任务卡出现在**触发它的那条用户消息下方**，不在时间线末尾；
- 任务执行完，紧接着发一句"你好"，直答回复出现在任务卡**下面**，任务卡不跟着移动，也不会把"你好呀"当成自己的 Final Answer；
- 刷新页面重新进入会话，历史任务卡显示"任务已完成"，**图标不转圈**；
- 点带工具的步骤行，右侧打开工具详情且该行显示选中态；没有工具的步骤行点了没反应、鼠标不是手型。

**锚定滚动**

- 在长会话里往上滚到中间再发一条追问：这条消息滚到视口顶部，**流式期间视图完全不动**；
- 回答结束的一刻视图**不跳底部**（这是坑三的验收点）；
- 不在底部时"回到底部"按钮出现，点击平滑滚到底；到底后按钮消失；
- 切换到另一个会话，直接定位在底部；
- 把标签页切到后台，等任务跑完再切回来，滚动位置正常。

**推理与打字机**

- 触发一次带思考的回答，推理块**逐字出现**而不是整段刷屏，大脑图标脉冲；
- 推理内容里的列表、代码块正确渲染成 Markdown，不是纯文本；
- 回答结束后推理块自动折叠，点击可展开回看，标题上显示字数。

**主题与交互**

- 主题菜单切换亮色/暗色/跟随系统，界面**立即变化**；切到亮色后刷新页面，**首帧就是亮色，不闪暗色**；
- 选"跟随系统"后在操作系统里切换深浅色，界面实时跟随；
- 滚动条是细圆角样式，颜色随主题变化；
- 代码块悬浮出现复制按钮，点击变成"已复制"并在约 1.6 秒后复位；
- 输入框初始一行高，输入多行后长高，超过上限内部滚动；删空后回到一行；
- 用中文输入法打字，选词按回车**不会误发消息**；
- 点侧栏折叠按钮，对话区铺满整个宽度；刷新页面仍保持收起状态；
