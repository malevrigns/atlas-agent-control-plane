# 第五十六章. 任务卡片、锚定滚动与界面主题化

## 56.1 本章目标

前面几章一直在往后端加能力：直答路由、知识库召回、浏览器读页。能力是够了，但把界面交给真人用一天，反馈全是界面问题，而且每一条都很扎心：

- "你任务框和展示的东西重复了，严重问题"——同一次任务在时间线里画了一排步骤卡片，底部又挂了一条计划进度条，两处显示同一件事。
- "我问了一个你好，但是你对你好的回复为什么还有上一个任务的任务栏呢"——任务卡固定挂在时间线末尾，新提的问题被上一轮的任务卡压在下面。
- "为什么他自动给我从上面滑到下面，而不是一直锁定在我当前消息的位置"——追问之后视图自己从当前位置滑到底部。
- "你的思考直播太快了，给我放慢一点"——推理流瞬间刷屏，根本来不及读。
- 还有一串"小事"：输入框巨大、侧栏占死屏幕、原生滚动条丑、代码块不能复制、主题切换点了没反应。

这些都不是后端问题，是**前端把"过程"呈现错了**。这一章把对话区从头改一遍。

完成本章后，你将能够：

- 把"一次任务运行"建模成时间线里的一条独立项，让任务卡属于触发它的那一轮对话，而不是永远挂在最后；
- 用 `plan_id` 精确匹配终结事件，并给旧数据设计时间窗兜底，避免一张卡吞掉另一次运行的结果；
- 实现 ChatGPT 式的锚定滚动：切会话跳底部、发追问锁顶部、流式期间绝不跟滚，并说清四个必踩的坑；
- 写一个真正能跑起来的打字机节流 hook，理解"定时器不能挂在依赖流式文本的 effect 上"这条铁律；
- 用 CSS 变量 + `data-theme` + `beforeInteractive` 脚本做出不闪白的主题系统；
- 处理一堆决定"这个界面是否像成品"的细节：自动伸缩输入框、中文输入法回车、可隐藏侧栏、自定义滚动条、代码块复制、品牌图标。

## 56.2 一次任务被画了两遍

先看清楚问题的形状。

旧的视图模型大意是这样的：

```typescript
// 旧实现的结构（示意）
return {
  plan: getLatestPlan(events),        // 整个会话只取"最新的那一个"计划
  timelineItems: messages.map(...),   // 时间线里只有消息
};
```

时间线只承载消息；计划被单独拎出来，由外层组件追加渲染在**整条时间线的末尾**，同时底部还有一条常驻的 `PlanProgressBar` 显示 n/m 进度。

**问题一：同一件事画了两遍。** 步骤卡片列表和底部进度条消费的是同一份 `buildStepViews` 结果，一个展开成一排卡片，一个压缩成一条进度。用户看到的是"上面刚说完第 3 步完成，下面又说一遍 3/5"。这不是冗余信息，是**噪音**——它让人怀疑是不是有两个任务在跑。

**问题二：任务卡不属于任何一轮对话。** `getLatestPlan` 只返回最新的一个计划，渲染位置又固定在末尾，于是"计划"和"提出这个计划的那句话"在视觉上彻底脱钩。用户发一句"你好"，得到的是一条直答气泡，**下面却还挂着上一个任务的卡片**——因为那张卡永远在最后。

两个问题的根因是同一个：**计划不是时间线里的一等公民**。

### 把 plan_created 变成时间线项

修法很直接：每个 `plan_created` 事件都变成一条时间线项，和消息一起按 `created_at` 排序。

`frontend/web/app/components/conversation/types.ts`：

```typescript
export type TimelineItem =
  | { kind: "message"; id: string; created_at: string; message: ChatMessage }
  | { kind: "plan"; id: string; created_at: string; event: SessionEventItem };
```

`frontend/web/app/components/conversation/view-model.ts`：

```typescript
function buildTimelineItems(
  messages: ChatMessage[],
  events: SessionEventItem[],
): TimelineItem[] {
  const planEvents = events.filter((event) => event.type === "plan_created");

  // 计划执行路径的最终回答由 AgentRunBlock 的 FinalAnswer 展示；
  // 同一内容的 assistant 消息不再重复渲染成气泡。
  // 只统计流水线运行（mode 非 chat）的 task_done——直接问答的回答
  // 没有 AgentRunBlock，它们的气泡必须保留。
  const finalAnswers = new Set(
    events
      .filter(
        (event) =>
          event.type === "task_done" && getString(event.payload.mode) !== "chat",
      )
      .map((event) => getString(event.payload.final_answer))
      .filter(Boolean),
  );
  const visibleMessages = planEvents.length
    ? messages.filter(
        (message) =>
          message.role !== "assistant" || !finalAnswers.has(message.content),
      )
    : messages;

  return [
    ...visibleMessages.map((message) => ({
      kind: "message" as const,
      id: `message-${message.id}`,
      created_at: message.created_at,
      message,
    })),
    ...planEvents.map((event) => ({
      kind: "plan" as const,
      id: `plan-${event.id}`,
      created_at: event.created_at,
      event,
    })),
  ].sort((left, right) => left.created_at.localeCompare(right.created_at));
}
```

三个细节值得拆开说。

**第一，`created_at` 排序解决了归属问题。** 计划事件的时间戳一定晚于触发它的用户消息、早于下一条用户消息，所以排序之后任务卡自然落在正确的位置。不需要额外维护"这个计划属于哪条消息"的关联字段——**时间本身就是关联**。

**第二，去重要挑对象。** 流水线路径的最终回答会由 `AgentRunBlock` 里的 `FinalAnswer` 渲染，如果同内容的 assistant 消息还渲染成气泡，就会出现"同一段回答连着出现两次"。所以要从消息列表里滤掉它。但注意过滤条件里的 `getString(event.payload.mode) !== "chat"`：直接问答路径也发 `task_done`，而直答**没有** `AgentRunBlock`，它的气泡是唯一显示位置。少了这个条件，用户会发现"问'你好'居然什么都没回"。

**第三，`planEvents.length` 的短路。** 一个从头到尾都是直答的会话不该跑去重逻辑，直接原样返回消息即可。

### 一张卡只负责一次运行

时间线拆开之后，`AgentRunBlock` 的输入也得跟着变——它不能再去"找最新的计划"，而要接收**属于自己的那个** `planEvent`，然后自己解析：

`frontend/web/app/components/conversation/agent-run-block.tsx`：

```tsx
type AgentRunBlockProps = {
  events: SessionEventItem[];
  /** 仅最新一张卡在会话执行中时为 true——历史卡片永远是 false。 */
  executing: boolean;
  /** store 里实时更新的计划（执行中步骤状态来自 SSE），仅当 id 匹配时覆盖事件快照。 */
  livePlan: AgentPlan | null;
  onSelectToolEvent: (eventId: string) => void;
  /** 本卡片对应的 plan_created 事件——一张卡只负责一次任务运行。 */
  planEvent: SessionEventItem;
  planning: boolean;
  selectedToolEventId: string | null;
};

const plan = useMemo(() => {
  const parsed = parsePlanPayload(planEvent.payload);
  return livePlan && livePlan.id === parsed.id ? livePlan : parsed;
}, [livePlan, planEvent]);
```

`livePlan` 是 store 里那份随 SSE 实时更新步骤状态的计划。这里的判断很关键：**只有 id 匹配才用 live 版本覆盖事件快照**。历史卡片解析出来的 plan id 跟当前 live plan 不同，于是它们永远显示自己那次运行的最终状态——不会被新任务的进度污染。

`parsePlanPayload` 是纯解析，负责把事件 payload 里可能缺字段的原始数据补齐成 `AgentPlan`：

```typescript
export function parsePlanPayload(payload: Record<string, unknown>): AgentPlan {
  const steps = Array.isArray(payload.steps) ? payload.steps : [];
  return {
    id: getString(payload.id) || getString(payload.plan_id),
    title: getString(payload.title) || "任务执行计划",
    goal: getString(payload.goal),
    source: getString(payload.source) || "unknown",
    steps: steps.map((item, index) => {
      const value = item as Record<string, unknown>;
      return {
        id: getString(value.id) || `step-${index + 1}`,
        title: getString(value.title) || `步骤 ${index + 1}`,
        description: getString(value.description),
        expected_output: getString(value.expected_output),
        status: getString(value.status) || "pending",
      };
    }),
  };
}
```

注意 `getString(payload.id) || getString(payload.plan_id)`——后端不同版本用过两个字段名，前端两个都认。这类兼容代码写在解析层，比散在业务逻辑里好得多。

### 终结事件归谁：plan_id 精确匹配 + 时间窗兜底

一张卡渲染完步骤，还要渲染这次运行的最终回答。问题来了：`task_done` / `task_error` 在事件流里是平铺的，怎么知道哪个属于哪张卡？

```tsx
// 只认属于本次运行的终结事件：优先按 plan_id 匹配；
// 旧数据没有 plan_id 时退回时间窗（本计划之后、下一个计划之前），
// 并排除直答路径的 task_done（mode=chat），避免旧任务卡吞掉新对话的结果。
const finalEvent = useMemo(() => {
  const terminals = events.filter(
    (event) => event.type === "task_done" || event.type === "task_error",
  );
  if (plan.id) {
    const byPlanId = terminals.find(
      (event) => getString(event.payload.plan_id) === plan.id,
    );
    if (byPlanId) {
      return byPlanId;
    }
  }
  const nextPlanAt = events.find(
    (event) =>
      event.type === "plan_created" && event.created_at > planEvent.created_at,
  )?.created_at;
  return (
    terminals.find(
      (event) =>
        event.created_at > planEvent.created_at &&
        (!nextPlanAt || event.created_at < nextPlanAt) &&
        getString(event.payload.mode) !== "chat",
    ) ?? null
  );
}, [events, plan.id, planEvent]);
```

这段是本节最容易写错的地方，三层逻辑缺一不可：

1. **优先按 `plan_id` 精确匹配。** 新数据都带这个字段，一句 `find` 搞定，没有歧义。
2. **旧数据用时间窗兜底。** 改造之前落库的事件没有 `plan_id`。规则是"晚于本计划、早于下一个计划"，物理上就是这次运行的区间。
3. **兜底时必须排除 `mode === "chat"`。** 这一条是踩出来的：会话里先跑了一次任务，然后用户问了句"你好"走直答路径。直答也发 `task_done`，它在时间上"晚于本计划"，而且**后面没有新的计划**，所以 `nextPlanAt` 是 undefined，时间窗右边界不存在——那条直答的 `task_done` 就被上一张任务卡认领了。现象是：任务卡下面挂着一句莫名其妙的"你好呀"作为 Final Answer。加上 `mode` 判断才修好。

### running 判定：不能靠步骤反推

最后一个坑藏在一行布尔里：

```tsx
const runningStep = steps.find((step) => step.status === "running") ?? null;
const failed = finalEvent?.type === "task_error";
// 不用 steps.some(pending) 推断运行中——被中断的历史任务没有终结事件，
// 会导致旧卡片永远转圈；执行态只信当前会话的 planning/executing。
const running = !finalEvent && (planning || executing || Boolean(runningStep));
```

直觉写法是"还有 pending 的步骤就是在跑"。这个推断对**正常结束**的任务成立，对**被中断**的任务完全错误：用户点了停止、或者后端进程挂了，那次运行既没有 `task_done` 也没有 `task_error`，步骤永远停在 pending。于是每次打开这个会话，那张三个月前的历史卡片都在兴致勃勃地转圈。

正确的心智模型是：**"正在运行"是当前会话的实时状态，不是历史数据能推导出来的属性。** 所以执行态从外部传入，而且只授予最新一张卡：

`frontend/web/app/components/conversation-timeline.tsx`：

```tsx
// 执行态只属于最新的任务卡；历史卡片一律静止。
const lastPlanItemId =
  [...viewModel.timelineItems]
    .reverse()
    .find((item) => item.kind === "plan")?.id ?? null;

// ...渲染时
<AgentRunBlock
  events={events.data}
  executing={executing && item.id === lastPlanItemId}
  livePlan={plan}
  onSelectToolEvent={onSelectToolEvent}
  planEvent={item.event}
  planning={planning && item.id === lastPlanItemId}
  selectedToolEventId={selectedToolEventId}
/>
```

`executing && item.id === lastPlanItemId` 这个写法看起来啰嗦，但它把"全局执行态"降级成了"这一张卡的执行态"，历史卡片拿到的永远是 `false`。

## 56.3 TaskRunCard：把一次运行收进一张卡

视图模型对了，组件也要跟着收敛。旧实现有三个组件在分摊同一件事：

- `StepCard`——每个步骤一张独立卡片，一次五步任务就是五张卡；
- `StepDetailDialog`——点步骤弹出模态框看详情；
- `PlanProgressBar`——底部常驻进度条。

新实现只有一个 `TaskRunCard`：头部是状态图标 + 标题 + `n/m` 计数 + 折叠箭头，展开区逐条列出步骤和一行摘要。

每行的摘要来自 `getStepDisplaySummary`，它按状态给不同文案，失败时还会把后端的建议拼进来：

```typescript
export function getStepDisplaySummary(step: StepView) {
  if (step.status === "running") {
    return getRunningCopy(step);
  }
  if (step.status === "completed") {
    return buildToolObservation(step).brief || step.expected_output || "步骤已完成。";
  }
  if (step.status === "failed") {
    const userMessage = getString(step.errorEvent?.payload.user_message);
    const suggestion = getString(step.errorEvent?.payload.suggestion);
    if (userMessage && suggestion) {
      return `${userMessage} 建议：${suggestion}`;
    }
    return userMessage || "步骤执行失败，请查看任务错误或工具详情。";
  }
  return step.description || step.expected_output || "等待执行。";
}
```

**删代码也是重构成果。** 这次改造净删掉三个组件文件，`conversation/` 目录从八个组件降到六个，`ConversationTimeline` 的分支从"消息 / 步骤卡 / 进度条 / 详情弹窗"简化成"消息 / 任务卡"。顺带说一句诚实的话：`view-model.ts` 里的 `buildPlanProgressView` 是给 `PlanProgressBar` 服务的，组件删掉之后它就没有调用方了——这种残留很容易在重构中被忽略，值得在下一轮清理里一并删除。

## 56.4 ChatGPT 式锚定滚动

这是本章技术含量最高的部分。

先说清楚**目标行为**，因为大部分实现问题都源于目标本身没定义清楚：

1. **切换会话**：直接跳到底部，看最新的内容。
2. **发出追问**：把这条用户消息滚到视口顶部并锁在那儿，回答在下方生长。
3. **流式期间**：绝不自动跟滚。用户滚到哪就停在哪，哪怕新内容在屏幕外。
4. **兜底**：不在底部时显示"回到底部"按钮。

第 3 条是关键。很多聊天界面的做法是"如果用户贴着底部就跟滚"，但这条规则和第 2 条直接冲突：锚定之后用户其实还没滚动，如果内容不足一屏，视口在物理上仍然贴底，跟滚逻辑立刻把刚锚好的位置推走。所以这里的选择是**彻底放弃自动跟滚**，只留"回到底部"按钮。

完整实现在 `frontend/web/app/hooks/use-auto-scroll.ts`：

```typescript
export function useAutoScroll({
  threshold = 96,
  sessionKey,
  lastUserMessageId,
}: UseAutoScrollOptions) {
  const bottomRef = useRef<HTMLDivElement | null>(null);
  const scrollRef = useRef<HTMLDivElement | null>(null);
  const [pinnedToBottom, setPinnedToBottom] = useState(true);
  // 锚定后在时间线尾部垫一段空白，保证"锚到视口顶部"物理上可达
  //（否则新消息下方内容不足一屏时滚不上去）。ChatGPT 同款行为。
  const [anchorSpacer, setAnchorSpacer] = useState(false);
  const anchoredMessageRef = useRef<string | null>(null);
  const sessionRef = useRef<string | null>(null);

  const scrollToBottom = useCallback((behavior: ScrollBehavior = "smooth") => {
    bottomRef.current?.scrollIntoView({ behavior, block: "end" });
  }, []);

  const handleScroll = useCallback(() => {
    const element = scrollRef.current;
    if (!element) {
      return;
    }
    // 以"内容末尾"（bottomRef，位于锚定空白之前）为贴底基准：
    // 锚定空白只是滚动缓冲，视口越过内容末尾就算到底，不再提示回到底部。
    const bottomElement = bottomRef.current;
    const distanceToBottom = bottomElement
      ? bottomElement.getBoundingClientRect().top -
        element.getBoundingClientRect().top -
        element.clientHeight
      : element.scrollHeight - element.scrollTop - element.clientHeight;
    setPinnedToBottom(distanceToBottom <= threshold);
  }, [threshold]);

  // 会话切换：跳到底部；同时重置锚定记录（避免把历史消息当新消息锚定）。
  useEffect(() => {
    if (sessionRef.current === sessionKey) {
      return;
    }
    sessionRef.current = sessionKey;
    anchoredMessageRef.current = lastUserMessageId;
    setAnchorSpacer(false);
    // 用 setTimeout 而非 requestAnimationFrame：后台/隐藏标签页的 rAF
    // 会被浏览器冻结，导致滚动永远不执行。
    window.setTimeout(() => scrollToBottom("auto"), 0);
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, [sessionKey]);

  // 新的用户消息出现：把它锚定到视口顶部（问题固定，回答向下生长）。
  useEffect(() => {
    if (!lastUserMessageId || anchoredMessageRef.current === lastUserMessageId) {
      return;
    }
    anchoredMessageRef.current = lastUserMessageId;
    setAnchorSpacer(true);
    // 等 spacer 渲染进 DOM 再滚动，否则底部空间不足仍会滚不到位。
    window.setTimeout(() => {
      const element = scrollRef.current?.querySelector(
        `[data-message-anchor="${lastUserMessageId}"]`,
      );
      element?.scrollIntoView({ behavior: "smooth", block: "start" });
    }, 50);
  }, [lastUserMessageId]);

  return {
    anchorSpacer,
    bottomRef,
    handleScroll,
    pinnedToBottom,
    scrollRef,
    scrollToBottom,
  };
}
```

代码本身不长。真正难的是下面四个坑，每一个都能让上面这段代码"看起来写对了但行为不对"。

### 坑一：浏览器有自己的滚动锚定，它会覆盖你

写完 hook，切会话正常、锚定也正常，但一到流式回答就发现视图还是慢慢往下爬。断点全打在 hook 里，没有任何自定义滚动被触发。

原因是浏览器的原生 **scroll anchoring**：当滚动容器接近底部、内容在下方增长时，浏览器会自动调整 `scrollTop` 保持视觉稳定，表现出来就是"自动跟滚"。这是规范行为，跟你的 JS 代码毫无关系，也不会经过任何事件回调。

解法是在滚动容器上关掉它：

```tsx
{/* overflow-anchor:none 关掉浏览器原生滚动锚定——
    否则视口贴底时流式内容增长，浏览器会自动跟滚到底部，
    覆盖我们"锁定在用户消息"的滚动策略。 */}
<div
  className="h-full overflow-x-hidden overflow-y-auto px-8 py-8 [overflow-anchor:none] max-md:px-4"
  onScroll={handleScroll}
  ref={scrollRef}
>
```

Tailwind 里没有现成的 `overflow-anchor` 工具类，用任意属性语法 `[overflow-anchor:none]`。桌面端是纯 CSS：

```css
.chat-timeline {
  /* 禁用浏览器原生滚动锚定：流式内容增长时不许自动跟滚，
     滚动策略（切会话跳底 / 追问锚定到顶）由代码控制。 */
  overflow-anchor: none;
}
```

**结论：任何自定义滚动策略的第一行代码，都应该是关掉 `overflow-anchor`。** 否则你是在和浏览器抢方向盘。

### 坑二：锚定需要尾部空白

第二个现象更隐蔽：`scrollIntoView({ block: "start" })` 明明调用了，消息却只往上挪了一点点，没顶到视口顶部。

原因是物理限制：容器最多只能滚到 `scrollHeight - clientHeight`。如果新消息下面的内容不足一屏，那条消息**根本没有可能**出现在视口顶部——不是代码没生效，是空间不够。

ChatGPT 的做法是在时间线尾部垫一段空白。我们照做：

```tsx
{/* bottomRef 标记内容末尾（在锚定空白之前）：
    贴底判断与"回到底部"都以它为准，空白只是滚动缓冲。 */}
<div ref={bottomRef} />
{/* 锚定后的尾部空白：保证最新提问能顶到视口顶部，回答在下方生长。 */}
{anchorSpacer ? (
  <div aria-hidden className="h-[calc(100dvh-360px)] shrink-0" />
) : null}
```

三个细节：

- **空白只在锚定后出现**（`anchorSpacer` 状态控制）。会话刚打开时不该有一大片留白。
- **`bottomRef` 放在空白之前**。贴底判断如果把空白算进内容，用户永远"到不了底"，"回到底部"按钮会一直挂着。所以 `handleScroll` 里用 `bottomRef` 的位置算距离，而不是 `scrollHeight`。
- **先 `setAnchorSpacer(true)` 再滚动，中间隔 50ms**。空白得先渲染进 DOM 才能提供滚动空间，同一帧里滚动仍然会滚不到位。

桌面端的等价实现：

```css
/* 锚定后的时间线尾部空白：保证最新提问能顶到视口顶部。 */
.anchor-spacer {
  flex-shrink: 0;
  height: calc(100vh - 320px);
  scroll-behavior: smooth;
}
```

### 坑三：静默刷新——"自动从上面滑到下面"的真正根因

这是最花时间的一个。

现象：追问锚定成功，回答流式生长，一切正常；**但回答结束的一瞬间，视图唰地滑到底部**。用户原话就是"为什么他自动给我从上面滑到下面"。

前两个坑都排除了：`overflow-anchor` 关了，spacer 也有，流式期间确实没有跟滚。问题只出在"结束的那一刻"。

根因在 store 里。流结束后要以服务端为准刷新一次会话详情，保证消息 id、事件时间戳跟数据库一致。原来的 `loadSessionDetail` 一进来就把四份数据置成 `loading`：

```typescript
set({
  context: { type: "loading" },
  events: { type: "loading" },
  files: { type: "loading" },
  messages: { type: "loading" },
  ...
});
```

而 `ConversationTimeline` 的第一行就是：

```tsx
if (messages.type === "loading" || events.type === "loading") {
  return <TimelineLoadingState />;
}
```

这条链路是致命的：置 loading → 时间线返回另一个组件 → **整棵子树卸载** → `useAutoScroll` 里的所有 ref 全部重置 → 数据回来后时间线重新挂载 → `sessionRef.current` 是 `null`，跟 `sessionKey` 不相等 → hook 判定"这是切换会话" → 跳到底部。

**用户看到的"自动滑到底部"，本质是一次组件重挂被误判成了会话切换。**

修法是给 `loadSessionDetail` 加一个 `silent` 选项，静默刷新时保留旧数据、原地替换：

`frontend/web/app/stores/session-store.ts`：

```typescript
loadSessionDetail: async (sessionId, options) => {
  // silent：流结束后的静默刷新。保留旧数据直接原地替换，
  // 不置 loading——否则时间线会卸载重挂，滚动位置被重置到底部。
  if (!options?.silent) {
    set({
      context: { type: "loading" },
      events: { type: "loading" },
      files: { type: "loading" },
      filePreview: { type: "ready", data: null },
      messages: { type: "loading" },
      selectedFile: null,
    });
  }
  try {
    const [messages, events, files, context] = await Promise.all([
      fetchMessages(sessionId),
      fetchEvents(sessionId),
      fetchSessionFiles(sessionId),
      fetchSessionContext(sessionId),
    ]);
    set({
      context: { type: "ready", data: context },
      events: { type: "ready", data: events },
      files: { type: "ready", data: files },
      latestPlan: applyExecutionEvents(getLatestPlan(events), events),
      messages: { type: "ready", data: messages },
    });
  } catch (error) {
    ...
  }
},
```

类型签名也跟着变：

```typescript
loadSessionDetail: (
  sessionId: string,
  options?: { silent?: boolean },
) => Promise<void>;
```

调用点在 `sendMessage` 的收尾：

```typescript
await Promise.all([
  get().loadSessionDetail(sessionId, { silent: true }),
  get().refreshSessions(),
  get().loadSessionContext(sessionId),
]);
```

这条经验值得记住：**加载态不是免费的**。`{ type: "loading" }` 会让消费它的组件走另一条渲染分支，任何挂在那棵子树上的 ref、DOM 位置、滚动状态、`useState` 全部归零。"用户已经看着内容了，只是去后台核对一遍"这种刷新，必须是静默的。

判断标准很简单：**这次请求会不会让屏幕上已有的东西消失？** 会，就用 loading；不会，就用 silent。

### 坑四：后台标签页里 rAF 和 smooth 动画会被冻结

最后一个坑只在特定场景暴露：把标签页切到后台，任务跑完再切回来，滚动位置完全没变。

浏览器对不可见页面有两套限制：

- `requestAnimationFrame` **完全不执行**（不是变慢，是根本不调）；
- CSS 平滑滚动动画同样被冻结，`scrollIntoView({ behavior: "smooth" })` 发出去了但动画不推进。

第一条决定了触发方式：所有滚动都用 `window.setTimeout` 触发，不用 rAF。代码里两处注释写得很直白：

```typescript
// 用 setTimeout 而非 requestAnimationFrame：后台/隐藏标签页的 rAF
// 会被浏览器冻结，导致滚动永远不执行。
window.setTimeout(() => scrollToBottom("auto"), 0);
```

第二条决定了 `behavior` 的选择：需要"立刻到位"的场景一律用瞬时滚动。桌面端切会话就是这么写的：

```tsx
timeline.scrollTo({ top: timeline.scrollHeight, behavior: "instant" as ScrollBehavior });
```

Web 端切会话用的是 `scrollToBottom("auto")`——`auto` 同样是瞬时，只有用户主动点"回到底部"才用 `smooth`：

```tsx
onClick={() => scrollToBottom("smooth")}
```

**写自动化测试时这条尤其重要。** Playwright 的无头浏览器里 smooth 动画时序不可靠，断言 `scrollTop` 经常读到动画中间的值，测试随机失败。要验证滚动策略，就在测试路径上用 `behavior: "instant"`，滚完立刻断言。

### 收口：锚点属性与 scroll-mt

锚定靠 DOM 查询定位，所以每条消息都要带一个稳定的标记：

```tsx
<div
  className="stream-in scroll-mt-2"
  data-message-anchor={item.message.id}
  key={item.id}
>
```

`data-message-anchor` 是查询用的属性；`scroll-mt-2` 给 `scroll-margin-top` 留 8px，避免消息紧贴视口边缘看起来像被裁掉。桌面端用的是 `data-mid`，同一套思路。

"回到底部"按钮绝对定位在滚动容器上，只在不贴底时出现：

```tsx
{!pinnedToBottom ? (
  <button
    aria-label="回到对话底部"
    className="absolute bottom-5 left-1/2 z-20 inline-flex -translate-x-1/2 items-center gap-2 rounded-full border border-(--accent)/30 bg-(--surface-3)/95 px-4 py-2 text-sm font-semibold text-(--accent) shadow-2xl shadow-black/40 backdrop-blur-xl transition hover:border-(--accent)/60"
    onClick={() => scrollToBottom("smooth")}
    type="button"
  >
    <ArrowDown size={15} aria-hidden="true" />
    回到底部
  </button>
) : null}
```

## 56.5 打字机节流：让"思考直播"慢下来

模型的思考流不是匀速到达的。后端一次 flush 可能带来几百个字符，前端直接渲染就是一整屏文字瞬间砸下来，然后卡住不动几秒，再砸一屏。用户的评价很准确："你的思考直播太快了。"

要的效果是：**按稳定速度把已到达的文本放出去；落后太多时加速追平**。

`frontend/web/app/hooks/use-typewriter.ts`：

```typescript
export function useTypewriter(
  text: string,
  { charsPerSecond = 45, catchUpThreshold = 400 }: UseTypewriterOptions = {},
) {
  const [visibleLength, setVisibleLength] = useState(0);
  const textRef = useRef(text);
  const progressRef = useRef(0);
  const lastTickRef = useRef(0);

  textRef.current = text;

  useEffect(() => {
    if (text.length < progressRef.current) {
      progressRef.current = 0;
      setVisibleLength(0);
    }
  }, [text]);

  useEffect(() => {
    lastTickRef.current = performance.now();
    const timer = window.setInterval(() => {
      const now = performance.now();
      const dt = Math.min((now - lastTickRef.current) / 1000, 2);
      lastTickRef.current = now;
      const full = textRef.current;
      if (progressRef.current >= full.length) {
        return;
      }
      const behind = full.length - progressRef.current;
      const rate = charsPerSecond + Math.max(0, behind - catchUpThreshold) * 2;
      progressRef.current = Math.min(
        full.length,
        progressRef.current + rate * dt,
      );
      setVisibleLength(Math.floor(progressRef.current));
    }, 50);
    return () => window.clearInterval(timer);
  }, [charsPerSecond, catchUpThreshold]);

  return text.slice(0, visibleLength);
}
```

### 最大的坑：定时器不能挂在依赖流式文本的 effect 上

第一版是这么写的：

```typescript
// 错误写法
useEffect(() => {
  const timer = window.setInterval(() => { /* 推进一格 */ }, 50);
  return () => window.clearInterval(timer);
}, [text]);          // ← 依赖 text
```

看起来天经地义：文本变了，重新起一个定时器继续推进。实际现象是**一个字都不出来**。

推理一遍就清楚了：流式 delta 每几十毫秒就更新一次 `text`，effect 的清理函数随即 `clearInterval`，然后 `setInterval` 重新计时。50ms 的 interval 撞上 30ms 一次的 delta，**永远活不到第一次触发**。整个流结束前，回调一次都没跑过。

这类 bug 的信号很典型：**"完全没反应"而不是"反应不对"**。看到定时器一次都没触发，第一件事就是查它挂在什么依赖上。

正确写法有三条：

1. **interval 常驻**，依赖数组里只有速度参数（`charsPerSecond`、`catchUpThreshold`），它们几乎不变，所以定时器实际上只创建一次。
2. **用 ref 读最新文本**。`textRef.current = text` 写在组件函数体里，每次渲染同步更新；tick 里读 `textRef.current` 永远是最新值，不需要重建定时器。
3. **进度也放 ref**。`progressRef` 是浮点数，`visibleLength` 只是它取整后的展示副本。用 state 存进度会让每次 tick 触发的重渲染再次影响下一次计算，逻辑立刻绕不清楚。

### 按 dt 推进，且给 dt 设上限

第二个设计点是"推进多少"。固定步长（每次放 3 个字）在后台标签页会出问题：浏览器会把 `setInterval` 钳制到 1 秒以上，固定步长意味着速度掉到原来的二十分之一。

改成按**实际耗时**推进：

```typescript
const dt = Math.min((now - lastTickRef.current) / 1000, 2);
progressRef.current = Math.min(full.length, progressRef.current + rate * dt);
```

这样 tick 变稀疏时每次多放几个字，单位时间的字数不变，**整体速度稳定**。

`Math.min(..., 2)` 这个上限也是必需的。标签页被深度节流几分钟后切回来，`now - lastTick` 可能是 300 秒，乘以速率就是几万个字——一次 tick 直接把全部积压倾泻出来，节流的意义荡然无存。截到 2 秒，最坏情况也只是"回来时快进了一小段"。

### 追赶策略

```typescript
const behind = full.length - progressRef.current;
const rate = charsPerSecond + Math.max(0, behind - catchUpThreshold) * 2;
```

基础速度 45 字/秒，大约是舒适的阅读速度上限。当积压超过 400 字时，每多积压 1 个字，速度就加 2 字/秒。这条线性追赶保证了**展示进度不会和真实进度脱节太远**——模型思考完两千字，界面不会还在慢悠悠地演前三百字。

最后，文本变短意味着新一轮流开始（store 里把 `liveThinking` 清空了），立刻重置进度：

```typescript
useEffect(() => {
  if (text.length < progressRef.current) {
    progressRef.current = 0;
    setVisibleLength(0);
  }
}, [text]);
```

消费端只有一行：

```tsx
// 思考流打字机节流：模型思考瞬间灌入大段文本，按稳定速度放出更易读。
const pacedThinking = useTypewriter(liveThinking);
```

**注意只对思考流节流，不对正文回答节流。** 正文是用户真正在等的东西，人为放慢等于故意让人等；思考过程是辅助信息，慢一点反而看得清。

## 56.6 推理块：可折叠、有字数、能渲染 Markdown

推理过程如果只是一坨灰色纯文本，读起来很痛苦——模型的思考里经常带列表、代码、公式。用户的要求很具体："推理过程的内容需要渲染，代码要放进代码块。"

`frontend/web/app/components/conversation/reasoning-block.tsx`：

```tsx
export function ReasoningBlock({ reasoning, streaming = false }: ReasoningBlockProps) {
  const [expanded, setExpanded] = useState<boolean | null>(null);
  const open = expanded ?? streaming;

  if (!reasoning) {
    return null;
  }

  return (
    <div className="mb-2 overflow-hidden rounded-2xl border border-(--line) bg-(--fill-1)">
      <button
        aria-expanded={open}
        className="flex w-full items-center gap-2 px-4 py-2.5 text-left text-xs font-medium text-(--text-4) transition hover:text-(--text-2)"
        onClick={() => setExpanded(!open)}
        type="button"
      >
        <Brain
          aria-hidden="true"
          className={streaming ? "animate-pulse text-(--accent)" : "text-(--text-4)"}
          size={14}
        />
        <span>{streaming ? "正在思考…" : "推理过程"}</span>
        <span className="text-(--text-5)">{reasoning.length} 字</span>
        <ChevronDown
          aria-hidden="true"
          className={`ml-auto transition-transform ${open ? "rotate-180" : ""}`}
          size={14}
        />
      </button>
      {open ? (
        <div className="max-h-64 overflow-y-auto border-t border-(--line-soft) px-4 py-3">
          <MarkdownContent compact content={reasoning} />
        </div>
      ) : null}
    </div>
  );
}
```

四个设计点：

**`useState<boolean | null>(null)` 表示"用户还没表态"。** `open = expanded ?? streaming` 的效果是：流式中默认展开（正在思考，让人看到进展），流式结束后默认折叠（结论已出，思考过程收起来）。一旦用户手动点过，就完全尊重用户的选择。用普通布尔做不到这种"默认值跟随状态、手动值优先"的语义。

**字数统计给的是预期。** "推理过程 1284 字"和"推理过程"是两种体验，前者让人知道展开会看到什么量级的内容。

**流式脉冲。** `animate-pulse` 加在大脑图标上，配合 accent 色，一眼能区分"还在想"和"想完了"。桌面端用的是自定义 keyframes：

```css
.thinking-block.streaming .thinking-toggle svg:first-child {
  color: var(--accent);
  animation: thinking-pulse 1.2s ease-in-out infinite;
}
```

**内容走 Markdown 渲染的 compact 变体。** `MarkdownContent` 的 `compact` 开关把正文字号从 15px 降到 13px、行高收紧、文字色降一级到 `--text-4`：

```typescript
const bodyText = compact
  ? "text-[13px] leading-6 text-(--text-4)"
  : "text-[15px] leading-7 text-(--text-3)";
const codeText = compact ? "text-xs leading-5" : "text-sm leading-6";
```

这样推理块和正文回答**共用一套 Markdown 组件**，但视觉层级明确区分——推理是辅助信息，不该和结论抢注意力。`max-h-64 overflow-y-auto` 再给它加个高度上限，避免一段超长思考把整个对话撑开。

```css
  /* 品牌强调色 */
  --accent: #60a5fa;
  --accent-strong: #3b82f6;
  /* 背景网格与滚动条 */
  --grid-line: rgba(80, 96, 130, 0.13);
  --grid-line-soft: rgba(255, 255, 255, 0.035);
  --scrollbar: rgba(122, 135, 162, 0.38);
  --scrollbar-hover: rgba(150, 162, 190, 0.55);
  --scrollbar-active: rgba(165, 178, 208, 0.72);

```

亮色主题只是换一组值，结构完全一致：

```css
:root[data-theme="light"] {
  color-scheme: light;
  --page: #f5f6fa;
  --surface: #ffffff;
  --line: rgba(15, 23, 42, 0.12);
  --fill-1: rgba(15, 23, 42, 0.045);
  --text-1: #111827;
  --accent: #2563eb;
  ...
}
```

关键在于**暗色用半透明白、亮色用半透明黑**。`--fill-1: rgba(255,255,255,0.04)` 在暗色下是"轻微提亮"，对应的亮色值 `rgba(15,23,42,0.045)` 是"轻微压暗"，两者在各自主题里表达的语义相同（比背景稍微突出一点的填充）。这样组件层不需要任何主题分支。

`color-scheme` 声明也别漏——它决定浏览器原生控件（滚动条默认样式、`<input>` 内部渲染、表单聚焦环）用哪套配色。

### Tailwind 4 的变量语法

Tailwind 4 消费 CSS 变量的写法和 3.x 不同，这是升级时最容易踩的地方：

```tsx
// Tailwind 4：括号语法
className="border border-(--line) bg-(--surface) text-(--text-1)"

// 带透明度修饰符
className="bg-(--accent)/10 ring-1 ring-(--accent)/40"
className="bg-(--surface-2)/95 backdrop-blur-xl"

// 任意属性（没有对应工具类时）
className="[overflow-anchor:none]"
```

`bg-(--accent)/10` 这种"变量 + 透明度"的组合特别好用：一个 accent 变量派生出边框（`/30`）、底色（`/10`）、选中环（`/40`）三档，主题切换时全部跟着变。如果你还在写 `bg-[var(--accent)]`，那是 3.x 的写法——4.x 下它也能工作，但没法接透明度修饰符。

### 防 FOUC：beforeInteractive 注入初始化脚本

主题存在 localStorage 里，而 localStorage 只能在客户端读。如果等 React 挂载后再设 `data-theme`，亮色用户会先看到一帧暗色再闪成亮色——非常明显的白屏/黑屏闪烁。

解法是在 body 最前面同步执行一小段脚本：

`frontend/web/app/layout.tsx`：

```tsx
// 首帧前从 localStorage 恢复主题，避免亮色用户看到暗色闪烁。
// system 或未设置时跟随操作系统配色。
const themeInitScript = `(function(){try{var p=localStorage.getItem("atlas-web-theme");var t=p==="light"||p==="dark"?p:(window.matchMedia("(prefers-color-scheme: light)").matches?"light":"dark");document.documentElement.dataset.theme=t;}catch(e){document.documentElement.dataset.theme="dark";}})();`;

export default function RootLayout({ children }: Readonly<{ children: React.ReactNode }>) {
  return (
    <html lang="zh-CN" suppressHydrationWarning>
      <body>
        <Script id="atlas-theme-init" strategy="beforeInteractive">
          {themeInitScript}
        </Script>
        {children}
      </body>
    </html>
  );
}
```

四个要点：

- **`strategy="beforeInteractive"`** 让 Next.js 把脚本放在任何水合之前执行，这是它区别于普通 `<script>` 的关键。
- **`suppressHydrationWarning` 加在 `<html>` 上。** 脚本修改了 `documentElement` 的属性，服务端渲染的 HTML 和客户端首帧必然不一致，不加这个会在控制台刷 hydration mismatch 警告。
- **`try/catch` 兜底。** 隐私模式下 `localStorage` 可能直接抛异常，catch 里退回暗色，不能让整个脚本挂掉。
- **脚本要写成一行压缩形式。** 它会被内联进 HTML，可读性让位于体积。

运行时的偏好管理在 `frontend/web/app/lib/theme.ts`：

```typescript
function applyTheme(preference: ThemePreference) {
  const resolved = preference === "system" ? systemTheme() : preference;
  document.documentElement.dataset.theme = resolved;
}

export function useThemePreference(): [ThemePreference, (next: ThemePreference) => void] {
  const [preference, setPreference] = useState<ThemePreference>("system");

  useEffect(() => {
    const saved = readThemePreference();
    setPreference(saved);
    applyTheme(saved);
  }, []);

  useEffect(() => {
    if (preference !== "system") return;
    const media = window.matchMedia("(prefers-color-scheme: light)");
    const onChange = () => applyTheme("system");
    media.addEventListener("change", onChange);
    return () => media.removeEventListener("change", onChange);
  }, [preference]);

  function update(next: ThemePreference) {
    setPreference(next);
    window.localStorage.setItem(STORAGE_KEY, next);
    applyTheme(next);
  }

  return [preference, update];
}
```

注意 `system` 不是"初始化时读一次系统配色"，而是**持续跟随**：第二个 effect 监听 `prefers-color-scheme` 变化，用户在操作系统里切换深浅色，界面实时跟着变。这是"跟随系统"这个选项应有的语义。

### 自定义下拉替代原生 select

主题选择器最初用的是原生 `<select>`。问题是**原生下拉的弹出层由操作系统渲染，CSS 完全管不到**：暗色界面上弹出一个白底黑字的系统列表，刺眼且割裂；不同平台的样式还各不相同。

所以抽了一个通用的 `SelectMenu`（`frontend/web/app/components/select-menu.tsx`）和一个专用的 `ThemeMenu`（`theme-menu.tsx`）。两者共用同一套交互骨架：

```tsx
useEffect(() => {
  if (!open) return;
  function onPointerDown(event: PointerEvent) {
    if (!rootRef.current?.contains(event.target as Node)) setOpen(false);
  }
  function onKeyDown(event: KeyboardEvent) {
    if (event.key === "Escape") setOpen(false);
  }
  window.addEventListener("pointerdown", onPointerDown);
  window.addEventListener("keydown", onKeyDown);
  return () => {
    window.removeEventListener("pointerdown", onPointerDown);
    window.removeEventListener("keydown", onKeyDown);
  };
}, [open]);
```

三个必备行为：**点击外部关闭**、**Escape 关闭**、**只在打开时挂监听**（`if (!open) return` 提前返回，避免永久挂着两个全局监听器）。

无障碍属性也要给全，否则自定义下拉对屏幕阅读器就是一堆匿名按钮：

```tsx
<button aria-expanded={open} aria-haspopup="listbox" aria-label={`界面主题：${active.label}`}>
...
<div role="listbox" aria-label="选择界面主题">

```

`ThemeMenu` 在此之上加了图标、说明文字和选中标记：

### 自定义滚动条

原生滚动条在暗色主题下是一条突兀的灰白色带。改造分两条路径：

```css
/* Chromium：细圆角滑块悬浮在透明轨道上，隐藏两端箭头按钮。 */
::-webkit-scrollbar {
  width: 10px;
  height: 10px;
}

::-webkit-scrollbar-track {
  background: transparent;
}

::-webkit-scrollbar-thumb {
  min-height: 32px;
  background: var(--scrollbar);
  background-clip: padding-box;
  border: 3px solid transparent;
  border-radius: 999px;
}

::-webkit-scrollbar-thumb:hover {
  background: var(--scrollbar-hover);
  background-clip: padding-box;
  border-width: 2px;
}

::-webkit-scrollbar-button {
  display: none;
  width: 0;
  height: 0;
}
```

`border: 3px solid transparent` + `background-clip: padding-box` 是让滑块"变细并留出内边距"的经典技巧——直接改 `width` 会连轨道一起变窄，热区太小不好抓。hover 时把边框收到 2px，滑块视觉上变粗，是个很轻的反馈。

Firefox 不支持 `::-webkit-scrollbar`，得用标准属性，但**不能无条件写**：

```css
/* Firefox 没有 ::-webkit-scrollbar，用标准属性给出等效的细滚动条。
   注意不能对 Chromium 应用这两个标准属性——它们会禁用上面的自定义样式。 */
@supports not selector(::-webkit-scrollbar) {
  * {
    scrollbar-width: thin;
    scrollbar-color: var(--scrollbar) transparent;
  }
}
```

Chromium 同时支持两套语法，而一旦设了 `scrollbar-width`/`scrollbar-color`，它就会**放弃 `::-webkit-scrollbar` 的自定义样式**回退到原生细滚动条。用 `@supports not selector(...)` 做特性检测，让两套样式各管各的浏览器。

### 代码块复制按钮

Agent 的回答里经常有命令和代码，不能复制就得手动框选，很痛苦。`MarkdownContent` 给 `pre` 换了个带复制按钮的容器：

```tsx
/** 代码块容器：右上角悬浮复制按钮，点击复制整段代码。 */
function PreBlock({ children }: { children?: React.ReactNode }) {
  const preRef = useRef<HTMLPreElement>(null);
  const [copied, setCopied] = useState(false);

  async function copy() {
    const text = preRef.current?.innerText ?? "";
    if (!text) return;
    try {
      await navigator.clipboard.writeText(text);
      setCopied(true);
      window.setTimeout(() => setCopied(false), 1600);
    } catch {
      // 剪贴板不可用（如非安全上下文）时静默失败。
    }
  }

  return (
    <div className="group relative my-4">
      <pre className="overflow-x-auto" ref={preRef}>
        {children}
      </pre>
      <button
        aria-label={copied ? "已复制" : "复制代码"}
        className={`absolute right-2.5 top-2.5 flex h-8 items-center gap-1.5 rounded-lg border border-(--line) bg-(--surface-2)/90 px-2.5 text-xs font-medium backdrop-blur transition ${
          copied
            ? "text-emerald-400 opacity-100"
            : "text-(--text-4) opacity-0 hover:text-(--text-1) focus-visible:opacity-100 group-hover:opacity-100"
        }`}
        onClick={copy}
        title="复制代码"
        type="button"
      >
        {copied ? <Check size={13} aria-hidden="true" /> : <Copy size={13} aria-hidden="true" />}
        {copied ? "已复制" : "复制"}
      </button>
    </div>
  );
}
```

细节：

- **从 `innerText` 取值而不是拼 children。** children 是 React 节点树，语法高亮之后结构复杂，`innerText` 直接拿到用户看到的纯文本。
- **`opacity-0 group-hover:opacity-100`**：平时隐藏不干扰阅读，悬浮才出现。加上 `focus-visible:opacity-100`，键盘用户 Tab 过去也能看到。
- **`navigator.clipboard` 在非安全上下文（http 且非 localhost）不可用**，所以整段包 try/catch 静默失败——按钮点了没反应，总比抛个未捕获异常炸掉整条回答强。
- **成功状态 1.6 秒后自动复位**，不需要额外的 toast 系统。

## 56.8 输入框与侧栏

两个小改动，但对"是否像成品"的影响很大。

### 输入框自动伸缩

原来的输入框是固定 `rows`，永远占着四五行的高度，把对话区挤掉一大块。改成单行起步、随内容长高、到上限后内部滚动：

`frontend/web/app/components/chat-input.tsx`：

```tsx
const MAX_INPUT_HEIGHT = 176;

// 随内容自动伸缩：先归零再按内容高度设置，超过上限后内部滚动。
useEffect(() => {
  const element = textareaRef.current;
  if (!element) {
    return;
  }
  element.style.height = "auto";
  element.style.height = `${Math.min(element.scrollHeight, MAX_INPUT_HEIGHT)}px`;
  element.style.overflowY =
    element.scrollHeight > MAX_INPUT_HEIGHT ? "auto" : "hidden";
}, [draft]);
```

**`element.style.height = "auto"` 这一行不能省。** `scrollHeight` 包含当前设定的高度，如果不先归零，删字的时候高度只会增不会减——输入框会越写越高，删空了还停在原来的高度。

`overflowY` 也要手动切：没到上限时设 `hidden`，否则某些浏览器会常驻一条滚动条槽位；到上限了才给 `auto`。

### Enter 发送与中文输入法

```tsx
onKeyDown={(event) => {
  // Enter 直接发送，Shift+Enter 换行；输入法候选确认的 Enter 不触发。
  if (
    event.key === "Enter" &&
    !event.shiftKey &&
    !event.nativeEvent.isComposing
  ) {
    event.preventDefault();
    if (!disabled && !sending && draft.trim()) {
      onSend();
    }
  }
}}
```

`event.nativeEvent.isComposing` 是这段的重点。中文、日文输入法在选字时，回车是用来**确认候选词**的。没有这个判断，用户打"你好"按回车选词，消息就直接发出去了，输入框里还留着拼音——中文用户几乎百分之百会踩到。

React 的合成事件对象上没有 `isComposing`，要从 `event.nativeEvent` 拿。桌面端因为组件结构不同，用的是 `onCompositionStart` / `onCompositionEnd` 配一个 ref：

```tsx
onCompositionStart={() => { composingRef.current = true; }}
onCompositionEnd={() => { composingRef.current = false; }}
onKeyDown={(event) => {
  if (event.key === "Enter" && !event.shiftKey && !composingRef.current) {
    event.preventDefault();
    void sendMessage();
  }
}}
```

两种写法都对，`isComposing` 更简洁。

### 可隐藏侧栏

侧栏固定 300px，在小屏笔记本上把对话区压得很窄。加一个折叠开关，偏好持久化：

`frontend/web/app/page.tsx`：

```tsx
// 左侧导航可隐藏：隐藏时对话区自动铺满整个宽度，偏好持久化。
const [sidebarOpen, setSidebarOpen] = useState(true);

useEffect(() => {
  if (window.localStorage.getItem("atlas-sidebar-open") === "0") {
    setSidebarOpen(false);
  }
}, []);

function toggleSidebar() {
  setSidebarOpen((open) => {
    window.localStorage.setItem("atlas-sidebar-open", open ? "0" : "1");
    return !open;
  });
}
```

布局用 grid 列定义切换，收起时直接变成单列，对话区自然铺满：

```tsx
<div
  className={`grid h-full min-h-0 ${
    sidebarOpen
      ? "grid-cols-[300px_1fr] max-lg:grid-cols-1 max-lg:grid-rows-[auto_1fr]"
      : "grid-cols-1"
  }`}
>
```

**注意默认值是 `true` 而不是从 localStorage 初始化。** 服务端渲染读不到 localStorage，如果把读取放进 `useState` 初始化函数，服务端和客户端首帧不一致会触发 hydration 错误。正确做法是给一个确定的默认值，挂载后在 effect 里纠正。代价是收起状态的用户会看到一帧侧栏，但这比 hydration 报错好。

收起后左上角留一个展开按钮，否则就没法再打开了：

```tsx
{!sidebarOpen ? (
  <button
    aria-label="展开侧边栏"
    className="absolute left-3 top-3 z-50 flex h-9 w-9 items-center justify-center rounded-xl border border-(--line) bg-(--surface-3)/90 text-(--text-3) shadow-lg shadow-black/20 backdrop-blur-xl transition hover:border-(--accent)/40 hover:text-(--text-1)"
    onClick={toggleSidebar}

  >

```

## 56.9 品牌图标

浏览器标签页上一直是 Next.js 的默认图标，看起来像个没做完的脚手架项目。

Next.js 的 app 目录有一套**文件约定**：把特定文件名放进 `app/` 根目录，框架自动生成对应的 `<link>` 标签，不需要写任何 metadata 配置。

```text
frontend/web/app/
├── icon.svg          浏览器标签页图标（矢量，优先级最高）
├── favicon.ico       传统 ICO，兼容老浏览器与部分工具链
└── apple-icon.png    iOS 添加到主屏幕时使用
```

注意路径是 `app/icon.svg`，**不是 `app/app/icon.svg`，也不是 `public/`**。放进 `public/` 需要手写 metadata，放进 app 目录才走约定。

图标本身是手写的 SVG（`frontend/web/app/icon.svg`）：

```xml
  <rect x="1" y="1" width="62" height="62" rx="16" fill="url(#shine)"/>

  <rect x="30.4" y="14.5" width="3.2" height="7" rx="1.6" fill="#FFFFFF"/>
```

设计约束只有一条：**16px 下还能认出来**。这条约束推出了所有决策——

- **圆角方底 + 高饱和渐变**：标签页背景色未知（亮色暗色都可能），实心底座保证图标在任何背景上都有明确边界。

- **形状极简**：一个圆角矩形头、两条胶囊眼睛、一根天线。没有描边、没有阴影、没有细节——16px 下这些全都糊成一团脏点。
- **元素占满画布**：机器人头从 y=23 到 y=52，加上天线几乎顶到边缘。留白太多会让图标在标签页里显得比别人小一号。

## 56.10 桌面端同构

Web 端定好的滚动策略和打字机，桌面端一比一搬了过去。

`frontend/desktop/src/use-typewriter.ts` 与 Web 端的 hook **逐行一致**——同样的常驻 interval、同样的 ref 读文本、同样的 `dt` 上限。差别只在两端的构建工具不同，无法共享包，所以是复制而非引用。

滚动策略因为组件结构不同（桌面端是单文件 `ChatView`，没有抽 hook），写成了一个 effect：

`frontend/desktop/src/views/ChatView.tsx`：

```tsx
// ChatGPT 式滚动：切会话跳到底部；发出追问时把该消息锚定到视口顶部，
// 回答在下方生长；流式期间不自动跟滚，用户停在哪就是哪。
const anchoredMessageRef = useRef<string | null>(null);
const anchoredSessionRef = useRef<string | null>(null);
// 锚定后垫在时间线尾部的空白，保证"提问顶到视口顶部"物理上可达。
const [anchorSpacer, setAnchorSpacer] = useState(false);
// 思考流打字机节流：按稳定速度放出，避免大段思考瞬间刷屏。
const pacedThinking = useTypewriter(liveThinking);
useEffect(() => {
  const timeline = timelineRef.current;
  if (!timeline) return;
  const lastUserId =
    [...messages].reverse().find((message) => message.role === "user")?.id ?? null;
  if (anchoredSessionRef.current !== selectedId) {
    // 切会话时列表先被清空再异步加载，等消息真正到位后再定位到底部。
    if (messages.length === 0) return;
    anchoredSessionRef.current = selectedId;
    anchoredMessageRef.current = lastUserId;
    setAnchorSpacer(false);
    timeline.scrollTo({ top: timeline.scrollHeight, behavior: "instant" as ScrollBehavior });
    return;
  }
  if (lastUserId && anchoredMessageRef.current !== lastUserId) {
    anchoredMessageRef.current = lastUserId;
    setAnchorSpacer(true);
    // setTimeout 而非 rAF：隐藏窗口的 rAF 会被冻结；50ms 等 spacer 渲染。
    window.setTimeout(() => {
      const element = timeline.querySelector(`[data-mid="${lastUserId}"]`);
      element?.scrollIntoView({ behavior: "smooth", block: "start" });
    }, 50);
  }
}, [messages, selectedId]);
```

有一处桌面端特有的处理值得注意：`if (messages.length === 0) return;`。桌面端切会话时先 `setMessages([])` 再异步加载，如果不等消息到位就跳底部，跳的是一个空列表，等数据回来位置又不对了。Web 端因为 store 保留旧数据不走这条路径，所以不需要这个判断。**同一套策略在不同的数据加载模型下，实现细节会有出入——这也是为什么"复制一份"比"强行抽公共包"更实际。**

桌面端没有 `loadSessionDetail` 的 silent 问题，因为它的刷新只 `setMessages`，不改变渲染分支——`loadingMessages` 只在时间线里多渲染一行提示文字，不会卸载整棵子树：

```tsx
{loadingMessages ? <p className="empty-hint">正在载入消息…</p> : null}
```

这其实反向印证了坑三的结论：**问题不在"刷新"，在"刷新导致渲染分支切换"。**

两端一套心智模型的价值在这一章特别明显：调试锚定行为时，只要在一端想清楚"为什么滚不到位"，另一端直接套用结论。如果两端各写各的策略，同样的坑要踩两遍，而且第二遍未必能想起第一遍是怎么解决的。

## 56.12 常见坑

**坑一：Turbopack 持久缓存会吃掉 `globals.css` 的修改。** 改了主题变量、滚动条样式，热更新没反应，甚至重启 dev server 也没反应。原因是 Turbopack 的持久化缓存对全局 CSS 的失效判断在某些情况下不准。解法很粗暴但有效：

```bash
rm -rf frontend/web/.next
pnpm dev
```

调主题的时候如果出现"我明明改了但没变"，**第一反应应该是删缓存，而不是怀疑自己的 CSS 写错了**。浪费半小时找一个不存在的语法问题，是这一章最没必要的时间开销。

**坑二：后台标签页的定时器钳制。** 浏览器对不可见页面会把 `setInterval`/`setTimeout` 的最小间隔钳制到 1 秒甚至更久，`requestAnimationFrame` 则完全不执行。凡是涉及节奏的代码都要按这个前提设计：打字机按 `dt` 推进而不是固定步长，滚动用 `setTimeout` 触发而不是 rAF，`dt` 还要设上限防止唤醒后倾泻。store 里 SSE 事件的展示延迟也遵循同一原则——流式增量的延迟必须是 0：

```typescript
// 零延迟事件（流式增量）不进定时器：后台标签页的 setTimeout
// 会被浏览器钳制到 1 秒以上，逐字流会被拖成龟速。
if (
  eventName === "answer_started" ||
  eventName === "answer_delta" ||
  eventName === "thinking_delta"
) {
  return 0;
}
```

**坑三：Tailwind 4 的变量语法和 3.x 不同。** `bg-(--token)` 是 4.x 写法，3.x 是 `bg-[var(--token)]`。混着写不会报错，但 3.x 的写法接不了 `/90` 这类透明度修饰符，`bg-[var(--surface)]/90` 不生效且没有任何提示。另外 Tailwind 4 不再需要 `tailwind.config.js` 声明这些变量——变量定义在 CSS 里，工具类直接引用。

**坑四：把 `overflow-anchor` 忘了。** 任何"我实现了自定义滚动策略但它偶尔会自己滑走"的问题，先查滚动容器有没有 `overflow-anchor: none`。这个属性默认是 `auto`，浏览器会在你不知情的情况下调整 `scrollTop`。

**坑五：`textarea` 自适应高度忘了先归零。** `element.style.height = "auto"` 必须在读 `scrollHeight` 之前执行，否则输入框只增不减。

**坑六：SSR 环境下从 localStorage 初始化 state。** `useState(() => localStorage.getItem(...))` 在服务端会直接抛错或返回不一致的值，导致 hydration mismatch。正确做法是给确定的默认值，在 `useEffect` 里纠正。唯一的例外是主题——它必须在首帧前生效，所以走 `beforeInteractive` 的内联脚本，并给 `<html>` 加 `suppressHydrationWarning`。

**坑七：把加载态当成免费的。** 见 56.4 坑三。任何会切换渲染分支的加载态都等于一次组件卸载，挂在那棵子树上的 ref、DOM 位置、滚动状态全部清零。后台核对性质的刷新一律走静默路径。

## 56.13 本章小结

这一章没有增加任何后端能力，全部改动都在前端，但它解决的是用户唯一能直接感知的东西：**过程是怎么被呈现的**。

四条经验值得带走：

1. **过程展示的正确性，取决于数据模型而不是样式。** "任务卡跟着上一轮跑"这个 bug，看起来是布局问题，实际是"计划不是时间线里的一等公民"。把 `plan_created` 变成 `TimelineItem`、按 `created_at` 排序之后，位置问题、归属问题、重复问题一起消失了。同理，终结事件归属靠 `plan_id` 匹配，运行态靠外部传入而不是从步骤反推——**每一个"看起来像 UI bug 的东西"，往下挖一层通常是模型没建对。**

2. **自定义滚动要先把浏览器的默认行为关掉。** `overflow-anchor: none` 是前提，尾部 spacer 是物理保障，`setTimeout` 是绕开 rAF 冻结的必需手段。三者缺一，策略就会"在大多数情况下工作"——而这种间歇性的不对，比彻底不工作更难查。

3. **加载态是有代价的。** "自动从上面滑到下面"折腾了最久，根因既不在滚动代码里也不在浏览器里，而在一次看似无害的 `set({ messages: { type: "loading" } })`。判断标准记住一句：**这次刷新会不会让屏幕上已有的东西消失？** 不会，就必须静默。

4. **定时器不能挂在高频变化的依赖上。** "一个字都不出来"的打字机是个很好的教学案例：50ms 的 interval 挂在每 30ms 更新一次的 `text` 上，永远活不到第一次触发。常驻定时器 + ref 读最新值 + 按实际 `dt` 推进，这套组合适用于所有"需要稳定节奏地消费高频数据"的场景。

顺带一提，这一章净删掉了三个组件（`StepCard`、`StepDetailDialog`、`PlanProgressBar`），`conversation/` 目录变小了，`ConversationTimeline` 的渲染分支从四种降到两种。**删代码同样是重构成果**——少一个组件就少一处状态、少一条渲染路径、少一批要维护的样式。

至此，AtlasAgent 的对话区从"能显示执行过程"变成了"把执行过程讲清楚"。Web 端和桌面端共用同一套滚动心智模型与打字机实现，主题、图标、输入交互也全部对齐。下一步该做的是把这套体验固化成自动化测试，让它不会在下一次重构中悄悄退化。
