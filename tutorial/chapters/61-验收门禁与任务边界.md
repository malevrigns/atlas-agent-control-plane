# 第六十一章. 验收门禁与任务边界

## 61.1 本章目标

第十三章把执行闭环从"规划 → 逐步执行 → 观察"跑通，第十四章之后任务状态落进了 Redis 与数据库。但这条闭环有一个结构性缺口：**任务"完成"的时刻由模型自己宣布**。本章在任务完成之前加一道边界——验收门禁链：验收命令、范围审计、覆盖度评审三级串行，全部通过，任务才有资格进入 completed 状态。

完成本章后，你将能够：

- 定义验收命令的 exit code 语义，把自然语言的"完成了"翻译成二值判定；
- 设计三级门禁的顺序，解释"先便宜后贵、先确定性后概率性"的经济逻辑；
- 为每一级门禁划定 fail-closed / fail-open 的分界，并说清各自的理由；
- 设置重试额度，把模型与门禁的"互博"变成有界、可审计的过程。

本章新增代码集中在（将如下所示）：

```text
backend/api/app/application/agent_execution_machine.py 门禁链接线（_gate_cycle/_scope_cycle）
backend/api/app/domain/acceptance/scope.py            范围审计：glob + LLM 复核
backend/api/app/domain/acceptance/coverage.py         覆盖度评审（LLM）
```

## 61.2 为什么需要这一章

先说"自证陷阱"。模型写完代码，跑了几条测试通过，宣布"完成了"。这个"完成"有一个结构性弱点：**宣布完成的人和验收完成的人是同一个**。它知道自己写了测试，不代表测试覆盖了该覆盖的行为；它知道自己只改了三个文件，不代表没动不该动的东西。让模型自证，等于让当事人给自己判案。验收必须外化——交给不受模型自述影响的判官：命令的 exit code、diff 的文件清单。

第二个问题是任务边界。"完成"必须有可机器验证的定义，验收命令就是定义本身：exit 0 通过，非 0 失败，语义窄到没有自然语言解释空间。范围审计管的是另一个边界——"只改了该改的"。长任务里模型顺手"优化"一个不相干文件的现象很常见，没有审计，这条边界就是名义上的。

第三个问题最难：门禁失败之后怎么办？直觉答案是"重试到通过为止"。实际上模型和门禁可以互博几十轮：门禁拒绝，模型辩解着改一版，门禁再拒，模型换个思路再改……每一轮都烧 token，任务永不收敛。所以重试必须有额度——**额度把无限博弈变成有界博弈**，额度耗尽就落 failed。这个 failed 是审计里最诚实的信息：它说明在当前能力下，这个任务到不了定义好的边界，而不是"它完成了但没人敢信"。

## 61.3 实现步骤

### 61.3.1 验收命令：只有 0 与非 0

任务创建时携带 `acceptance_command`（仓库里就是 `uv run pytest` 或部署方自定义的脚本）。门禁不解析命令输出，只看 exit code：

```python
@dataclass(frozen=True, slots=True)
class GateVerdict:
    gate: str          # "acceptance" | "scope" | "coverage"
    passed: bool
    reason: str = ""   # 失败原因，作为重试输入回喂给模型
```

exit code 的语义被刻意收窄：0 通过，其余一律失败。命令打印了什么门禁一概不读——输出回喂给模型（下一轮看），判定回喂给门禁（这一轮用）。**门禁只做是/否，"怎么修"留给模型**，这个分工和第四十六章同构：Runtime 只做策略判定，handler 只做业务执行。

### 61.3.2 三级门禁：先便宜，先确定性

门禁链顺序执行，顺序固定：

```python
GATE_ORDER = ("acceptance", "scope", "coverage")

async def run_gate_chain(task, sandbox) -> GateReport:
    for gate in GATE_ORDER:
        verdict = await GATES[gate].run(task, sandbox)
        if not verdict.passed:
            return GateReport(failed_at=gate, verdict=verdict)
    return GateReport(failed_at=None)
```

这个顺序不是拍脑袋，是经济账：

1. **验收命令在前**——确定性、便宜（秒级）、信号最强。测试都没过，"是否只改了该改的文件""覆盖是否完整"都是空谈，后面的门禁跑起来纯属浪费 token。
2. **范围审计居中**——glob 部分是确定性，LLM 复核部分才引入概率性，且只在"有越界文件"的子集上触发，成本可控。
3. **覆盖度评审殿后**——要 LLM 完整读 diff 和测试代码，最贵；信号也最弱（覆盖"是否完全"本身就是概率判断）。放在最后，意味着前两级已经把大部分不合格完成拦掉了，只有"看起来过了"的任务才付最贵的代价。

### 61.3.3 范围审计：确定性过滤在前，LLM 复核在后

范围审计分两级。第一级是 glob：任务声明一组 `allowed_paths`，diff 里不匹配的文件直接进"越界"列表。第二级是 LLM 复核——越界文件不一定有罪：模型可能因为需要而改了一个共享工具的类型签名，这有正当理由。LLM 拿到越界文件的 diff 和任务描述，逐文件输出 allow/deny 加理由：

```python
async def audit_scope(diff, allowed_globs, llm=None) -> ScopeAuditResult:
    out_of_scope = [f for f in diff.files if not matches_any(f, allowed_globs)]
    if not out_of_scope:
        return ScopeAuditResult(passed=True)
    if llm is None:
        # 没有 LLM 时越界即失败：宁严勿松，但审计里留下原因
        return ScopeAuditResult(passed=False, reason=f"越界文件: {out_of_scope}")
    ...  # LLM 逐文件裁决；任一 deny 即整体失败，理由全量落审计
```

### 61.3.4 fail-closed / fail-open 的分界

门禁自身崩溃时（命令起不来、LLM 超时、脚本自身报错）怎么判？答案是分级的：

- **验收命令、范围审计：fail-closed**。崩溃视为失败。理由：这两级承担的是"强声明"——"测试全部通过""我只动了该动的文件"。误放行的代价（假完成流到生产）远高于误拦截的代价（模型多重试一轮）。门禁是最后一道防线，防线不能因为守夜人自己倒下就自动解锁。
- **覆盖度评审：fail-open**。LLM 不可用或输出解析失败时视为通过，但审计里打上 `coverage: "unverified"` 标记。理由不同：覆盖评审是软信号，它的判断本身就是概率性的；把它升级成硬依赖，等于让 LLM 的抖动（或者离线部署根本没有 LLM 这个事实）绑架整条任务链——手段否决了目的。unverified 标记保证这次放行不是无声的，审计可查、人可复查。

这条分界可以压缩成一句判据：**误放行会造成不可挽回损失的，fail-closed；误失败只会造成绕路的，fail-open，但必须在审计里留痕。**

### 61.3.5 重试额度：把互博变成有限博弈

门禁失败不是终点。失败判定（exit code、stderr 尾部、越界文件清单、LLM 的理由）要写回模型上下文，作为下一轮的第一条观察。重试额度挂在**任务级**，三级门禁共享：

```python
task.retry_budget -= 1   # 例如共 3 次
if task.retry_budget <= 0:
    task.status = "failed"      # 额度耗尽，落 failed，理由全量落审计
    return
await runner.resume_with_feedback(task, verdict.reason)
```

额度设在任务级而不是单门禁级，目的只有一个：限制模型和门禁总共能互博多少轮，而不是调节单个门禁的行为。有额度，"嘴硬"的模型最多再辩三轮就落定——失败原因、最后一次判定、完整审计链路都在，人可以接手。没额度，互博没有终态：实测里模型可以在"我修好了 / 你没修对"之间反复横跳十几轮，每轮消耗可观的 token 却不收敛。

一个细节值得点出来：门禁失败的回喂结果，和第六十章 `tool_budget.py` 里的 `budget_exceeded` 是同一种模式——**结构化 JSON 回喂给模型，而不是抛异常打断外层**。模型可以解析 `reason` 字段有针对性地收敛；审计里多一条 `gate_failed` 标记并附完整 verdict。可以直接对照现有实现：

```python
# tool_budget.py 的现成模式：超预算不抛异常，构造结构化结果回喂
return ToolCallResult(
    output=json.dumps(payload, ensure_ascii=False),
    status=ToolInvocationStatus.failed,
    audit={"budget_exceeded": check.reason, "budget": self.to_audit()},
)
```

门禁失败走同样的形状：结构化、可解析、可审计，模型自己决定下一轮怎么收尾。

## 61.4 本章小结

- 任务"完成"的时刻不能由模型宣布。验收必须外化成不受自述影响的判官：exit code、diff、审计记录。
- 门禁顺序是经济问题：先确定性、便宜、强信号，后概率性、昂贵、弱信号。弱信号放前面只是白付成本。
- fail-closed / fail-open 是误差成本问题：误放行不可挽回的（验收命令、范围审计）fail-closed；误失败只是绕路的（覆盖度评审）fail-open，但必须留 unverified 痕。
- 重试额度挂在任务级，三级门禁共享。额度把互博从活锁变成以 failed 落定的有界过程——而那个 failed 本身就是最诚实的审计信息。
- 门禁失败以结构化 JSON 回喂模型，不抛异常：模型能收敛，审计可追溯。与工具预算超额的 `budget_exceeded` 同构。
