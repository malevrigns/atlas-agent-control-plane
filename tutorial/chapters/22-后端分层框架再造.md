# 第二十二章. 后端分层框架再造

## 22.1 本章目标
​        前面三十二章一直在快速堆功能：会话、文件、LLM、Planner、ReAct、任务队列、Sandbox、Browser、Search、MCP 都已经进入项目。这个阶段再看后端目录，就会发现一个语义问题：外层 `backend/api/` 是 monorepo 里的后端服务目录，内层 `app/api/` 又是 FastAPI 路由目录。两个 `api` 同时出现，读者容易分不清哪个是服务边界，哪个是 HTTP 表现层。
​        本章的目标，就是把内层 HTTP 路由从 `app/api` 重构到 `app/presentation/http`，同时补充项目整体架构说明、后端分层规则和依赖说明。这个重构不改变接口路径，不改变业务行为，也不引入新的功能；它解决的是“后续代码放哪里、依赖方向怎么走、架构规则在哪里查”的问题。
​        这一章也会说明一个重要取舍：我们不在第 1 章就设计完整架构，而是在功能复杂度真的出现后再整理边界。过早架构会让读者先背目录，后理解业务；太晚整理则会让代码继续膨胀。本章正好处在一个合适时间点，项目已经有足够多模块，也还没有复杂到无法移动。

## 22.2 最终效果
​        本章结束后，后端目录中原来的 HTTP 路由层：

```Plain
backend/api/
  app/
    backend/api/
      router.py
      routes/
      sse.py
```

​        会被调整为：

```Plain
backend/api/
  app/
    presentation/
      http/
        router.py
        routes/
        sse.py
```

​        外层 `backend/api/` 不动。外层 `backend/api/` 表示后端服务，它和 `frontend/web/`、`backend/sandbox/`、`nginx/` 是同一级服务目录；内层原来的 `app/api/` 表示 HTTP 路由层，移动到 `presentation/http` 后，语义更接近分层架构中的表现层。
​        应用入口也会随之调整。`main.py` 不再从 `app.api.router` 导入路由，而是从新的表现层路径导入：

```Python
from app.presentation.http.router import api_router
```

​        对用户来说，接口路径不发生变化。`GET /api/status`、`GET /api/mcp/servers`、`GET /api/agent-core/tools` 仍然照常访问。Nginx、前端请求和测试命令都不需要因为这次目录整理改变 URL。
​        本章还会新增三份文档：根目录的 `ARCHITECTURE.md` 说明整个项目的服务关系；`backend/api/ARCHITECTURE.md` 说明后端分层规则；`backend/api/DEPENDENCIES.md` 说明后端依赖用途和新增依赖时的维护规则。这样目录结构和规则不只写在教程里，也沉淀到项目自身。

## 22.3 本章要解决的问题
​        过去的章节里，`app/api/routes` 这个名字并不会造成太大问题。项目只有几个健康检查和会话接口时，大家都能理解它是 FastAPI 路由。可是当 MCP、Sandbox、Agent Core、SSE、文件、任务队列这些模块都出现以后，`backend/api/app/api` 这个路径就不够清楚了。它既像服务名，又像接口层，读者进入代码时会多一次理解成本。
​        更大的问题是后续扩展。第 23 章开始会进入 A2A，第 24 章会进入多 Agent 协作，第 27 章以后还会进入长期记忆、任务恢复、测评和生产部署。如果现在不整理表现层、应用层、领域层和基础设施层，后面每个新功能都会继续往已有目录里塞代码，最后很难判断一个类应该放在 `application`，还是放在 `infrastructure`，更难判断路由能不能直接访问数据库模型。
​        本章要解决的是工程秩序，而不是业务能力。它让 HTTP 路由层的名字更准确，让架构说明有地方查，让依赖说明有维护入口，也让后续章节在新增功能时有一套共同语言。对于一个教程项目来说，这一点很重要：读者不仅要看到代码能跑，还要看到代码为什么这样组织。

## 22.4 本章技术方案
​        本章采用简化 Clean Architecture 的思路，而不是严格套用 DDD，也不是回到普通 CSR。当前项目更适合这样理解：

```Plain
presentation/http -> application -> domain
application       -> infrastructure
infrastructure    -> domain
```

​        `presentation/http` 是表现层，负责把 HTTP 请求转换成应用服务调用，再把应用服务结果转换成 HTTP 响应。`application` 是应用服务层，负责会话、计划、任务执行、文件、MCP 等用例编排。`domain` 保存核心实体、协议和抽象。`infrastructure` 保存数据库、Redis、LLM、Sandbox、Search、MCP Client 和工具适配器等外部实现。
​        这不是严格 DDD，因为当前的 `SessionService`、`McpService` 这类类名里的 Service 主要表示应用服务，而不是领域服务。它们负责用例编排，例如校验输入、调用 Repository、调用外部 Client、提交事务和写事件。这个说明会写进 `backend/api/ARCHITECTURE.md`，避免后续读者把术语理解成另一套严格模型。
​        本章的代码改动范围很小：移动目录，修正 import，检查旧路径。文档改动范围更重要：写清楚目录结构、分层职责、依赖方向、依赖管理规则和后续新增代码时的落点。这个章节的价值不在于移动多少文件，而在于把之后几十章的后端组织规则固定下来。

### 22.4.1 后端最终会怎么划分领域
​        重构后的后端目录可以这样理解：

```Plain
backend/api/
  app/
    main.py
    core/
    presentation/http/
    schemas/
    application/
    domain/
    infrastructure/
  config/
  migrations/
  ARCHITECTURE.md
  DEPENDENCIES.md
  pyproject.toml
```

​        `core` 保存跨层通用能力，例如配置、日志、异常和配置文件读取。`schemas` 保存 Pydantic 请求响应模型，它面向接口输入输出，不等同于数据库模型，也不等同于领域实体。`domain` 中的实体和协议应尽量少依赖 FastAPI、SQLAlchemy、Redis 和 HTTP Client。`infrastructure` 负责和外部系统打交道，包括数据库实现、Redis 队列、LLM 客户端、Sandbox 客户端、Search 客户端、MCP Client 和 AgentTool 适配器。
​        这个划分不是为了让目录看起来高级，而是为了降低后续改动成本。比如未来要替换搜索供应商，应该主要动 `infrastructure/search`；要新增一个 HTTP 接口，应该主要动 `presentation/http/routes` 和 `schemas`；要新增用例流程，应该先看 `application`；要沉淀核心概念，才进入 `domain`。

## 22.5 新增和修改的文件
​        本章涉及的代码文件主要是路径移动和 import 调整：

```Plain
backend/api/app/main.py
backend/api/app/presentation/__init__.py
backend/api/app/presentation/http/__init__.py
backend/api/app/presentation/http/router.py
backend/api/app/presentation/http/sse.py
backend/api/app/presentation/http/routes/*.py
```

​        原来的 `backend/api/app/api/router.py`、`backend/api/app/api/sse.py` 和 `backend/api/app/api/routes/*.py` 会移动到新目录。路由文件内部如果引用了 `app.api.sse`，也要改成 `app.presentation.http.sse`。主路由汇总文件里的 import 也要从 `app.api.routes` 改为 `app.presentation.http.routes`。
​        文档方面，本章新增或更新：

```Plain
ARCHITECTURE.md
backend/api/ARCHITECTURE.md
backend/api/DEPENDENCIES.md
README.md
backend/api/README.md
docs/course/chapters/33-backend-layering.md
```

​        这些文档不是装饰。根目录架构说明面向整个项目，解释 UI、API、Sandbox、Nginx、PostgreSQL、Redis 之间的关系；后端架构说明面向 API 服务内部，解释分层职责；依赖说明面向依赖治理，解释 `fastapi`、`sqlalchemy`、`redis`、`httpx`、`pyyaml` 等包为什么存在。

## 22.6 实施步骤
​        本章实施时要先移动目录，再修 import，最后补文档和验证接口。顺序不要反过来。如果先写文档再移动目录，文档会短暂失真；如果只移动目录不跑旧路径检查，很容易留下某个路由仍然从 `app.api` 导入。

### 22.6.1 移动 HTTP 路由层目录
​        第一步是创建 `app/presentation/http`，并把原来 `app/api` 下的 `router.py`、`sse.py` 和 `routes` 目录移动过去。移动后的结构是：

```Plain
backend/api/app/presentation/http/
  router.py
  sse.py
  routes/
    status.py
    sessions.py
    files.py
    config.py
    llm.py
    mcp.py
    sandboxes.py
    agent_core.py
    agent_thinking.py
```

​        这一步只改变 Python 模块路径，不改变 HTTP URL。FastAPI 中真正决定 URL 前缀的是 `app.include_router(api_router, prefix=settings.api_prefix)` 和各路由自己的 prefix，而不是源码目录名。因此内层目录从 `api` 改成 `presentation/http`，用户访问的 `/api/...` 路径不会变。

### 22.6.2 修改应用入口 import
​        `backend/api/app/main.py` 是后端入口。它创建 FastAPI，注册中间件、异常处理和路由，也负责后台任务生命周期。本章只需要把路由 import 改成新路径。

```Python
from app.presentation.http.router import api_router
```

​        其他逻辑不需要动。`create_app()` 仍然通过 `app.include_router(api_router, prefix=settings.api_prefix)` 注册所有 API 路由，`lifespan()` 仍然负责 Redis 连接和 `AgentTaskRunner`。这次重构不应该顺手改生命周期、任务队列或 CORS 配置，否则验证范围会变大。

### 22.6.3 修改 HTTP Router 内部 import
​        新的 `backend/api/app/presentation/http/router.py` 要从同一个表现层包中导入 routes：

```Python
from app.presentation.http.routes import (
    agent_core,
    agent_thinking,
    config,
    files,
    llm,
    mcp,
    sandboxes,
    sessions,
    status,
)
```

​        下面的路由注册顺序保持不变。这样做能降低行为变化风险。重构目录时，目标是让模块路径更清晰，而不是改变接口注册顺序或路由行为。对于这类结构整理，稳定性比顺手优化更重要。

### 22.6.4 修改路由文件内部引用
​        多数路由文件只引用 application、schemas、core 和 infrastructure，不受目录移动影响。真正需要关注的是从旧 `app.api` 内部引用辅助模块的地方。例如 SSE 编码辅助原来可能从 `app.api.sse` 导入，移动后要改成：

```Python
from app.presentation.http.sse import encode_sse_event
```

​        这个细节说明了为什么本章要全局检查旧路径。Python import 不会因为文件移动自动更新，漏掉一个路径，接口启动时就会在运行期报错。

### 22.6.5 全局检查旧路径
​        目录移动后，用 `rg` 检查旧路径引用：

```PowerShell
rg -n "app\.api|from app\.api|import app\.api" backend/api/app
```

​        如果输出为空，说明后端代码里不再引用旧的内层 `app.api`。这里不要把历史课程章节或旧备份文档也强行改掉，因为它们描述的是当时的阶段。当前代码和当前架构文档必须准确，历史章节可以保留演进痕迹。

### 22.6.6 新增项目整体架构说明
​        根目录 `ARCHITECTURE.md` 面向整个项目，不只讲后端。它会解释 monorepo 中各服务如何协作：UI 通过 Nginx 访问 API，API 连接 PostgreSQL、Redis、Sandbox 和外部工具，Sandbox 承载文件、Shell、浏览器和 VNC，Nginx 负责统一入口。
​        这份文档的定位是“当前项目整体怎么组织”。课程章节负责解释“为什么一步步这样演进”，架构文档负责沉淀“现在项目处于什么结构”。两者不要混在一起，否则读者既难复盘演进过程，也难快速查当前规则。

### 22.6.7 新增后端架构说明
​        `backend/api/ARCHITECTURE.md` 是本章最重要的治理文档。它写清楚后端不是完整严格 DDD，也不是纯 CSR，而是：

```Plain
简化 Clean Architecture + 领域模块逐步收敛
```

​        文档还会解释 `presentation/http`、`schemas`、`application`、`domain`、`infrastructure`、`core`、`config` 和 `migrations` 各自放什么。尤其要说明 `schemas` 不是数据库模型，SQLAlchemy 模型属于 `infrastructure/database/models`，Repository 实现属于 `infrastructure/repositories`。这样后续新增功能时，文件落点会更一致。

### 22.6.8 新增后端依赖说明
​        `backend/api/DEPENDENCIES.md` 说明后端 `pyproject.toml` 中主要依赖的用途。比如 `fastapi` 用于 HTTP 路由，`uvicorn` 用于 ASGI 运行，`pydantic-settings` 用于配置读取，`sqlalchemy[asyncio]` 和 `asyncpg` 用于 PostgreSQL 异步访问，`alembic` 用于迁移，`redis` 用于任务队列，`httpx` 用于外部 HTTP 调用，`pyyaml` 用于 YAML 配置解析。
​        这份文档还写明依赖管理规则：新增依赖前要确认是否真的需要；如果标准库、现有依赖或项目已有封装能解决问题，不要轻易增加第三方包；新增运行时依赖后，要同步更新 `pyproject.toml`、锁文件、依赖说明和相关教程。这个规则能避免后面章节随手加包，最后没人知道每个依赖的用途。

### 22.6.9 更新 README 和课程说明
​        根 README 和 API README 也要更新，让读者知道架构说明和依赖说明在哪里。教程章节本身则记录这次重构发生在本章，而不是从第 1 章开始就假装目录已经如此成熟。
​        这一点和真实项目很接近。架构不是一次性写完的，它会随着业务和能力增长而调整。教程保留这个演进过程，读者才能理解为什么现在需要重构，而不是只看到一个最终目录。

## 22.7 关键理解
​        本章最重要的理解，是外层 `backend/api/` 和内层 HTTP 路由不是同一个概念。外层 `backend/api/` 是后端服务目录，属于 monorepo 的服务边界；内层 `presentation/http` 是这个服务内部的表现层，负责 HTTP 接口。把两者分开命名，后端结构会清楚很多。
​        第二个关键点是目录重构不等于行为重构。接口 URL 不变，业务服务不变，数据库不变，任务队列不变。只要 import 修正正确，用户和前端感知不到这次移动。这也是结构重构应该追求的状态：改善内部可维护性，同时尽量不扩大外部行为变化。
​        第三个关键点是文档也是工程资产。`ARCHITECTURE.md` 和 `DEPENDENCIES.md` 不是写给评审看的摆设，而是后续新增功能时的规则入口。没有这些文档，架构规则只能存在开发者脑子里；一旦多人协作或隔一段时间再回来维护，规则就会散掉。
​        第四个关键点是分层不是为了限制开发速度，而是为了让新增能力有稳定落点。前面章节中，Search、MCP、Sandbox、AgentTool 都已经开始跨越多个模块。如果没有分层规则，后面新增 A2A 时，很可能把协议对象、HTTP 路由、外部 Client 和任务编排混在一起。现在把表现层、应用层、领域层和基础设施层讲清楚，后续每次新增能力都能先判断它属于哪一层。
​        第五个关键点是本章只重构 API 服务内部，不试图一次整理整个 monorepo。UI、Sandbox 和 Nginx 仍然保留自己的结构。API 内部复杂度已经先达到需要整理的程度，所以先整理 API；Sandbox 后续如果继续膨胀，也可以按类似方式再整理。架构演进应该跟着复杂度走，而不是为了统一形式把所有服务同时大改。

## 22.8 技术难点与亮点
​        本章的技术难点不在代码，而在边界控制。移动目录时很容易顺手重构业务逻辑，甚至改接口命名、改服务创建方式、改依赖注入。这样会让一次简单结构调整变成多风险改动。本章只改路径和文档，把行为变化压到最低。
​        第二个难点是 import 检查。Python 项目移动包路径后，旧引用可能藏在某个路由、测试或脚本里。用 `rg` 检查 `app.api` 是必要步骤。只要还有运行时代码引用旧路径，就说明重构没有收干净。
​        第三个亮点是架构说明主动承认项目状态。文档没有把当前后端包装成严格 DDD，而是明确说它是简化 Clean Architecture，并且领域模块会逐步收敛。这个表达更诚实，也更适合教程项目。架构文档不是用来贴概念标签的，而是帮助后续维护者做具体决策。
​        第四个亮点是把目录规则和依赖规则一起写。很多项目只写“代码放哪里”，却不写“依赖为什么存在”。结果是目录看起来清楚，但 `pyproject.toml` 越来越重。本章同步补 `DEPENDENCIES.md`，就是为了让结构治理和依赖治理同时开始。后续新增依赖时，开发者要能说明它解决什么问题、属于运行时还是开发时、是否会影响镜像构建和教程解释成本。
​        第五个难点是保持历史演进和当前规则之间的关系。教程前面很多章节自然会出现旧路径，如果全部回改，读者就看不到项目是如何从简单结构演进到分层结构的；如果当前代码还保留旧路径，又会让架构文档失真。本章的处理方式是：当前代码和当前文档必须使用新路径，历史章节保留演进痕迹，并在本章明确说明这次迁移发生的时间点。
​        第六个亮点是重构后的目录能直接支撑后续协议扩展。A2A、Agent Runner、长期记忆和测评回放都需要新的 HTTP 入口、应用服务和基础设施适配器。现在分层位置已经明确，后面新增模块时就不必重新争论目录命名。

## 22.9 面试考点
​        如果面试官问“为什么把 `app/api` 改成 `app/presentation/http`”，可以回答：外层 `backend/api/` 已经表示后端服务，内层 `app/api` 再叫 api 容易混淆。HTTP 路由本质上是表现层，把它放到 `presentation/http` 能更清楚表达职责，也为后续接入非 HTTP 表现层留下空间。
​        如果被问到“这次重构为什么不影响接口路径”，要说明源码目录名不决定 URL。URL 由 FastAPI 的 router prefix 和路由定义决定。`main.py` 仍然用 `settings.api_prefix` 注册 `api_router`，所以 `/api/status`、`/api/mcp/servers` 等路径保持不变。
​        如果被问到“本项目是 DDD 吗”，不要硬说是。更准确的回答是：当前项目采用简化 Clean Architecture，并逐步向领域模块收敛。`application` 层主要承载应用服务，`domain` 层承载实体和核心抽象，`infrastructure` 层承载外部实现，但还没有使用严格 DDD 的全部战术模式。
​        如果被问到“为什么要写依赖说明”，可以回答：后端依赖会影响构建速度、镜像体积、安全维护和学习成本。把依赖用途写清楚，能让后续新增依赖时有依据，也能避免把前端、Sandbox 或临时调试工具误加到 API 运行时依赖里。

## 22.10 运行验证
​        本章验证要证明两件事：旧路径已经清掉，接口行为仍然正常。因为这章没有新增业务能力，所以验证重点不是页面功能，而是结构移动后应用能否启动、路由能否注册、核心接口能否访问。

### 22.10.1 检查旧路径
​        先检查后端代码中是否还引用旧的 `app.api`：

```PowerShell
rg -n "app\.api|from app\.api|import app\.api" backend/api/app
```

​        这个命令应该没有输出。如果还有输出，需要判断它是不是当前运行代码里的 import。如果是，就必须改成 `app.presentation.http`。

### 22.10.2 编译后端
​        运行 Python 编译检查：

```PowerShell
python -m compileall backend/api/app
```

​        这一步能发现大部分 import 语法错误和模块路径错误。目录重构后，编译检查比只手动打开几个文件更可靠。

### 22.10.3 用 TestClient 验证核心接口
​        可以用 FastAPI TestClient 或已有测试方式验证核心接口仍然可访问。至少要覆盖健康检查、MCP 列表和 Agent Core 工具列表。

```Plain
GET /api/status
GET /api/mcp/servers
GET /api/agent-core/tools
```

​        这些接口分别覆盖基础路由、MCP 路由和 Agent 工具路由。如果它们都能正常返回，说明主路由汇总和多类 routes 的 import 基本没有问题。
​        只验证一个健康检查接口是不够的。健康检查通常依赖最少，可能只证明 `status.py` 被正确加载；而 MCP 和 Agent Core 会覆盖更复杂的 route import、schema import、application service import 和 infrastructure import。目录移动后，越是跨层调用多的接口，越能暴露路径遗漏。

### 22.10.4 Docker Compose 验证
​        最后用容器启动项目：

```PowerShell
docker compose up --build
```

​        结构重构后，容器环境也要验证。因为本地 Python 路径和容器工作目录可能不同，只有容器能启动，才能确认 Dockerfile、工作目录和 import 路径都没有隐性问题。

## 22.11 本章小结
​        本章完成了一次结构性重构：把后端 HTTP 路由层从 `app/api` 移动到 `app/presentation/http`，修正应用入口和路由内部 import，并新增项目架构说明、后端架构说明和依赖说明。对外接口路径保持不变，内部目录语义变得更清楚。
​        这章的意义在于给后续复杂功能建立秩序。A2A、多 Agent、长期记忆、任务恢复和测评都会继续增加后端复杂度。如果没有清晰分层，后面的代码会越来越难维护。现在把表现层、应用层、领域层和基础设施层边界讲清楚，是为了让后面的扩展有稳定落点。
​        从教程节奏看，本章也是一个分水岭。前半部分更像把一个 Agent 工作台从零跑通，后半部分会更关注协议、协作、记忆、恢复、测评和生产化。越往后，单个功能越容易跨多个模块，所以本章提前把结构规则写清楚，是为了让后续章节继续扩展时不失控。
​        这次整理也让读者以后回看代码时更容易判断入口、用例和外部实现分别在哪里。
