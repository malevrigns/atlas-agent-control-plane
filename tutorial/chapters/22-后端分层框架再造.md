# 第二十二章. 后端分层框架再造

功能堆到第二十章附近，目录开始说话。会话、文件、SSE、沙箱、搜索、MCP 面板都要有地方放。放错一层，过两周就分不清：这段逻辑是 HTTP 适配，是用例编排，还是对 SQLite 的细节。TypeScript 控制平面从一开始就按分层来写，这一章把那张地图钉死，后面 A2A、记忆、Harness 才知道该进哪扇门。

代码在 `backend/api-ts`。入口是 Hono 的 `createApp()`。不要再新建 Python 服务，也不要把路由写回某个 `app/api` 目录。

![入口像一扇刚打开的门](../assets/ch03-gateway.jpg)

## 四层，不是口号

`src/presentation/http` 是表现层。它把 Request 变成一次应用服务调用，再把结果包进统一信封。路由文件不该自己 `insert` 表，也不该直接 `fetch` 模型网关。`src/application` 是用例：开会话、存文件、推 SSE。`src/domain` 放会话状态、标识符、和框架无关的小函数。`src/infrastructure` 现在主要是 Drizzle 的 schema 和数据库客户端；以后 MCP Client、对象存储、搜索适配器也该进这里。

`src/core` 是横切：配置、鉴权、错误。它不是第五层业务，是所有层都要用的钉子。`loadSettings()` 用 zod 收环境变量；`AppError` 决定信封里的 `error.type` 和 HTTP 状态。表现层捕获它，应用层抛出它，领域层尽量不引用 Hono。

依赖方向只准向内。HTTP 可以叫 application，application 可以叫 domain 和 infrastructure，infrastructure 实现 domain 里的抽象。反过来不行。路由一旦直接碰 `sqliteTable`，测试就只能靠整进程，分层也就只剩文件夹名字。Hono 路由文件不准直接 `fetch` 大模型。测试里替换的是 application 依赖的端口，不是把整张表 mock 掉。

笔者不把这套叫严格 DDD。`SessionService` 是应用服务，不是「领域专家口中的领域服务」。它编排校验、写库、写事件。名字里的 Service 表示用例，不表示又一套战术模式。把术语说破，后面的人就不会把每个函数都改名叫 Aggregate。

现在 `api-ts` 的 domain 还薄，很多逻辑挤在 application。分层不是教条，是为了以后把 ToolRuntime、执行机、RAG 塞进来时，不把 `app.ts` 写成上帝文件。新代码继续往对应目录放，不要图省事写进路由。

## 装配发生在一个函数里

进程入口 `src/main.ts` 只做三件事：读配置、打开数据库、把 `createApp(settings, db)` 交给 `@hono/node-server`。真正的装配在 `src/app.ts`：

```ts
export function createApp(settings: Settings, db: Database) {
  const sessions = new SessionService(db);
  const files = new FileService(db, sessions, settings);
  const app = new Hono<AppEnv>();

  app.use("*", async (c, next) => {
    const requestId = c.req.header("x-request-id") || crypto.randomUUID();
    c.set("requestId", requestId);
    await next();
    c.header("X-Request-ID", requestId);
  });

  app.use("*", cors({ origin: corsOrigins(settings), credentials: true }));
  app.use("*", authMiddleware(settings));

  const api = new Hono<AppEnv>();
  api.route("/auth", authRoutes(settings));
  api.route("/status", statusRoutes(settings, db));
  api.route("/sessions", sessionRoutes(sessions, files, settings));
  api.route("/files", fileRoutes(files));
  api.route("/control-plane", controlPlaneRoutes(db));
  api.route("/", stubRoutes());
  app.route(settings.apiPrefix, api);
  return app;
}
```

中间件顺序是有意的。先有 request id，后面的错误信封才能带上它；再 CORS，浏览器预检才过得去；再鉴权，业务路由不必每个自己查 cookie。`onError` 把 `AppError` 和未知异常分成两条路，未知异常打日志，对外只说 internal server error。

`createApp` 和 `serve` 分开，vitest 才能 `app.request("/api/status")` 打到同一套路由。契约测试不听端口，分层才测得动。这一点在第 3 章已经用过，本章只是把它写成规则：新路由先进 `presentation/http/routes`，在 `createApp` 里挂上，测试走 `makeTestApp()`。传入内存库和关鉴权的 settings，比拉起真实服务器再 curl 要快，也逼你把副作用从路由里拿开。

## 占位路由也是分层的一部分

`stubRoutes()` 挂在 `api.route("/", ...)` 上，路径是 `/api/mcp/servers`、`/api/memories`、`/api/a2a/agents` 这类工作台会打的地址。它们返回空 `items`，不是因为分层失败，而是因为那些用例还没从旧实现搬过来。占位放在 presentation，至少工作台不会 404；等 application 里有了真正的 `McpService`，再把 stub 换成真路由，目录不用打乱。

`control-plane` 已经不是 stub。`POST /api/control-plane/tasks` 会往 `agent_tasks` 表插一行，带 `progress` JSON。检查点列表仍返回空 `items`。真实能力和空位并存，分层的好处是一眼能看出哪段是用例、哪段是门面。

对外 URL 不随内部搬家而变。`/api/status` 永远是 `/api/status`。Nginx、前端 rewrite、健康检查都认这条路径。分层是给写代码的人看的，不是给浏览器看的。

根目录的 `ARCHITECTURE.md` 还画着旧的 FastAPI 树，那是演进史上的总图，动手以 `backend/api-ts/src` 为准。文档落后代码的时候，信代码，再回头改文档，不要把教程写成两套目录同时正确。

## 这一章留下了什么

一张 TypeScript 控制平面的分层地图，一个只负责装配的 `createApp()`，以及「占位也要站对层」的约定。下一章用这张地图接 A2A：概念可以先讲，Client 仍然可以是空列表，但文件不该再塞进路由函数的肚子里。
