# 第十三章. 会话文件与预览开卷

## 13.1 本章目标
​        第 12 章已经让文件可以上传、保存和下载，但那一章里的文件仍然是独立资源。对于 Agent 工作台来说，独立文件还不够，因为用户真正关心的是“这个文件属于哪个会话”“这个会话有哪些材料”“我能不能先看一眼文件内容”。如果这些关系没有建立，后续让 Agent 读取上下文时就会缺少基础。
​        本章要把文件推进到会话上下文中。后端会新增 `session_files` 关系表，实现上传文件到指定会话、查询某个会话的文件列表，以及文本文件预览接口。前端会在右侧工作区展示会话文件列表，并提供下载和预览面板。读者在这一章要重点理解下载和预览的差异：下载交付的是完整文件，预览交付的是受限制、可直接展示的文本片段。

## 13.2 最终效果
​        本章结束后，访问：

```Plain
http://localhost:8088
```

​        进入任意会话后，可以完成下面的操作：

```Plain
选择会话 -> 上传附件 -> 右侧会话文件列表出现文件 -> 点击文件 -> 点击预览 -> 查看文本内容
```

​        后端新增接口：

```Plain
POST /api/sessions/{session_id}/files
GET  /api/sessions/{session_id}/files
GET  /api/files/{file_id}/preview
```

​        第 12 章已经有独立文件上传。本章让文件真正进入会话上下文。

## 13.3 本章要解决的问题
​        第 12 章完成了文件上传、元数据保存和下载。
​        但是第 12 章有一个明显边界：文件是独立存在的，页面只知道“刚刚上传成功了某个文件”，不知道这个文件属于哪个会话。
​        这会带来几个问题：

```Plain
刷新页面后，当前会话看不到之前上传的文件
切换会话后，不知道哪些文件属于哪个会话
后续发送消息时，很难把附件和任务上下文放在一起
文件预览没有统一入口
```

​        所以本章要给文件增加会话归属。
​        文件和会话不是一对一关系。一个会话可以有多个文件，后续一个文件也可能被多个任务引用。因此本章使用关系表：

```Plain
sessions
  |
  +-- session_files
        |
        v
      files
```

## 13.4 本章技术方案
​        本章采用“文件表 + 会话文件关系表”的方案。
​        可选方案有三种：
​        一种做法是在 `files` 表里直接增加 `session_id`，这样实现最短，但会把文件元数据和归属关系揉在一起。另一种做法是在消息表里直接保存附件信息，适合很轻的聊天 Demo，却不利于后续独立预览、权限控制和多次引用。课程在这里选择新增 `session_files` 关系表，让文件本身和文件归属各自保持清楚的职责。
​        本章选择第三种。
​        原因是：
​        `files` 表继续只描述文件是什么，包括原始文件名、存储文件名、类型、大小和存储路径；`session_files` 表只描述这个文件属于哪个会话，不重复保存文件内容，也不复制元数据。这样拆开后，文件下载、预览和未来权限控制仍然围绕 `file_id` 展开，而会话文件列表只需要围绕 `session_id` 查询关系表。
​        本章请求链路如下：

```Plain
浏览器选择文件
  |
  v
POST /api/sessions/{session_id}/files
  |
  v
FileService
  |
  +-- 检查会话是否存在
  +-- 保存文件内容
  +-- 写入 files 表
  +-- 写入 session_files 表
  +-- 更新会话 updated_at
  |
  v
GET /api/sessions/{session_id}/files
  |
  v
前端展示会话文件列表
```

​        预览链路如下：

```Plain
用户选择文件
  |
  v
GET /api/files/{file_id}/preview
  |
  v
只读取有限大小的文本内容
  |
  v
前端预览面板展示
```

​        本章暂时不做这些内容：
​        本章的预览能力只面向文本类文件，不做 PDF、Word、Excel 的富文本预览，也不做图片预览。文件删除、对象存储、消息附件关系和 Agent 文件读取同样先不展开。课程在这里先把“会话能拥有文件，页面能看见文件，文本能被预览”这条链路建立起来。

## 13.6 实施步骤
### 13.6.1 增加预览大小配置
​        打开 `api/app/core/config.py`，在上传配置后加入：

```Python
max_file_preview_size: int = 64 * 1024
```

​        这个配置控制预览接口最多读取多少字节。
​        为什么需要它？
​        下载接口可以把完整文件交给浏览器，但预览接口会把文件内容放进 JSON 响应里。如果一个文件有几十 MB，直接塞进 JSON 会导致接口很慢，也会让页面卡住。
​        本章先限制为 64KB。它足够预览普通文本文件的开头，也能避免误把大文件一次性读进响应。
​        同步更新 `.env.example`：

```Plain
MAX_FILE_PREVIEW_SIZE=65536
```

​        同步更新 `docker-compose.yml` 的 API 环境变量：

```YAML
MAX_FILE_PREVIEW_SIZE: ${MAX_FILE_PREVIEW_SIZE:-65536}
```

from uuid import UUID, uuid4
from sqlalchemy import DateTime, ForeignKey, UniqueConstraint, func
from sqlalchemy.dialects.postgresql import UUID as PgUUID

from app.domain.files.entities import SessionFile
from app.infrastructure.database.base import Base
from app.infrastructure.database.models.file_object import FileObjectModel


class SessionFileModel(Base):

    __table_args__ = (

        server_default=func.now(),

            session_id=self.session_id,
            file=self.file.to_entity(),
            created_at=self.created_at,

### 13.6.5 实现会话文件 Repository
​        打开 `api/app/infrastructure/repositories/file_repository.py`，新增 `SqlAlchemySessionFileRepository`：

```Python
class SqlAlchemySessionFileRepository(SessionFileRepository):
    def __init__(self, db_session: AsyncSession) -> None:
        self.db_session = db_session
    async def add(self, session_id: UUID, file_id: UUID) -> SessionFile:
        # 关系表只保存归属关系，不冗余保存文件内容和文件元数据。
        model = SessionFileModel(session_id=session_id, file_id=file_id)
        self.db_session.add(model)
        await self.db_session.flush()
        stmt = select(SessionFileModel).where(SessionFileModel.id == model.id)
        result = await self.db_session.execute(stmt)
        created = result.scalar_one()
        return created.to_entity()
    async def list_by_session(self, session_id: UUID) -> list[SessionFile]:
        stmt = (
            select(SessionFileModel)
            .where(SessionFileModel.session_id == session_id)
            .order_by(SessionFileModel.created_at.desc())
        )
        result = await self.db_session.execute(stmt)
        return [model.to_entity() for model in result.scalars()]
```

​        这段代码的业务流程：

```Plain
写入 session_files
  |
  v
重新查询这条关系
  |
  v
返回带 file 元数据的 SessionFile
```

​        这里写完后重新查询一次，是为了稳定拿到 `relationship` 中的文件元数据。异步数据库会话中，不建议依赖隐式加载关系数据。

from app.infrastructure.repositories.file_repository import (

class UnitOfWork:

        self.files = SqlAlchemyFileRepository(db_session)

### 13.6.7 扩展文件应用服务
​        打开 `api/app/application/file_service.py`，新增三个能力：
​        `save_session_upload()` 负责把上传文件保存下来，并在同一个业务动作里建立会话归属；`list_session_files()` 负责读取某个会话下已经绑定的文件；`preview_file()` 则负责在下载之外提供一个轻量文本预览入口。三个方法放在同一个应用服务里，是因为它们共同维护文件资源和会话上下文之间的边界。
​        关键代码如下：

```Python
async def save_session_upload(
    self,
    session_id: UUID,
    original_name: str,
    content_type: str | None,
    content: bytes,
) -> SessionFile:
    session = await self.uow.sessions.get(session_id)
    if session is None:
        raise AppException(
            message="session not found",
            code=404,
            status_code=404,
        )
    clean_name = self._clean_filename(original_name)
    stored_name, storage_path = self._write_upload_file(
        clean_name=clean_name,
        content=content,
    )
    try:
        file_object = await self.uow.files.add(
            original_name=clean_name,
            stored_name=stored_name,
            content_type=content_type or "application/octet-stream",
            size=len(content),
            storage_path=str(storage_path),
        )
        session_file = await self.uow.session_files.add(
            session_id=session_id,
            file_id=file_object.id,
        )
        await self.uow.sessions.touch(session_id)
        await self.uow.commit()
    except Exception:
        # 会话归属写入失败时也要清理文件，避免页面永远找不到这份上传内容。
        storage_path.unlink(missing_ok=True)
        await self.uow.rollback()
        raise
    return session_file
```

​        这段代码的业务流程：

```Plain
检查会话
  |
  v
写入磁盘
  |
  v
写入 files
  |
  v
写入 session_files
  |
  v
更新会话 updated_at
  |
  v
commit
```

​        为什么先检查会话？
​        如果会话不存在，就不应该保存文件内容。否则磁盘里会留下无法从页面访问的文件。
​        为什么异常时要删除文件？
​        文件写磁盘和数据库事务不是同一个系统。数据库可以回滚，但磁盘写入不会自动回滚。所以在数据库写入失败时，要手动清理文件。
​        预览代码如下：

```Python
async def preview_file(self, file_id: UUID) -> tuple[FileObject, str, bool]:
    file_object, path = await self.get_download_path(file_id)
    if not self._is_text_preview_supported(file_object):
        raise AppException(
            message="file preview is not supported",
            code=415,
            status_code=415,
        )
    # 预览只读取有限字节，避免把大文件一次性塞进接口响应。
    content = path.read_bytes()
    truncated = len(content) > settings.max_file_preview_size
    preview_bytes = content[: settings.max_file_preview_size]
    return file_object, preview_bytes.decode("utf-8", errors="replace"), truncated
```

​        预览和下载不是一回事。
​        下载可以返回完整文件流。预览需要把内容变成页面可展示的文本，所以必须限制类型和大小。

@router.post(
    "/{session_id}/files",
    response_model=ApiResponse[SessionFileResponse],
)
async def upload_session_file(
    session_id: UUID,
    upload: UploadFile = File(...),
    service: FileService = Depends(build_file_service),
) -> ApiResponse[SessionFileResponse]:
    content = await upload.read()
    session_file = await service.save_session_upload(
        session_id=session_id,
        original_name=upload.filename or "",
        content_type=upload.content_type,
        content=content,
    )
    return ApiResponse(data=to_session_file_response(session_file))


@router.get(
    "/{session_id}/files",
    response_model=ApiResponse[SessionFileListResponse],
)
async def list_session_files(
    session_id: UUID,
    service: FileService = Depends(build_file_service),
) -> ApiResponse[SessionFileListResponse]:
    files = await service.list_session_files(session_id)
    return ApiResponse(
        data=SessionFileListResponse(
            items=[to_session_file_response(file) for file in files],
        )
    )

    (data) => data.items,
  );
}
export async function uploadSessionFile(
  sessionId: string,
  file: File,
): Promise<SessionFileItem> {
  const formData = new FormData();
  formData.append("upload", file);
  const response = await fetch(`/api/sessions/${sessionId}/files`, {
    method: "POST",
    body: formData,
  });
  const payload = (await response.json()) as {
    code: number;
    message: string;
    data: SessionFileItem | null;
  };
  if (!response.ok || payload.code >= 400) {
    throw new Error(payload.message || `HTTP ${response.status}`);
  }
  if (!payload.data) {
    throw new Error("empty response");
  }
  return payload.data;
}

## 13.7 关键理解
​        第一个重点：文件和会话要通过关系表关联。

```Plain
files          文件是什么
session_files  文件属于哪个会话
```

​        第二个重点：下载和预览不是同一个接口。

```Plain
download  返回完整文件
preview   返回有限文本内容
```

​        第三个重点：前端文件状态分成两类。

```Plain
files       当前会话已经保存的文件列表
attachments 本次刚上传成功、靠近输入框展示的附件
```

​        后续章节如果要把附件真正挂到某条消息上，可以继续增加消息附件表，而不需要推翻本章结构。

## 13.8 技术难点与亮点
​        本章的难点不在于多写一个上传接口，而在于关系和一致性。`session_files` 不能冗余保存文件元数据，否则文件名、大小和下载地址将来会出现多处来源；上传会话文件时，又要让文件记录、关系记录和会话更新时间尽量在一次业务事务中完成。如果数据库写入失败，已经落盘的文件还要清理掉，避免留下页面永远查不到的孤立文件。
​        另一个难点是预览边界。下载接口可以交付完整文件，但预览接口会把内容塞进 JSON 响应，因此必须限制文件类型和读取大小。前端也不只是多一个按钮，它要同时处理文件列表、选中文件、预览加载、预览失败和截断提示。到这一章，右侧工作区已经开始形成“文件 + 事件”的双栏信息结构，项目的工作台感也更明显。

## 13.9 面试考点
​        这一章适合在面试里讲系统建模能力。你可以从为什么不用在 `files` 表里直接加 `session_id` 讲起，再解释下载接口和预览接口为什么要分开。随后补充上传成功但数据库写入失败时如何清理落盘文件、预览接口为什么限制类型和大小，以及前端为什么把文件面板拆成独立组件。这个回答的重点不是“我会上传文件”，而是“我知道文件在会话系统里如何成为可管理资源”。

## 13.11 常见问题

### 13.11.1 执行迁移后提示找不到 `files` 表怎么办
​        这通常说明第 12 章的 `files` 表迁移还没有执行。直接执行 `docker compose exec api uv run alembic upgrade head`，Alembic 会按版本顺序从旧迁移推进到最新版本，不需要手动跳到第 13 章迁移。

### 13.11.2 上传文件返回 `session not found` 怎么办
​        传入的 `session_id` 不存在，或者这个会话已经被删除。先调用 `GET /api/sessions` 查看当前可用会话，再把返回的真实 `id` 放进上传接口。不要复用旧页面或旧命令里已经失效的会话 id。

### 13.11.3 页面右侧没有文件列表怎么办
​        本章修改了 UI 组件和页面布局，需要重新构建并重启 UI。执行 `docker compose build ui`，再执行 `docker compose up -d ui nginx`。如果后端接口已经能返回文件列表，而页面仍然没有右侧面板，优先检查浏览器加载的是否还是旧前端资源。

### 13.11.4 `docker compose build api` 在 `uv sync --frozen --no-dev --no-install-project` 失败怎么办
​        这一行是在 Docker 镜像里安装后端依赖。如果日志里出现下载包很慢、连接超时或下载中断，通常是网络问题，不是业务代码错误。可以重新执行 `docker compose build api`；如果一直失败，先确认本机网络能访问 Python 包源。构建成功后，依赖层会被 Docker 缓存，下一次会快很多。

### 13.11.5 构建一开始就提示 `load metadata for docker.io` 或 `load metadata for ghcr.io` 失败怎么办
​        这是 Docker 在读取基础镜像元数据时网络中断。可以不要同时构建两个服务，改成 `docker compose build api` 和 `docker compose build ui` 分开执行。已经构建成功的服务不需要重复构建，直接执行 `docker compose up -d api ui nginx` 即可。

### 13.11.6 预览接口返回 `file preview is not supported` 怎么办
​        当前只支持文本类文件预览，图片、压缩包和多数二进制文件都会被拒绝。这个错误不影响下载功能，用户仍然可以通过下载入口拿到原始文件。富文本和图片预览需要额外解析器或渲染逻辑，后续再扩展。

### 13.11.7 上传后页面文件列表没有更新怎么办
​        先刷新页面并确认当前选中的会话没有切换。如果 `GET /api/sessions/{session_id}/files` 能返回数据，说明后端关系表和查询接口正常，重点检查浏览器控制台和 store 状态更新。当前章节上传成功后，store 会把新文件插入 `files` 列表。

## 13.12 本章小结
​        本章完成了会话文件能力。后端新增 `session_files` 关系表，文件可以绑定到具体会话，会话也可以查询自己的文件列表；文本文件可以通过预览接口查看有限内容，下载接口仍然负责交付原始文件。前端新增会话文件面板和文本预览面板，上传附件后右侧文件列表会同步更新。
​        从这一章开始，文件不再只是独立上传结果，而是进入了会话上下文。后续无论做文件解析、Agent 引用，还是消息附件，都可以沿着这个关系继续扩展，而不必推翻第 12 章建立的文件基础模型。
