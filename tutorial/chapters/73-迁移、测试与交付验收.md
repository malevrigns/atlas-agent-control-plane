# 第七十三章. 迁移、测试与交付验收

## 73.1 本章目标

本章不再增加功能，而是将 Memory Control Plane、Tool Runtime、Electron 和 TUI 收敛成一套可重复的迁移与交付流程。

## 73.2 升级前检查

执行数据库升级前，先完成：

1. 备份 PostgreSQL 数据库与上传文件卷；
2. 记录当前 Alembic revision；
3. 确认未运行旧版 API 容器与新版共用数据库；
4. 为 `ARTIFACT_DIR` 准备可持久、不对公网直接暴露的存储路径；
5. 核对 `TOOL_AUTO_APPROVE_RISK`、`TOOL_DEFAULT_TIMEOUT_SECONDS` 和 `TOOL_OUTPUT_INLINE_LIMIT`。

## 73.3 数据库迁移

```bash
cd api
uv sync --frozen
uv run alembic current
uv run alembic upgrade head
```

升级 migration 为：

```text
202608010001_memory_tool_control_plane.py
```

它会扩展 `agent_memories`，并新建任务、需求、决策、Checkpoint、Artifact、记忆关系、环境快照、Skill 执行、检索轨迹和工具审计等表。

为避免到生产环境才发现 SQL 方言问题，使用离线生成先检查迁移 SQL：

```bash
uv run alembic upgrade head --sql > /tmp/atlas-migration.sql
```

离线 SQL 用于审查，不代替真实数据库的升级验证。

## 73.4 自动化测试

后端：

```bash
cd api
uv run python -m unittest discover -s tests
```

重点用例：

- `test_memory_control_plane.py`：写入门、验证、替代与检索上下文；
- `test_checkpoint_service.py`：稳定哈希、证据完整性、约束继承；
- `test_tool_runtime.py`：权限、审批、幂等、超时、脱敏和 Artifact；
- 原有 Agent Runner、搜索、安全、可观测与产品验收测试：保证兼容性。

TUI：

```bash
cd tui
uv sync --frozen
uv run python -m unittest discover -s tests
```

Electron：

```bash
cd desktop
npm ci
npm run build
npm run test:sites
node --check electron/main.cjs
node --check electron/preload.cjs
```

## 73.5 手工端到端验收

自动测试通过后，按以下顺序做一次真实链路：

1. 创建一个带验收标准和 `must_preserve` 的任务；
2. 为它捕获环境快照；
3. 上传一个测试报告 Artifact；
4. 创建 Checkpoint，确认 `validator_report.valid=true`；
5. 新建候选记忆，带 provenance 验证；
6. 执行一个低风险工具，然后用相同幂等键再调用一次；
7. 查看工具审计，确认第二次为 `deduplicated`；
8. 在 Web、Electron 和 TUI 中查看同一任务状态。

## 73.6 交付包卫生

交付源码不应包含：

```text
.venv/
node_modules/
dist/
release/
__pycache__/
.pytest_cache/
.mypy_cache/
本地 Artifact 实例
测试过程产生的截图与临时文件
```

必须包含：

- 依赖锁文件；
- `.env.example`，但不包含真实 `.env`；
- Alembic migration；
- 后端、Electron 和 TUI 测试；
- 运行文档、教程更新和交付说明。

## 73.7 回滚策略

数据库结构回滚不等于数据回滚。如果新版已经产生 Checkpoint、Artifact 和工具审计数据，直接 downgrade 可能丢失这些记录。正式环境应优先：

1. 停止写入；
2. 备份升级后数据；
3. 回滚应用并恢复升级前数据库快照；
4. 将升级期间的新数据另行导出审查。

不要在没有备份时直接对生产数据库执行 `alembic downgrade`。

## 73.8 最终验收清单

- [ ] 迁移可从旧 revision 升级到 head；
- [ ] 后端全部测试通过；
- [ ] TUI 无头测试通过；
- [ ] Electron 生产构建通过；
- [ ] 三套桌面主题切换和持久化正常；
- [ ] 高风险工具未审批不执行；
- [ ] 幂等调用不产生二次副作用；
- [ ] Checkpoint 丢失约束时不可验证；
- [ ] 过期/被替代/敏感记忆不进入普通上下文；
- [ ] 交付包不包含虚拟环境、依赖目录、密钥或运行产物。

## 73.9 本章小结

到这里，AtlasAgent 从“可以调工具的 Web Agent”演进成“有事实源、可恢复、可追溯、可审批、有多客户端的 Agent Control Plane”。交付的完成标准不是文件数量，而是迁移、测试、手工链路和交付包卫生都有明确证据。
