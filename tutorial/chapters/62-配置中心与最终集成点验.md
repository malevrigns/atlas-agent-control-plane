## 62.3 本章要解决的问题

​        前面章节已经实现了很多能力：

```Plain
LLM
Search
MCP
A2A
多 Agent
Sandbox
Browser
VNC
Shell

```

​        但如果这些能力只散落在接口、配置文件和教程命令里，用户遇到问题时会很难判断：

```Plain
到底是没配置密钥？
还是服务没启动？
还是工具没有启用？
还是网络搜索不稳定？
还是 Sandbox 没连上？
```

​        成熟 Agent 产品必须有一个清晰的控制入口。这个入口不一定要在第一版就支持在线保存密钥，但至少要做到：

​        放到工程语境里看，第一，看得见当前配置；第二，看得见配置来源；第三，看得见是否可用；第四，看得见如何验证；第五，不泄露真实密钥。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

## 62.6 实施步骤
### 62.6.1 扩展后端设置模块模型

​        打开 `api/app/application/app_settings_service.py`，给 `SettingsModule` 增加状态字段：

```Python
@dataclass(slots=True)
class SettingsModule:
    """设置页中的一个能力模块。"""

    key: str
    name: str
    description: str
    enabled: bool
    default_item: str | None = None
    items: list[dict[str, object]] = field(default_factory=list)
    status: str = "ready"
    status_message: str = ""
    source: str = ""
    verify_command: str = ""
```

#### 62.6.1.1 代码讲解

​        前 6 个字段是第 37 章已有的配置摘要。

​        本章新增的 4 个字段让设置页从“列表展示”升级为“可排查入口”：

​        具体来说，第一，`status`：模块健康状态，例如 `ready` 或 `warning`；第二，`status_message`：解释为什么可用或为什么需要处理；第三，`source`：配置来自哪里，例如 `.env`、`config/llm.yaml`；第四，`verify_command`：用户可以直接复制执行的验证命令。这些点放在一起看，构成了本章叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        注意，这里仍然不返回真实密钥。

### 62.6.2 使用 runtime-config 保存页面配置

​        打开 `api/app/core/config.py`，把配置路径改成运行时目录：

```Python
llm_config_path: str = "runtime-config/llm.yaml"
mcp_config_path: str = "runtime-config/mcp.yaml"
a2a_config_path: str = "runtime-config/a2a.yaml"
```

​        打开 `.gitignore`，加入：

```Plain
runtime-config/
api/runtime-config/
```

​        打开 `docker-compose.yml`，给 API 服务增加 volume：

```YAML
volumes:
  - api_uploads:/app/uploads
  - api_runtime_config:/app/runtime-config
```

​        并在底部声明：

```YAML
volumes:
  api_runtime_config:
```

#### 62.6.2.1 为什么这样设计

​        课程仓库里的：

```Plain
api/config/llm.yaml
api/config/mcp.yaml
api/config/a2a.yaml
```

​        是示例配置，适合提交到 Git。

​        页面保存的真实配置，尤其是 LLM API Key，不应该写回这些示例文件。所以本章把页面保存结果写入：

```Plain
runtime-config/
```

​        这个目录不进 Git，Docker Compose 中也有独立 volume。这样 API 容器重启后配置不会丢，重新构建镜像也不会把密钥烤进镜像层。

### 62.6.3 让设置快照覆盖所有核心集成

​        继续打开 `api/app/application/app_settings_service.py`，把 Search 和 Sandbox 也加入设置快照：

```Python
def get_snapshot(self) -> AppSettingsSnapshot:
    """返回设置页需要展示的完整快照。"""

    modules = [
        self._build_llm_module(),
        self._build_search_module(),
        self._build_mcp_module(),
        self._build_a2a_module(),
        self._build_multi_agent_module(),
        self._build_sandbox_module(),
    ]
    return AppSettingsSnapshot(
        modules=[self._apply_override(module) for module in modules],
        integrations=list(self.integrations.values()),
    )
```

#### 62.6.3.1 业务流程

​        前端只请求一次：

```Plain
GET /api/config/app
```

​        后端就返回所有核心集成状态：

```Plain
LLM + Search + MCP + A2A + 多 Agent + Sandbox
```

​        这样设置页不需要到处分别请求多个接口，也不会出现页面上某个模块漏显示。

### 62.6.4 补充 Search 配置状态

​        在 `AppSettingsService` 中新增 `_build_search_module()`：

```Python
def _build_search_module(self) -> SettingsModule:
    api_key_configured = bool(settings.bing_search_api_key)
    return SettingsModule(
        key="search",
        name="Search",
        description="搜索工具配置，包括 Bing API 和页面搜索兜底。",
        enabled=True,
        default_item="bing-api" if api_key_configured else "page-fallback",
        status="ready" if api_key_configured else "warning",
        status_message=(
            "Bing API Key 已配置，搜索工具会优先调用官方 API。"
            if api_key_configured
            else "Bing API Key 未配置，搜索工具会使用页面搜索兜底，稳定性取决于网络。"
        ),
        source=".env",
        verify_command="curl http://localhost:8088/api/config/app",
        items=[
            {
                "name": "bing-api",
                "description": settings.bing_search_endpoint,
                "enabled": api_key_configured,
                "metadata": {
                    "market": settings.bing_search_market,
                    "api_key_env": "BING_SEARCH_API_KEY",
                    "configured": api_key_configured,
                },
            },
            {
                "name": "page-fallback",
                "description": "不需要密钥的页面搜索兜底，会解析公开搜索结果页。",
                "enabled": True,
                "metadata": {
                    "provider": "bing-page / duckduckgo-page",
                    "timeout_seconds": settings.search_timeout_seconds,
                },
            },
        ],
    )
```

#### 62.6.4.1 为什么这样设计

​        搜索工具有两种模式：

```Plain
Bing API Key 已配置 -> 优先走官方 API
Bing API Key 未配置 -> 走页面搜索兜底
```

​        页面搜索兜底适合课程和本地开发，但它依赖公开搜索页结构和网络状态，稳定性不如官方 API。

​        所以配置中心必须把这件事明说，不能让用户看到搜索失败时才猜原因。

### 62.6.5 补充 Sandbox 配置状态

​        在 `AppSettingsService` 中新增 `_build_sandbox_module()`：

```Python
def _build_sandbox_module(self) -> SettingsModule:
    browser_enabled = getenv("SANDBOX_BROWSER_ENABLED", "true").lower() == "true"
    vnc_enabled = getenv("SANDBOX_VNC_ENABLED", "true").lower() == "true"
    return SettingsModule(
        key="sandbox",
        name="Sandbox",
        description="文件、Shell、浏览器、截图和 VNC 的隔离执行环境。",
        enabled=True,
        default_item=settings.docker_sandbox_id,
        status="ready",
        status_message="Sandbox 连接信息已配置，运行时状态可通过沙箱接口验证。",
        source=".env / docker-compose.yml",
        verify_command="curl http://localhost:8088/api/sandboxes/current",
        items=[
            {
                "name": "file",
                "description": "读取、写入和同步会话附件到 Sandbox 工作目录。",
                "enabled": True,
                "metadata": {"base_url": settings.sandbox_api_base_url},
            },
            {
                "name": "shell",
                "description": "在 Sandbox 中执行命令并读取输出。",
                "enabled": True,
                "metadata": {
                    "wait_timeout_seconds": settings.sandbox_shell_wait_timeout_seconds,
                },
            },
            {
                "name": "browser",
                "description": "通过 Playwright 控制 Sandbox 浏览器。",
                "enabled": browser_enabled,
                "metadata": {"browser_env": "SANDBOX_BROWSER_ENABLED"},
            },
            {
                "name": "vnc",
                "description": "通过 noVNC 查看 Sandbox 浏览器远程桌面。",
                "enabled": vnc_enabled,
                "metadata": {"status_url": "/sandbox-api/vnc/status"},
            },
        ],
    )
```

#### 62.6.5.1 代码讲解

​        Sandbox 不是一个普通配置项，它是一组能力的集合：

```Plain
file
shell
browser
vnc
```

​        这些能力最终都会被 Agent 工具调用，所以配置中心要把它们放在一起展示。

​        这里的 `status="ready"` 表示“连接信息已经配置”。真实运行状态仍然要通过：

```Bash
curl http://localhost:8088/api/sandboxes/current
curl http://localhost:8088/sandbox-api/vnc/status
```

### 62.6.6 同步响应模型和路由转换

​        打开 `api/app/schemas/app_settings.py`，给响应模型增加字段：

```Python
class SettingsModuleResponse(BaseModel):
    key: str
    name: str
    description: str
    enabled: bool
    default_item: str | None
    items: list[SettingsItemResponse]
    status: str
    status_message: str
    source: str
    verify_command: str
```

​        同时把集成类型扩展为：

```Python
SettingsIntegrationKind = Literal[
    "llm",
    "search",
    "mcp",
    "a2a",
    "multi_agent",
    "sandbox",
]
```

​        打开 `api/app/presentation/http/routes/config.py`，在 `to_settings_module_response()` 中补上：

```Python
return SettingsModuleResponse(
    key=module.key,
    name=module.name,
    description=module.description,
    enabled=module.enabled,
    default_item=module.default_item,
    status=module.status,
    status_message=module.status_message,
    source=module.source,
    verify_command=module.verify_command,
    items=[...],
)
```

#### 62.6.6.1 为什么要同步三层

​        这里涉及三层：

```Plain
application dataclass
  |
  v
schema response model
  |
  v
route converter
```

​        只改应用服务不改 schema，接口会校验失败。

​        只改 schema 不改路由转换，前端收不到新字段。

​        所以这三处必须同步。

## 62.7 关键理解

​        本章最重要的是理解：

```Plain
功能可用 != 产品可用
```

​        代码里有 LLM 客户端，不代表用户知道自己有没有配 Key。

​        代码里有 MCP Client，不代表用户知道哪些 Server 已启用。

​        代码里有 A2A 调用，不代表用户知道远程 Agent 地址是什么。

​        代码里有 Sandbox，不代表用户知道浏览器、VNC、Shell 是否能跑。

​        配置中心解决的就是这个“可见性”问题。

## 62.9 常见问题

- 问题：Search 显示“待配置”是不是不能用？

​        解释：不是。它表示 `BING_SEARCH_API_KEY` 没有配置，系统会走页面搜索兜底。兜底模式能用于课程验证，但稳定性会受网络和搜索页结构影响。

- 问题：LLM API Key 保存在哪里？

​        解释：课程环境会写入 `runtime-config/llm.yaml`，这个目录被 `.gitignore` 排除，Docker Compose 中也使用独立 volume 持久化。生产环境建议改为加密数据库字段、KMS、Vault 或云厂商 Secret Manager。

- 问题：MCP/A2A 新增集成重启后还在吗？

​        解释：在 Docker Compose 中会保存在 `api_runtime_config` volume 里，普通重启不会丢。如果执行了 `docker compose down -v`，volume 会被删除，配置也会被清空。

- 问题：为什么不继续要求手动改 `.env` 或 YAML？

​        解释：真实产品里用户不应该进服务器手改配置文件。本章把 LLM、MCP、A2A 配置入口放进页面，让保存动作直接写入后端配置存储。

- 问题：Sandbox 显示 ready，但浏览器/VNC 仍然失败怎么办？

​        解释：配置中心显示的是连接配置是否存在。运行时还需要执行 `/api/sandboxes/current`、`/sandbox-api/vnc/status` 和浏览器工具任务验证。
