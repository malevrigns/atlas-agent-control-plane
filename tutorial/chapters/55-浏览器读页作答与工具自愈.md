# 第五十五章. 浏览器读页作答与工具自愈

## 55.1 本章目标

第十八章把 Playwright 塞进沙箱，让 Agent 能打开网页、能截图。但那套能力有一个很尴尬的边界：**浏览器动起来了，Agent 一个字也读不到。**

在对话里说"打开 https://example.com 读取网页内容，根据网页上的实际文字告诉我这个网站是干什么用的"，当前实现下 Agent 最多回答"页面已打开，标题是 Example Domain"。标题是 Playwright 顺手带回的元数据，不是网页内容。要它"根据网页信息作答"，它手里根本没有作答的原料。

同一次实测还顺带暴露了工具选择层的一批老毛病：模型反复打开同一个页面；分析步骤挑中 `draft_plan`，吐一段"1. 明确目标 2. 拆解步骤 3. 验证结果"的空话；多行 Python 被塞进 shell 单行命令，必然语法错误；模型把 `observable_summary` 混进 `arguments`，直接让整个任务崩掉。

这一章把这两件事一起做完：让浏览器能读，让工具选择能自愈。

完成本章后，你将能够：

- 在沙箱里实现一个"读正文"接口，并说清为什么用 `document.body.innerText` 而不是 `page.content()`；
- 设计一个 url 参数**可选**的 `browser_read` 工具，把"打开 + 读取"压成一步，显著降低模型的多步失误；
- 用 `truncated` / `total_chars` 让模型知道自己只看到了页面的一部分，而不是拿半截内容当全文；
- 给工具选择器写出可执行的工具使用准则，包括"同一网页不许读第二次"这种从实测里长出来的规则；
- 用 `step_history` + schema 白名单 + `write_content` 三件套，让 Agent 从自己的失败里爬出来，而不是一步失败整任务失败；
- 说清沙箱改代码后为什么必须重建镜像，以及 Windows 检出的 `*.sh` 为什么会让容器根本起不来。

## 55.2 第十八章留下的缺口

先看第十八章交付的浏览器工具集，一共四个：

```text
browser_status       查会话状态、当前地址、视口
browser_open         打开一个 URL，返回 url + title
browser_screenshot   截图，返回 PNG base64
browser_close        关掉会话
```

这四个工具背后是三层：主 API 的 `AgentTool` → `SandboxBrowserClient` → 沙箱的 `/browser/*` 路由 → Playwright/Chromium。链路本身没问题，问题在于**没有一个工具返回文字**。

`browser_open` 的输出格式是这样的：

```python
def _format_page(data: dict) -> str:
    return "\n".join(
        [
            f"页面已打开：{data.get('url')}",
            f"页面标题：{data.get('title') or '-'}",
        ]
    )
```

两行。这两行会进 `tool_called` 事件，会进最终回答的证据块。模型看到的全部素材就是一个 URL 加一个标题。所以它给出的回答只能是"我已经打开了 example.com，页面标题是 Example Domain"——这句话是真的，但它没有回答用户的问题。

`browser_screenshot` 更不解决问题。它返回的是 base64 PNG，进 JSON 结构给前端渲染缩略图。文本模型看不懂 base64，`_summarize_tool_output` 对它的处理是"已完成浏览器截图，图片大小约 45 KB"。**截图是给人看的，不是给模型读的。**

除了读不到内容，第十八章到第二十八章这条链路上还积了四个毛病，实测里全部命中：

**问题一：反复打开同一个页面。** 计划拆出三步"打开页面 / 提取信息 / 总结"，工具选择器对每一步单独判断，三步全部命中 `browser_open`，同一个 URL 打开三次。选择器根本不知道第一步已经打开过了。

**问题二：分析步骤挑中模板工具。** `draft_plan`、`summarize_text`、`extract_keywords` 是第十二章为了让课程本地可跑而写的确定性工具，输出是固定模板拼字符串。它们出现在工具注册表里，模型就会选它们，然后一个"分析该网站用途"的步骤产出"1. 明确目标：确认"分析该网站用途"的最终交付物。"这种零信息量的文本。

**问题三：多行代码塞进 shell 单行命令。** 模型选 `shell_run`，参数里塞 `python3 -c "import json\nfor i in range(3):\n    print(i)"`。这在 shell 里是必然的语法错误，重试多少次都一样。

**问题四：参数里混进协议字段。** 工具选择器要求模型返回 `{"tool_name":..., "arguments":{...}, "observable_summary":"..."}`。模型有相当比例会把 `observable_summary` 也写进 `arguments` 里。而 `AgentTool._validate_arguments` 是严格的：

```python
declared_names = {parameter.name for parameter in self.definition.parameters}
unexpected = sorted(set(arguments) - declared_names)
if unexpected:
    raise AppException(
        message=f"unexpected tool arguments: {', '.join(unexpected)}",
        code=400,
        status_code=400,
    )
```

一个多余的键，`unexpected tool arguments: observable_summary`，整步抛异常，`ReActAgentService` 的 try/except 兜住，写一条 `task_error`，**整个任务结束**。用户看到的是一次彻底失败，而模型其实只是多写了一个说明字段。

## 55.3 沙箱侧：读取页面正文

### 为什么是 innerText，不是 content()

Playwright 给了两条读页面的路：

- `page.content()` 返回序列化后的完整 HTML；
- `page.evaluate("document.body.innerText")` 返回渲染后的可见文本。

选 innerText，理由有三条，都很实在。

**第一，innerText 天然过滤噪音。** 它是浏览器渲染引擎给出的结果，`<script>`、`<style>`、`<meta>` 里的内容不会出现，`display:none` 的元素也不会出现。HTML 全文里这些东西能占到七八成。

**第二，innerText 最接近人眼所见。** 用户问的是"网页上的实际文字"。innerText 就是浏览器实际画在屏幕上的那些字，顺序和视觉顺序一致，块级元素之间自带换行。HTML 全文里一句话可能被十几个 `<span>` 切碎，模型要重新拼。

**第三，token 成本差一个数量级。** 一个普通新闻页的 HTML 常在 300 KB 以上，innerText 通常只有几 KB。把整页 HTML 塞进模型既贵又没用，还会把真正的正文淹没在标签海里——这是典型的"上下文污染"。

代价是丢掉了结构信息（链接的 href、表格的行列关系、图片的 alt）。对"根据网页内容作答"这个目标，这个代价可以接受。真需要结构化抽取，那是另一个工具的事。

### schema：把截断状态显式回传

`backend/sandbox/app/schemas/browser.py` 新增一对请求/响应模型：

```python
class BrowserTextRequest(BaseModel):
    max_chars: int = Field(default=8000, ge=200, le=60000)  # 返回正文的最大字符数。


class BrowserTextResponse(BaseModel):
    url: str  # 读取正文时的页面地址。
    title: str  # 页面标题。
    text: str  # 页面可见正文（body.innerText，截断到 max_chars）。
    total_chars: int  # 截断前的正文总字符数。
    truncated: bool  # 是否发生截断。
```

`total_chars` 和 `truncated` 这两个字段是本章的一个关键设计。截断本身不可避免——正文可能十万字，不能全塞给模型。但**不告诉模型它被截断了，比截断本身危险得多**：模型会默认自己读到的是全文，然后基于半截内容给出"该页面共讲了三点"这种断言。把截断状态显式回传，模型至少有机会说"页面较长，以下结论基于前 8000 字"。

`max_chars` 用 `Field(ge=200, le=60000)` 夹在合理区间。下限 200 是因为再小就读不出任何有效信息；上限 60000 是防止一次请求把整个上下文预算烧光。

### service：读取、清洗、截断

`backend/sandbox/app/services/browser_service.py` 新增 `page_text` 方法：

```python
    # ===================== 第3.5步：读取页面正文 =====================
    async def page_text(self, max_chars: int = 8000) -> BrowserTextResponse:
        """读取当前页面的可见正文，供 Agent 依据网页内容作答。

        用 innerText 而不是 content()：前者是渲染后的可见文本，
        天然过滤 script/style 和隐藏元素，最接近人眼读到的内容。
        """
        runtime = await self._ensure_runtime()
        try:
            text = await runtime.page.evaluate(
                "() => document.body ? document.body.innerText : ''"
            )
        except PlaywrightError as exc:
            raise SandboxException(message=f"failed to read page text: {exc}") from exc

        clean_text = "\n".join(
            line.rstrip() for line in str(text).splitlines() if line.strip()
        )
        total_chars = len(clean_text)
        truncated = total_chars > max_chars
        return BrowserTextResponse(
            url=runtime.page.url,
            title=await self._safe_title(runtime.page) or "",
            text=clean_text[:max_chars],
            total_chars=total_chars,
            truncated=truncated,
        )
```

有四个细节值得说。

**`document.body ? ... : ''` 的三元判断。** 页面还没加载 body（about:blank、导航中断、纯 XML 响应）时 `document.body` 是 `null`，直接取 `.innerText` 会在页面上下文里抛 `TypeError`，Playwright 把它包成 `PlaywrightError` 冒上来。返回空串比抛异常好——空正文是一个合法的观察结果，不是错误。

**空行清洗。** `innerText` 在有大量空 `<div>` 的页面上会产生成片的连续空行，有些页面空行数量比正文行数还多。`if line.strip()` 直接丢掉纯空白行，`line.rstrip()` 去掉行尾空格。这一步在真实页面上通常能省掉 20% 到 40% 的字符。

**先清洗，再算 total_chars。** `total_chars` 是**清洗后**的长度，不是原始 innerText 的长度。这样 `total_chars` 和 `text` 用的是同一把尺子，`truncated` 的判断才是准的。

**复用 `_ensure_runtime`。** 第十八章写的这个方法在浏览器没启动时自动 `start()` 一次：

```python
    async def _ensure_runtime(self) -> BrowserRuntime:
        # BrowserTool 调用前可以显式 start；如果忘记启动，这里自动启动一次。
        if self._runtime is None:
            await self.start()
        if self._runtime is None:
            raise SandboxException(message="browser session is not available")
        return self._runtime
```

`page_text` 直接吃到这个便利：即使 Agent 没调过 `browser_status`、没调过任何导航，直接 `browser_read` 也能工作——只不过读到的是 `about:blank` 的空正文。真正的价值是配合下一节的"传 url 就先导航"逻辑：一次调用就能从零启动浏览器、打开页面、读出正文。

### route：一条 POST

`backend/sandbox/app/api/routes/browser.py` 加一个路由：

```python
@router.post("/page/text", response_model=ApiResponse[BrowserTextResponse])
async def read_page_text(
    payload: BrowserTextRequest,
    service: SandboxBrowserService = Depends(get_browser_service),
) -> ApiResponse[BrowserTextResponse]:
    # 返回当前页面可见正文，Agent 依据它回答与网页内容相关的问题。
    return ApiResponse(data=await service.page_text(payload.max_chars))
```

用 POST 而不是 GET，是因为 `max_chars` 属于请求参数而不是资源定位符，而且未来还要往这个请求里加选择器、区域裁剪之类的参数。放在 body 里比堆 query string 干净。路由层依然只做转发，会话状态全部在模块级的 `browser_service` 里——这是第十八章定下的规矩，跨请求保持浏览器会话。

## 55.4 主 API 侧：客户端与 browser_read 工具

### 客户端方法

`backend/api/app/infrastructure/sandbox/browser_client.py` 加一个方法，和其它方法一样只是一次转发：

```python
    def page_text(self, max_chars: int = 8000) -> dict[str, Any]:
        return self._request(
            "POST",
            "/browser/page/text",
            json={"max_chars": max_chars},
        )
```

真正干活的是第十八章就写好的 `_request`，它把沙箱的 `ApiResponse` 信封拆开并把非 200 的 `code` 也当错误：

```python
        if response.status_code >= 400 or payload.get("code") != 200:
            raise AppException(
                message=str(payload.get("message") or "sandbox browser request failed"),
                code=int(payload.get("code") or response.status_code),
                status_code=response.status_code,
            )
```

注意这个 `or`：沙箱可能返回 HTTP 200 但 `code: 500`（`SandboxException` 走的就是这条路），只看 HTTP 状态码会把失败当成功。`page_text` 里 Playwright 抛出的 `failed to read page text: ...` 就是通过这条分支变成主 API 的 `AppException`，最终变成一条带原文的 `task_error`。

### browser_read：url 参数必须可选

工具注册在 `backend/api/app/infrastructure/agent_tools/sandbox_browser.py`：

```python
    registry.register(
        AgentTool(
            definition=ToolDefinition(
                name="browser_read",
                description=(
                    "读取网页正文内容用于作答：传入 url 时先打开该网页再读取；"
                    "不传 url 则读取当前已打开页面。返回页面可见文本，"
                    "适合'根据网页内容回答问题/提取信息/总结页面'类步骤。"
                ),
                risk_level=ToolRiskLevel.medium,
                required_permissions=("network:access", "browser:read"),
                parameters=[
                    ToolParameter(
                        name="url",
                        type="string",
                        description="要读取的网页地址；留空表示读取当前页面。",
                        required=False,
                    ),
                    ToolParameter(
                        name="max_chars",
                        type="number",
                        description="返回正文的最大字符数，默认 8000。",
                        required=False,
                    ),
                ],
            ),
            handler=lambda url="", max_chars=8000: _read_page(
                browser_client, url, max_chars
            ),
        )
    )
```

**`url` 设成 `required=False` 是本章最重要的一个工具设计决策。** 它带来两种用法：

```text
browser_read(url="https://example.com")   打开 + 读取，一步完成
browser_read()                            读当前页，用于翻页/交互之后
```

为什么这样能显著减少模型失误？因为它把一个必然的两步序列压成一步。原来模型必须先出 `browser_open`，下一步再出某个读取工具——**中间隔着一次完整的工具选择**，而每一次工具选择都是一次可能失误的机会：可能选错工具，可能忘了带 URL，可能因为不知道页面已打开而重复导航。步骤数减少一半，失误率不是线性下降而是明显更好。

同时保留"不传 url"这条路，是因为将来有了点击、滚动、输入这些交互工具后，"操作完再读一次当前页"是刚需，那时候强制传 url 反而会把页面导航回初始状态，把交互结果冲掉。

`description` 里写"适合'根据网页内容回答问题/提取信息/总结页面'类步骤"，不是装饰。整个 `ToolDefinition` 会被 `_render_tool_schema` 序列化成 JSON 塞进工具选择器的 system prompt，**description 就是模型判断该不该选这个工具的主要依据**。写"读取网页"不如写清楚它适配哪一类步骤描述。

`risk_level` 设为 `medium` 且要 `network:access` 权限，和 `browser_open` 一致——它确实会发起外网请求。

### _read_page：拼装带表头的输出

```python
def _read_page(client: SandboxBrowserClient, url: object, max_chars: object) -> str:
    """打开（可选）并读取页面正文，输出带来源信息的纯文本。"""

    clean_url = str(url or "").strip()
    if clean_url:
        client.navigate(url=clean_url)
    limit = _to_int(max_chars, default=8000, low=200, high=60000)
    data = client.page_text(max_chars=limit)
    header = [
        f"页面地址：{data.get('url')}",
        f"页面标题：{data.get('title') or '-'}",
    ]
    if data.get("truncated"):
        header.append(
            f"（正文共 {data.get('total_chars')} 字，已截断到前 {limit} 字）"
        )
    return "\n".join([*header, "", "页面正文：", str(data.get("text") or "(页面无可见文本)")])
```

`str(url or "")` 看着啰嗦，但它是必需的。`AgentTool._validate_arguments` 对可选参数的处理是这样的：

```python
        for parameter in self.definition.parameters:
            value = arguments.get(parameter.name)
            ...
            checked[parameter.name] = value
```

**没传的可选参数也会以 `None` 落进 `checked`**，然后 `handler(**checked_arguments)` 把 `url=None` 传进来，lambda 的默认值 `url=""` 根本轮不到生效。`str(None or "")` 得到 `""`，`str(None)` 得到 `"None"` ——后者会让工具去导航到 `https://None`。一个字符之差。

输出格式刻意做成"页面地址 / 页面标题 / （截断提示）/ 空行 / 页面正文："这样的表头结构，有三个用处：

**一，给模型标注来源。** 最终回答生成时，模型手里可能有搜索结果、文件内容、多个页面的正文。每段正文顶上有"页面地址"，模型才能在回答里写出"根据 https://example.com 的说明……"，引用体系（第四十一章）也才有的可依。

**二，让 `_summarize_tool_output` 能提取摘要。** `ReActAgentService` 的摘要器是按"标签：值"格式做行匹配的：

```python
        if tool_name.startswith("browser_"):
            page_title = self._match_line_value(output, "页面标题")
            ...
            if page_title:
                return f"浏览器已打开页面，页面标题为：{page_title}。"
```

`browser_read` 复用 `browser_` 前缀这条分支，只要输出里有 `页面标题：` 这一行就能被摘要。（顺带一提：这条分支的措辞现在对 `browser_read` 有点不准，它会说"已打开页面"而不是"已读取正文"。这个偏差只影响步骤历史里的一行摘要，不影响最终回答的素材——原因见 55.6。）

**三，截断提示写在正文前面而不是后面。** 模型读长上下文时对开头的注意力最强。把"已截断"放在正文末尾，很可能被忽略。

### _to_int：为什么需要一个专门的夹取函数

```python
def _to_int(value: object, default: int, low: int, high: int) -> int:
    try:
        number = int(float(str(value)))
    except (TypeError, ValueError):
        return default
    return max(low, min(high, number))
```

三层防御，每一层都对应一个真实输入：

**`float(str(value))` 的两次转换。** `max_chars` 在 `ToolParameter` 里声明的是 `type="number"`，而 `AgentTool._coerce_value` 对 `number` 的处理是 `return float(value)` ——**参数到达 handler 时已经是 `8000.0` 这个浮点数了**，`int("8000.0")` 会直接抛 `ValueError`。先 `float` 再 `int` 才吃得下。同时它也顺手吃下了模型直接写字符串 `"8000"` 的情况。

**`except` 返回默认值。** 参数没传时是 `None`，`float("None")` 抛 `ValueError`，落回 8000。模型写了 `"最大"` 这种鬼话也一样落回默认值，而不是让整步失败。

**`max(low, min(high, number))` 的夹取。** 沙箱侧的 `Field(ge=200, le=60000)` 是 Pydantic 校验，超界会返回 422，那是一次浪费掉的往返。在主 API 侧先夹一次，模型写 `max_chars=999999` 时静默收敛到 60000 而不是报错。**能就地修正的输入不要用报错回应模型**——这是本章后半段"工具自愈"的同一条思路。

## 55.5 工具选择准则升级

第二十八章的 `ModelToolSelectionService` 已经把工具 schema 注入 system prompt 让模型输出结构化 tool call。但只给 schema 不够——schema 告诉模型每个工具**能做什么**，不告诉它**什么时候该用哪个、什么时候不该用**。缺的这部分要写成显式准则。

现在的 system prompt 里有六条准则，逐条都对应一个实测踩过的坑：

```python
                            "工具使用准则：\n"
                            "1. 分析、推演、解释、撰写这类纯思考步骤（不需要外部操作）必须用 "
                            "write_content，并把该步骤要产出的具体内容要求完整写进 task 参数；"
                            "严禁使用 draft_plan / summarize_text / extract_keywords 这类模板工具，"
                            "它们只会输出无信息量的固定文本。\n"
                            "2. 执行多行代码时，禁止塞进 shell 单行命令（python -c 多行必然语法错误）；"
                            "正确做法：先用 file_write 把完整代码写入脚本文件（如 main.py），"
                            "下一步再用 shell_run 执行 `python3 main.py`。\n"
                            "3. 上下文里已有此前步骤的执行结果；根据当前步骤的目的选择工具，"
                            "不要重复做已完成的事（例如页面已打开就不要再 browser_open）。\n"
                            "4. 若历史里有 ⚠️ 失败 的步骤，本步优先补救：缺文件就先写文件，"
                            "写完的脚本还没成功执行就再次执行，然后才继续原步骤目标。"
                            "严禁执行尚未创建的脚本文件。\n"
                            "5. 需要根据网页内容回答问题、提取网页信息或总结页面时，"
                            "必须用 browser_read（可直接传 url，一步完成打开+读取正文），"
                            "然后基于返回的正文作答；同一网页的正文已经出现在步骤历史里时，"
                            "严禁再次 browser_read，后续分析/总结步骤直接用 write_content 引用已读内容。"
                            "browser_open 只用于确认页面可达或为截图做准备；"
                            "截图必须用 browser_screenshot；查会话状态用 browser_status。\n"
                            "6. 文件读写用 file_read / file_write，路径相对于沙箱工作目录。\n\n"
```

第五条是本章新加的，也是最长的一条。它做了四件事：

**指定入口。** "需要根据网页内容回答问题、提取网页信息或总结页面时，必须用 browser_read"——把一类步骤描述直接映射到一个工具。

**给出捷径。** "可直接传 url，一步完成打开+读取正文"——55.4 的设计只有写进 prompt，模型才会真的用它。

**禁止重复读。** 这条是实测逼出来的。第一版 E2E 里，计划拆成"打开并读取页面 / 提取网站用途相关信息 / 组织回答"三步，模型对后两步都判断"我需要网页内容"，于是**连着 `browser_read` 了三次同一个 URL**。三次调用、三份几乎一样的正文进上下文、三倍延迟，最后一步才开始写回答。加上这句之后，第二步和第三步改用 `write_content`，直接引用步骤历史里已经读到的正文。

**给旧工具划定边界。** `browser_open` 不能删（确认可达性、为截图准备页面都需要它），但必须明确它"不是用来获取内容的"，否则模型会在两个工具间反复横跳。

准则要写得可执行，这一点值得单独强调。对比这两种写法：

```text
差：合理使用浏览器工具。
好：同一网页的正文已经出现在步骤历史里时，严禁再次 browser_read，
    后续分析/总结步骤直接用 write_content 引用已读内容。
```

第一种模型无法据此做出任何具体判断。第二种给了触发条件（正文已在历史里）、禁止动作（再次 browser_read）、替代方案（write_content 引用）。**准则里的每一句都应该能翻译成"在什么情况下、不做什么、改做什么"。**

同时，`_select_with_rules` 这条 fallback 路径保持不变——它仍然是关键词规则，仍然会在"网页/浏览器/打开"命中时选 `browser_open`。这是有意的：fallback 的价值在于**模型完全不可用时课程本地仍能跑通**，它不需要聪明，只需要确定。真实运行里只要 LLM 可用就走不到它。

## 55.6 自愈之一：step_history 把失败喂回选择器

工具选择器每一步都是无状态的：给它任务文本和压缩上下文，让它输出一个 tool call。它不知道上一步干了什么，更不知道上一步失败了。`step_history` 就是补这个洞的。

`ReActAgentService` 在循环里维护一个字符串列表：

```python
        created_events: list[SessionEvent] = []
        step_history: list[str] = []
        ...
        try:
            for index, step in enumerate(steps, start=1):
                ...
                step_events = await self._execute_step(
                    session_id=session_id,
                    plan=plan,
                    step=step,
                    index=index,
                    memory_context=memory_context,
                    agent_context=agent_context,
                    step_history=step_history,
                )
                created_events.extend(step_events)
                self._append_step_history(step_history, index, step, step_events)
```

`_execute_step` 把它拼进给工具选择器的上下文：

```python
        step_context = agent_context
        if step_history:
            history_text = "\n".join(step_history)
            step_context = (
                f"{agent_context}\n\n本轮已完成步骤的结果（不要重复做）：\n{history_text}"
                if agent_context
                else f"本轮已完成步骤的结果（不要重复做）：\n{history_text}"
            )
```

真正有意思的是 `_append_step_history` 里的失败标记：

```python
    def _append_step_history(
        self,
        step_history: list[str],
        index: int,
        step: dict,
        step_events: list[SessionEvent],
    ) -> None:
        """把刚完成步骤的工具与观察摘要追加进历史，供后续步骤选择工具时参考。"""

        for event in step_events:
            if event.type is not SessionEventType.tool_called:
                continue
            tool_name = str(event.payload.get("tool_name") or "")
            output = str(event.payload.get("output") or "")
            summary = self._summarize_tool_output(tool_name, output)
            # 失败信号显式标注（工具状态非成功，或 shell 非零退出码），
            # 后续步骤的工具选择器会优先修复而不是机械推进。
            failed = str(event.payload.get("status") or "") not in {"", "success", "succeeded"}
            if tool_name.startswith("shell_"):
                return_code = self._match_line_value(output, "退出码")
                if return_code and return_code != "0":
                    failed = True
            prefix = "⚠️ 失败" if failed else "已完成"
            step_history.append(
                f"- 步骤{index}「{step.get('title', '')}」{prefix}（{tool_name}）："
                f"{self._trim_text(summary, 200)}"
            )
```

三个设计点。

**两套失败判定。** 第一套看 `ToolInvocationStatus`，覆盖权限拒绝、超时、异常。第二套专门给 shell：`shell_run` 执行 `python3 main.py` 时脚本报错，**工具本身是成功的**（命令跑完了，有输出），只有退出码是 1。不额外看退出码，一次失败的脚本执行会被记成"已完成"，后续步骤就会心安理得地去读一个根本没生成的结果文件。

**用醒目标记而不是结构化字段。** `⚠️ 失败` 这几个字符最终是拼进一段自然语言 prompt 的。给模型看的东西，视觉显著性就是有效的——纯文本里一个 emoji 前缀比 `"status": "failed"` 更容易被注意到。这和给人看日志是一个道理。

**摘要限长 200 字。** `_trim_text(summary, 200)` 保证十步的历史也就两千字。历史是给工具选择用的**导航信息**，不是证据。真正的证据在别处。

这里必须说清一件容易搞混的事：**页面正文不是通过 step_history 进入最终回答的。** step_history 里 `browser_read` 那一条只有一句"浏览器已打开页面，页面标题为：Example Domain。"正文进入最终回答走的是另一条路——`_build_final_answer_evidence`：

```python
            block_lines = [
                f"## {title}",
                f"- 工具：{tool_name}",
                f"- 参数：{json.dumps(arguments, ensure_ascii=False)}",
                f"- 摘要：{summary}",
            ]
            ...
            block_lines.extend(["- 原始观察摘录：", self._trim_text(output, 900)])
```

`原始观察摘录` 带的是**工具的原始输出**，截到 900 字。`browser_read` 返回的页面正文正是从这里进入最终回答生成的。两条链路各司其职：step_history 负责"别重复、先补救"，evidence 负责"拿什么作答"。

配套的是第四条准则："若历史里有 ⚠️ 失败 的步骤，本步优先补救"。这两件事必须成对出现——只标记不给指令，模型会看到失败然后继续按原计划走；只给指令不标记，模型不知道哪一步失败了。有了这一对，Agent 才第一次具备了"从自己的失败里爬出来"的能力：脚本没写成功，下一步重新写；写了没执行成功，下一步重新执行。

## 55.7 自愈之二：按 schema 白名单清洗 arguments

回到 55.2 的问题四：模型把 `observable_summary` 塞进 `arguments`，`AgentTool` 抛 `unexpected tool arguments`，整个任务失败。

这个失败有多冤枉，值得说透。模型选对了工具，填对了所有真参数，只是**多写了一个它自己被要求输出的说明字段**。为了这个，用户的整个任务终止了。

修复点在 `_repair_arguments` 的第一句：

```python
    def _repair_arguments(
        self,
        *,
        tool: AgentTool,
        arguments: dict[str, Any],
        task_text: str,
        agent_context: str,
    ) -> dict[str, Any]:
        """在 AgentTool 校验前清洗多余参数并补齐可推断参数。

        模型偶尔会把协议字段（observable_summary / tool_name）或臆造的
        键混进 arguments；严格校验会因此拒绝整次调用。这里先按工具
        schema 白名单过滤，小偏差不应毁掉整个任务。
        """

        allowed_names = {parameter.name for parameter in tool.definition.parameters}
        repaired = {
            key: value for key, value in arguments.items() if key in allowed_names
        }
```

四行代码。**白名单来自工具定义本身**，不是硬编码的黑名单——这一点很重要。写 `if key != "observable_summary"` 只能挡住已知的那一个字段；模型下次可能塞 `reason`、`thought`、`why`、`step_id`，黑名单永远追不上。用 `tool.definition.parameters` 生成白名单，任何工具定义之外的键一律丢弃，一劳永逸。

白名单过滤之后是补齐逻辑，第二十八章就有：

```python
        for parameter in tool.definition.parameters:
            value = repaired.get(parameter.name)
            if not parameter.required or value not in (None, ""):
                continue

            if parameter.name in {"query", "q"}:
                repaired[parameter.name] = self._extract_search_query(task_text)
            elif parameter.name in {"text", "task", "message"}:
                repaired[parameter.name] = text_with_context
            elif parameter.name == "url":
                repaired[parameter.name] = self._extract_url(task_text)
            ...
```

`if not parameter.required or value not in (None, ""): continue` 这一句决定了补齐只管必填参数。`browser_read` 的 `url` 和 `max_chars` 都是可选的，不会被这里碰到——模型没传 url 就是"读当前页"的合法意图，替它猜一个 URL 反而是错的。

**这里有一条通用原则值得记住：在严格校验的前一步做宽容修正。** `AgentTool._validate_arguments` 必须严格，它是工具执行的最后一道闸；但闸门之前应该有一层清洗，把模型的格式抖动吸收掉。严格校验保证正确性，宽容修正保证鲁棒性，两者不矛盾，只是位置不同。

## 55.8 自愈之三：用 write_content 替掉模板工具

第一条准则要求分析/撰写步骤用 `write_content`，前提是这个工具真的存在。它在 `backend/api/app/infrastructure/agent_tools/builtin.py`：

```python
# ===================== 第3.5步：真实内容生成工具 =====================
@agent_tool(
    name="write_content",
    description=(
        "用大模型完成分析、推演、解释或撰写类步骤，产出真实的 Markdown 内容。"
        "适用于不需要外部操作（沙箱/浏览器/搜索）的思考型步骤。"
    ),
    parameter_descriptions={
        "task": "本步骤要产出的内容要求，包含必要的上下文与约束。",
    },
)
async def write_content(task: str) -> str:
    """调用配置的 LLM 真实生成内容；模型不可用时明确说明。

    draft_plan/summarize_text 是教学用的确定性工具，输出是无信息量的
    模板文本；分析与撰写类步骤必须由这个工具产出真实内容。
    """

    from app.application.llm_service import LLMService
    from app.core.exceptions import AppException
    from app.domain.llm.entities import LLMMessage

    try:
        result = await LLMService().chat(
            messages=[
                LLMMessage(
                    role="system",
                    content=(
                        "你是 AtlasAgent 的内容执行器，负责完成任务计划中的一个分析/撰写步骤。"
                        "直接产出该步骤要求的实质内容（Markdown），"
                        "不要复述步骤名称，不要输出与内容无关的过程说明。"
                    ),
                ),
                LLMMessage(role="user", content=task),
            ],
            temperature=0.3,
            max_tokens=2500,
        )
        return result.content.strip() or "（模型没有返回内容）"
    except AppException as error:
        return f"（内容生成失败：{error.message}）"
```

对比一下它要替掉的东西：

```python
def draft_plan(task: str) -> str:
    """生成固定格式的计划草稿。"""

    return "\n".join(
        [
            f"1. 明确目标：确认“{task}”的最终交付物。",
            "2. 拆解步骤：列出需要完成的关键阶段。",
            "3. 验证结果：检查输出是否满足目标和约束。",
        ]
    )
```

`draft_plan` 是第十二章为了让工具协议在无 API Key 环境下也能演示而写的确定性工具。它没错，但它**不该出现在真实任务的执行路径上**。无论 task 是什么，输出永远是那三行。一个"分析这个网站的用途"步骤命中它，产出的就是"1. 明确目标：确认"分析这个网站的用途"的最终交付物。"——用户看到这句话会认为这个 Agent 是个笑话。

三个实现细节：

**`temperature=0.3`。** 比工具选择器的 0.1 高，比创作场景低。内容生成需要一点表达自由度，但不需要发散。

**函数内延迟导入。** `LLMService` 在函数体里 import，避免模块加载期的循环依赖——`builtin.py` 被应用层导入，而 `LLMService` 也在应用层。

**异常返回文本而不是抛出。** `except AppException` 之后返回 `（内容生成失败：...）` 字符串。这样这一步在事件流里是"成功执行了工具、工具说自己失败了"，任务继续往下走，后续步骤还有机会补救；抛异常则整个任务终止。这和 55.7 是同一条思路的两个应用。

顺带解决第三个老毛病——多行代码。第二条准则给出的是一个明确的两步序列：

```text
第一步：file_write  path=main.py   content=<完整多行代码>
第二步：shell_run   command=python3 main.py
```

`python3 -c` 传多行代码在 shell 里必然出问题：换行符被 shell 吃掉，Python 缩进结构崩掉。**这不是模型能力问题，是通道能力问题**——不该指望模型把多行代码正确转义成单行，该给它一条不需要转义的路。写文件、执行文件，就是那条路。

## 55.9 镜像重建与容器重启

沙箱的 Dockerfile 用的是 `COPY`：

```dockerfile
COPY app ./app
COPY scripts ./scripts
RUN chmod +x ./scripts/start.sh
```

`COPY` 意味着代码在**构建期**被固化进镜像层。改了 `browser_service.py` 之后，`docker compose restart sandbox` 重启的还是旧镜像里的旧代码。这一点在开发主 API 时不明显（主 API 也是 COPY，但你可能一直在本地跑 uvicorn），到了沙箱这里就必须显式重建。

正确的流程：

```bash
# 1. 重建沙箱镜像（只重建 sandbox，不动其它服务）
docker compose build sandbox

# 2. 用新镜像重建容器并启动
docker compose up -d --force-recreate sandbox

# 3. 确认新路由已经生效
docker compose exec sandbox curl -s -o /dev/null -w '%{http_code}\n' \
  -X POST http://127.0.0.1:8100/api/browser/page/text \
  -H 'Content-Type: application/json' -d '{"max_chars":500}'
```

第三步返回 `200` 就说明新代码进去了；返回 `404` 说明还在跑旧镜像，回第一步。

如果主 API 侧也改了（本章改了 `browser_client.py`、`sandbox_browser.py`、`tool_selection_service.py`），一起重建：

```bash
docker compose build api sandbox
docker compose up -d --force-recreate api sandbox
docker compose logs -f --tail=50 sandbox
```

一个能省很多时间的经验：**沙箱镜像的重建是分层的。** Dockerfile 里 `playwright install --with-deps chromium` 这一层在 `COPY app ./app` 之前，只要 `pyproject.toml` 和 `uv.lock` 没变，Chromium 那几百 MB 就命中缓存不会重下。所以只改 Python 代码时，`docker compose build sandbox` 通常十几秒就完成。如果你发现每次都在重新下载 Chromium，检查是不是有什么东西让上层缓存失效了。

## 55.10 本章验收

### 一、直接打沙箱接口

先绕过 Agent，确认接口本身是通的。沙箱通过 Nginx 的 `/sandbox-api` 前缀暴露，密钥在 `.env` 里：

```bash
ATLAS_KEY="$(sed -n 's/^ATLAS_API_KEY=//p' .env | tail -n 1)"
BASE="http://127.0.0.1:8088/sandbox-api"

# 1. 打开页面
curl -s -X POST "${BASE}/browser/page/navigate" \
  -H 'Content-Type: application/json' \
  -H "X-Atlas-API-Key: ${ATLAS_KEY}" \
  -d '{"url":"https://example.com","wait_until":"domcontentloaded"}'

# 2. 读正文
curl -s -X POST "${BASE}/browser/page/text" \
  -H 'Content-Type: application/json' \
  -H "X-Atlas-API-Key: ${ATLAS_KEY}" \
  -d '{"max_chars":2000}'
```

第二条应返回：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "url": "https://example.com/",
    "title": "Example Domain",
    "text": "Example Domain\nThis domain is for use in illustrative examples in documents. You may use this domain in literature without prior coordination or asking for permission.\nMore information...",
    "total_chars": 183,
    "truncated": false
  }
}
```

重点看三处：`text` 里没有任何 HTML 标签；没有空行；`truncated` 为 `false` 且 `total_chars` 小于 `max_chars`。

再验一次截断行为，把 `max_chars` 压到最小：

```bash
curl -s -X POST "${BASE}/browser/page/text" \
  -H 'Content-Type: application/json' \
  -H "X-Atlas-API-Key: ${ATLAS_KEY}" \
  -d '{"max_chars":200}'
```

`truncated` 应变成 `true`，`total_chars` 仍是 183——等等，183 小于 200，所以这里 `truncated` 仍是 `false`。想看到截断，换一个长一点的页面，或者直接读 `max_chars` 边界值 200 以下会被 Pydantic 拒成 422，这本身也是一条该验的行为。

### 二、端到端对话验收

在 Web 端（`http://localhost:8088`）新建会话，发这句话：

```text
打开 https://example.com 读取网页内容，根据网页上的实际文字告诉我这个网站是干什么用的
```

应该依次看到：

1. **计划事件**：Planner 拆出若干步骤，第一步是打开并读取页面。
2. **`tool_called` 事件，工具名 `browser_read`**，参数里带 `url`。展开工具输出，应看到：

```text
页面地址：https://example.com/
页面标题：Example Domain

页面正文：
Example Domain
This domain is for use in illustrative examples in documents. You may use this domain in literature without prior coordination or asking for permission.
More information...
```

3. **后续分析步骤用的是 `write_content`，不是第二次 `browser_read`。** 这是 55.5 第五条准则的直接验收点。如果这里又出现一次 `browser_read`，说明准则没进 prompt，或者步骤历史没拼进上下文。
4. **最终回答完全基于正文。** 实测的回答准确复述了 example.com 是"用于文档示例的保留域名，可以在文献中直接使用而无需事先协调或申请许可"。这句话在页面正文里有明确出处，不是模型的先验知识——把 URL 换成一个模型训练时不可能见过的内网页面，回答应该同样准确，这才是真正的验收。

对照第十八章的行为：同样的提问，旧实现的回答只能是"已打开页面，标题为 Example Domain"。**这就是这一章的全部意义。**

### 四、逐项确认清单

- 沙箱 `POST /browser/page/text` 返回 200，`text` 无 HTML 标签、无空行；
- `max_chars` 传 100 返回 422（低于 `ge=200`），传 999999 返回 422（高于 `le=60000`）；
- 主 API 侧 `browser_read` 不传 url 时读当前页，不会导航到 `https://None`；
- 对话里一次 `browser_read` 完成打开 + 读取，事件面板能看到完整正文；
- 同一页面在一次任务里只被 `browser_read` 一次；
- 分析类步骤用 `write_content`，输出是真实内容而不是三行模板；
- 故意让一步失败（例如让计划先执行一个不存在的脚本），下一步应看到工具选择转向补救而不是继续推进。

## 55.11 常见坑

**坑一：Windows 检出的 `*.sh` 是 CRLF，容器根本起不来。** 沙箱的 `CMD ["./scripts/start.sh"]` 指向一个 `#!/usr/bin/env bash` 开头的脚本。Git 在 Windows 上默认 `core.autocrlf=true`，检出时把 LF 换成 CRLF，行尾那个 `\r` 就变成了解释器名字的一部分——Linux 内核去找一个叫 `bash\r` 的程序，找不到，容器直接退出。报错通常长这样：

```text
exec ./scripts/start.sh: no such file or directory
: not found/start.sh: 1:
```

第二行那个诡异的空标签就是 `\r` 把光标打回行首造成的。解法是在仓库根加 `.gitattributes`：

```gitattributes
# Shell 脚本必须保持 LF：Windows 上 checkout 成 CRLF 会让容器内的
# /usr/bin/env bash 解析成 "bash\r" 而无法启动。
*.sh text eol=lf
```

注意 `.gitattributes` 只影响**之后**的检出。已经是 CRLF 的工作区文件不会自动修好，要强制刷新一次：

```bash
git add --renormalize .
git checkout -- .
```

**这个坑值得单独记住的地方在于它的症状具有极强的误导性**——"no such file or directory"会让你去查路径、查 `chmod +x`、查 WORKDIR，而真正的问题是一个看不见的字节。任何跨平台仓库都应该在第一天就把 `.gitattributes` 加上。

**坑二：沙箱代码改完不重建镜像，接口一直 404。** 见 55.9。这个坑的隐蔽之处在于 `docker compose restart sandbox` 会正常执行、容器会正常起来、健康检查会通过、其它接口全都正常——只有你新加的那个路由是 404。查了半天路由注册、查了 prefix、查了 Nginx，最后发现容器里跑的是三小时前的代码。**判断依据很简单：`docker compose exec sandbox` 进去看一眼文件内容**，或者直接看新路由返不返回 404。

**坑三：单页应用读到骨架屏。** `browser_read` 走的是 `navigate` 的默认 `wait_until="domcontentloaded"`，DOM 结构一就绪就返回。对静态页面这没问题，对 React/Vue 单页应用就是灾难——DOM 已经有了，但里面全是 loading 占位符，innerText 读出来是"加载中…"或者一片空白。表现为 `total_chars` 只有几十，`text` 里全是导航栏文字没有正文。

现阶段的应对是分两步走，第一步用更保守的等待策略：

```text
browser_open(url="https://spa.example.com")   # wait_until 默认 domcontentloaded
browser_read()                                 # 不传 url，读当前页
```

两次调用之间有一次完整的工具选择往返，通常足够 SPA 完成首屏渲染。更彻底的做法是把 `wait_until` 提升为 `browser_read` 的参数，支持 `networkidle`；再进一步是等待某个选择器出现。这些留给后续章节。**但先要能识别这个症状：正文异常短、内容全是导航和页脚，基本就是渲染没完成。**

**坑四：正文截断后模型基于半截内容作答。** `truncated: true` 已经回传了，`_read_page` 也把"（正文共 N 字，已截断到前 M 字）"写进了输出表头，但这只是**提示**，不是保证。模型完全可能无视它，把前 8000 字当全文，然后写出"该页面共列举了三条理由"——而第四条在第 9000 字。

这里还有一个更容易被忽略的叠加效应：`_build_final_answer_evidence` 会把工具原始输出**再截一次到 900 字**：

```python
            block_lines.extend(["- 原始观察摘录：", self._trim_text(output, 900)])
```

也就是说，你把 `max_chars` 调到 60000，最终回答生成时实际能看到的仍然只有前 900 字左右。**调大 `max_chars` 对最终回答几乎没有帮助**，它只影响事件面板里人能看到多少。真要让模型消费长正文，得改的是证据构建这一层的预算分配，而不是工具参数。知道这条边界在哪，比盲目调参有用。

**坑五：不要把整页 HTML 塞进模型。** 有人会想"innerText 丢了链接和表格结构，那我加个参数支持返回 HTML 吧"。别这么做，至少别做成默认选项。一个中等新闻页的 HTML 300 KB 起步，按中英混排大约 10 万 token——单次请求就能烧穿大部分模型的上下文窗口，而其中 90% 是 class 名、内联样式和 SVG 路径。真需要结构化数据时，正确的方向是**在沙箱侧做定向抽取**（用选择器取出表格、用 `page.eval_on_selector_all` 收集链接），返回已经结构化的小体积结果，而不是把原料整个丢给模型让它自己淘。

**坑六：`str(None)` 变成字符串 "None"。** 55.4 说过，可选参数没传时 handler 收到的是 `None` 而不是 lambda 默认值。`str(url or "")` 和 `str(url)` 差一个 `or ""`，后者会让工具去访问 `https://None`。这类问题在 Python 里格外容易犯，因为它不报错——它会给你一个语法完全合法、语义完全错误的字符串。**凡是 `str()` 包裹可能为 `None` 的值，都该问一句默认值应该是什么。**

## 55.12 本章小结

这一章做的事情用一句话概括：**让 Agent 从"能操控浏览器"变成"能读懂网页"，顺便让它在自己犯错时不至于全盘皆输。**

四条经验值得带走：

1. **给模型的观察，要按"人眼所见"来裁剪。** innerText 而不是 HTML、清掉空行、带上来源表头、显式标注截断——每一处都在回答同一个问题："如果我是模型，这段文本够不够我作答，会不会误导我"。工具输出的格式设计，重要性不亚于工具功能本身。

2. **减少模型的决策次数，比提升每次决策的质量更有效。** `browser_read` 的 url 可选设计，本质上是把两次工具选择合成一次。每一次工具选择都是一次可能出错的机会，能合并的步骤就合并。这个思路可以推广到所有工具设计上。

3. **准则要写成可执行的判断，不是原则性表态。** "合理使用浏览器工具"没有任何用；"同一网页的正文已经出现在步骤历史里时，严禁再次 browser_read，后续分析步骤直接用 write_content 引用已读内容"才有用。判断条件、禁止动作、替代方案，三样齐全。而这些准则几乎全部来自实测——**你不可能预先想到模型会连读三次同一个页面。**

4. **在严格校验的前一步做宽容修正。** `AgentTool` 必须严格拒绝非法参数，这是最后一道闸；但闸门之前应该有一层 schema 白名单清洗，把模型的格式抖动吸收掉。同理，`_to_int` 夹取越界值而不是报错，`write_content` 返回失败文本而不是抛异常，`step_history` 标记失败并要求下一步补救。**这些加在一起，才是"自愈"的完整含义：不是不出错，而是出错之后还能往前走。**

至此，AtlasAgent 的浏览器能力从"看得见"走到了"读得懂"。下一步的方向是显而易见的：点击、输入、滚动，以及在多次交互之间保持对页面状态的理解——那时候 `browser_read()` 不传 url 的那条路，才会真正显出它的价值。
