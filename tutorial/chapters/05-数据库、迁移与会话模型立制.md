# 第五章. 数据库、迁移与会话模型立制

第 3 章的 status 接口是写死在配置里的。刷新页面，什么都不会被记住。Agent 工作台如果连「用户开过哪些会话」都记不住，后面的计划、事件、文件都无处可挂。这一章给控制平面加上第一张业务表。

现行实现不走 Alembic，也不绑 PostgreSQL。`backend/api-ts` 用 Drizzle 描述表结构，启动时对 SQLite 跑一遍 `CREATE TABLE IF NOT EXISTS`。文件库的路径来自 `DATABASE_URL`，本机默认 `file:./var/atlas.db`，Compose 里是 `file:/app/data/atlas.db`。

![账本：先有格子，才谈记住什么](../assets/ch05-db.jpg)

会话不是聊天窗口的别名。它有标题、状态、未读数、工作区目录，以及一个软删除时间。删掉不该物理抹掉：用户误点之后还要能在审计里看见它曾经存在。`deleted_at` 为空才出现在列表里。

```ts
export const sessions = sqliteTable("sessions", {
  id: text("id").primaryKey(),
  title: text("title").notNull(),
  status: text("status").notNull().default("idle"),
  unreadCount: integer("unread_count").notNull().default(0),
  workspaceDir: text("workspace_dir").notNull().default(""),
  fullAccess: integer("full_access", { mode: "boolean" }).notNull().default(false),
  createdAt: text("created_at").notNull(),
  updatedAt: text("updated_at").notNull(),
  deletedAt: text("deleted_at"),
});
```

时间戳存 ISO 文本，而不是 SQLite 的整数 unix。前后端已经在信封里用字符串传时间，少一次时区换算。布尔在 SQLite 里是 0/1，Drizzle 的 `mode: "boolean"` 让 TypeScript 侧仍是 `true` / `false`。

`openDatabase()` 打开 libsql 客户端之后立刻执行 `SQLITE_DDL`。没有单独的 `migrate` 命令，是因为这一阶段表还少，IF NOT EXISTS 够用。表变多、列要改的时候，再引入 drizzle-kit 的版本迁移——那是第 49 章的事，不要现在为三张表搭一套迁移仪式。

`GET /api/status/database` 对 `sessions` 做一次 `select limit 1`。连不上返回 `{ status: "error" }`，不把驱动异常原文塞给浏览器。网关和首页用它判断「库活着」，不是用来做 ORM 自检的。

验证很短：

```bash
cd backend/api-ts
pnpm dev
curl http://127.0.0.1:8000/api/status/database
```

应看到 `"status":"ok"`。`var/atlas.db` 会出现在目录里。用任意 SQLite 浏览工具打开，应能看见 `sessions` 表，此时还是空的。下一章往里面插入第一行。
