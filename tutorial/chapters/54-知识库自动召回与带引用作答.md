# 第五十四章. 知识库自动召回与带引用作答

## 54.1 本章目标

第五十章把 RAG 后端做完了：切分、向量化、混合检索、编号引用、审计 trace。第五十二章把管理界面做完了：建库、摄取、文档状态、检索验证台。第五十三章把直答路径做完了：普通提问不再走 Planner，模型的回答逐字流出来。

然后出现了一件很讽刺的事——**用户在对话框里问知识库里的内容，模型说它没有知识库。**

这一章解决这个断点：把知识库从"一个能在管理页面里查询的独立模块"，变成"每一轮对话都会自动查一次的上下文来源"，并让回答带上可核对的引用。

完成本章后，你将能够：

- 说清"让模型自己决定要不要调检索工具"和"每轮直答前自动召回"的代价，知道什么场景选哪个；
- 实现跨知识库的自动召回：独立会话、跳过空库、不污染审计、跨库排序、双重阈值、字符预算；
- 判断一处宽 `except` 是合理降级还是坏味道，并说出判据；
- 写出能真正约束模型行为的注入提示词，理解"片段无关就忽略"和"不要编造"为什么删不得；
- 用三个配置项调节自动召回的召回率、精确率与成本，并用 `chat_rag_top_k=0` 做总开关；
- 把命中来源写进 `task_done` 事件，让引用可追溯到具体文档；
- 用同一条思路把附件内容（文本与 PDF 文本层）喂进直答上下文，并处理扫描件这类边界；
- 诊断"知识库里明明有、就是搜不到"的召回失败，并知道该改文档而不是改代码。

本章改动集中在三个文件：`agent_runner_service.py`（直答路径注入 RAG 与附件上下文）、`core/config.py`（`chat_rag_*` 与 `chat_attachment_*` 配置）、`attachment_excerpt.py`（附件文本节选）。代码量很小，真正的内容在取舍上。

## 54.2 知识库是个孤岛

先把现场还原清楚。

知识库里已经灌了文档，管理页面的检索验证台能查出结果，能看到 `综合 0.83 · 向量 0.79 · 词法 0.91` 这样的评分。然后你回到对话页，问了一个文档里明明写着答案的问题，模型回了这么一段：

> 当前对话并没有实际启用 RAG 功能，我无法主动连接外部知识库。

用户的原话是：**"为什么你的回答不会触发 rag 检索"**。

问得很准。答案是：**它确实不会触发，因为没有任何代码让它触发。**

**问题一：直答路径根本不查知识库。** 第五十三章给会话做了意图分流，`needs_agent_pipeline` 决定一条消息走哪条路：

```python
def needs_agent_pipeline(content: str) -> bool:
    """判断一条用户消息是否需要完整的计划执行流水线。

    默认走直接问答（像 GPT 一样流式回答）——这是对话产品的主路径。
    只有出现明确的工具意图（沙箱、搜索、网页、文件动作、终端、集成），
    或"执行/运行 + 对象"的组合语义时，才启动 Planner + ReAct。
    """
```

这个设计本身没问题：对话产品的主路径就该是直答。问题在于改造之前的 `_stream_direct_answer` 只做三件事——取上下文快照、拼 system 提示、调模型流式输出，整条路径里**没有一行代码碰过知识库**。而"公司的报销流程是什么"这种问题恰恰长得就像一句普通问答：没有 URL、没有"沙箱"、没有"执行脚本"。它 100% 走直答路径，也就是 100% 查不到知识库。

**问题二：流水线路径有工具，但普通聊天绕不过去。** 第五十章确实注册了 `knowledge_search`，但看一眼参数定义就知道卡在哪：

```python
ToolParameter(
    name="knowledge_base_id",
    type="string",
    description="知识库 ID（UUID）。可先通过 /api/rag/knowledge-bases 查询。",
),
```

**这个工具要求模型先知道一个 UUID。** 模型不知道。它没见过知识库列表，`/api/rag/knowledge-bases` 也不是一个工具，没法先查再调。真要走通，得再加一个列举工具、让模型先列举、再挑一个、再检索——三次模型往返，才能回答"报销上限是多少"。更根本的是，**用户根本不会说"沙箱"或"执行脚本"**，这条消息压根到不了流水线，`knowledge_search` 有没有都一样。

于是形成了一个完整的孤岛：

| 路径 | 会不会查知识库 | 为什么 |
| --- | --- | --- |
| 直答（绝大多数对话） | 不会 | 代码里没有检索这一步 |
| 流水线 + `knowledge_search` | 理论上会 | 模型不知道库 ID，且普通提问进不了这条路 |
| 管理页面检索验证台 | 会 | 但那是给运维调参用的，不是对话 |

**一个 Agent 记不住团队资料，和没有团队资料是一回事。**

## 54.3 设计取舍：自动召回，还是让模型决定

修的方向有两个，值得摊开比。**方案 A** 是把检索做成模型可自主调用的工具（Assistants API、file_search 那一派）：去掉库 ID 参数或补一个列举工具，让直答路径也支持 tool calling，模型判断"这个问题需要查资料"就自己调。**方案 B** 是每轮直答之前无条件先检索一次，把命中片段拼进 system 提示——模型不知道有检索这件事，它只知道 system 里多了一段"知识库检索结果"。

我们选了 B。三个理由：

**理由一：A 要求模型知道库 ID，B 不需要。** 这不是改 prompt 能绕过去的——UUID 不在模型的知识里，只能靠额外一轮工具调用去拿。B 在服务端直接遍历所有知识库，用户和模型都不需要感知库的存在。

**理由二：A 多一次往返，B 不多。** 工具调用的最小成本是"模型输出 tool_call → 服务端执行 → 结果回灌 → 模型再输出"，两次模型请求起步。对流式对话产品，这意味着首字延迟从几百毫秒变成两三秒。B 只多一次向量检索（本地 pgvector 是一次 SQL）。

**理由三：小模型经常不调。** 这是最现实的一条。7B/14B 级别的模型在"该不该用工具"上判断很不稳定，尤其问题看起来像常识题的时候（"我们公司年假几天"——模型觉得自己能编）。**工具式检索的召回率取决于模型的自觉性，自动召回的召回率是 100%。**

B 的代价也要说清楚：每一轮对话都多一次向量检索（哪怕用户只说了"你好"）、无关片段可能被塞进上下文、上下文变长导致 token 成本上升。这三条都靠本章的三个配置项控制，`chat_rag_top_k=0` 则整体关掉。

一句话总结这次取舍：**在对话产品里，检索的确定性比模型的自主性更值钱。**

两种方式并不互斥。`knowledge_search` 仍然保留在流水线路径上——当 Agent 执行一个多步任务、需要在第三步查一份特定知识库时，工具式检索才是对的形态。**自动召回服务对话，工具式检索服务任务。**

## 54.4 `_load_rag_context`：一次跨库自动召回

改造的核心是一个函数（`backend/api/app/application/agent_runner_service.py`）：

```python
async def _load_rag_context(self, question: str) -> tuple[str, list[str]]:
    """直答前自动检索所有知识库，返回（注入文本, 命中文档标题）。

    与 knowledge_search 工具一致，用独立数据库会话执行检索，
    不与当前请求事务纠缠。任何失败（无知识库、向量服务异常、
    测试环境无数据库）都静默降级为无知识库上下文，绝不阻断问答。
    """

    if settings.chat_rag_top_k <= 0:
        return "", []
    try:
        from app.application.rag_service import RagService
        from app.infrastructure.database.session import AsyncSessionLocal

        async with AsyncSessionLocal() as db_session:
            service = RagService(UnitOfWork(db_session))
            bases = await service.list_knowledge_bases()
            scored: list[tuple[str, object]] = []
            for base in bases:
                if not base.chunk_count:
                    continue
                result = await service.query(
                    base.id,
                    query=question,
                    top_k=settings.chat_rag_top_k,
                    record_trace=False,
                )
                scored.extend((base.name, chunk) for chunk in result.chunks)
    except Exception:  # noqa: BLE001 —— RAG 是增强项，失败不影响直答。
        return "", []

    relevant = sorted(
        (
            item
            for item in scored
            if item[1].final_score >= settings.chat_rag_min_score
        ),
        key=lambda item: item[1].final_score,
        reverse=True,
    )[: settings.chat_rag_top_k]
    if not relevant:
        return "", []

    lines: list[str] = []
    sources: list[str] = []
    remaining = settings.chat_rag_context_chars
    for index, (base_name, chunk) in enumerate(relevant, start=1):
        content_text = chunk.content.strip()
        if len(content_text) > remaining:
            content_text = content_text[:remaining]
        remaining -= len(content_text)
        lines.append(
            f"[{index}]《{chunk.document_title}》（知识库：{base_name}，"
            f"相关度 {chunk.final_score:.2f}）：\n{content_text}"
        )
        if chunk.document_title not in sources:
            sources.append(chunk.document_title)
        if remaining <= 0:
            break
    return "\n\n".join(lines), sources
```

四十行不到，每一条都有理由。逐条拆。

**第一行就是总开关。** 设成 0 之后，后面的 import、会话创建、数据库往返全都不发生——**关闭一个功能应该零成本，而不是"走完流程然后丢掉结果"**。排查性能问题时，你需要一个能干净把某条链路摘掉的开关来做 A/B 对比。

### 用独立数据库会话，而不是复用当前 UnitOfWork

`AgentRunnerService` 手边就有 `self.session_service.uow`，直接用它构造 `RagService` 能少两行代码。为什么不？

**原因一：事务边界。** 当前请求的 UnitOfWork 正在一个跨越整次 SSE 流式响应的事务里——要写 `message_created`、写 `task_done`、更新会话状态，中间还夹着一次可能持续几十秒的模型流式输出。把向量检索挂进去，等于让一个只读操作参与长写事务，白白拉长持锁时间。

**原因二：失败隔离。** 检索中任何一次 SQL 出错（pgvector 扩展没装、`knowledge_chunk_embeddings` 表不存在），都会把 asyncpg 的连接标记成"事务已中止"。此后当前 UnitOfWork 上的任何写操作都会失败——**一次可选的知识库检索失败，会导致这轮对话的回答存不进数据库**。这是最不能接受的耦合：增强项拖垮主路径。

**原因三：一致性。** 第五十章的 `knowledge_search` 工具就是这么做的，注释也写了"工具自己开会话就是为了这个"。

推广一下：**给主流程做增强的旁路逻辑，永远不要和主流程共享事务。**

### 遍历所有知识库，跳过空库

`list_knowledge_bases()` 不带 `project_id` 时返回所有未删除的知识库（上限 100）。对每个库单独发一次检索是必须的——第五十章的设计里**知识库是租户边界，向量存储按库隔离**（pgvector 按 `knowledge_base_id` 过滤，Qdrant 是独立 collection），不存在"一次查完所有库"的接口。

`chunk_count` 为 0 的库直接跳过：刚建好还没灌文档的库、文档全部摄取失败的库，检索都会走完"查询向量化 → 向量库查询 → 回读 chunk"整条链路才返回空，而**查询向量化本身就可能是一次 HTTP 请求**。`chunk_count` 是摄取成功后维护在知识库行上的统计值，读它不额外花钱。

### `record_trace=False`：自动召回不该污染审计

第五十章给 `RagService.query` 加了 `record_trace` 参数，默认 `True`——每次检索都往 `retrieval_traces` 写一条审计，记下检索计划、所有候选及分数、最终选了哪几条，用来回答"为什么模型当时答错了"。

自动召回必须关掉它，因为**量级完全不同**：人在管理页面点一次检索是一条 trace；自动召回是**每轮对话 × 每个非空知识库**一条。三个库、一天一千轮对话就是三千条，其中绝大多数是"用户说了句你好，什么都没命中"。这张表的价值在于人工排查时能快速定位那次可疑的检索，被淹没之后它就废了。附带的理由是写 trace 会 `commit()`，而自动召回本该是纯只读旁路。

**结论：审计记录要留给"人主动发起的、需要解释的"操作**，系统自动做的高频操作该进 metrics。

### 跨库归并：排序、双重阈值、字符预算

每个库各返回 top_k 条，合起来可能几十条。这里做三件事：过阈值、按 `final_score` 全局排序、砍到 `chat_rag_top_k` 条。注意这是**跨库竞争**：三个库各返回 4 条共 12 条，最终只留 4 条，完全可能全部来自同一个库。这正是想要的行为——用户不关心答案在哪个库里，只关心哪几段最相关。

这里有一层容易被忽略的细节：**阈值实际上有两道。** `RagService.query` 内部已用 `rag_min_score`（默认 0.15）过滤过一次，`_load_rag_context` 又用 `chat_rag_min_score`（默认 0.3）过滤第二次。前者是**检索层的底线**，所有调用方都受它约束；后者是**注入层的门槛**，只管自动召回，而且更严——管理页面上你看到一条低分结果会自己判断"没用"，自动注入没人把关。**"给人看"和"给模型吃"应该用不同的阈值**，这是本章一条可以带走的通用结论。字符预算同理：算上库内那道 `rag_max_context_chars`（3600），`chat_rag_context_chars`（6000）已经是第三层，因为前者的上限乘以库数才是后者要防的量。

最后，函数返回二元组：第一项是注入文本，直接进 system 提示；第二项是去重后的命中文档标题，进 `task_done` 事件给前端展示引用来源（见 54.7）。**把"给模型的"和"给界面的"在同一次检索里一起产出**，避免为了展示引用再查一次库——这也是为什么不直接返回 `RagQueryResult`。

### 那个宽 `except`：什么时候它是对的

`except Exception` 在代码评审里通常要被打回。这里为什么可以？判据有三条，必须**同时**满足：

1. **这段逻辑是纯增强的。** 没有它，主功能（回答问题）完全正常，只是少了知识库这一路信息。用户拿到的是"基于模型自身知识的回答"，不是错误页。
2. **失败模式多且不可穷举。** 数据库连不上、pgvector 扩展缺失、embedding 服务 401、Qdrant 超时、单元测试环境压根没有数据库——异常来自五六个不同的层，一一列举既写不全也维护不动。而且**新增一个向量后端就会带来一类新异常**，白名单式捕获注定要漏。
3. **降级结果明确且安全。** 返回 `("", [])` 之后，`_build_chat_messages` 里的 `if rag_context:` 不成立，system 提示里就是没有知识库那一段。没有半成品，没有"部分注入"，没有要清理的中间状态。

三条里少任何一条就变成坏味道：逻辑是**必需的**（扣款、鉴权、写主表）时，宽捕获是在掩盖故障；失败模式**可穷举**时，该精确捕获让预料之外的异常正常抛出；降级会留下**不完整状态**时，宽捕获把明确的失败变成隐蔽的数据问题。另外，**宽捕获必须配注释和 `noqa` 标记**——没有注释的宽捕获，半年后没人敢动，因为不知道它在挡什么。

至于可观测性，这里连日志都没打，这一点可以商榷：好处是不会在"根本没配知识库"的部署里刷屏，坏处是向量服务故障导致静默失效时你只能靠"回答里没引用"发现。如果部署确实依赖知识库，改成 `logger.warning` 是合理的加强。

## 54.5 注入提示词：编号、来源标注与两条禁令

检索到的片段怎么进 prompt，直接决定回答质量。`_build_chat_messages` 里的相关段落：

```python
if rag_context:
    sections.append(
        "知识库检索结果（系统已自动检索，按相关度排序）：\n"
        f"{rag_context}\n\n"
        "回答与知识库内容相关的问题时，优先依据以上片段作答，"
        "并在对应句子末尾用（来源：《文档标题》）标注引用；"
        "片段与问题无关时直接忽略，不要强行引用，"
        "也不要编造知识库里没有的内容。"
    )
```

`sections` 最后被 `"\n\n".join()` 拼成**一条 system 消息**，用户的历史对话轮次跟在后面。

第五十三章讲过"记忆和附件进 system，不进 user"，检索片段同理，而且多一条理由：**塞进用户消息的内容会进入对话历史**。第二轮对话时第一轮那一大坨片段还在上下文里，和新检索的片段并存，很快把窗口撑满，模型也分不清哪些片段对应哪个问题。放在 system 段则是每轮重建的——`_build_chat_messages` 每次都重新拼 `sections`，上一轮的检索结果自然消失。

**片段的格式。** `_load_rag_context` 生成的每条片段长这样：

```text
[1]《员工手册 2026》（知识库：行政制度，相关度 0.83）：
年假天数按司龄计算：满 1 年 5 天，满 3 年 10 天，满 5 年 15 天。……
```

三个元素各有用处：`[1]` 编号沿用第五十章 `citation` 的约定，让模型能在回答里交叉引用多个片段；`《文档标题》`是模型要写进回答的东西，必须是人能看懂的名字而不是 UUID；`（相关度 0.83）`告诉模型这条有多可信——实测下来它能让模型在片段之间做取舍，0.83 的和 0.42 的说法冲突时更倾向前者。用书名号而不是引号，是为了和要求输出的 `（来源：《文档标题》）` 对齐，格式一致能显著提高指令遵循的稳定性。

**最后两句约束为什么必不可少。** 指令前半段（"优先依据片段作答 + 标注来源"）是所有 RAG 教程都会写的。真正关键的是后半段：

> 片段与问题无关时直接忽略，不要强行引用，也不要编造知识库里没有的内容。

**第一句防"强行关联"。** 自动召回是无条件的——用户问"帮我写个快排"，系统照样查库，照样可能返回几条分数刚过阈值的片段（某份文档里提到过"排序"）。没有这句话，模型会认为"system 里给了资料，那就是要我用"，于是憋出一段"根据《数据仓库设计规范》，排序应遵循……（来源：《数据仓库设计规范》）"。**这比不检索还糟——它把一个正确的通用回答污染成了一个看起来有依据的错误回答。** 这也是自动召回相比工具式检索的固有代价：工具式检索里"不调工具"本身就表达了"这题不需要资料"，自动召回没有这个信号，只能靠提示词补回来。

**第二句防"引用式幻觉"。** 这是 RAG 里最危险的一类错误：模型在检索片段的基础上"顺手补全"。片段说了年假天数，没说病假；用户问病假，模型答"病假每年 10 天（来源：《员工手册 2026》）"。**带着来源标注的编造，可信度比裸编造高得多，危害也大得多**——用户会去核对吗？大概率不会，因为它看起来已经核对过了。

这两句话成本三十个字，收益是把两类最典型的 RAG 失败挡在门外。**在 RAG 提示词里，"什么时候不要用检索结果"和"怎么用检索结果"同样重要。**

完整的 system 提示按这个顺序拼装：角色与基本要求 → 会话概要 → 长期记忆 → **知识库检索结果** → 会话附件内容。第一段里本来就有"不知道就说不知道，不要编造"，第四段又强调一次。这不是冗余——**通用约束和局部约束的作用范围不同**，紧挨着检索片段的那句约束，模型遵守得明显更好。

## 54.6 三个配置项与调参

`backend/api/app/core/config.py`：

```python
# ===================== 直答路径的知识库自动检索（RAG） =====================
# 每次直答前自动检索所有知识库；top_k 设为 0 可整体关闭。
chat_rag_top_k: int = 4
chat_rag_min_score: float = 0.42
chat_rag_context_chars: int = 6000
```

这三项目前只在 `config.py` 里有默认值，**没有写进 `.env.example`**。要覆盖就在 `.env` 里加大写同名项（pydantic-settings 自动映射）：

```bash
CHAT_RAG_TOP_K=4
CHAT_RAG_MIN_SCORE=0.42
CHAT_RAG_CONTEXT_CHARS=6000
```

**`chat_rag_top_k`：条数与总开关。** 默认 4，有两个身份：跨库归并后的最终条数，以及**传给每个库的 `top_k`**——三个非空库时候选池是 12 条，最终留 4 条。问答型知识库（FAQ、制度、手册）3-4 条足够，答案通常集中在一两段里，多给反而稀释；叙述型知识库（设计文档、技术方案）可以到 6-8 条。设成 0 则整体关闭。

**`chat_rag_min_score`：最需要标定的一项。** 默认 0.3，**它对应的分数尺度不直观**。第五十章的评分公式是 `final_score = match.score * 0.7 + lexical_score * 0.3`，而所有 VectorStore 实现都把余弦相似度**线性映射**到 [0, 1]：

```python
score=max(0.0, min(1.0, (float(row[2]) + 1) / 2)),
```

也就是说，**两段完全无关的文本（余弦 ≈ 0）拿到的向量分是 0.5，不是 0**。词法分为 0 时综合分是 `0.5 × 0.7 = 0.35`——这是这套评分的**噪声地板**。任何低于 0.35 的阈值都形同虚设：所有片段都能过，真正在限流的只有 `top_k` 的条数上限。

这一点是踩出来的。自动召回刚上线时阈值取的 0.3，结果一次与知识库无关的提问，`rag_sources` 里赫然躺着一份完全无关的图片文档——它的分数是 0.38，稳稳高过 0.3。

所以默认值不能拍脑袋，要测。拿真实语料跑一组对照（两个相关问题、两个明确无关的问题），记下每条的综合分：

```text
[相关] 学院是什么时候成立的？院长是谁？
   final=0.463  vec=0.597 lex=0.150   学院简介与成立背景
   final=0.435  vec=0.601 lex=0.050   培养体系
[相关] 培养体系是怎么设计的？
   final=0.502  vec=0.546 lex=0.400   培养体系
[无关] 如何用 Python 实现快速排序算法？
   final=0.388  vec=0.554 lex=0.000   培养体系          ← 噪声天花板
[无关] 今天晚饭吃什么比较好
   final=0.385  vec=0.529 lex=0.050   某图片文档
```

**噪声天花板 0.388，信号地板 0.463**，中点约 0.425——默认值 `0.42` 就是这么定出来的，它能滤掉上面全部四条噪声，同时保住三条真实命中。注意这组数据是**本地哈希向量**跑的：两条通道退化成同一套 n-gram 匹配，信噪比本来就窄（0.388 对 0.463 只差 0.075）。接上真实 embedding 服务后间距会明显拉开，阈值可以更自信地提到 0.45-0.55。

标定方法本身比这个数字更重要：**准备 5-8 个真实会问的问题和 3-5 个明确无关的问题，用第五十二章的检索验证台各查一遍，取"无关最高分"与"相关最低分"的中点。** 如果前者比后者还高，说明**阈值救不了你**——问题出在 embedding 模型不匹配、文档写法有问题（见 54.9）或切分粒度不对。换语料、换 embedding 模型、改切分，都要重新测一次。

**`chat_rag_context_chars`：字符预算。** 默认 6000，中文粗略按 1 字 ≈ 1 token 算。8K 窗口的模型要压到 2000-2500，否则历史消息会被挤掉；32K 用默认值；128K 以上可以放到 12000-16000，但不建议无脑拉满——上下文越长模型对每一条的注意力越稀薄，**4 条精准片段的效果通常好于 20 条相关片段**。

## 54.7 引用可追溯：`task_done` 带上 `rag_sources`

模型在回答里写"（来源：《员工手册 2026》）"只解决了一半问题——那是模型说的，而模型可能说错。真正的追溯需要**系统侧记录本轮实际注入了哪些文档**。

这就是 `_load_rag_context` 返回二元组第二项的去处：

```python
done_event = await uow.session_events.add(
    session_id=session_id,
    event_type=SessionEventType.task_done,
    payload={
        "mode": "chat",
        "final_answer": final_answer,
        "reasoning": reasoning,
        "message_id": str(message.id),
        "memory_ids": [str(item.id) for item in snapshot.memory_context.items],
        "memory_count": len(snapshot.memory_context.items),
        # 本轮自动检索命中的知识库文档，便于前端展示引用来源。
        "rag_sources": rag_sources,
    },
)
```

三点值得注意。

**第一，它和 `memory_ids` 放在一起。** 第四十五章就确立了这个模式：`task_done` 是这轮回答的"物料清单"，注入了哪些记忆、哪些知识库文档都记在这里。事后有人质疑一个回答，翻这条事件就知道模型当时看到了什么。

**第二，存的是标题不是 ID。** 主要消费者是前端展示，标题可以直接渲染；更重要的是，标题正是模型在回答里写的那个字符串，**两边能对上**——如果模型写了"（来源：《XX规范》）"但 `rag_sources` 里根本没有《XX规范》，那就是抓了个现行的引用幻觉。代价是文档改名后历史事件里的标题会过时，但对一个用于事后核对的快照来说，"记录当时的样子"反而是对的。

**第三，前端目前还没有渲染它。** 说实话：`frontend/web` 里只消费了 `task_done` 的 `reasoning` 和 `message_id`（`view-model.ts` 的 `buildReasoningMap`），`rag_sources` 还是个只写不读的字段。这不是遗漏，是有意的分层——**后端先把数据吐出来，前端按自己的节奏消费**。事件 payload 多一个字段不会破坏任何现有客户端，而缺了它，前端想做引用展示就得反过来推后端。要接的话，解析 `task_done` 时多读一个 `string[]`，在回答气泡下方渲染一排来源标签即可。

## 54.8 附件理解：另一条喂进直答上下文的通道

自动召回解决的是"知识库里的内容进不了对话"。同一时期还有一个长得几乎一样的问题：**用户传了个文件，模型只看得到文件名。**

改造前 `_build_chat_messages` 对附件只做一件事——拼一份 `- 文件名（类型，字节数）` 的清单。用户传了一份 PDF 然后问"总结一下"，模型手里只有 `report.pdf（application/pdf，482913 字节）`，它要么说"我看不到文件内容"，要么**根据文件名开始编**。后者更常见，也更糟。

这和知识库孤岛是同一类问题：**内容存在于系统里，但没有任何代码把它送到模型面前。** 解法也同构：在直答前把它读出来、裁剪好、拼进 system 段。

### `attachment_excerpt.py`：文本直读与 PDF 文本层

`backend/api/app/application/attachment_excerpt.py` 是纯函数模块，没有数据库、没有网络，因此可以完整单元测试。入口 `build_attachment_excerpt` 按格式分三条路：

```python
    if char_budget <= 0:
        return None
    if is_pdf_attachment(content_type, filename):
        return _extract_pdf_text(data, char_budget)
    if is_text_attachment(content_type, filename):
        text = data.decode("utf-8", errors="replace").strip()
        if not text:
            return None
        return _truncate(text, char_budget)
    return None
```

三个实现细节值得说。

**文本类判断走"MIME + 扩展名"双通道。** 只信 MIME 会漏——浏览器上传 `.md` 时 `content_type` 经常是空串或 `application/octet-stream`；只信扩展名也会漏——有些客户端上传不带后缀。`is_text_attachment` 两个都试，并用 `.split(";")[0]` 剥掉 `text/plain; charset=utf-8` 这种参数。

**解码用 `errors="replace"` 而不是 `strict`。** GBK 编码的日志、混了二进制的 CSV——严格解码会抛异常，宽松解码会得到几个替换字符但正文可读。对"给模型看个大概"这个目的，后者明显更有用。

**PDF 只抽文本层，抽不到就说抽不到。** `_extract_pdf_text` 用 pypdf 逐页 `extract_text()`，受 `_PDF_MAX_PAGES = 80` 和字符预算双重约束，两条失败路径都返回一句人话：

```python
        if not text:
            return "（该 PDF 没有可提取的文本层，可能是扫描件或图片型 PDF。）"
        return _truncate(text, char_budget)
    except Exception:
        # 加密、损坏或非标准 PDF：给出确定性的失败说明。
        return "（PDF 解析失败，无法提取文本内容。）"
```

**关键在于三种情况必须区分开**：没有文本层说明文件正常但没字可抽；解析失败说明文件本身有问题（加密、损坏）；返回 `None` 则由上层转成"该格式暂不支持内容提取，仅可引用文件名与大小"。三句话都是给模型看的——**它需要知道自己为什么没看到内容，才不会去编。**

**扫描件 PDF 是这条链路的硬边界。** pypdf 只能读文本层，扫描件里那一页页图片对它来说就是空白。这不是 bug，是能力边界，处理办法就是**把边界明确告诉模型**。真要处理扫描件，路径是第五十章那条多模态摄取（`ingestImageDocument`，视觉模型解析图片入库），不在附件直读这条链路上。

### 预算控制与注入

三个配置项分别管条数、字数和单文件大小：

```python
chat_attachment_limit: int = 3                      # 只取最近 3 个附件
chat_attachment_context_chars: int = 20000          # 字符总预算
chat_attachment_max_file_bytes: int = 15 * 1024 * 1024
```

`limit` 取的是**最近**三个（`session_files[-limit:]`）——长会话可能传过二十个文件，用户问的多半是刚传的那个。字符预算 20000 比知识库的 6000 大得多，因为附件是用户**主动**传的、意图明确，值得多花；知识库是系统自动召回的，宁少勿滥。15MB 那道闸在**读文件之前**，防的是把一个 500MB 的文件整个读进内存。

预算逐个文件递减，超限或超预算时仍然往列表里写一条说明（"（附件内容预算已用完，本文件未注入。）"、"（文件过大，未注入内容；可拆分后重新上传。）"），而不是静默跳过——这样模型知道"还有第三个文件，但我没看到内容"。**静默丢弃会导致模型以为自己看全了。**

注入部分用 `if attachment_excerpts: … elif snapshot.files:` 保持向后兼容：**能抽到内容就给内容，抽不到就退回原来的文件清单**。格式上和知识库片段刻意保持一致，都用 `《标题》：` 开头、都要求注明出处——**同一个 system 提示里，不同来源的外部内容用同一套格式，模型的遵循度明显更高。**

## 54.9 一次真实的召回失败：简称查不到全称

链路打通之后，遇到了一个更有意思的问题。

知识库里有一份介绍某研究院的文档，正文从头到尾用的都是机构全称"星海人工智能研究院"。用户在对话里问：

> 星智院有哪些专业？

自动召回跑了，但这份文档要么没进 top_k，要么分数低到排在其他库的无关片段后面。模型只好用自己那点先验知识含糊回答了几句。

**这不是代码 bug，是检索机制的必然结果。** 拆开算一遍就清楚了。

**词法通道为什么归零。** 第五十章的 `_tokenize` 是中英文混合分词，中文按 2/3/4 字滑动窗口切 n-gram：

```python
for block in re.findall(r"[一-鿿]+", normalized):
    for size in (2, 3, 4):
        if len(block) < size:
            continue
        terms.update(
            block[index : index + size] for index in range(len(block) - size + 1)
        )
```

查询"星智院有哪些专业"切出来跟机构名有关的是 `星智`、`智院`、`星智院`；文档正文"星海人工智能研究院……"切出来的是 `星海`、`海人`、`人工`、`工智`、`智能`、`能研`、`研究`、`究院`、`星海人`……

**两个集合在机构名上的交集是空的。** "星智院"是首字加中间字加尾字的缩合，任何滑动窗口的 n-gram 都构造不出来。词法分只能靠"专业"这类通用词撑着，`lexical_score` 大概在 0.1 上下，按 `final = vector × 0.7 + lexical × 0.3` 算只贡献了约 0.03。这个本该把精确术语排名顶上去的第二信号，在这里完全失效。

**向量通道也帮不上多少。** 剩下全靠向量分，而这取决于 embedding 配置：本地哈希向量就是 n-gram 哈希，和词法通道是同一套失效逻辑——没有共享 n-gram，向量近乎正交，映射后约 0.5，综合分 `0.5 × 0.7 + 0.03 ≈ 0.38`，勉强过阈值但排名比不过任何一条字面对得上的片段。换成真实 embedding 模型会好一些，但那依赖模型在训练数据里见过这个简称——冷门机构、内部代号、项目化名，它不可能见过。

**结论：越是内部的、口语化的、缩写的说法，两条通道越是同时失效。** 这恰恰是团队知识库最常被问到的那类词。

**解法不在代码里。** 第一反应通常是加同义词表、加查询扩展、上 rerank 模型。这些都能做，但对一个已经跑起来的系统，性价比最高的是**改文档**——在正文里补一行别名：

```text
星海人工智能研究院（口语中也常被简称为星智院）是……
```

重新摄取后，"星智院"这个 3-gram 就实实在在出现在 chunk 里了。词法通道立刻恢复，向量通道也因为共现而受益。一行字，两个通道同时修好。

### "写给检索看的文档"和"写给人看的文档"

这个案例背后是一条值得单独提炼的原则。

人写文档的默认习惯是**避免重复**：全称第一次出现时定义，后面一律用简称；同义概念挑一个说法用到底；缩写在开头统一说明。这是给人看的好文风。

但检索是**字面匹配 + 向量相似**，它不做指代消解，也不会翻回文档开头看你的缩写表。**在 chunk 这个粒度上，每一段都必须自带足够的识别信息**——切分之后，第一段里的"下文简称 XX"对第七段的 chunk 毫无帮助，它们是两条独立的检索单元。

所以写给检索看的文档，规矩是反过来的：

1. **别名、简称、同义说法要显式出现在正文里**，不是脚注，不是只出现一次的"（下称 XX）"——`回滚（也叫降级、rollback）`、`CI（持续集成，Continuous Integration）`；
2. **关键实体在每个大节重述一次全名**，别让第五节全是"该系统""它"；
3. **标题要具体**，因为 `document_title` 会被拼进注入文本、也会被模型写进"（来源：《……》）"——`《部署手册》` 不如 `《订单服务生产环境部署手册》`。

这几条对人类读者略显啰嗦，但对检索是决定性的。**知识库文档的第一读者是检索器，第二读者才是人。**

这也是判断"该不该改代码"的好例子：召回失败时先问一句，是**检索机制的问题**（阈值、权重、模型），还是**语料的问题**（写法、粒度、别名）。语料问题用代码修，通常会修出一堆越来越复杂的规则；用语料修，一行就够。

**二、在对话里直接提问（不提"知识库""RAG"）。**

```bash
curl -N -s -X POST $BASE/sessions/$SESSION/messages/stream "${AUTH[@]}" \
  -d '{"content":"司龄满四年的员工每年有多少天年假？"}'
```

预期回答里出现"10 天"，并带上 `（来源：《员工手册 2026》）`。注意这句提问既不含"知识库"也不含任何流水线关键词，`needs_agent_pipeline` 返回 `False`，走的确实是直答路径——**这正是要验的东西，用户不需要说任何咒语。**

**三、检查 `task_done` 的 `rag_sources`。**

```bash
curl -s -H "X-Atlas-API-Key: ${ATLAS_KEY}" $BASE/sessions/$SESSION/events \
  | python3 -c '
import sys, json
for event in json.load(sys.stdin)["data"]["items"]:
    if event["type"] == "task_done":
        print(event["payload"].get("mode"), event["payload"].get("rag_sources"))
'
# chat ['员工手册 2026']
```

这一步比看回答文本更硬：它证明**系统确实注入了这份文档**，而不是模型碰巧猜对了。如果 `rag_sources` 是空列表、回答里却写了"（来源：《员工手册 2026》）"，那就抓到了一个引用幻觉，说明阈值或提示词还要调。放进冒烟脚本就是三行 httpx 断言：

```python
done = next(e for e in events if e["type"] == "task_done")
assert "员工手册 2026" in done["payload"]["rag_sources"], "自动召回没有命中"
assert "10" in done["payload"]["final_answer"], "回答没有用上知识库内容"
```

**四、关掉总开关，确认能退回纯模型知识。** 在 `.env` 里加 `CHAT_RAG_TOP_K=0` 并重启 API，再问同一个问题。预期回答里不再出现"（来源：……）"，`rag_sources` 是空列表 `[]`，模型给出泛泛的通用回答。这一步验的是开关真的有效——如果关掉之后回答没变化，说明模型本来就在编，前面那次"命中"是巧合。

**五、附件路径。** 在 Web 端上传一份纯文本 `.md` 或有文本层的 PDF，问"总结一下这份文件"，预期回答基于文件真实内容并注明出自哪个附件；再传一份扫描件 PDF，预期模型明确说这是扫描件、无法读取内容，而不是根据文件名编造。

**六、单元测试。**

```bash
cd backend/api
uv run pytest -q          # 97 passed
```

和本章直接相关的两个文件：`tests/test_attachment_excerpt.py` 守住文本判定、PDF 无文本层、截断标注等分支；`tests/test_agent_runner_direct_chat.py` 守住直答路径的事件序列——加了 RAG 之后这条序列必须**一字不变**：

```python
self.assertEqual(
    names,
    [
        "session_status", "message_created", "answer_started",
        "answer_delta", "answer_delta", "message_created",
        "task_done", "session_status", "stream_done",
    ],
)
```

这条断言的价值在这一章体现得特别明显：测试环境没有数据库，`_load_rag_context` 会走那条宽 `except` 静默返回 `("", [])`。**测试全绿本身就证明了降级路径是通的**——如果宽捕获写漏了某类异常，这个测试会直接炸。

## 54.11 常见坑

**坑一：阈值定太低，无关文档被灌进上下文。** 前面算过，向量分的"噪声地板"是 0.5 而不是 0，所以 `chat_rag_min_score` 低于 0.35 基本等于没有阈值（默认值 0.42 就是实测标定出来的，见 54.6）。表现是模型开始在不相关的问题上强行引用，或回答里混进别的业务域的内容。**别靠猜，用第五十二章的检索测试台标定**：几个真实问题 + 几个明确无关的问题各查一遍，取噪声最高分和信号最低分的中点。如果噪声比信号还高，那是语料或 embedding 的问题，调阈值没用。

**坑二：embedding 服务没配，静默降级成本地哈希向量。** `build_embedding_provider()` 在密钥缺失时返回 `HashingEmbeddingProvider`，**不报错、不告警**。这在第五十章是"教学环境可运行"的贴心设计，到自动召回这里就变成隐蔽的质量陷阱：哈希向量没有语义能力，两条通道退化成同一套 n-gram 匹配，同义改写、上位词、简称统统召回不到。查一眼 `GET /api/rag/health` 里的 `embedding.provider`，是 `local_hash` 就说明降级了——这种情况下不要抬阈值，先把 embedding 服务接上。

**坑三：知识库文档过长，单片段被截断。** `chat_rag_context_chars` 用完时，最后一条片段被 `content_text[:remaining]` 硬截断，而且**没有加"已截断"标记**（第五十章库内裁剪时是加的）。表现是模型看到一句半截话，回答跟着半截。要防它，一是把知识库的 `chunk_size` 调小，二是别把两个参数配成矛盾值——4 条 × 800 字 = 3200，6000 够用；`chunk_size` 是 2000 时 4 条要 8000 字，一定会截。**`top_k × chunk_size` 和 `chat_rag_context_chars` 应该配套。**

**坑四：每轮多一次检索的延迟。** 自动召回在模型开始输出之前串行执行，耗时直接加在首字延迟上：一次查询向量化（接了真实 embedding 服务就是一次 HTTP 往返，通常 100-300ms）+ 每个非空知识库一次向量查询。后者**按库线性增长**，十个知识库就是十次 SQL。目前是串行 `for` 循环，库多了可以改成 `asyncio.gather` 并发，但注意别把连接池打满。更简单的优化是别建那么多库：知识库是租户边界，不是分类目录。

**坑五：以为 `record_trace=False` 会影响管理页面的检索记录。** 不会，管理页面和 `knowledge_search` 走的是默认 `True`。反过来说，**要排查"某次对话为什么召回成这样"，`retrieval_traces` 里是查不到的**——那次检索没留痕。临时办法是在检索测试台里用同样的问题查一次，参数一致就能复现。

**坑六：改了知识库文档但没重新摄取。** 这是第五十章"索引漂移"的老问题，在自动召回下更隐蔽：以前你得主动检索才会发现内容是旧的，现在每轮对话都在用旧索引回答，而且带着"（来源：《XX》）"的标注，看起来煞有介事。改完文档记得点"重建索引"。

**坑七：把宽 `except` 当成通用写法抄走。** 54.4 列了三条判据，三条同时满足才行。抄到一个"必须成功"的路径上，就是在生产事故里挖坑。

## 54.12 本章小结

这一章代码量在整本书里算最少的之一，但它修的是一个典型的**系统性断点**：第五十章的 RAG 后端是对的，第五十二章的管理界面是对的，第五十三章的直答路由也是对的——三个正确的设计拼在一起，得到的是一个用户用不上的功能。

**做完一个模块，一定要问一句：普通用户在主路径上能不能用到它？** 如果答案是"要先去某个管理页面"或"要说某个特定的词"，那它就还没做完。

四条经验值得带走：

1. **在对话产品里，检索的确定性比模型的自主性更值钱。** 让模型自己决定要不要查资料听起来更"智能"，实际是把召回率押在模型的判断力上。自动召回把这件事变成 100% 确定，代价用阈值和预算控制。工具式检索没有被废弃——它服务的是任务流水线，不是对话。
2. **给主流程做增强的旁路，必须在事务、失败、审计三个维度上完全隔离。** 独立数据库会话隔离事务，宽 `except` 隔离失败，`record_trace=False` 隔离审计。少任何一条，一个可选功能就能拖垮主功能。
3. **提示词里"什么时候不要用检索结果"和"怎么用检索结果"同样重要。** 自动召回没有"不调工具"这个天然信号，两条禁令必须显式写上，否则你会得到带来源标注的幻觉——比裸幻觉更难识别。
4. **召回失败先看语料，再看代码。** "星智院"查不到"星海人工智能研究院"不是检索器有 bug，是文档里没写这个词。知识库文档的第一读者是检索器：别名、同义词、展开的缩写要显式出现在正文里，而且要出现在**每一个可能被切开的段落**里。

至此，AtlasAgent 的直答路径终于拿到了它应有的三条外部上下文：长期记忆（Agent 自己的经验）、知识库（团队的资料）、会话附件（用户当下给的材料）。三条通道用同一套注入格式、同一套预算纪律、同一套"可引用但不可编造"的约束——**统一的不只是代码，更是模型看到的世界的形状。**
