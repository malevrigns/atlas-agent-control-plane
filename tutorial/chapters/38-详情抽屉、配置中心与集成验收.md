# 第三十八章. 详情抽屉、配置中心与集成验收

## 38.1 合章说明

​        旧版教程把“右侧详情抽屉与工具内容渲染”与“配置中心与最终集成点验”拆成了相邻两章。两者实际上属于同一条能力链：前者把基础结构立住，后者让它进入可用状态。本章将它们合并为前后两个阶段，保留原来的实现、验证与工程判断，同时减少能力尚未闭环时的章节跳转。

## 38.2 第一阶段：右侧详情抽屉与工具内容渲染

### 38.2.1 本阶段目标

​        学完本阶段后，你将能够：

​        具体来说，第一，理解为什么中间对话流和右侧详情抽屉要分工；第二，把右侧工具详情从“调试输出面板”升级为“工具证据抽屉”；第三，在右侧展示工具观察摘要、调用参数和结构化结果；第四，让搜索、Shell、浏览器截图、VNC、MCP、A2A、多 Agent 结果按类型渲染；第五，避免默认把原始 JSON 铺给用户；第六，在任务完成时展示基于工具观察结果整理出的最终总结；第七，理解为什么浏览器、截图和 VNC 只在浏览器工具详情里出现。这些点放在一起看，构成了本阶段叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

### 38.2.2 最终效果

​        本阶段结束后，用户点击中间执行流里的工具节点，右侧会打开当前工具详情。

​        右侧结构会变成：

```Plain
AtlasAgent Computer
  |
  +-- 工具名称和工具类型
  |
  +-- 工具观察摘要
  |
  +-- 调用参数
  |
  +-- 按类型渲染的工具结果
      |
      +-- search_web        搜索结果列表
      +-- shell_run         终端输出
      +-- browser_open      页面信息
      +-- browser_screenshot截图预览 + VNC
      +-- mcp_call          MCP 返回内容
      +-- a2a_call          远程 Agent 协作结果
      +-- multi_agent_*     多 Agent 子任务和评审结果
```

​        浏览器远程桌面不再作为首页常驻演示面板，而是只跟随浏览器工具详情出现。

### 38.2.3 本阶段要解决的问题

​        第 37 章已经解决了中间执行流的可读性问题：

```Plain
中间只显示步骤和观察摘要
```

​        但右侧详情仍然有两个问题：

​        换句话说，第一，视觉上还像后台管理页，浅色卡片和暗色工作台不统一；第二，参数、MCP 内容等区域仍然容易显示原始 JSON。这些点放在一起看，构成了本阶段叙述中需要连续理解的一条线索，而不是彼此孤立的项目清单。

​        真实 Agent 产品里，右侧详情的职责不是“把数据库 payload 倒出来”，而是帮助用户确认：

```Plain
这个工具为什么被调用？
调用了什么参数？
看到了什么结果？
有没有截图、终端输出、搜索来源或远程协作证据？
```

​        所以本阶段把右侧详情继续产品化。

​        同时，本阶段修正一个任务收尾体验问题。

​        如果后端 `task_done` 事件只返回：

```Plain
计划步骤已全部执行完成。
```

​        前端就只能显示一句很泛的完成提示。真实 Agent 产品应该在任务结束时给用户一个可读总结：搜索到了什么、截图是否完成、Shell 命令是否执行、文件工具返回了什么。

​        所以本阶段会让后端在 `task_done.payload.final_answer` 中写入一段最终总结。后端会优先调用 LLM，把工具输出整理成正文式总结；如果 LLM 不可用，再使用规则摘要兜底。前端优先展示这段总结；如果旧事件没有这个字段，再使用前端根据步骤观察生成的兜底总结。

​        本阶段还补齐文件任务的一条关键链路：页面上传的附件存放在主 API 文件存储里，而 Agent 的 `file_read` 工具读取的是 Sandbox 工作目录。为了让“上传 Page.tsx 后让 Agent 解析文件”真正跑通，执行计划前会把文本附件同步到 Sandbox。

```TypeScript
function getArgumentEntries(value: unknown): Array<[string, unknown]> {
  if (!value || typeof value !== "object" || Array.isArray(value)) {
    return [];
  }
  return Object.entries(value as Record<string, unknown>);
}

function formatArgumentValue(value: unknown): string {
  if (value === null || value === undefined || value === "") {
    return "-";
  }
  if (typeof value === "string") {
    return value;
  }
  if (typeof value === "number" || typeof value === "boolean") {
    return String(value);
  }
  if (Array.isArray(value)) {
    return value
      .map((item) =>
        typeof item === "string" || typeof item === "number" || typeof item === "boolean"
          ? String(item)
          : "结构化项",
      )
      .join("、");
  }
  return "结构化参数，已传给工具执行";
}
```

##### 38.2.6.4.1 这段代码在流程中的位置

​        工具参数来自：

```Plain

```

​        这些参数是后端真正传给工具的输入。

##### 38.2.6.4.2 为什么这样设计

​        参数需要让用户能看懂，但不需要默认展示完整 JSON。

​        例如搜索工具参数：

```JSON

```

​        右侧应该展示成：

```Plain

AI Agent latest news

count
5
```

​        复杂对象则提示“结构化参数，已传给工具执行”，避免右侧再次变成调试控制台。

#### 38.2.6.7 在任务结束时生成最终总结

​        打开 `api/app/application/react_agent_service.py`，在写入 `task_done` 事件前，先根据本轮工具事件生成最终回答。

​        执行完成后调用：

```Python
final_answer = await self._build_final_answer(plan, completed_events)
```

​        核心逻辑如下：

```Python
# ===================== 第7步：根据工具输出生成最终总结 =====================
async def _build_final_answer(
    self,
    plan: dict,
    events: list[SessionEvent],
) -> str:
    """把本轮执行的工具观察结果整理成面向用户的最终回答。"""

    # 1. 先准备规则兜底结果。外部模型不可用时，任务仍然能正常收尾。
    fallback_answer = self._build_rule_based_final_answer(plan, events)

    # 2. 把 tool_called 事件整理成 LLM 可以阅读的观察材料。
    evidence = self._build_final_answer_evidence(plan, events)
    if not evidence:
        return fallback_answer

    try:
        result = await LLMService().chat(
            messages=[
                LLMMessage(
                    role="system",
                    content=(
                        "你是 AtlasAgent 的任务总结器。"
                        "请根据可观察的工具输出写最终回复正文，不要编造未执行的动作。"
                    ),
                ),
                LLMMessage(
                    role="user",
                    content=(
                        f"任务目标：{plan.get('goal') or plan.get('title')}\n\n"
                        f"工具观察材料：\n{evidence}"
                    ),
                ),
            ],
            temperature=0.2,
            max_tokens=900,
        )
    except AppException:
        return fallback_answer

    clean_content = result.content.strip()
    return clean_content or fallback_answer
```

​        然后在 `task_done` 的 payload 中加入：

```Python
payload={
    "plan_id": plan.get("id") or plan.get("plan_id"),
    "final_answer": final_answer,
    "message": "计划步骤已全部执行完成。",
}
```

##### 38.2.6.7.1 这段代码的业务流程

​        任务执行完成后，后端不再只告诉前端“完成了”。

​        它会先把本轮所有 `tool_called` 事件整理成可观察材料：

```Plain
搜索工具 -> 搜索了什么，找到几条结果
浏览器工具 -> 打开了什么页面，页面标题是什么
截图工具 -> 截图是否完成，图片大小是多少
Shell 工具 -> 执行了什么命令，退出码是多少
文件工具 -> 读取或写入了什么文件
```

​        然后让 LLM 生成最终正文。比如文件解析任务会输出：

```Plain
我已经读取并分析了 Page.tsx。这个页面主要由会话侧边栏、任务执行流和右侧工具详情组成...
```

​        这段正文进入 `task_done.payload.final_answer`，前端就能在对话末尾显示真正的任务收尾，而不是只显示一句泛泛提示。

##### 38.2.6.7.2 为什么还要保留规则兜底

​        本地课程环境可能没有配置 LLM API Key，或者网络临时失败。

​        如果最终总结完全依赖 LLM，任务会在最后一步失败；保留规则兜底后，即使模型不可用，也至少能看到每一步工具观察摘要。

​        同步方法核心代码如下：

```Python
# ===================== 第5步：把会话附件同步到 Sandbox =====================
async def _sync_session_files_to_sandbox(self, session_id: UUID) -> None:
    """把当前会话上传的文本附件写入 Sandbox 工作目录。"""

    # 1. 读取当前会话绑定的附件。没有附件时直接返回，不影响普通任务。
    session_files = await self.uow.session_files.list_by_session(session_id)
    if not session_files:
        return

    # 2. 主 API 本地文件存储负责读上传内容，Sandbox API 负责写入工作目录。
    storage = build_file_storage()
    sandbox_files = SandboxFileClient(
        base_url=settings.sandbox_api_base_url,
        timeout_seconds=settings.sandbox_api_timeout_seconds,
    )

    for session_file in session_files:
        file_object = session_file.file
        if not self._is_syncable_text_file(
            content_type=file_object.content_type,
            filename=file_object.original_name,
        ):
            continue

        # 3. 读取文本文件内容，读取上限和文件预览保持一致。
        raw_content = storage.read_bytes(
            file_object.storage_path,
            max_size=settings.max_file_preview_size,
        )
        content = raw_content.decode("utf-8", errors="replace")
        safe_name = Path(file_object.original_name).name

        # 4. 同时写入根目录和 attachments 目录。
        for path in {safe_name, f"attachments/{safe_name}"}:
            sandbox_files.write_file(
                path=path,
                content=content,
                create_parent=True,
            )
```

##### 38.2.6.9.1 为什么这样设计

​        上传附件和 Sandbox 文件是两套位置：

```Plain
上传附件 -> 主 API uploads 目录 + 数据库 files/session_files
file_read -> Sandbox 工作目录
```

​        如果不做同步，Agent 会出现这种尴尬情况：

```Plain
上下文里看得到 Page.tsx
工具执行时读不到 Page.tsx
```

​        同步后，Sandbox 中会出现：

```Plain
Page.tsx
attachments/Page.tsx
```

​        根目录文件兼容模型直接读取 `Page.tsx`，`attachments/` 目录保留上传来源，方便排查。

​        当前只同步文本类文件，例如：

```Plain
.tsx .ts .js .py .md .json .txt .yaml .csv
```

​        PDF、Word、Excel 这类文件需要专门解析器，本阶段先不把它们当作普通文本写入 Sandbox。

#### 38.2.6.10 文件工具路径兜底

​        打开 `api/app/application/tool_selection_service.py`。

​        如果模型选择了 `file_read`，但漏掉 `path` 参数，就从上下文里的文件引用提取文件名：

```Python
elif parameter.name == "path" and tool.definition.name.startswith("file_"):
    repaired[parameter.name] = self._extract_file_path(agent_context)
```

​        辅助函数如下：

```Python
@staticmethod
def _extract_file_path(agent_context: str) -> str:
    """从上下文里的文件引用提取一个可读文件名。"""

    for line in agent_context.splitlines():
        clean_line = line.strip()
        if not clean_line.startswith("- "):
            continue
        candidate = clean_line.removeprefix("- ").split(" (", 1)[0].strip()
        if candidate and "." in candidate and "/" not in candidate:
            return candidate
    return "."
```

##### 38.2.6.10.1 这段代码解决什么问题

​        上下文里文件引用长这样：

```Plain
- Page.tsx (text/plain, 可在需要时读取文本预览或下载内容。)
```

​        如果模型只说“读取上传文件”，没有明确输出：

```JSON
{"path":"Page.tsx"}
```

​        工具执行前会自动补成：

```Plain
path=Page.tsx
```

​        这样文件解析任务会更稳定。

### 38.2.7 关键理解

​        本阶段最重要的是明确两个区域的职责：

```Plain
中间执行流：讲任务过程
右侧详情抽屉：展示工具证据
```

​        中间不要出现完整 JSON。

​        右侧也不要默认铺原始 JSON，而是优先展示结构化结果；复制按钮保留完整输出，方便调试和复盘。

​        第二个重点是浏览器和 VNC 的出现时机。

​        浏览器远程桌面只在浏览器工具详情中出现，因为它是浏览器工具的观察窗口，不应该作为首页常驻面板。

​        第三个重点是最终总结的来源。

​        最终总结不应该由前端硬写一句固定文案，而应该来自后端本轮真实执行产生的工具事件。这样搜索、截图、Shell、文件和多 Agent 协作都能进入任务收尾。

​        页面上传只是把文件交给主 API 保存；Agent 工具执行发生在 Sandbox，所以执行前需要把文本附件同步进去。

```Python
    browser_enabled = getenv("SANDBOX_BROWSER_ENABLED", "true").lower() == "true"
    vnc_enabled = getenv("SANDBOX_VNC_ENABLED", "true").lower() == "true"
    return SettingsModule(
        key="sandbox",
        name="Sandbox",

        source=".env / docker-compose.yml",
        verify_command="curl http://localhost:8088/api/sandboxes/current",
        items=[
            {
                "name": "file",
                "description": "读取、写入和同步会话附件到 Sandbox 工作目录。",
                "enabled": True,
                "metadata": {"base_url": settings.sandbox_api_base_url},
            },
            {
                "name": "shell",
                "description": "在 Sandbox 中执行命令并读取输出。",
                "enabled": True,
                "metadata": {
                    "wait_timeout_seconds": settings.sandbox_shell_wait_timeout_seconds,
                },
            },
            {
                "name": "browser",
                "description": "通过 Playwright 控制 Sandbox 浏览器。",
                "enabled": browser_enabled,
                "metadata": {"browser_env": "SANDBOX_BROWSER_ENABLED"},
            },
            {
                "name": "vnc",
                "description": "通过 noVNC 查看 Sandbox 浏览器远程桌面。",
                "enabled": vnc_enabled,
                "metadata": {"status_url": "/sandbox-api/vnc/status"},
            },
        ],
    )
```

##### 38.3.6.5.1 代码讲解

​        Sandbox 不是一个普通配置项，它是一组能力的集合：

```Plain
file
shell
browser
vnc
```

​        这些能力最终都会被 Agent 工具调用，所以配置中心要把它们放在一起展示。

​        这里的 `status="ready"` 表示“连接信息已经配置”。真实运行状态仍然要通过：

```Bash
curl http://localhost:8088/api/sandboxes/current
curl http://localhost:8088/sandbox-api/vnc/status
```

#### 38.3.6.6 同步响应模型和路由转换

​        打开 `api/app/presentation/http/routes/config.py`，在 `to_settings_module_response()` 中补上：

```Python
return SettingsModuleResponse(

    verify_command=module.verify_command,
    items=[...],
)
```

##### 38.3.6.6.1 为什么要同步三层

​        这里涉及三层：

```Plain
application dataclass
  |
  v
schema response model
  |
  v
route converter
```

​        只改应用服务不改 schema，接口会校验失败。

​        只改 schema 不改路由转换，前端收不到新字段。

​        所以这三处必须同步。

### 38.3.7 关键理解

​        本阶段最重要的是理解：

```Plain
功能可用 != 产品可用
```

​        代码里有 LLM 客户端，不代表用户知道自己有没有配 Key。

​        代码里有 MCP Client，不代表用户知道哪些 Server 已启用。

​        代码里有 A2A 调用，不代表用户知道远程 Agent 地址是什么。

​        代码里有 Sandbox，不代表用户知道浏览器、VNC、Shell 是否能跑。

​        配置中心解决的就是这个“可见性”问题。
